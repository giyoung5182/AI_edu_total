## 파싱과 청킹 — 문서를 조각으로 만드는 두 단계
문서를 AI가 다루려면 먼저 두 단계를 거칩니다.
- \*파싱(Parsing)\*\*은 PDF에서 글자를 뽑아내는 작업입니다.<br>PDF는 사람 눈에 보기 좋게 만든 형식이라,<br>프로그램이 글자를 꺼내는 과정에서 원형이 어긋나기도 합니다.<br>표의 줄이 무너지거나, 그림 설명만 덩그러니 남는 식입니다.
- \*청킹(Chunking)\*\*은 뽑아낸 텍스트를 일정한 조각으로 자르는 작업입니다.<br>잘린 조각 하나를 청크(Chunk)라고 부릅니다.<br>이번 실습의 기준은 두 가지 숫자입니다.
```plain text
청크 크기 500자   ← 조각 하나의 길이
오버랩   50자    ← 이웃 조각과 겹치는 길이
```
오버랩은 문장이 조각 경계에서 두 동강 나는 피해를 줄이는 장치입니다.<br>앞 조각의 끝 50자를 뒤 조각이 다시 품고 시작합니다.
500자는 문서의 사정을 모르는 기계적 기준입니다.<br>조항의 중간이든, 표의 한복판이든, 500자가 차면 자릅니다.<br>이 방식이 내 문서에서 무슨 일을 일으키는지가 실습 1의 관찰 대상입니다.

## 임베딩 — 문장을 숫자 목록으로 바꾸는 계산
컴퓨터는 "문장 두 개의 뜻이 비슷한가"를 직접 판단하지 못합니다.<br>대신 문장을 숫자 목록으로 바꾼 뒤, 숫자끼리 비교합니다.<br>이 변환을 임베딩(Embedding)이라고 부릅니다.
```php
"탁자 아래로 들어가 몸을 보호한다"  → [0.12, -0.83, 0.44, ...]
"책상 밑에서 흔들림이 멈추길 기다린다" → [0.11, -0.79, 0.41, ...]
"점심으로 김치찌개를 먹었다"          → [-0.67, 0.25, -0.90, ...]
```
첫 문장과 둘째 문장은 단어가 거의 겹치지 않습니다.<br>탁자와 책상, 보호와 기다림처럼 표현이 다릅니다.<br>그런데 임베딩 결과의 숫자는 서로 가깝습니다.<br>뜻이 비슷한 문장은 숫자도 비슷해지도록 임베딩 모델을 학습시켰기<br>때문입니다. 셋째 문장의 숫자가 동떨어진 것도 같은 원리입니다.
우리는 Gemini의 임베딩 모델(gemini-embedding-001)을 API로 호출합니다.<br>채팅방에 쓰는 키와 같은 키로, 문장을 보내면 숫자 목록이 돌아옵니다.

## 벡터DB — 숫자를 저장하고 비교해 주는 데이터베이스
청크마다 임베딩을 계산했으면 저장할 곳이 필요합니다.<br>숫자 목록(벡터)을 저장하고, "이 벡터와 가장 비슷한 벡터를 찾아줘"라는<br>비교 요청을 빠르게 처리하는 데이터베이스가 벡터DB입니다.<br>우리는 로컬에서 동작하는 ChromaDB를 사용합니다.
벡터DB에 들어가는 한 건의 데이터는 다음 묶음입니다.
```plain text
저장 1건 = 청크 원문 + 임베딩 벡터 + 부가 정보(출처 문서명, 청크 번호)
```
이 묶음을 청크 수만큼 저장하는 작업을 적재(Loading)라고 부릅니다.

임베딩 계산을 위해 청크 원문이 외부 API로 전송됩니다.<br>공개 문서라서 지금은 문제없습니다.<br>만약 이 자리에 회사 내부 문서를 넣는다면, 전송 시점에<br>문서 내용이 회사 밖으로 나간다는 뜻입니다.<br>실무 적용 전에 반드시 확인해야 하는 지점입니다.

```php
6. 필요한 패키지 설치 명령을 알려 주세요.
```
진행 순서

2. 터미널 B에서 서버를 재시작하고 문서 페이지를 새로고침합니다.

4. 터미널 B의 로그에서 배치 진행률이 올라가는 과정을 지켜봅니다.
5. 적재 완료 후, 페이지 상단의 적재 현황에서<br>청크 개수가 실습 1의 청크 개수와 같은지 확인합니다.

**FAQ**
- **Q. 적재 도중 에러가 납니다**

## 의미 검색 — 뜻이 가까운 조각을 꺼낸다
적재가 끝났으면 이제 꺼내 쓸 차례입니다.<br>질문도 청크와 똑같이 임베딩해 숫자 목록으로 바꿉니다.<br>그리고 저장된 모든 청크의 숫자와 비교해,<br>가장 가까운 조각부터 K개를 꺼냅니다.<br>숫자의 가까움, 곧 뜻의 가까움으로 찾기 때문에<br>이 방식을 의미 검색이라고 부릅니다.
실제 검색 결과는 이런 모습입니다.
```php
질문: "지진 나면 제일 먼저 뭘 해야 하나요?"   (K=3)

1위  청크 #041  유사도 0.81
2위  청크 #043  유사도 0.74
3위  청크 #112  유사도 0.58
```
유사도는 질문과 청크가 얼마나 가까운지 나타내는 점수입니다.<br>1에 가까울수록 관련이 깊다는 뜻입니다.<br>K는 몇 개를 꺼낼지 정하는 값입니다.

### 실습 3. 검색 실험 — 성공과 실패를 모두 목격한다
검색 페이지를 만들고, 내 문서를 상대로 질문 실험을 합니다.
**Claude Code 프롬프트**
```php
지금 프로젝트에 검색 페이지를 추가해 주세요. 요구사항입니다.

1. /search 경로에 새 페이지를 만들고,
   상단 메뉴바에 "검색" 메뉴를 추가해 주세요.

2. 질문을 입력하면 벡터DB에서 의미 검색을 실행합니다.
   질문을 임베딩하고, 유사도가 높은 상위 K개 청크를 찾습니다.
   K 기본값은 3이고, 페이지의 입력칸에서 바꿀 수 있게 해 주세요.

3. 결과는 청크 카드 목록으로 보여 주세요.
   카드마다 순위, 유사도 점수, 청크 번호, 원문 미리보기를 표시하고,
   누르면 전문이 펼쳐지게 해 주세요.

4. 서버 로그에 검색 한 건마다 질문과 1위 청크 번호가
   한 줄로 출력되게 해 주세요.
```
진행 순서

1. 프롬프트를 입력해 진행하고, 서버를 재시작한 뒤<br>/search 페이지를 엽니다.
2. 준비 질문 두 개를 만듭니다. 내가 고른 문서에 답이 있는<br>내용으로, 서로 다른 방식의 질문입니다.
- 질문 A: 문서의 표현을 쓰지 않고, 일상 말로 풀어 묻는 질문<br>(예: ① "밖에 있는데 땅이 흔들리면 어디로 가요?" /<br>② "회사 기술을 몰래 빼돌리면 어떻게 되나요?" /<br>③ "우리 회사 요즘 돈 잘 벌고 있나요?")
- 질문 B: 문서에 있는 정확한 용어나 번호를 그대로 쓰는 질문<br>(예: ① "지진발생 때 불을 끌 기회 3번은?" /<br>② "제10조에서 금지하는 행위는?" /<br>③ "1Q26 영업이익률은?")
3. \[예측\] 두 질문 중 어느 쪽을 의미 검색이 더 잘 찾아낼지,<br>근거와 함께 예측해 적습니다.
4. 질문 A를 검색하고, 1위 카드를 펼쳐 원문을 읽습니다.<br>질문의 답이 실제로 그 조각에 있는지 확인합니다.
5. 질문 B를 검색하고, 같은 방법으로 확인합니다.
6. \[확인\] 예측과 실제를 비교합니다.<br>더 헤맨 쪽이 있다면, 상위 카드에 어떤 조각이 올라왔는지<br>살펴보고 이유를 추측해 적습니다.
7. 자유 질문을 서너 개 더 던지며 잘 되는 질문과<br>안 되는 질문을 각자 수집합니다.
8. 실습 1에서 메모한 손상 조각과 관련된 내용을 질문해 봅니다.<br>깨진 조각이 검색 품질에 어떤 영향을 주는지 관찰합니다.

**FAQ**
- **Q. 검색 결과가 비어 있습니다**
- 벡터DB가 빈 상태입니다. 문서 페이지의 적재 현황을 확인하고, 0건이면 실습 2를 다시 진행합니다.
- **Q. 유사도 점수가 전부 낮게 나옵니다**
- 문서에 없는 내용을 물었을 가능성이 큽니다. 문서 원문에 분명히 있는 내용으로 다시 질문합니다.
- **Q. 엉뚱한 청크만 계속 나옵니다**
- 정상 범위의 실패일 수 있습니다. 이번 실습의 관찰 대상이므로, 어떤 질문에서 그랬는지 메모해 둡니다.

## 우리가 본 것 정리 — 의미 검색의 강점과 빈틈
실습 3에서 각자 목격한 장면을 정리합니다.
**의미 검색이 강한 질문은 A 유형입니다.**<br>문서에는 "부정한 방법으로 취득·사용 또는 공개"라고 적혀 있어도,<br>"기술을 몰래 빼돌리면"이라는 일상 말로 그 조각을 찾아냅니다.<br>단어가 하나도 안 겹쳐도 뜻이 가까우면 숫자가 가깝기 때문입니다.<br>키워드를 모르는 사람도 검색할 수 있다는 것이 의미 검색의 힘입니다.
**의미 검색이 흔들리는 질문은 B 유형입니다.**<br>"제10조", "1Q26", 특정 실적 항목처럼 드물고 정확한 표기를 물으면,<br>이웃 주제의 조각이 비슷한 유사도로 몰려 순위가 흐려지곤 합니다.<br>뜻의 가까움으로 찾다 보니, 정확히 그 글자가 있는 조각이<br>반드시 1위가 된다는 보장이 없기 때문입니다.<br>문서 ②의 조항 번호, 문서 ③의 수치 항목에서<br>이 흔들림이 특히 자주 보입니다.
그리고 실습 1의 손상 조각이 여기서 다시 등장합니다.<br>표가 무너진 조각, 어색하게 끊긴 조각은 담긴 뜻 자체가 훼손되어<br>검색에 잘 잡히지 않거나, 잡혀도 읽을 수 없는 근거가 됩니다.<br>잘리는 방식과 찾는 방식, 두 가지 모두에 손볼 여지가 있다는 사실을<br>확인한 상태로 이번 세션을 마칩니다.

## 실습 확장 (선택)
기본 실습을 마친 분은 아래를 자유롭게 시도합니다.
- **오버랩 실험**: Claude Code에 "오버랩을 0으로 바꾸는 옵션을<br>추가해 주세요"라고 요청하고 재업로드합니다.<br>청크 경계의 절단면이 어떻게 달라지는지 비교합니다.
- **손상 조각 목록화**: 손상 조각을 두 개 더 찾아<br>청크 번호와 손상 유형을 기록합니다.
- **임베딩 구경**: "청크 카드를 펼치면 임베딩 벡터의 앞 10개<br>숫자도 보여 주세요"라고 요청합니다.<br>문장이 실제로 숫자가 된 모습을 확인합니다.
- **코드 열어 보기**: "질문을 받아 유사한 청크를 찾는 함수를<br>보여 주고, 한 줄씩 설명해 주세요"라고 요청합니다.<br>검색의 심장을 직접 들여다봅니다.
- **다른 문서 맛보기**: 고르지 않은 문서 하나를 추가 업로드해<br>적재하고, 청크의 생김새가 내 문서와 어떻게 다른지 구경합니다.

## 이번 실습 결과물
이번 세션을 마친 우리 손에는 다음이 있습니다.
- 내가 고른 문서를 청크 카드로 펼쳐 보여주는 문서 처리 페이지
- 내 문서 고유의 손상 조각을 찾아낸 기록
- 문서 전체가 적재된 벡터DB
- 의미 검색 페이지, 그리고 검색이 실패하는 질문을<br>직접 확인한 경험
지금 프로젝트 폴더의 구조입니다.
```plain text
~/my-chat/
├── CLAUDE.md
├── .env                    ← API 키 보관 (외부 공유 금지)
├── server.py               ← 채팅 + 문서 처리 + 적재 + 의미 검색
├── static/
│   ├── index.html          ← 채팅 화면 (각자 고른 스타일)
│   ├── documents.html      ← 문서 처리 화면
│   └── search.html         ← 검색 화면
├── docs/                   ← 배부받은 문서 3종
├── chroma_db/              ← 벡터DB 저장 폴더 (적재된 청크)
└── requirements.txt
```
파일 이름과 구조는 Claude Code의 작업에 따라 조금 다를 수 있습니다.<br>업로드부터 적재, 검색까지 동작하면 문제없습니다.
