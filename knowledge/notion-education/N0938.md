## 오늘의 목표 한 줄 요약
> **각자 만든 앱을 "내 코드"로 소유하고, 전문 개발 도구로 다듬어서, 인터넷에 정식 배포한다.**
지금까지 앱은 Lovable 서버 안에서만 존재했습니다. 오늘부터는 코드가 여러분의 GitHub 계정에 저장되고, Cursor라는 전문 도구로 수정할 수 있으며, Vercel이라는 배포 서비스로 인터넷에 공개됩니다. 이것은 실제 개발 회사들이 쓰는 것과 완전히 동일한 작업 방식입니다.
---
## 오늘 전체 흐름 한눈에
```plain text
Lovable (앱 다듬기)
    ↓ GitHub 연동 (코드 내보내기)
GitHub (코드 저장소 — 코드의 구글 드라이브)
    ↓ Clone (내 컴퓨터로 복사)
Cursor (AI 코드 편집기 — 기능 추가·수정)
    ↓ Commit + Push (수정한 코드 올리기)
Vercel (배포 서비스 — 인터넷에 공개)
    ↓
실제 URL로 누구나 접속 가능한 앱 완성
```
**왜 이 4단계 구조를 쓰는가 — 실무 관점:**
```plain text
"Lovable 하나로 끝내면 안 되나?"라는 질문이 나올 수 있습니다.
가능은 하지만, 이 구조로 옮기면 세 가지가 달라집니다:

① 소유권: 코드가 Lovable 서버가 아니라 내 GitHub에 있으므로
   Lovable 서비스가 사라지거나 정책이 바뀌어도 내 앱은 유지됩니다.

② 비용: Lovable은 수정 요청마다 크레딧을 소비하지만,
   Cursor는 무료 플랜으로도 월 50회 정도의 AI 요청이 가능하고
   직접 붙여넣는 수정은 무제한 무료입니다.

③ 확장성: 실제 개발자와 협업하거나, 회사 차원에서
   시스템을 키울 때 GitHub 저장소가 표준 출발점이 됩니다.
```

# Lovable 추가 수정 단계 (필요시, 오늘은 생략)

## 왜 수정 시간을 따로 주는가
GitHub로 코드를 내보내기 전에, Lovable에서 할 수 있는 것은 지금 다 해두는 것이 효율적입니다.
```plain text
같은 수정이라도 도구별 특성이 다릅니다:

Lovable에서 수정:
  · 말로 요청 → 화면 전체를 알아서 다시 구성
  · 큰 구조 변경(탭 추가, 화면 재배치)에 유리
  · 단, 요청마다 크레딧 소비

Cursor에서 수정 (오후):
  · 코드 수준의 정밀한 수정
  · 세부 기능·버그 수정에 유리
  · 무료 한도(월 50회 AI 요청) 내 자유롭게 사용

→ 구조적인 변경은 지금 Lovable에서,
  세부 기능·버그는 오후 Cursor에서.
```

```plain text
세부 디자인:

추가하고 싶은 것:
□ 7회차 전 과제에 적었던 요청 기능 중
  "구조가 크게 바뀌는 것"이 있나요? → 지금 Lovable에서
  "세부 기능 추가·버그 수정"인가요? → 오후 Cursor에서
```

## 수정 요청하는 법 (복습 + 크레딧 절약 전략)
**방법 1 — Edit 모드 (크레딧 소비 없음):**
```plain text
Lovable 미리보기 화면에서 [Edit] 모드 진입
→ 수정할 요소 클릭 → 선택 표시 확인
→ 텍스트 직접 수정 / 색상 변경 / 여백 조정
→ 저장

💡 이 방법은 크레딧을 소비하지 않습니다.
   텍스트·색상·간격 수정은 무조건 이 방법을 먼저 쓰세요.
```
**방법 2 — AI 채팅창 요청 (크레딧 소비):**
```plain text
왼쪽 채팅창에 원하는 것을 말로 입력
→ Lovable AI가 코드를 수정하고 미리보기가 바뀜

💡 수정 사항이 여러 개라면 "서로 관련 있는 것끼리" 묶어서 요청하세요.

⚠️ 주의 — 프로님이 7회차 전 과제에 남긴 질문과 연결됩니다:
   "복잡하고 긴 프롬프트에 관련 없는 여러 영역의 수정을
    같이 넣어도 잘 반영되나요?"
   → 관련 없는 영역을 한 번에 섞으면 일부를 놓치거나
     엉뚱하게 반영될 가능성이 높아집니다.
   → 크레딧을 아끼려면 "여러 개 묶기"가 아니라
     "관련 있는 것끼리만 묶기"가 정확한 전략입니다.

예시:
  ✅ 좋은 묶음 (같은 화면, 같은 맥락):
  "휴무 등록 폼에서 ① 제출 버튼 색을 짙은 초록으로,
   ② 버튼 텍스트를 '등록하기'로, ③ 제출 후 성공 메시지가
   3초간 표시되게 해줘"

  ❌ 나쁜 묶음 (서로 무관한 영역):
  "휴무 폼 버튼 색 바꾸고, 관리자 페이지에 통계 추가하고,
   로그인 화면 로고도 바꿔줘"
```
**방법 3 — 특정 섹션 선택 후 요청 (정밀 수정):**
```plain text
Edit 모드에서 수정하고 싶은 섹션 클릭 (선택 표시 확인)
→ 채팅창에 "이 부분을 [수정 내용]으로 바꿔줘"
→ 다른 부분 건드리지 않고 선택한 부분만 정확하게 수정됨
```

## 0. 시작 전 마음가짐 — "완벽"이 아니라 "우선순위"
앱은 절대 한 번에 완벽해지지 않습니다. 특히 화면이 많은 앱(프로님 22화면)은<br>**수정 1건이 다른 화면에 영향을 미쳐 "고치면 새 버그"가 구조적으로 발생**합니다.<br>이건 실력 문제가 아니라 규모의 문제입니다.
그래서 목표는 "다 고치기"가 아니라 **"가장 중요한 것부터, 정해진 시간 안에<br>할 수 있는 만큼"** 입니다. 아래 순서로 접근하세요.

## 1단계 — 수정 포인트 발견하기 (뭘 고칠지 찾는 법)
무작정 앱을 들여다보지 말고, **정해진 5가지 관점으로 앱을 점검**하면 고칠 것이<br>체계적으로 드러납니다.
### 점검 1 — 데이터가 진짜 저장되나? (가장 먼저)
```plain text
□ 데이터를 입력하고 새로고침(F5) → 그대로 남아있는가?
  → 사라지면: "저장이 안 되는 앱"입니다. 최우선 수정 대상.

□ PC에서 입력한 게 스마트폰에서도 보이는가?
  → 안 보이면: 역시 저장 미연동. 1권 데이터 연동 챕터로.
```
### 점검 2 — 버튼·기능이 의도대로 동작하나?
```plain text
□ 모든 버튼을 하나씩 눌러본다. 엉뚱한 일이 일어나는 버튼이 있는가?
  → 예: "삭제 버튼을 눌렀는데 오히려 항목이 생성됨" (프로님 디자인핀)
  → 예: "수량만 수정했는데 상태가 '완료'로 바뀜" (프로님이 PRD에
        Event Isolation 규칙으로 방지하려 한 것)
  → 이런 "이벤트가 잘못 연결된" 버그가 가장 흔합니다.
□ 저장·완료·확정 같은 중요한 버튼이 실제로 DB에 반영되는가?
```
### 점검 3 — 숫자·계산이 정확한가?
```plain text
□ 합계·평균·잔액 등 계산 결과가 손으로 검산한 값과 맞는가?
  → 예: 정육 법인/개인을 vendor_name의 "(법)"/"(개)"로
        분류해 각각 집계하는데, 총합은 맞아도 법/개 분류가 틀리기 쉬움.
        (정확값: 법인 1,083,892,350원 / 개인 879,223,150원)
  → 금액·수량이 걸린 앱은 계산 오류가 치명적이므로 반드시 검산.
□ 조건부 표시(음수면 빨강, 기준 미만이면 경고 등)가 조건대로 작동하는가?
```
### 점검 4 — 데이터가 충분히 들어있나?
```plain text
□ 목록(지점·매장·업체 등)이 실제 전체가 아니라 샘플 몇 개만 있지 않은가?
  → 예: 프로님 디자인핀 — 지점이 4개만 등록됨.
     원인: PRD에 전체 목록을 안 줘서 Lovable이 샘플 4개만 생성.
  → 실제 데이터를 제공하면 해결됩니다.
```
### 점검 5 — 쓰기 불편한 곳이 있나? (UI·흐름)
```plain text
□ 자주 쓰는 기능이 너무 깊이 숨어있지 않은가?
□ 모바일에서 봤을 때 깨지거나 불편하지 않은가?
□ 색상·글자 크기·정렬이 업무용으로 보기 좋은가?
→ 이건 "치명적"은 아니지만, 매일 쓸 도구라면 누적 효과가 큽니다.
```
> 💡 이 5가지 점검을 순서대로 하면, 고칠 것이 저절로 목록이 됩니다.<br>발견한 것을 메모장에 다 적어두세요. 다음 단계에서 분류·정렬합니다.

## 2단계 — 발견한 것을 유형별로 분류
적어둔 수정 포인트를 아래 4유형으로 나눕니다. 유형에 따라 **어디서(Lovable/Cursor)<br>고칠지, 얼마나 급한지**가 달라집니다.





유형

설명

예시

어디서 고치나




**A. 데이터/저장**

저장 안 됨, 연동 문제

새로고침 시 소실

데이터 연동 챕터 → Lovable




**B. 버그**

의도와 다르게 동작

삭제가 생성됨, 계산 오류

간단하면 Lovable, 세밀하면 Cursor




**C. 기능 추가**

없던 기능을 새로

대시보드 추가, 알럿

구조 변경은 Lovable, 로직은 Cursor




**D. UI/흐름**

보기·쓰기 개선

색상, 정렬, 레이아웃

세밀 조정은 Cursor가 유리


> 💡 **Lovable이 유리한 것 vs Cursor가 유리한 것**
- Lovable: 화면 추가, 큰 구조 변경, "새 기능 통째로 만들기" (말로 크게 지시)
- Cursor: 세밀한 버그 수정, 계산 로직 검증, 색상·여백 미세 조정<br>(크레딧 0으로 자유롭게 반복)<br>→ 크레딧이 부족하면 A·C(구조)만 Lovable에서 최소한으로 하고,<br>B·D(세밀)는 오후 Cursor로 미루세요.

## 3단계 — 우선순위 정하기
분류한 것을 아래 순서로 정렬합니다. **위에서부터 고칩니다.**
```plain text
1순위 — 데이터가 저장 안 됨 (유형 A)
  → 저장이 안 되면 다른 걸 아무리 고쳐도 소용없습니다. 무조건 먼저.

2순위 — 데이터를 망가뜨리는 버그 (유형 B 중 치명적)
  → 삭제가 생성되거나, 계산이 틀리거나, 데이터가 덮어써지는 버그.
    잘못된 데이터가 쌓이면 나중에 되돌리기 어렵습니다.

3순위 — 핵심 업무를 막는 것
  → 그 기능이 안 되면 앱을 쓸 수 없는 것 (예: 매출 입력이 안 됨).

4순위 — 있으면 좋은 기능 추가 (유형 C)
  → 대시보드, 알럿 등. 없어도 앱은 돌아가지만 편해지는 것.

5순위 — UI·흐름 개선 (유형 D)
  → 색상, 정렬, 레이아웃. 마지막에.
```
> ⚠️ **한 번에 하나씩.** 여러 개를 한 프롬프트에 몰아넣으면, Lovable이<br>엉뚱한 곳까지 건드려 새 버그가 생깁니다(크레딧도 낭비). 1순위 하나 고치고<br>→ 확인 → 다음, 순으로 진행하세요.
---
## 4단계 — 효과적으로 수정 요청하기 (크레딧 절약의 핵심)
같은 수정도 **어떻게 요청하느냐**에 따라 한 번에 되기도, 코인을 태우기도 합니다.
### 원칙 1 — "무엇을·어디서·어떻게"를 구체적으로
```plain text
❌ 나쁜 예: "삭제가 안 돼요. 고쳐줘."
   → Lovable이 뭘 어떻게 고칠지 몰라 엉뚱하게 건드림.

✅ 좋은 예: "디자인핀 갤러리에서 [삭제] 버튼을 누르면 항목이 삭제되지 않고
   오히려 새 항목이 생성됩니다. 삭제 버튼의 클릭 이벤트가 등록 폼의 제출
   이벤트와 분리되어, 삭제만 수행하도록 고쳐주세요. 삭제가 실제 DB에서
   해당 행을 지우는지도 확인해주세요."
   → 증상 + 위치 + 원인 추정 + 원하는 결과가 다 있음.
```

## 왜 이 단계가 GitHub보다 먼저인가
```plain text
지금 앱 상태 점검:
  앱에 데이터를 입력 → 새로고침(F5) → 데이터가 사라진다면
  → 데이터가 브라우저 메모리(React state)에만 있는 상태입니다.
  → 화면은 완성됐지만 "저장 기능이 없는 앱"입니다.

이 상태로 GitHub·Vercel까지 가도 앱은 배포되지만,
```

## B. 데이터를 "어떻게" 채우나 — 4가지 방식 (가장 중요)
데이터를 테이블에 채우는 방식은 크게 4가지입니다. 각각 **무엇인지 / 어떤 경우에 맞는지 / 어떻게 하는지**를 정리합니다.
### 방식 ① 앱에서 직접 입력 (기본)
```plain text
무엇: 앱 화면의 입력 폼에 사람이 손으로 입력 → 저장 버튼 → DB 저장
어떤 경우: 데이터가 앱 안에서 발생할 때 (체크리스트, 메모 등)
어떻게: 별도 작업 없음. Lovable에 "입력 폼 만들어줘"로 기본 제공
한계: 이미 엑셀·시트에 쌓인 대량 데이터를 옮기기엔 비효율(한 건씩 손입력)
예시: 프로님 매장점검(직원이 앱에서 체크리스트 입력)
```
### 방식 ② 앱에 파일 업로드 기능
```plain text
무엇: 앱에 [CSV/엑셀 업로드] 버튼 → 앱이 직접 파일을 읽어서
     DB에 한 줄씩 저장(INSERT)
⚠️ 핵심: GAS 없이, 앱이 직접 파일을 파싱해서 넣음 (방식 ③과 다른 점)
어떤 경우: 가끔 대량 데이터를 통째로 올릴 때
예시: 프로님 업체별 결제데이터

어떻게 (Lovable 프롬프트에 반드시 포함 — 강사 검증):
  · "Supabase에 실제 저장, mock 아님, 새로고침해도 유지" (강조)
  · 저장할 테이블 컬럼 명시
  · CSV 컬럼 순서 명시 + "첫 줄(헤더) 건너뛰기"
  · "UTF-8로 읽어 한글 안 깨지게"
  · "금액은 콤마 제거 후 숫자 변환"
  · "○건 저장되었습니다 메시지" + "실패 시 어느 줄인지 표시"
  · 하단에 "총 ○건, 합계 ○○원" 요약 (저장 검증에 유용)

검증: 업로드 후 ① 새로고침해도 유지되나 ② Database 화면에 행이 실제로 들어갔나
```

## ⚠️ GAS 연동의 핵심 — Lovable Cloud는 안 되고, 개인 Supabase는 된다 (강사 리허설 결과)
방식 ③(구글시트+GAS)을 쓰려는 분은 이 부분을 반드시 이해해야 합니다. 강사가 직접 리허설하며 확인한 내용입니다.
```plain text
문제: GAS가 Supabase에 데이터를 보내려면 Supabase의 URL과 key가 필요한데,
     Lovable Cloud는 이 정보를 감춰둡니다.
     (Cloud → Secrets 화면에 LOVABLE_API_KEY만 있고 SUPABASE_URL·key가 없음)
     → 그래서 Lovable Cloud 앱은 GAS 직접 연동이 막힙니다.

해결 2가지:
  1) Edge Function 경유 — Cloud 안에 "외부요청 창구"를 만들어
     GAS → Edge Function → Supabase (유지되나 복잡)
  2) 개인 Supabase(길3) — supabase.com에서 URL/key를 직접 복사해
     GAS에 넣으면 바로 연결 (쉬움)
```
> ⚠️ **강사가 개인 Supabase로 GAS 연동을 실제로 완주한 결과 (핵심 함정 포함):**<br>개인 Supabase는 URL과 key가 노출되어 GAS 연동이 실제로 됩니다. 다만 함정이 하나 있습니다.
```plain text
1) supabase.com → New project (Region: Seoul)
2) Settings → API Keys에서 key 확보
   ⚠️ 새 방식 "sb_secret_..." key는 GAS에서 401 거부됨
      (오류: "Forbidden use of secret API key in browser")
   → 반드시 [Legacy anon, service_role] 탭의 service_role key
      (eyJ로 시작하는 긴 키)를 사용해야 함
3) Table Editor에서 데이터 받을 테이블 생성 (열 이름은 시트와 일치)
4) 구글시트 → 확장프로그램 → Apps Script에 코드 작성
   (UrlFetchApp.fetch로 Supabase /rest/v1/테이블명 에 POST,
    헤더 apikey/Authorization = service_role key)
5) 첫 실행 시 "확인 안 된 앱" 경고 → [고급] → [이동] → [허용] (정상)
6) 실행 로그 응답코드 201 = 성공 → Table Editor에서 행 확인
```

## D. 데이터 보안 (RLS) — 왜, 언제, 어떻게
### 왜 기본이 "공개"인가
로그인/권한을 프롬프트에 안 넣으면, DB가 "지금 접근하는 게 누구인지" 모릅니다. <br>그래서 사람 구분을 못 해 "다 열어두는" 공개 테이블이 됩니다. <br>Lovable이 "로그인 없이 누구나 조회/입력 가능한 공개 테이블로 만들었어요"라고 하는 게 이 상태입니다.
### RLS란
```plain text
RLS(Row Level Security) = 행 단위 잠금. DB가 직접 "이 행을 누가 볼지" 차단.
앱 화면을 우회해 DB에 직접 접근해도 막아줌 = 진짜 보안.
단, DB가 "지금 누구"인지 알아야 하므로 Supabase 정식 인증(Supabase Auth)이 전제.

참고: 2025년 보안 분석에서 AI 생성 앱의 10.3%가 RLS 미설정으로 데이터 노출.
```
### 보안 강화 3단계 (약 → 강)
```plain text
1단계 — 로그인 붙이기 (기본 잠금)
  프롬프트: "로그인 기능 추가, 로그인한 사용자만 조회/업로드,
            로그인 안 하면 아무것도 안 보이게"
  → 아무나 URL로 접근하는 것만 막음

2단계 — RLS로 행 단위 잠금 (진짜 DB 보안)
  프롬프트: "Supabase Auth로 로그인 구현하고 테이블에 RLS 적용해
            로그인 사용자만 DB 레벨에서 접근 가능하게"
  → mock auth를 Supabase Auth로 바꾸는 큰 작업

3단계 — 역할별 권한 (관리자/일반 분리)
  프롬프트: "관리자는 전체, 일반은 본인 데이터만 role 기반으로 분리"
```

### 키 2종의 구분 (Cursor로 코드 다룰 때 필수)

## GitHub가 뭐예요? — 쉽게 설명하면
**GitHub**는 코드를 저장하고 관리하는 세계 최대 플랫폼입니다. <br>2026년 현재 전 세계 1억 명 이상의 개발자가 사용하며, Microsoft가 운영합니다.
```plain text
코드도 파일입니다.
Word 파일을 구글 드라이브에 저장하듯이,
코드 파일을 GitHub에 저장합니다.

구글 드라이브와 다른 점:
  · 버전 관리가 됩니다
    모든 변경 이력이 기록되어 "어제 버전으로 되돌려줘"가 가능합니다
  · 다른 사람과 공유·협업이 쉽습니다
  · Vercel 같은 배포 서비스가 여기서 코드를 가져다가 인터넷에 올려줍니다
```
**오늘 GitHub를 쓰는 이유 딱 두 가지:**
```plain text

```

# Cursor — AI와 대화하면서 코드를 고치는 도구
---
## Cursor가 뭐예요? — 쉽게 설명하면
**Cursor**는 AI가 내장된 코드 편집기입니다. 2026년 현재 전 세계 100만 명 이상의 유료 개발자가 사용하며, Stripe·Figma·Adobe 같은 회사들도 업무에 씁니다.
```plain text
코드 편집기(Code Editor)가 뭔가요?
  코드를 보고 수정하는 프로그램입니다.
  Word가 문서를 편집하는 도구라면,
  Cursor는 코드를 편집하는 도구입니다.

그런데 Cursor에는 AI가 내장되어 있어서:
  "이 버튼 색을 초록으로 바꿔줘"라고 말하면
  → AI가 프로젝트 전체 코드를 읽고
  → 해당 부분을 찾아 자동으로 수정해줍니다.
```
**Cursor의 결정적 강점 — Lovable·Claude 채팅과의 차이:**
```plain text
Cursor는 "프로젝트 전체 구조를 스스로 파악"합니다.

Claude.ai 채팅: 여러분이 보여준 코드만 알 수 있음
Cursor: 프로젝트의 모든 파일을 자동으로 읽고,
        "어느 파일의 어느 부분을 고쳐야 하는지" 스스로 찾음
        여러 파일에 걸친 수정도 동시에 처리 가능

→ 이미 만들어진 앱에 기능을 추가·수정하는 오늘 같은 작업에서는
  Cursor가 가장 안전하고 빠릅니다.
```

### 5-2. (Windows만) 실행 정책 풀기
> 💡 **이게 뭔가요?**<br>Windows는 보안을 위해 **외부에서 받은 스크립트 실행을 기본으로 막아둡니다.** npm도 스크립트로 동작하기 때문에, 이 차단을 풀어주지 않으면 다음 단계에서 바로 오류가 납니다.
> 💡 **왜 지금 하나요?**<br>안 풀고 `npm install`을 치면 `npm.ps1 파일을 로드할 수 없습니다`라는 빨간 오류가 납니다. 미리 풀어두면 그 오류를 아예 안 만납니다. **컴퓨터당 한 번만 하면 됩니다.**
```plain text
아래를 그대로 입력하고 Enter:Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned  Set-ExecutionPolicy  → 실행 정책을 설정해라  -Scope CurrentUser   → 이 컴퓨터의 내 계정에만 적용해라 (안전)  RemoteSigned         → 내가 만든 건 허용, 외부 것은 서명된 것만 허용
```
> ⚠️ **아무 반응이 없으면 성공입니다.**<br>"변경하시겠습니까? \[Y/N\]"이 뜨면 **Y** 입력 후 Enter.<br>아무것도 안 묻고 그냥 다음 줄로 넘어가면 **이미 풀려 있었다는 뜻**이라 정상입니다.<br>화면 변화가 없어서 "안 된 거 아닌가요?"라고 묻게 되는데, 그게 정상 동작입니다.

### 5-3. npm install — 부품 내려받기
> 💡 **이게 뭔가요?**<br>이 앱을 돌리는 데 필요한 **부품 수백 개를 인터넷에서 내려받아 설치**하는 명령입니다.
> 💡 **왜 필요한가요?**<br>Clone으로 받은 것은 완성품이 아니라 **설계도**입니다.<br>`package.json` 파일에 "이 앱은 이런 부품 400여 개로 만들어졌다"는 **명세서**만 들어 있습니다. 부품 실물은 용량이 수백 MB라 GitHub에 올리지 않습니다. 그래서 각자 자기 컴퓨터에서 내려받아야 합니다.
```plain text
비유:  이케아 가구를 주문했는데 조립 설명서만 배송된 상태입니다.  npm install은 설명서를 보고 나사·판자·경첩을 창고에서  전부 꺼내오는 작업입니다.  부품이 400개라 몇 분 걸리고, 한 번만 하면 됩니다.
```
> 💡 **이름 뜯어보기**`npm` = Node Package Manager (Node.js에 딸려오는 부품 관리 프로그램)<br>`install` = 설치해라
**실행**
```plain text
npm install→ ⠋ 같은 기호가 빙글빙글 돌거나 글자가 계속 바뀝니다→ 멈춘 것처럼 보여도 절대 끄지 마세요. 실제로 내려받는 중입니다→ 예상 시간: 3~5분 (혼자 할 때 기준)
```
**완료 신호**
```plain text
added 417 packages, and audited 418 packages in 3mfound 0 vulnerabilities→ "added ○○○ packages"가 나오고  입력 커서(PS ...>)가 다시 돌아오면 완료입니다.
```
**화면에 뜨는 메시지 판별법**
```plain text
✅ 무시해도 되는 것 (전부 정상)  npm warn deprecated ○○○    → "이 부품은 더 이상 관리되지 않는다"는 안내.      쓸 수는 있고 작동에 문제없습니다.  packages are looking for funding    → 후원 안내. 광고입니다.  found 0 vulnerabilities    → 보안 문제 0건. 좋은 신호입니다.  npm notice New major version of npm available!    → ★ npm 자체를 업데이트하라는 광고입니다.      절대 하지 마세요. 아래 경고 참고.❌ 진짜 문제인 것  npm error ○○○    → 빨간 error. 전체를 복사해서 강사에게 보여주세요.  npm.ps1 파일을 로드할 수 없습니다    → 5-2를 건너뛴 경우입니다. 5-2를 실행하고 다시 시도.
```
> ⚠️ **npm 업데이트 광고를 절대 따르지 마세요.**`npm install -g npm@12.0.1` 같은 안내가 나오는데, 수업 중에 npm 버전을 바꾸면 방금 설치한 부품과 어긋날 수 있습니다. 게다가 6명이 각기 다른 버전이 되면 오류가 나도 원인을 찾을 수 없습니다. **오늘은 지금 버전 그대로 씁니다.**
**설치가 끝나면 왼쪽 파일 목록에 새로 생기는 것**
```plain text
node_modules/        부품 실물이 들어있는 폴더                     파일 3~5만 개, 용량 300~600MB                     ★ 앞에서 OneDrive 폴더를 피한 이유가 이것입니다package-lock.json    이번에 실제로 설치한 부품의 정확한 버전 기록                     ★ 나중에 GitHub에 올릴 때 함께 올라갑니다 (정상).tanstack/           앱이 실행되면서 만드는 임시 작업 폴더
```
> 💡 **빨간 줄이 사라집니다.** 설치 전에 있던 문제 표시(`⊗ 2` 등)가 `⊗ 0`으로 바뀌는 것을 확인하세요. 부품이 없어서 났던 경고였기 때문입니다.
> 💡 **한 번만 하면 됩니다.** 프로젝트당 최초 1회입니다. 앞으로 이 프로젝트를 다시 열 때는 `npm install`을 또 할 필요가 없습니다.

### 7-3. ★ Git 사용자 정보 설정 — 지금 안 하면 오후에 막힙니다
> 💡 **이게 뭔가요?**<br>Git에게 **"이 컴퓨터에서 코드를 수정하는 사람이 누구인지"** 알려주는 설정입니다.
> 💡 **왜 필요한가요?**<br>Git은 커밋(택배 상자에 송장 붙이기)을 만들 때 **"누가 · 언제 · 무엇을 바꿨는지"를 반드시 함께 기록**합니다. 송장에 보내는 사람 이름이 없으면 접수가 안 되는 것과 같습니다.
이름과 이메일이 등록되어 있지 않으면 **기록을 만들 수 없어서 커밋 자체가 거부됩니다.**
```plain text
Make sure you configure your "user.name" and "user.email" in git.(git에 사용자 이름과 이메일을 설정하세요)
```
**원인:** Git은 모든 기록에 **"누가 이 변경을 했는지"** 서명을 남깁니다. 그런데 이 컴퓨터에 이름/이메일이 등록된 적이 없어서 서명을 못 하는 겁니다. **커밋이 실패한 상태**입니다.
**왜 지금까지 안 났나:** Clone(가져오기)은 읽기만 하니 서명이 필요 없었습니다. **처음 커밋할 때 딱 한 번** 터집니다. 한 번 설정하면 그 컴퓨터에서는 다시 안 뜹니다.

**설정을 안 하면 오후에 만나게 될 오류**


```plain text
[Commit] 버튼을 누르는 순간:  Make sure you configure your "user.name" and "user.email" in git.
```

**① 인증 요청**
```plain text
The extension 'GitHub' wants to sign in using GitHub.
```
→ `Allow`(허용) 클릭 → 브라우저가 열리고 `Authorize`(승인) → Cursor 복귀
*아까 Clone은 공개 저장소라 인증이 필요 없었지만, **쓰기(Push)는 반드시 인증이 필요**합니다.* 여기서 처음 뜰 가능성이 높습니다. 내일 6명이 겪을 지점이라 **뜨는지 여부를 꼭 기록**해야 합니다.
**② 주기적 Fetch 제안**
```plain text
Would you like Code to periodically run "git fetch"?
```
→ `Yes` 또는 `Ask Me Later` 아무거나.
#### 성공하면
- 왼쪽 아래가 **`main ↓0 ↑0`** 또는 `main`만 남습니다
- `GRAPH`에서 `main`과 `origin/main`이 **같은 줄**에 표시됩니다
- 버튼이 다시 `Commit` 상태로 돌아갑니다
