## 이 앱의 진단 — 왜 검증이 먼저인가
과장님이 겪은 **"① 새로고침하면 휴무가 사라짐 ② 한 기기에서 고쳐도 다른 기기에 반영 안 됨"** 두 증상은 **데이터가 실제 DB가 아니라 브라우저 메모리(React state)에만 저장됐다는 전형적 신호**입니다. React state는 그 탭이 열려있는 동안만 유지되므로, 새로고침하면 초기화되고(①) 기기 간 공유가 원천적으로 불가능(②)합니다. 이 진단이 맞기 때문에 GAS+구글시트로 전환한 방향은 타당합니다. **다만 "전환했다"와 "전환이 완전히 작동한다"는 다르므로, 오늘 제일 먼저 그 전환이 진짜 됐는지 검증해야 합니다.**

### 미션 1 — GAS 전환 완전성 검증 **\[필수\]**


# 🟩 프로님 — 발주·렌탈 관리 시스템
**앱:** [개별 링크 제외] (admin / 1234)<br>**데이터 저장:** 구글시트 + GAS (방식③)
## 지금 상태 (구체적)
- 전체 매장(58개) 대상 식자재·소모품 발주 + 렌탈 그릇 출고·회수 관리.
- **PRD 단계에서 "Event Isolation(이벤트 격리)" 규칙을 명시** — "수량 인라인 수정 시 상태 변경이 함께 발동되면 안 됨". 한 번 겪은 버그를 규칙으로 문서화한, 실무 시니어 기획자 수준의 접근.
- 3탭 구조: \[당일 현황\] \[전체 현황\] \[완료 이력\]
- 상태값 체계: 발주(대기→입고완료) / 렌탈(출고대기→출고중→회수완료)
- **데이터 규모 6명 중 최대**: 발주내역 999행 + 렌탈출고 920행 = 약 2,000행
## 이 앱의 진단 — 왜 방어 코드가 필요한가
과장님 원문: "gas수정, 시트양식 수정... 러버블에서 내용이 표시되지 않거나 db에 기록을 안 해주는 오류가 많아 시간이 오래 걸렸음."
**근본 원인은 "암묵적 스키마 계약"입니다.** 코드는 "3번째 열은 상태값이고 '대기' 또는 '입고완료'만 온다"고 가정하는데, 사람이 시트를 직접 수정하는 순간 이 가정이 깨집니다:
- 열 순서를 바꾸면 → 코드가 엉뚱한 열을 읽음
- `대기 `처럼 뒤에 공백이 붙으면 → 필터 조건 불일치 → 화면에 안 나옴
- 셀 형식이 텍스트→날짜로 바뀌면 → 파싱 오류
전용 DB는 이런 계약을 시스템이 강제하지만, 구글시트는 사람의 규율에 의존합니다. **이것이 시간이 오래 걸린 진짜 이유이고, 데이터 2,000행에 시트 수정이 잦은 이 앱은 6명 중 스키마 깨짐 재발 확률이 가장 높습니다.** 그래서 신규 기능보다 "깨져도 안 죽는 방어 코드"가 우선입니다.
## 개선 미션 (우선순위)
### 미션 1 — PRD 규칙 3종 검증 **\[필수\]**
- **무엇을:**
```plain text
□ Event Isolation 작동 확인 (수량 인라인 수정 시 상태가 안 바뀌는가)□ 발주(orders)/렌탈(rentals) 데이터가 섞이지 않고 분리돼 있는가
```
- **왜 필요한가:** 과장님이 PRD에 직접 명시한 규칙이 실제 코드에서 지켜지는지 확인하는 것입니다. Event Isolation이 깨지면 "수량만 고쳤는데 상태가 완료로 바뀌는" 사고가 나므로, 데이터 신뢰성의 핵심입니다.
### 미션 2 — 방어 코드 3종 추가 **\[Cursor·오후\]**
- **무엇을:**
```plain text
① 시트 값을 읽을 때 모두 trim(앞뒤 공백 제거) 처리② 상태값이 허용 목록(대기/입고완료 등)에 없으면 화면에 경고 표시③ 시트 쪽에도 데이터 유효성 검사(드롭다운)로 상태값 입력 제한
```
- **왜 필요한가:** 위 진단의 세 가지 깨짐 원인(공백·오타·형식)을 코드가 스스로 방어하게 만드는 것입니다. `대기 `(공백)를 trim으로 없애고, 이상한 상태값은 조용히 무시하는 대신 경고를 띄우면, "화면에 안 나오는데 왜인지 모르는" 상황이 사라집니다. **버그를 없애는 게 아니라, 버그가 나도 원인이 바로 보이게** 만드는 미션입니다.
- **어떻게 (Cursor 프롬프트 예:**
```plain text
"시트에서 값을 읽어오는 모든 부분에 trim()으로 앞뒤 공백을 제거해줘. 그리고 상태값이 정해진 목록(대기/입고완료/출고대기/출고중/회수완료)에 없으면, 콘솔이 아니라 화면에 '알 수 없는 상태값: OOO' 경고를 띄워줘."
```
## ⚠️ 이 앱 특유의 주의점
- 상태값 기반 필터링이 앱 전체 로직의 중심이라, **상태값 오타 하나가 화면 전체 표시 오류**로 이어집니다.
- 데이터 규모가 계속 커지고 다중 사용자가 동시에 쓰게 되면 **6명 중 Supabase 전환이 가장 먼저 필요해질 케이스**입니다. GAS를 계속 쓸 거면 개인 Supabase(길3)가 연동에 유리합니다.

## 이 앱의 진단 — 세 가지 문제와 원인
**문제 1 — Lovable 크레딧 과다 소모.** 22개 화면 규모에서는 수정 1건이 여러 화면에 연쇄 영향을 미쳐 "수정 → 새 버그 → 재수정" 루프가 **구조적으로** 발생합니다. 개인 잘못이 아니라 규모의 문제입니다. → 그래서 세부 수정을 무료인 Cursor로 옮기는 것이 핵심 해법입니다.

**문제 3 — Make 간헐적 끊김.** 7/7 저녁 다수 성공 기록이 있어 완전 단절이 아닌 간헐적 문제입니다. 유력 후보는 무료 플랜 ops 소진, Webhook 큐 지연, GAS 실행 시간 초과 등이며, History에서 실패 시점·사유 확인이 진단의 출발점입니다.
## 개선 미션 (우선순위)
### 미션 1 — Supabase 저장 + 보안(RLS) 상태 이해 **\[필수\]**
- **무엇을:** Cloud→Database에서 테이블·데이터 확인(이미 정상) + 보안 상태 이해.
- **왜 필요한가 (여기가 오늘 정정된 부분):** 과거 자료엔 "RLS를 켜서 권한을 나눠라"고 돼 있었는데, **강사가 실제로 확인해보니 이 앱은 그렇게 단순하지 않습니다.** 이 앱의 로그인은 Supabase 정식 인증이 아니라 \*\*자체 로그인(mock auth, 서버 RPC + bcrypt)\*\*입니다. 그래서:
- 관리자/일반 권한 분리는 **RLS가 아니라 앱 코드의 role 필드**로 처리됩니다.
- RLS는 **부분만** 적용돼 있습니다(비밀번호가 있는 staff 테이블만 강화, 나머지는 내부용이라 느슨). 이는 실수가 아니라 의도된 트레이드오프입니다.
- ⚠️ **strict RLS를 무작정 다 켜면 mock auth라서 앱이 멈춥니다.** (과장님이 보안 경고에서 "3번=staff만 부분강화"를 고른 이유가 바로 이것)

## 이 앱의 진단 — 왜 배포 자체가 최대 가치인가
부장님의 핵심 문제는 \*\*"파생자료 작업이 부장 PC에서만 가능(장소 제약) + 매일 사진으로 촬영해 임원·비서실에 발송(형식 비일관)"\*\*입니다.
**이 문제의 해법이 바로 오늘 배우는 Vercel 배포입니다.** URL만 있으면 어느 기기·어디서든 작업·조회가 가능해지므로, "부장 PC 종속"과 "사진 발송"이 **동시에** 해소됩니다. 즉 이 앱은 화려한 기능보다 **"인터넷에서 실제로 열리는 것" 자체가 가장 큰 가치**입니다.
## 개선 미션 (우선순위)
### 미션 1 — 3탭 로직 검증 **\[Cursor·오후\]**
- **무엇을:**
```plain text
□ 날짜 → 요일·주차 자동 계산이 맞는가□ Cross-Tab 즉시 반영 (탭1 입력 → 탭2·3 자동 갱신)□ 객단가(매출÷객수) 자동 계산 + 정렬□ 조건부 하이라이트 (전월 대비 음수→빨강 / 단가 2만원 미만→배지)
```
- **왜 필요한가:** 문서가 워낙 탄탄해 "새로 만들 것"보다 "PRD대로 작동하는지 검증"이 우선입니다. 특히 날짜→요일·주차 자동 계산과 Cross-Tab 반영은 이 앱의 핵심 로직이라, 여기가 정확해야 나머지가 신뢰됩니다.
### 미션 2 — GitHub·Vercel 배포 **\[필수 — 이 앱의 최대 가치\]**
- **무엇을:** 앱을 Vercel에 배포해 실제 URL 생성.
- **왜 필요한가:** 위 진단대로, **배포가 곧 이 앱의 존재 이유**입니다. 다른 분들에게 배포가 "다음 단계"라면, 부장님께는 배포가 "핵심 목표"입니다.
### 미션 3 — 실데이터 전환 판단 **\[8회차 / 오늘은 방향만\]**
- **무엇을:** 시뮬레이션 → 실제 매출 데이터로 전환. 매일 들어오는 구조면 방식③(구글시트+GAS), 가끔 파일 통째로면 방식②(앱 업로드).
- **왜 지금이 아니라 방향만인가:** 지금 시뮬레이션 방식은 화면·로직 검증에 최적이라, 먼저 로직을 확정하고 실데이터는 그 뒤에 붙이는 게 안전합니다. ⚠️ **매출은 6명 중 가장 민감(전사 매출)하므로, 실데이터 전환 시 로그인이 반드시 선행**돼야 합니다.
## ⚠️ 이 앱 특유의 주의점
- 완벽한 기능보다 \*\*"실제로 배포되어 뜨고, 데이터가 저장되는 것"\*\*을 먼저 목표로.
- 방식③(GAS)로 가면 개인 Supabase(길3)가 연동에 유리합니다.
