지금 우리 벡터DB에는 내가 고른 문서가 500자 고정으로 잘려<br>적재되어 있습니다. 의미 검색도 동작합니다.<br>그리고 우리는 두 가지 불편을 눈으로 확인한 상태입니다.<br>기계적으로 잘리다 망가진 손상 조각,<br>그리고 정확한 용어나 번호를 묻는 질문에서 흔들리는 검색 순위입니다.
이번 세션에서는 이 두 불편을 순서대로 고칩니다.<br>자르는 방식을 내 문서에 맞게 바꾸고,<br>찾는 방식에 두 번째 검색을 더해 약점을 메웁니다.<br>마지막에는 완성된 검색을 채팅방에 연결합니다.<br>내 문서를 근거로, 근거 번호를 달고 답하는 챗봇이<br>이번 세션의 종착점입니다.

## 청킹 전략 — 자르는 기준이 다른 세 가지
500자 고정은 문서의 사정을 모르는 기준이었습니다.<br>자르는 기준을 문서의 생김새에 맞추는 전략이 여럿 있습니다.<br>이번에 고를 수 있는 전략은 세 가지입니다.
- **전략 ① 고정 길이 (기준선)**
- 지금까지 쓴 방식 그대로입니다. 500자마다 자르고 50자를 겹칩니다.
- 어떤 문서에든 똑같이 동작하고, 결과를 예측하기 쉽습니다.
- **전략 ② 구조 경계 우선**
- "제N조" 같은 조항 표기나 제목을 먼저 찾아, 그 경계에서 자릅니다.
- 한 덩어리가 너무 길면 800자 상한으로 다시 나눕니다.
- 문서가 뚜렷한 구획 구조를 가질 때 그 구획을 통째로 보존합니다.
- **전략 ③ 문단 경계**
- 빈 줄로 나뉜 문단을 최소 단위로 삼아, 문단 중간을 자르지 않습니다.
- 짧은 문단은 500자 내외까지 묶고, 이웃과 100자를 겹칩니다.
- 문장과 문단의 흐름을 지키는 데 초점을 둡니다.
어느 전략이 내 문서의 정답인지는 이 자료에 적혀 있지 않습니다.<br>Ch2에서 각자 메모한 손상 조각이 진단서입니다.<br>손상이 어디서, 왜 생겼는지를 보면 처방이 보입니다.

## 키워드 검색 — 글자가 겹치는 조각을 찾는다
전략을 바꿔도 남는 불편이 있습니다.<br>"제10조", "1Q26"처럼 정확한 표기를 묻는 질문에서<br>의미 검색의 순위가 흔들리는 현상입니다.<br>뜻의 가까움으로 찾는 방식은, 정확히 그 글자가 있는 조각을<br>반드시 1위에 올린다는 보장이 없기 때문입니다.
이럴 때 쓰는 두 번째 검색이 키워드 검색입니다.<br>질문과 청크에 같은 단어가 얼마나 겹치는지로 점수를 매깁니다.<br>가장 널리 쓰는 계산 방식의 이름이 BM25입니다.<br>BM25는 흔한 단어보다 드문 단어의 일치에 높은 점수를 줍니다.<br>"제10조"처럼 문서에 몇 번 안 나오는 표기가 겹치면 강하게 반응합니다.
### 두 가지 검색 — 단어로 찾기와 의미로 찾기
검색에는 서로 다른 두 계열이 있습니다.<br>각자 잘하는 것과 못하는 것이 뚜렷합니다.
**의미 검색 (벡터 검색)**
임베딩 숫자의 가까움으로 점수를 매깁니다.<br>단어가 하나도 안 겹쳐도 뜻이 비슷하면 찾아냅니다.<br>"목에 뭐가 걸렸어요"로 "기도폐쇄" 문단을 찾는 것이 이 방식입니다.
**키워드 검색 (BM25)**
질문과 청크에 같은 단어가 얼마나 겹치는지로 점수를 매깁니다.<br>BM25는 이 계열에서 가장 널리 쓰이는 계산 방식의 이름입니다.<br>흔한 단어보다 드문 단어의 일치에 높은 점수를 줍니다.<br>"AED"처럼 드물고 정확한 용어가 겹치면 강하게 반응합니다.
한국어에는 준비물이 하나 필요합니다.<br>한국어는 "기술을", "기술이", "기술은"처럼 명사에 조사가 붙어,<br>띄어쓰기로만 자르면 전부 다른 단어로 취급됩니다.<br>형태소 분석기 kiwipiepy로 "기술"과 조사를 분리해 주면<br>키워드 검색이 제 성능을 냅니다.
두 검색은 잘하는 질문이 서로 다릅니다.<br>그래서 하나를 고르지 않고 둘 다 실행한 뒤 순위를 결합합니다.<br>결합 방식으로는 RRF(Reciprocal Rank Fusion)가 널리 쓰입니다.<br>양쪽 검색에서 모두 상위에 오른 조각일수록 최종 순위가 높아집니다.<br>점수가 아니라 순위로 결합하는 이유가 있습니다.<br>BM25 점수와 유사도 점수는 계산법이 달라 크기 단위가 다르므로,<br>점수를 그대로 더하면 한쪽이 결과를 지배하기 때문입니다.<br>이 결합을 하이브리드 검색이라고 부릅니다.

### kiwipiepy(키위파이파이)란?
`kiwipiepy`는 **'Kiwi(Korean Intelligent Word Identifier)'라는 빠르고 정확한 한국어 형태소 분석기를 파이썬에서 사용할 수 있도록 만든 라이브러리**입니다.
RAG나 자연어 처리에서 이 도구가 중요한 이유는 **한국어의 언어적 특성** 때문입니다. 영어는 띄어쓰기 기준으로 단어를 쪼개도 어느 정도 의미가 분리되지만, 한국어는 명사에 조사(은, 는, 이, 가, 을, 를)나 어미가 찰싹 붙어 있는 '교착어'입니다.
- **문제 상황:** "데이터베이스를", "데이터베이스가", "데이터베이스는" 이 세 단어를 컴퓨터는 띄어쓰기만으로 자르면 서로 완전히 다른 3개의 단어로 인식합니다. 검색이나 키워드 추출 시 성능이 크게 떨어집니다.
- **kiwipiepy의 역할:** 문장을 입력하면 여기서 순수하게 의미를 가진 명사("데이터베이스")와 조사("를", "가")를 정확하게 쪼개줍니다.
**RAG 파이프라인에서의 활용:**<br>특히 BM25 같은 키워드 기반 검색 엔진을 벡터 검색과 함께 사용하는 하이브리드 검색(Hybrid Search)을 구현할 때, 문서와 사용자의 질문에서 핵심 명사만 추출해 검색 정확도를 높이는 전처리 과정에 필수적으로 사용됩니다. 속도가 매우 빠르고 신조어 처리 능력도 뛰어나 실무에서도 널리 쓰입니다.
진행 순서

1. 프롬프트를 입력해 진행하고, 패키지 설치 후<br>서버를 재시작합니다.
2. Ch2의 준비 질문 B(정확한 용어·번호 질문)를 다시 꺼냅니다.
3. \[예측\] 세 열 중 어느 검색이 정확한 조각을 1위에 올릴지<br>예측해 적습니다.
4. 질문 B를 검색하고, 세 열의 1위 카드를 펼쳐 비교합니다.<br>\[확인\] 예측과 실제를 대조합니다.
5. 준비 질문 A(일상 말 질문)도 검색해, 이번에는<br>키워드 검색 열이 어떤 결과를 내는지 살펴봅니다.
6. 두 질문 모두에서 하이브리드 열이 정확한 조각을<br>상위에 올렸는지 확인합니다.
7. 자유 질문을 두세 개 던지며 세 열의 차이를 관찰합니다.<br>내 문서에서 키워드 검색이 특히 강한 질문 유형을<br>하나 찾아 메모합니다.

> 💡 4\~6번이 이번 실습의 관전 포인트입니다.<br>"하이브리드가 좋다"를 외우는 것이 아니라, 단일 검색이<br>각자 놓치는 현장을 본 뒤에 하이브리드가 둘을 모두<br>받아내는 것을 확인하는 순서입니다.
**FAQ**
- **Q. 키워드 검색 열만 결과가 이상합니다**
- 형태소 분석기가 빠졌을 가능성이 큽니다. Claude Code에 "BM25 토큰화에 kiwipiepy가 쓰이는지 확인해 주세요"라고 요청합니다.
- **Q. 형태소 분석기 설치가 실패합니다**
- 오류 로그를 Claude Code에 붙여넣고 해결을 요청합니다. 해결이 늦어지면 강사를 부릅니다.
- **Q. 점수 크기가 열마다 다릅니다**
- 정상입니다. BM25 점수와 유사도 점수는 계산법이 달라 범위도 다릅니다. 열 안에서의 순위만 비교하면 됩니다. 점수를 직접 더하지 않고 순위로 결합하는 이유가 바로 이것입니다.

## RAG 연결 — 검색된 청크만 프롬프트에 들어간다
이제 완성된 검색을 채팅방에 연결합니다.<br>"챗봇이 문서를 근거로 답한다"의 실체는 프롬프트 조립입니다.<br>질문이 들어오면 서버가 하이브리드 검색을 실행하고,<br>찾아온 청크를 질문과 함께 하나의 프롬프트로 묶어 Gemini에 보냅니다.
실제로 조립되어 전송되는 프롬프트는 이런 모습입니다.

당신은 문서 안내원입니다.<br>아래 근거만 사용해 답하고, 근거에 없는 내용은<br>"문서에서 확인되지 않습니다"라고 답하세요.<br>답변 끝에 사용한 근거 번호를 표기하세요.
\[근거 1\] (청크 #023, 방위산업기술 보호법)<br>제10조(방위산업기술의 유출 및 침해 금지) 누구든지 다음 각 호의<br>어느 하나에 해당하는 행위를 하여서는 아니 된다. 1. 부정한<br>방법으로 대상기관의 방위산업기술을 취득, 사용 또는 공개...
\[근거 2\] (청크 #024, 방위산업기술 보호법)<br>제11조(방위산업기술의 유출 및 침해 신고 등) ...
\[질문\] 회사 기술을 몰래 빼돌리면 어떻게 되나요?

여기서 이 과정 전체를 관통하는 사실 하나가 보입니다.<br>**Gemini에 문서 전체를 보내지 않습니다.**<br>검색이 골라낸 청크 몇 개만 보냅니다.<br>문서가 수백 페이지여도, AI가 매번 읽는 것은 이 몇 조각뿐입니다.<br>그래서 검색의 품질이 곧 답변의 품질입니다.<br>우리가 청킹을 고치고 검색을 결합한 이유가 전부 이 한 줄에 있습니다.
이 조립 덕분에 두 가지가 달라집니다.<br>답변의 재료가 일반 지식에서 내 문서로 바뀝니다.<br>그리고 답변마다 어느 청크를 썼는지 번호가 남아,<br>사람이 원문을 열어 사실을 대조할 수 있습니다.

### 실습 3. 채팅방에 검색을 연결하기
채팅방이 하이브리드 검색 결과를 근거로 답하게 만듭니다.
**Claude Code 프롬프트**
```plain text
채팅 페이지에 문서 근거 기반 대화를 추가해 주세요. 요구사항입니다.

1. 채팅 페이지에 [지식 기반 답변 모드] 토글 버튼을 추가해 주세요.
   아래는 토글이 켜졌을 때의 동작입니다.

2. 질문이 들어오면 하이브리드 검색으로 상위 K개(기본 3) 청크를
   찾은 뒤, 청크를 근거로 포함한 프롬프트를 조립해
   Gemini(gemini-2.5-flash)에 보내 주세요.

3. 프롬프트에는 다음 지시를 포함해 주세요.
   - 근거만 사용해 답할 것
   - 근거에 없는 내용은 "문서에서 확인되지 않습니다"라고 답할 것
   - 답변 끝에 사용한 근거의 청크 번호를 표기할 것
   기존의 채팅방 말투 지시는 그대로 유지해 주세요.

4. 답변 말풍선 아래에 근거 청크 목록을 작게 표시해 주세요.
   청크 번호와 출처 문서명이 보이고, 누르면 청크 원문이
   펼쳐지게 해 주세요.

5. 서버 로그에 질문 수신 → 검색 완료(청크 번호들) →
   Gemini 호출 → 응답 반환이 순서대로 출력되게 해 주세요.
```
진행 순서

1. 프롬프트를 입력해 진행하고, 서버를 재시작한 뒤<br>채팅 페이지를 엽니다.
2. \[지식 기반 답변 모드\]를 켭니다.
3. 준비 질문 A를 채팅방에 그대로 묻습니다.
4. 답변 아래 근거 청크 번호를 확인하고, 눌러서 원문을 폅니다.
5. 답변의 문장과 청크 원문을 한 줄씩 대조합니다.<br>답변 내용이 실제로 근거 안에 있으면 성공입니다.
6. 문서에 없을 질문을 일부러 던집니다.<br>(예: "달에서 지진이 나면?", "이 법의 벌금을 달러로 내면?",<br>"10년 뒤 주가는?")<br>"문서에서 확인되지 않습니다" 계열의 답이 오는지 확인합니다.
7. 토글을 끄고 같은 질문을 다시 던져, 일반 지식 답변과<br>문서 근거 답변의 차이를 나란히 비교합니다.
8. 자유 질문 시간입니다. 내 문서에 궁금했던 것을 마음껏 묻고,<br>답변마다 근거 번호가 붙는지 지켜봅니다.

> 💡 7번의 비교가 이번 세션 전체의 요약입니다.<br>같은 채팅방, 같은 질문인데 토글 하나로 답의 재료가 바뀝니다.<br>꺼진 쪽은 Gemini의 기억이고, 켜진 쪽은 내 문서입니다.
**FAQ**
- **Q. 답변에 근거 번호가 안 붙습니다**
- 프롬프트 지시가 빠진 상태입니다. Claude Code에 "답변에 청크 번호 표기가 빠집니다. 프롬프트를 점검해 주세요"라고 요청합니다.
- **Q. 문서에 없는 내용을 그럴듯하게 답합니다**
- 근거 제한 지시가 약한 상태입니다. Claude Code에 "근거에 없으면 모른다고 답하도록 지시를 강화해 주세요"라고 요청합니다.
- **Q. 답변이 이전보다 느려졌습니다**
- 정상 범위입니다. 검색과 프롬프트 조립 단계가 추가되었기 때문이며, 어느 단계가 오래 걸리는지는 터미널 B의 로그에서 확인할 수 있습니다.
- **Q. 말투가 딱딱해졌습니다**
- 근거 지시가 말투 지시를 덮은 상태입니다. Claude Code에 "지식 기반 모드에서도 기존 말투 지시가 유지되게 해 주세요"라고 요청합니다.

## 품질을 숫자로 관리하고 싶다면 — 자동 채점이라는 방법
> 💡 지금은 답변의 품질을 사람 눈으로 확인했습니다.<br>질문이 수십 개로 늘면 사람이 매번 검사할 수 없습니다.<br>실무에서는 정답을 아는 질문 세트를 만들어 두고,<br>챗봇의 답변을 AI가 정답·근거와 비교해 1\~5점으로 채점하게 합니다.<br>이 방식을 LLM-as-a-Judge라고 부릅니다.<br>채점 프롬프트의 뼈대는 단순합니다. 질문, 정답, 검색된 근거,<br>챗봇 답변을 나란히 주고 "점수와 사유를 출력하라"고 지시합니다.<br>점수 리포트가 쌓이면 K값이나 프롬프트를 바꾼 수정이<br>개선이었는지 개악이었는지 숫자로 판정할 수 있습니다.<br>채점자도 AI라서 항상 옳지는 않으므로, 이상한 점수는<br>사람이 원문을 열어 재확인합니다.

## 실습 확장 (선택)
기본 실습을 마친 분은 아래를 자유롭게 시도합니다.
- **전략 맞대결**: 고르지 않은 전략으로 재적재해 같은 질문을<br>검색하고, 내 처방과 결과를 비교합니다.
- **K값 실험**: K를 1, 5, 10으로 바꿔 가며 같은 질문을 던집니다.<br>K가 크면 근거가 풍부해지는지, 무관한 조각이 섞이는지 관찰합니다.
- **다른 문서 합치기**: 고르지 않은 문서 하나를 추가 적재하고<br>두 문서에 걸친 질문을 던져 봅니다. 근거에 두 문서가<br>함께 등장하는지 확인합니다.
- **코드 열어 보기**: "RRF로 순위를 결합하는 함수를 보여 주고,<br>한 줄씩 설명해 주세요"라고 요청합니다.<br>하이브리드의 심장을 직접 들여다봅니다.
- **근거 문장 표기**: "답변의 문장마다 사용한 근거 번호를<br>괄호로 붙여 주세요"라고 요청해, 문장 단위 대조를 시험합니다.
