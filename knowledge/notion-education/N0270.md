# R.O.P.E. + K — 설계 체크리스트
R.C.T.C는 **한 번 쓰는 프롬프트용**입니다. 저장해서 반복 사용할 Gems는 **다섯 칸**으로 확인합니다.


<colgroup>
<col width="60">
<col width="110">
<col width="513.9999847412109">
</colgroup>





항목

자문해볼 것




**R**

Role

직업뿐 아니라 **경력 연차와 전문 분야**를 설정했는가




**O**

Objective

존재 이유를 **한 문장**으로 요약할 수 있는가




**P**

Process

일하는 순서를 **단계별**로 명시했는가<br><br>→ cot (chain of thought) / 생각의 사슬을 만드는 기법




**E**

Example

원하는 결과물의 **출력 예시**를 제공했는가




**K**

Knowledge

약어 목록·단위 규칙 같은 **우리만의 정보**를 넣었는가



**R.C.T.C와 R.O.P.E.+K는 다른 게 아닙니다**
맥락(C)이 **목표(O)**로 바뀌고, **예시(E)와 지식(K)**이 추가된 것입니다.
저장해서 반복 쓰려면 **예시와 지식이 있어야** 품질이 유지됩니다.

<summary>역설계 — 회사 가셔서 쓰시면 좋습니다</summary>
잘 쓴 결과물을 주고 **「이렇게 쓰는 기계를 만들어줘」**라고 시키는 방법입니다.
절차를 말로 설명하기 어려울 때, 우리만의 문체를 복제하고 싶을 때 강력합니다.
```plain text
아래는 내가 작성한 [문서 종류] 중 가장 잘 된 것입니다.

[여기에 결과물 붙여넣기]

이 문서를 분석해서 아래 세 가지를 추출해 주세요.
1. 검토·작성 순서 (어떤 항목을 어떤 차례로 다뤘는가)
2. 판단 기준 (무엇을 근거로 결론을 냈는가)
3. 문체와 형식 (어미·표 구조·항목 구성)

그리고 앞으로 내가 어떤 자료를 던지든
이 문서와 똑같은 방식으로 작성해주는 시스템 프롬프트를
R.O.P.E.+K 형식으로 직접 짜 주세요.

단, 아래는 반드시 제약에 포함해 주세요.
- 문서에 없는 값은 만들지 않는다
- 원문 단위를 그대로 쓰고 변환하지 않는다
- 없는 항목은 [확인 필요]로 표시한다
```
**핵심은 「이렇게 해」가 아니라 「이걸 보고 배워」입니다.**
오늘 실습에서 안 하는 이유는 **여러분이 잘 쓴 문서가 여기 없기 때문**입니다.
회사에 돌아가셔서 기술검토 회신서나 규격 검토서로 해보시면 됩니다.
**대외비 문서는 쓰지 마십시오.** 고객사명·단가·실적은 지우고 구조만 남겨 쓰시면 됩니다.
</details>


# 실습 · 부서 전용 Gems 지침 작성

**산출물 — 부서 전용 Gems 1개** · 소요 40분
오늘은 **지침까지** 만듭니다. 자료는 회사 돌아가셔서 붙이시면 됩니다.

Gems는 파일을 붙일 수 있지만 **오늘 여러분 자료가 여기 없습니다.**
지침이 제대로 서 있으면 **자료는 갈아끼우기만 하면 됩니다.** 오늘은 지침 설계에 40분을 온전히 씁니다.
## Step 01 :: 새 Gem을 만듭니다 (5분)
브라우저에서 Gemini → 왼쪽 메뉴 **Gems** → **새로 만들기**
이름은 모듈 01에서 고르신 업무명을 그대로 쓰시면 됩니다.
## Step 02 :: R·O·P를 채웁니다 (15분)
먼저 세 칸만 씁니다.
```plain text
[R] 역할
당신은 (어느 분야)를 (몇 년간) 담당하며
(어떤 산출물)을 직접 작성해 온 (직책)입니다.

[O] 목표 — 한 문장으로
사용자가 (무엇을) 넣으면 (무엇을) 만듭니다.

[P] 절차 — 번호로
1.
2.
3.
4.
```

**O는 반드시 한 문장으로 쓰십시오.**
두 문장이 되면 과업이 두 개라는 뜻입니다. **Gem을 둘로 나누시는 편이** 낫습니다.

<details>
<summary>막힐 때 — AI에게 인터뷰시키는 방법</summary>
절차를 글로 적기 어려우면 이걸 먼저 돌리시면 됩니다.
```plain text
나는 ESS 제어 소프트웨어를 개발하며 [내가 고른 업무]를 한다.
이 업무를 Gems로 만들려고 한다.

내가 어떤 순서로 이 일을 하는지 알아내기 위해
한 번에 하나씩 질문해줘. 5개 정도 물어본 뒤
[P] 절차 부분을 번호로 정리해줘.

내 업무에 대해 모르는 부분은 추측하지 말고 질문해줘.
```
절차를 글로 적기 어려운 이유는 몰라서가 아니라 **너무 익숙해서 의식하지 않기 때문**입니다.
</details>
## Step 03 :: E와 K를 채웁니다 (10분)
여기가 **품질을 가르는 칸**입니다.
```plain text
[E] 출력 예시
원하는 형태를 짧게라도 직접 그려 넣습니다.
예) | 항목 | 값 | 단위 | 문서 위치 |

[K] 지식
약어 — MESSIS(피크저감 EMS), PCS(전력변환장치) …
단위 — 시간 ms, 전력 kW, 용량 kWh. 원문 단위를 그대로 유지
쓰지 말 표현 — "문제없을 것으로 사료됨" 같은 근거 없는 단정
```

**설문에 이런 답변이 있었습니다**
매번 반복해서 설명해야 하는 것을 물었더니 「**프로젝트에 대한 도메인 지식**」이라고 답하셨습니다.
**K 블록이 정확히 그걸 위한 자리입니다.** 한 번 적어두면 다시 설명하지 않아도 됩니다.
```plain text
현장에 A사·B사 PCS가 혼재돼 있고 레지스터 맵이 다릅니다.
통신 타임아웃이 월 2회 발생하며 재연결은 자동입니다.
현장 재기동이 어려워 무중단 처리가 필요합니다.
```

## Step 04 :: 제약을 붙입니다 (2분)
아래를 그대로 복사해 맨 끝에 붙이시면 됩니다.
```plain text
[제약]
- 제가 제공한 문서에 없는 값은 절대 만들지 마세요.
- 문서에 없는 항목은 [확인 필요]로 표시하세요.
- 원문의 단위를 그대로 쓰고 변환하지 마세요.
- 일반적인 기술 지식으로 빈칸을 채우지 마세요.
- 정보가 부족하면 추측하지 말고 먼저 물어보세요.

[자주 틀리는 것]
(비워 둡니다)
```

내용이 내 업무와 안 맞아도 괜찮습니다. 지금 보는 건 **지침이 작동하는가**입니다.
