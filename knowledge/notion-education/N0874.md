## 지금까지 우리가 온 길
6회차를 시작하기 전에, 1\~5회차에서 무엇을 해왔는지 흐름을 한 번 짚어봅니다.
```plain text
1회차 — 비정형 → 정형 (변환)
  사진으로 온 발주서, 메신저 메시지를
  Claude가 읽고 정리된 표로 만들어줬다

2회차 — 정형 → 분석 (패턴 발견)
  엑셀 파일을 Claude에 올리면
  오입력을 탐지하고, 재고 위험 품목을 분류해줬다

3회차 — 분석 → 보고서 (전달)
  분석 결과를 차트·인포그래픽·Word 보고서·PPT로
  자동 완성했다

4회차 — 반복 → 자동화 (GAS)
  버튼 하나로 구글 시트 데이터를 자동 처리하고
  이메일까지 자동으로 보냈다

5회차 — 연결 → 자동화 심화 (Make.com)
  구글 시트, Gmail, 외부 서비스까지 연결해서
  데이터 흐름 전체를 자동화했다

6회차 — 자동화 → 웹/앱 제작 (바이브코딩) ← 오늘
  지금까지는 "있는 도구"를 활용했다면
  오늘부터는 "없는 도구를 직접 만든다"
```
1\~5회차가 AI를 **활용**하는 것이었다면, 6\~8회차는 AI에게 **만들게** 하는 단계입니다.

## 바이브코딩이란 무엇인가
- \*바이브코딩(Vibe Coding)\*\*이란 코드를 직접 작성하는 것이 아니라, AI에게 자연어로 요청해서 앱을 만드는 방식입니다. 2024년 초 Andrej Karpathy(전 Tesla AI 총괄, OpenAI 공동창업자)가 처음 명명한 개념으로, 지금 전 세계 스타트업·대기업에서 가장 빠르게 확산되고 있는 개발 방식입니다.
```plain text
기존 개발 방식:
  HTML·CSS·JavaScript·React 문법 공부 (6개월~2년)
  → 코드 직접 작성
  → 오류 직접 수정 (Stack Overflow 검색, 디버깅)
  → 서버 설정
  → 배포

바이브코딩 방식:
  "이런 화면을 만들어줘" (자연어)
  → AI가 코드 생성
  → 결과 확인
  → 추가 요청
  → 완성 (수시간~수일)
```
GAS에서 이미 이 경험을 했습니다. "Claude에게 코드를 받아서 구글 시트에 붙여넣었더니 작동했다." 바이브코딩은 그것의 완전한 확장판입니다. 오늘은 붙여넣는 것조차 AI가 합니다.
---
## 바이브코딩이 가능해진 이유 — 기술적 배경
왜 지금 이것이 가능해졌는지 이해하면 더 잘 활용할 수 있습니다.
```plain text
2022년 이전:
  AI는 간단한 코드 조각만 제안 가능
  복잡한 앱 전체를 만드는 것은 불가능

2023년 이후 (GPT-4, Claude 3 등장):
  AI의 코드 이해·생성 능력이 인간 상위 10% 수준으로 향상
  수천 줄의 코드를 한 번에 작성·이해·수정 가능

2024~2025년 (Lovable, v0, Bolt 등장):
  "프롬프트 → 완성된 앱" 파이프라인이 상용화됨
  UI 디자인·기능·데이터 처리까지 한 번에 생성
  비개발자도 1시간 안에 작동하는 앱 완성 가능

핵심 변화:
  "코드를 짜는 능력"보다
  "무엇을 만들지 정확히 설명하는 능력"이 더 중요해짐
```

## 웹(Web)과 웹앱(Web App) — 정확히 이해하기
오늘 만드는 것의 정체를 명확히 알아야 PRD 작성이 잘 됩니다.
```plain text
웹 (Web):
  정보를 보여주는 것이 주목적
  사용자는 보기만 함 (입력 없음)
  예: 매장별 현황 대시보드 / 휴무자 조회 화면 / 발주 누적 현황

웹앱 (Web App):
  정보를 입력하고, 저장하고, 처리하는 것이 주목적
  사용자가 직접 데이터를 다룸
  예: 정비 접수 폼 / 발주 입력 화면 / 공급가 변경 등록

둘 다 가능 (오늘 대부분이 이 경우):
  보는 화면(웹) + 입력하는 화면(웹앱)이 한 도구에 함께
  예: 현황판을 보면서 + 새 데이터도 입력 가능
```
> 💡 **쉬운 비유**
GAS로 만든 것 = 회사 건물 안의 자판기 (건물=구글 시트에 들어가야만 작동)<br>웹/앱으로 만든 것 = 배달 앱 (어디서든 스마트폰만 있으면 접속 가능)
앱 스토어에 올리는 앱이 아닙니다. URL을 열면 바로 나오는 도구입니다.<br>스마트폰에서 열면 앱처럼, PC에서 열면 웹사이트처럼 보입니다. 설치가 필요 없습니다.

## 바이브코딩의 핵심 기술 개념 (알아두면 도움 되는 것들)
직접 코드를 짜지 않아도, 아래 개념을 알면 Lovable·Cursor와의 대화가 훨씬 정확해집니다.
**React — 오늘 만드는 앱의 기반 기술**
```plain text
Lovable이 만들어주는 앱은 대부분 React로 만들어집니다.
React는 화면을 "컴포넌트"(부품) 단위로 조립하는 방식입니다.

컴포넌트 = 화면의 부품
  예: 버튼 하나 / 테이블 하나 / 입력 폼 하나 / 요약 카드 하나
  → 이 부품들을 조합해서 하나의 앱이 만들어짐

알아두면 좋은 이유:
  "이 버튼 컴포넌트만 수정해줘"
  "테이블 컴포넌트에 검색 기능 추가해줘"
  이렇게 말하면 Lovable이 더 정확하게 수정해줌
```
**State (상태) — 동적 기능의 핵심**
```plain text
State = 앱이 기억하는 현재 데이터

예시:
  버튼을 클릭했는지 안 했는지 → State로 관리
  목록에 몇 개 항목이 있는지 → State로 관리
  검색어를 입력했는지 → State로 관리

동적 기능 = State가 바뀌면 화면도 즉시 바뀌는 것
정적 기능 = State 없이 그냥 고정된 화면

PRD에 "React useState 사용"이라고 명시하는 이유:
  → Lovable에게 "이 기능이 실제로 작동해야 한다"고 알려주는 것
```
**프론트엔드 vs 백엔드**
```plain text
프론트엔드 (Front-end):
  사용자 눈에 보이는 화면
  → Lovable이 오늘 만들어주는 것

백엔드 (Back-end):
  데이터 저장, 서버, 데이터베이스
  → 오늘은 샘플 데이터로 대체
  → 나중에 Supabase 연동으로 해결 가능

오늘의 현실적 한계:
  오늘 만드는 앱은 프론트엔드만 있음
  브라우저를 닫으면 입력한 데이터가 사라짐
  → 오늘 목표는 "화면과 기능 구조 완성"
  → 실제 데이터 저장은 Supabase 연동으로 추후 해결
```

## 동적 기능이란 — 실제로 작동해야 한다
Lovable로 만들 때 가장 중요한 원칙입니다.
```plain text
❌ 정적(Static) 화면 — 작동 안 하는 것:
  버튼이 있지만 눌러도 반응 없음
  폼이 있지만 제출해도 아무 일도 없음
  테이블이 있지만 필터가 작동 안 함
  요약 숫자가 항상 같은 값으로 고정됨

✅ 동적(Dynamic) 화면 — 실제로 작동하는 것:
  버튼을 누르면 즉시 반응이 생김
  폼을 제출하면 성공 메시지가 뜨고 목록에 추가됨
  필터 버튼을 누르면 즉시 목록이 바뀜
  요약 숫자가 새 데이터 입력 시 자동으로 갱신됨
```
오늘 만드는 것은 반드시 동적으로 작동해야 합니다. <br>Gems가 만들어주는 PRD에 이 내용이 이미 포함되어 있으므로, PRD를 그대로 Lovable에 붙여넣으면 됩니다.
> ⚠️ 버튼이 눌리지 않거나 기능이 작동하지 않으면 → "이 기능들이 실제로 작동하게 고쳐줘. React useState를 사용해서 버튼, 폼, 필터 모두 클릭하면 즉시 반응이 있어야 해."라고 요청하세요.

## 바이브코딩의 현실적 한계 — 기대치 설정
바이브코딩이 강력하지만, 알아야 할 현실적 한계도 있습니다.
```plain text
한계 1: 데이터가 저장되지 않음 (오늘)
  브라우저를 새로고침하면 입력한 데이터가 사라짐
  → 해결: Supabase 데이터베이스 연동 (추후)

한계 2: 복잡한 비즈니스 로직은 여러 번 시도 필요
  "55개 매장, 38개 품목 매핑, ERP 대조" 같은 복잡한 로직은
  첫 번째 PRD로 완벽하게 나오지 않을 수 있음
  → 해결: 단계별 요청, 원샷 수정 반복

한계 3: 컨텍스트 토큰 한계
  대화가 길어지거나 수정을 많이 하면 AI가 앞 내용을 "잊기" 시작함
  → 증상: 이전에 만든 기능이 갑자기 사라지거나 이상해짐
  → 해결: 새 채팅 시작 + PRD 다시 붙여넣기

한계 4: 완벽한 디자인이 첫 번째에 나오지 않을 수 있음
  → 해결: Edit 모드로 직접 수정 + AI 채팅으로 수정 요청 반복

한계 5: 실제 서비스로 쓰려면 추가 작업 필요
  보안 설정, 사용자 인증, 서버 비용 등
  → 오늘 목표: "업무에서 쓸 수 있는 수준의 프로토타입 완성"
```
> 💡 "100% 완벽한 앱을 오늘 완성한다"가 아니라 "내 업무 화면이 URL로 열리는 경험을 완주한다"가 오늘의 목표입니다.

Lovable 등 바이브코딩 도구로 실제로 만들어진 사례들입니다.

# 오늘 쓰는 도구 — Lovable 완전 정복

## Lovable이란
```plain text
lovable.dev — 브라우저에서 바로 실행
자연어 프롬프트(또는 PRD) → 실시간으로 앱이 생성됨
프런트엔드부터 기본 백엔드 구조까지 자동 생성
코드 설치 없음 / 터미널 없음 / 문법 공부 없음
```
**Lovable을 선택한 이유:**
```plain text
① 결과물이 즉시 눈에 보임
  요청하면 오른쪽 화면에 앱이 실시간으로 만들어짐

② 완성도가 높음
  UI 디자인까지 포함해서 실제로 쓸 수 있는 수준의 결과물

③ 수정이 쉬움
  말로 요청하면 즉시 반영됨. Edit 모드로 직접 수정도 가능

④ 배포까지 한 번에
  [Publish] 버튼 하나로 실제 URL 생성
  GitHub·서버 설정 없이 바로 공개 가능

⑤ 이미지·파일 업로드 가능
  채팅창에 이미지를 드래그&드롭하면
  Lovable이 해당 이미지를 앱에 적용해줌
  "이 이미지를 배경으로 써줘" / "이 로고를 상단에 넣어줘"
```

## Lovable 화면 구조 완전 이해
```plain text
┌─────────────────────────────────────────────┐
│  상단 메뉴바                                 │
│  [프로젝트명]  [Share]  [Publish]  [Settings]│
├──────────────┬──────────────────────────────┤
│              │                              │
│  왼쪽        │  오른쪽                      │
│  채팅창      │  미리보기                    │
│              │                              │
│  대화 내역   │  [Preview] [Code]            │
│  쌓임        │                              │
│              │  실제 앱 화면이 보임          │
│              │  버튼 클릭·입력 가능          │
│              │                              │
├──────────────┤                              │
│  [Edit] 버튼 │  (PC/태블릿/모바일 전환)     │
│  입력창      │                              │
└──────────────┴──────────────────────────────┘
```
**각 영역 설명:**
```plain text
[왼쪽 채팅창]
  모든 요청과 수정을 여기에 입력
  이미지 드래그&드롭 가능
  대화 내역이 쌓이면서 프로젝트 히스토리가 됨

[오른쪽 미리보기]
  Preview 탭: 실제 앱처럼 작동하는 미리보기
    → 버튼 클릭, 폼 입력, 필터 등 모두 테스트 가능
  Code 탭: 생성된 코드
    → 볼 필요 없음 (참고용)

[상단 전환 아이콘]
  PC / 태블릿 / 모바일 화면 미리보기 전환
  모바일 아이콘 클릭 → 스마트폰 크기로 화면 확인

[Edit 버튼] (왼쪽 하단)
  클릭 모드 전환 → 화면 요소를 직접 클릭해서 수정 가능
```

## Lovable 편집 방법 세 가지
결과물을 수정하는 방법은 세 가지가 있습니다. 상황에 맞게 선택합니다.
**방법 1 — Edit 모드 (직접 수정, 크레딧 절약)**
```plain text
언제: 텍스트·색상·여백·폰트 등 단순한 수정
방법:
  왼쪽 하단 [Edit] 버튼 클릭 → 편집 모드 전환
  → 수정할 부분 클릭 → 파란 테두리로 선택됨
  → 텍스트: 클릭 후 직접 입력
  → 색상: 스타일 패널에서 색상 선택
  → 여백: 마진·패딩 숫자 조정
  → 삭제: 휴지통 아이콘
  수정 후 [Save] 버튼 클릭

장점: 크레딧 소모 없음
단점: 코드와 연결된 동적 기능은 수정 불가
```
**방법 2 — AI 채팅창 요청 (기능·레이아웃·이미지 수정)**
```plain text
언제: 기능 추가, 레이아웃 변경, 이미지 교체, 동적 기능 수정
방법:
  왼쪽 채팅창에 말로 요청 입력
  → Lovable AI가 코드를 수정하고 미리보기가 갱신됨

크레딧 소모: 요청 1회당 크레딧 소비
핵심 원칙: 한 번에 많이 요청할수록 크레딧 절약
```
**방법 3 — 특정 섹션 선택 후 AI 요청 (정밀 수정)**
```plain text
언제: 앱의 특정 부분만 집중 수정하고 싶을 때
방법:
  [Edit] 모드에서 수정할 섹션 클릭 (파란 테두리)
  → 왼쪽 채팅창에 "이 부분을 [수정 내용]으로 바꿔줘"
  → Lovable이 선택된 섹션에만 집중해서 수정

장점: 다른 부분에 영향 없이 원하는 곳만 정확하게 수정
예시:
  테이블 섹션 선택 → "이 테이블에 검색창 추가해줘"
  버튼 선택 → "이 버튼 스타일을 더 크고 눈에 띄게 해줘"
```
> 💡 **Edit 모드로 할 수 있는 수정은 Edit 모드로 먼저 처리하세요.** 크레딧을 아낄 수 있습니다.

## Lovable 크레딧 관리
```plain text
AI 요청(채팅창 전송)을 할 때마다 크레딧이 소모됩니다.

Pro 플랜: 넉넉한 크레딧 제공 (월 단위)
무료 플랜: 하루 5 크레딧, 월 최대 30 크레딧

크레딧 절약 원칙:

  ❌ 비효율 — 한 번에 하나씩 요청
     "버튼 색 바꿔줘" [전송] → 크레딧 1 소비
     "글씨 크게 해줘" [전송] → 크레딧 1 소비
     "여백 줄여줘"   [전송] → 크레딧 1 소비
     총 크레딧 3 소비

  ✅ 효율 — 한 번에 묶어서 요청
     "버튼 색을 초록으로 바꾸고,
      글씨 크기 키우고,
      상단 여백 줄여줘.
      제출 후 성공 메시지도 추가해줘." [전송]
     총 크레딧 1 소비

  ✅ Edit 모드 활용
     텍스트·색상 수정은 Edit 모드로 → 크레딧 0 소비
     기능 수정만 AI 채팅으로 → 크레딧 절약
```

## Lovable 프롬프트 잘 쓰는 법 — 7가지 원칙
바이브코딩에서 가장 중요한 능력은 \*\*"내가 원하는 것을 정확하게 설명하는 것"\*\*입니다.
**원칙 1: 구체적인 수치를 사용한다**
```plain text
❌ "버튼을 크게 해줘"
✅ "버튼의 높이를 최소 48px, 너비를 160px로 설정하고
    폰트 사이즈를 16px, 볼드체로 해줘"

❌ "초록색으로 바꿔줘"
✅ "메인 컬러를 #1B4332 (짙은 초록)으로 바꿔줘.
    버튼 배경색과 테이블 헤더에 적용해줘."
```
**원칙 2: 조건을 명확하게 설명한다**
```plain text
❌ "위험한 거 빨간색으로 해줘"
✅ "잔액이 500,000원 미만인 행은
    행 전체 배경색을 #FFE0E0 (연한 빨간색)으로 표시해줘.
    500,000원 이상은 기본 흰색 배경 유지."
```
**원칙 3: 동작의 흐름을 단계별로 설명한다**
```plain text
❌ "폼 제출 기능 만들어줘"
✅ "제출 버튼을 클릭했을 때 다음 순서로 동작해야 해:
    1. 필수 항목이 비어있으면 해당 필드 아래에 빨간 오류 메시지 표시
    2. 모든 필수 항목이 입력됐으면 목록 맨 위에 새 항목 추가
    3. '접수되었습니다' 성공 메시지 표시 (2초 후 자동으로 사라짐)
    4. 입력 폼의 모든 필드를 빈 값으로 초기화"
```
**원칙 4: 맥락(역할·배경)을 알려준다**
```plain text
❌ "발주 앱 만들어줘"
✅ "교육기관이라는 외식 프랜차이즈 기업의
    영업관리부 직원이 사용하는
    매장별 발주 현황 입력·조회 앱을 만들어줘."
```
**원칙 5: 디자인 분위기를 구체적으로 표현한다**
```plain text
❌ "예쁘게 해줘"
✅ "깔끔하고 전문적인 B2B 내부 도구 느낌.
    흰색 배경, 짙은 초록 포인트 컬러, 둥근 모서리 카드,
    그림자 효과는 최소화."

또는:
✅ "모바일에서 현장 직원이 빠르게 입력하는 앱이야.
    버튼은 크고 눈에 띄게,
    입력 필드는 손가락으로 탭하기 편한 크기로."
```
**원칙 6: 이미지를 직접 올린다**
```plain text
Lovable 채팅창에 이미지 드래그&드롭 가능:

  "이 이미지를 메인 화면 배경으로 써줘"
  "이 로고를 상단 왼쪽에 넣어줘. 높이 40px"
  "이 화면처럼 레이아웃을 만들어줘" (다른 앱 스크린샷 참고)
  "이 오류 화면이야. 원인이 뭐고 어떻게 고쳐?" (오류 스크린샷)
```
**원칙 7: 수정 요청은 무엇이 문제인지 + 어떻게 되어야 하는지를 함께 말한다**
```plain text
❌ "이상해. 고쳐줘"
✅ "제출 버튼을 클릭했을 때 아무 반응이 없어.
    클릭하면 성공 메시지가 뜨고 목록에 항목이 추가되어야 해."

❌ "모바일에서 이상해"
✅ "스마트폰(375px)에서 봤을 때 테이블이 가로로 잘려.
    모바일에서는 테이블을 스크롤 가능하게 하거나
    카드 형식으로 변경해줘."
```

## Lovable 활용 꿀팁 모음
실제로 사용하면서 알게 되는 꿀팁들을 미리 공유합니다.
**꿀팁 1: PRD를 한 번에 붙여넣으면 완성도가 높아진다**
```plain text
PRD 없이 한 줄씩 요청: "비즈머니 현황 앱 만들어줘"
→ Lovable이 임의로 판단해서 만듦, 원하는 것과 다를 수 있음

PRD 통째로 붙여넣기:
→ 유형·기능·디자인·동적 요구사항까지 한 번에 전달
→ 첫 결과물 완성도가 훨씬 높음
→ 수정 횟수(=크레딧 소모)가 줄어듦
```
**꿀팁 2: 생성 중에는 기다린다**
```plain text
PRD 붙여넣기 후 → 오른쪽 화면이 만들어지는 동안:
  절대 중간에 채팅창에 새 요청 입력하지 않기
  → 완성 전에 새 요청이 들어오면 충돌 가능성

완성 신호:
  왼쪽 채팅창에 AI 응답이 완료됨
  오른쪽 미리보기가 안정된 상태로 표시됨
  → 그때부터 테스트하고 수정 요청
```
**꿀팁 3: ****`작동 안 하는 기능은 구체적인 기술 지시어를 추가한다`**
```plain text
기능이 작동 안 할 때 (버튼 눌러도 반응 없음):
  → "React useState를 사용해서
     이 기능이 실제로 작동하게 해줘.
     페이지 새로고침 없이 즉시 화면이 업데이트돼야 해."

요약 카드 숫자가 안 바뀔 때:
  → "요약 카드의 숫자가 테이블 데이터에서
     자동으로 계산되도록 해줘.
     새 데이터가 추가될 때마다 즉시 갱신돼야 해."
```
**꿀팁 4: "이 부분만" 선택해서 수정하면 정확하다**
```plain text
전체를 다시 만들지 말고:
  Edit 모드 → 수정할 섹션 클릭(파란 테두리)
  → 채팅창에 "이 섹션의 [구체적 수정]"
  → 다른 부분 건드리지 않고 원하는 곳만 수정
```
**꿀팁 5: 컨텍스트 한계에 걸리면 새 프로젝트 + PRD 재활용**
```plain text
증상:
  대화가 많이 쌓인 후 수정 요청을 했는데
  이전에 만든 기능이 갑자기 사라지거나 이상해짐
  → 컨텍스트 토큰 한계에 걸린 것

해결:
  Lovable에서 새 프로젝트 시작
  → 원래 PRD + 지금까지 추가한 기능을 합친 새 PRD 작성
  → 붙여넣기
  → 깨끗하게 다시 시작
```
**꿀팁 6: 디자인 참고 이미지를 활용한다**
```plain text
원하는 디자인이 있는 웹사이트를 캡처해서 올리기:
  "이 디자인처럼 만들어줘" (캡처 이미지 첨부)
  → Lovable이 디자인 스타일을 참고해서 적용

교육기관 로고나 브랜드 컬러가 있다면:
  로고 이미지 첨부 → "이 로고를 상단에 넣어줘"
  "교육기관 브랜드 컬러는 [색상 코드]야. 적용해줘."
```
**꿀팁 7: 한글로 요청하면 한글 UI가 나온다**
```plain text
PRD는 영어로 작성 (Lovable이 영어에서 품질이 높음)
but, 채팅창 수정 요청은 한글로 해도 됨

단, UI 텍스트가 영어로 나왔을 때:
  → "모든 버튼, 라벨, 메시지, 플레이스홀더 텍스트를
     한글로 바꿔줘. 영어가 하나도 없어야 해."
```

## 실전 상황별 대처법
Lovable 사용 중 가장 자주 마주치는 상황과 해결법입니다.
**상황 1: 화면이 하얗게 빈 채로 아무것도 안 나올 때**
```plain text
원인: 코드에 오류가 있거나 로딩 중
해결:
```

# Gemini Gems 실습 — PRD 완성하기 (30분)

## Gems란 무엇인가
**Gemini Gems**는 특정 역할과 전문성을 가진 AI 파트너입니다.<br>오늘 사용할 Gems('지음')는 교육기관 업무에 특화된 웹/앱 기획 파트너입니다.
```plain text
Gems와 대화하면:
  업무 상황 설명 → 가장 적합한 유형 제안
  어떤 기능을 넣을지 → 함께 선택
  앱 이름 → 후보 3개 제안 후 선택
  디자인 방향 → 분위기·컬러 직접 결정
  최종 PRD → 영문으로 출력 (Lovable에 바로 붙여넣기 가능)
```

```plain text
STEP 1. 워크시트 작성 (20분)
```

#### Gems 답변 잘 하는 법
단계별 꿀팁같은 질문이라도 어떻게 답하느냐에 따라 PRD 품질이 크게 달라집니다. <br>단계별로 어떤 식으로 답하면 좋은지 참고하여 답변을 고도화해주세요.<br><br>**1. 유형 제안 받았을 때:**
그냥 "네"보다는 한 줄이라도 이유를 더하면 좋습니다.
❌ "네 맞아요"
✅ "네 맞아요. 근데 입력하고 끝나는 게 아니라 바로 아래 목록에서 확인도 같이 됐으면 좋겠어요"
→ Gems가 다음 단계 설계에 그 맥락을 반영합니다.
<br>**2. 기능 선택할 때:**
추천 기능 중에서 고르기만 해도 되지만,
"이 기능을 쓸 때 추가로 필요한 디테일"까지 말하면 훨씬 좋습니다.
❌ "1번, 3번 할게요"
✅ "1번 좋다. 1번을 할 때는 휴대폰에 아예 알람까지 뜨게 해주면 좋을 것 같아."
✅ "3번도 좋아. 직원별로 검색하고 누적 카운팅도 됐으면 좋겠어"
→ 실제 업무에서 어떻게 쓰일지 상상하면서 답하면 Gems가 그 디테일까지 설계에 포함시킵니다.
**<br>3. Gems가 추천하지 않은 기능을 직접 제안할 때:**
추천 목록에 없어도 업무에 필요하면 자유롭게 요청하면 됩니다.
✅ "추가적인 의견은 오늘 연차인 직원 항목을 총 정리해서 한번에 pdf 파일 형태의 보고서로 뽑아주는 그런 기능이 있으면 좋을 것 같아. 이것도 되려나?"
→ Gems가 가능 여부를 판단하고 설계에 반영해줍니다. "이것도 될까?"라고 편하게 물어보는 것이 핵심입니다.

1. **디자인을 정할 때:**
색상은 정확한 이름을 몰라도 비유로 말하면 됩니다.
✅ "스타벅스 로고 색깔과 같은 짙은 초록색으로 하고 싶어"
✅ "쨍하지 않은 노란색?"
→ Gems가 알아서 정확한 Hex 코드로 변환해줍니다. 브랜드, 자연물, 느낌 등 무엇이든 비유로 설명하면 됩니다.
`<br>`**5. 최종 요약을 받았을 때 — 가장 중요한 단계:**
여기서 "네 좋아요"로 바로 끝내지 마세요.
실제 업무 시나리오를 하나씩 떠올리면서 빠진 부분이 없는지 점검하는 것이 핵심입니다.

**체크 관점 예시:**
· 예외 상황은 처리되나? (예: 휴무 "취소"의 경우는?)
· 한눈에 보고 싶은 정보가 더 있지 않나? (예: 내일 휴무자도?)
· 위험한 경우를 빠르게 찾을 방법이 있나? (예: 과다 휴무자 필터?)
· 실수로 잘못 누르는 걸 막을 장치가 있나? (예: 등록 전 확인?)

**\<실제 작성 예시\>**
✅ 전체적으로 너무 좋은데, 몇 가지만 더 짚고 갈게요.
1. 변경 후 휴무일을 비워두면 '휴무 취소'로 인식되게 할 수 있을까요?
2. 내일 휴무자 수도 같이 보였으면 좋겠어요.
3. 누적 일수 기준으로도 필터링이 되면 좋겠어요.
4. 등록 버튼 누르기 전에 확인 팝업이 있으면 좋겠어요."

→ 최소 2\~3개는 더 짚어보고 PRD를 받는 것을 권장합니다. AI가 만든 첫 결과물에 만족하지 않고 "내 업무라면 이게 또 필요하지 않을까?"를 한 번 더 점검하는 습관이 완성도를 크게 높입니다.

## 실습 1 — 강사 시연 (15분)
강사가 먼저 시연합니다. 흐름만 봐두세요.
**시연 흐름:**
```plain text
1. Gems에서 출력된 PRD 전체 복사
2. lovable.dev → 새 프로젝트 → 입력창에 붙여넣기
3. 생성되는 과정 관찰 (1~3분)
4. 동적 기능 테스트 (버튼·폼·필터)
5. Edit 모드로 텍스트 직접 수정 시연
6. 원샷 수정 요청 시연
7. Publish → URL 공유 시연
```
**시연 중 주목할 것:**
```plain text
① PRD 붙여넣기 즉시 화면이 만들어지기 시작
② 완성까지 1~3분 소요 → 중간에 추가 입력 하지 않기
③ 동적 기능 테스트: 버튼 클릭 → 반응 확인
④ 결과가 마음에 안 들어도 추가 요청으로 수정 가능
⑤ Edit 모드로 크레딧 절약하면서 텍스트 수정
```

#### 📌 PRD/초안 완성 후 체크리스트
markdown
- Lovable에서 첫 결과물이 나온 뒤에도 작업은 끝이 아닙니다. 아래 4가지 관점으로 점검하고, 각각 어떻게 피드백하면 되는지 정리했습니다.

#### **체크 1 — 예외/엣지 케이스가 빠지지 않았는가**
- 점검 질문: "이 업무에서 흔히 발생하는 특이 케이스가 빠졌나?"<br>→ 예시 (휴무 변경 앱): 일반 변경 말고 "휴무 취소"라는 케이스도 있는데 PRD에는 "변경"만 가정되어 있었음
- 피드백 방법: "변경 후 날짜를 비워두면 '취소'로 인식되게 해주세요. 목록에서도 일반 변경과 다른 색 배지로 구분해주세요."
#### `<br>`체크 2 — 한눈에 보고 싶은 정보가 다 들어있는가
- 점검 질문: "이 화면을 열었을 때 가장 먼저 보고 싶은 게 다 보이나?"<br>→ 예시: "오늘 휴무자 수"만 있었는데 업무상 "내일 휴무자 수"도 미리 알아야 하는 상황이 있었음
- 피드백 방법: "상단 요약 카드에 '내일 휴무자 수'도 같이 추가해주세요."
#### <br>체크 3 — 위험하거나 중요한 것을 빠르게 찾을 수 있는가
- 점검 질문: "데이터가 많아졌을 때도 중요한 것을 빨리 찾을 수 있나?"<br>→ 예시: 직원 이름으로만 검색 가능했는데 "과다 휴무자"처럼 조건 기반으로 찾을 방법이 없었음
- 피드백 방법:<br>→ "검색·필터에 '이번 달 누적 5일 이상'처럼 숫자 기준으로도 필터링되게 해주세요."
#### <br>체크 4 — 실수를 막는 안전장치가 있는가
- 점검 질문: "바쁠 때 실수로 잘못 입력·제출할 가능성은 없나?"<br>→ 예시: 버튼 한 번 누르면 바로 등록·발송되는 구조라 오등록 시 되돌리기 어려운 구조였음
- 피드백 방법:<br>→ "등록 버튼을 누르면 입력 내용을 한 번 더 보여주는 확인 팝업을 추가해주세요. 확인을 눌러야 최종 등록되게 해주세요."
💡 정리하면:<br>첫 PRD는 "기본 설계도"입니다. 위 4가지 관점(예외 케이스 / 한눈에 보기 / 빠른 검색 / 실수 방지)으로 한 번 더 점검하면, 실제로 매일 쓸 수 있는 수준의 완성도로 올라갑니다. <br>이 점검은 PRD 단계에서 해도 되고, Lovble로 화면이 다 만들어진 뒤 수정 요청으로 해도 됩니다.
