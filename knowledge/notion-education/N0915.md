## Lovable과 Claude Code, 근본적으로 무엇이 다른가
```plain text
Lovable: "완성된 서비스" — 클릭 몇 번으로 미리보기·배포까지 원스톱
  → 화면 오른쪽에 미리보기가 항상 떠 있고, [Publish] 버튼 하나로 URL 생성

Claude Code: "범용 코딩 도구" — 터미널에서 파일을 직접 다루는 에이전트
  → 미리보기 화면이 따로 없습니다. 만들어진 파일을 내가 직접 열어봐야 합니다
  → [Publish] 버튼도 없습니다. 배포는 별도 서비스를 이용해야 합니다
```
**왜 이런 차이가 있는가 — 원리**
```plain text
Lovable은 "웹앱 만들기"라는 하나의 목적에 맞춰 미리보기·배포·크레딧
관리까지 전부 갖춘 전용 서비스입니다.

Claude Code는 웹앱 개발자, 데이터 분석가, 문서 검수 담당자 등
누구나 쓸 수 있는 범용 도구입니다. 1권에서는 문서를 검수하는
용도로, 오늘은 코드를 짜는 용도로 썼습니다 — 똑같은 도구가
목적에 따라 다르게 쓰이는 것이지, 웹앱 전용 도구가 아닙니다.

→ 그래서 Lovable에 있던 편의 기능(미리보기·Publish)이
   Claude Code에는 기본으로 없고, 우리가 직접 채워야 합니다.
   오늘 그 채우는 법을 배웁니다.
```

## 오늘의 핵심 습관 — Plan Mode
> 6회차에서 "계획을 먼저 승인받는 것이 가장 중요한 습관"이라고 배웠던 것, 기억하시죠. Claude Code에는 이 원칙이 아예 기능으로 내장되어 있습니다. 이것이 Plan Mode입니다.
```plain text
Plan Mode란: Claude Code가 파일을 하나도 건드리지 않고,
"이렇게 만들 계획입니다"라는 계획만 먼저 세워서 보여주는 모드

진입 방법: Shift + Tab 을 두 번 눌러 Plan Mode로 전환

작동 흐름 — Explore → Plan → Code → Commit
① Explore(탐색): Claude가 지금 폴더 상태를 읽기만 함, 아무것도 안 바꿈
② Plan(계획): "이렇게 만들 것이다"를 요약해서 보여줌
③ Code(구현): 계획을 확인·승인하면 그때부터 실제로 파일을 만듦
④ Commit(기록): 완성된 상태를 git으로 기록해 안전하게 저장

★ 실무자들이 입을 모아 하는 말:
"한 가지 습관만 기억한다면, 코딩 전에 Plan Mode를 쓰는 것이다.
 계획에 시간을 더 쓸수록 Claude가 성공할 확률이 올라간다."
```
**왜 이게 6회차 원칙과 같은가**
```plain text
6회차에서 PRD 마지막에 넣었던 문장을 기억하시나요.
"Before generating, briefly summarize your build plan in 3-4 lines
 so I can confirm before you proceed."

Plan Mode는 이걸 매번 문장으로 요청할 필요 없이,
아예 도구 차원에서 강제해주는 장치입니다.
Lovable에서는 프롬프트로 부탁해야 했던 것이,
Claude Code에서는 모드 전환 한 번으로 항상 지켜집니다.
```

## 안전장치 — Git과 Rewind
```plain text
git init — 시작 전 안전망 설치
  실습 폴더에서 가장 먼저 git init을 실행해두면,
  Claude Code가 무언가를 잘못 만들어도 이전 상태로 되돌릴 수 있는
  기록이 남습니다. Lovable의 Pin과 같은 역할을 합니다.

Rewind(되감기) — 방향이 틀렸을 때 빨리 되돌리기
  결과가 원하는 방향과 다르게 흘러간다고 느껴지면,
  끝까지 밀어붙이지 말고 일찍 Rewind해서 그 이전 지점으로
  돌아가는 것이 실무자들의 공통된 조언입니다.
  ("잘못된 방향으로 10번 더 시도하는 것보다,
    일찍 되돌려서 계획을 다시 세우는 게 항상 빠르다.")
```

## 오늘 만드는 방식 — 설치 없이 바로 되는 순수 HTML
```plain text
Claude Code로 웹앱을 만드는 방법은 여러 가지가 있지만,
오늘은 가장 간단한 방식을 씁니다.

❌ React + 개발 서버 방식 (6회차 Lovable이 쓰던 방식)
   Node.js 설치, 패키지 설치(npm install), 개발 서버 실행이 필요
   → 처음 코딩을 시작하는 분께는 진입장벽이 높음

✅ 순수 HTML + CSS + JavaScript 단일 파일 방식 (오늘 방식)
   파일 하나(index.html)로 완성. 설치 과정 전혀 없음
   → 파일을 더블클릭하면 바로 브라우저에서 열림
   → 6회차에서 배운 동적 기능(State, 클릭 반응)도
     JavaScript만으로 충분히 구현 가능
```
> 💡 오늘 목표는 "가장 빠른 도구"가 아니라 "설치 장벽 없이 완주하는 경험"입니다. React 방식은 이후 더 복잡한 프로젝트가 필요할 때 다시 다룰 수 있습니다.

## PRD 재사용 — Claude Code용으로 살짝 수정
6회차에서 만든 3층 구조 PRD를 그대로 씁니다. 딱 한 줄만 바꿉니다.
```plain text
[6회차 PRD의 Tech constraint 항목을 아래로 교체]

기존 (Lovable용):
Tech constraint: React + useState for all interactive elements.

오늘 (Claude Code용):
Tech constraint: Pure HTML, CSS, and vanilla JavaScript in a single
index.html file. No frameworks, no build step, no npm install required.

```
나머지 항목(대상, 화면 구조, 디자인 톤, 인터랙티브 요구사항)은 6회차에서 쓴 것을 그대로 재사용합니다. 6회차 워크시트·PRD 결과물이 있다면 그걸 그대로 가져오고, 없다면 오늘 자리에서 간단히 새로 정합니다.

## 실습 흐름
### STEP 1 — Plan Mode에서 PRD 전달
```plain text
Plan Mode 상태에서 PRD 전체를 붙여넣습니다.
Claude가 파일을 만들지 않고, 먼저 "이렇게 만들 계획입니다"를
보여줍니다.
```
### STEP 2 — 계획 검토 및 승인
```plain text
계획을 읽고 확인합니다.
□ 화면 구성이 원하는 것과 맞는가
□ 빠진 기능은 없는가
□ 순수 HTML 방식이 맞게 반영됐는가

수정하고 싶은 부분이 있으면 이 단계에서 바로 말합니다.
"3번 항목은 빼고, 대신 검색 기능을 추가한 계획으로 다시 짜줘."

문제없으면 승인하고 진행합니다 (Plan Mode 해제 → 코드 생성 시작).
```
### STEP 3 — 파일 확인 및 브라우저에서 열기
```plain text
생성이 끝나면 폴더 안에 index.html 파일이 만들어집니다.
그 파일을 더블클릭하면 기본 브라우저에서 바로 열립니다.

(Claude Code Desktop 앱을 쓰는 경우 앱 안에서 바로 미리보기가
 뜨는 기능도 있습니다 — 있다면 그 화면을 활용해도 됩니다.)
```
### 잠깐 — "완성했습니다"라는 말을 그대로 믿지 않기
```plain text
실무자들이 반드시 지키는 원칙: "확인 없는 신뢰(Trust without verify)"가
가장 흔한 실패 원인입니다.

Claude Code는 코드를 다 만들고 나면 "완성했습니다"라고 말합니다.
하지만 이 말은 "코드 문법이 맞다"는 뜻이지, "실제로 브라우저에서
버튼을 눌러봤을 때 기대한 대로 작동한다"는 뜻이 아닙니다.

★ Claude가 "완성했다"고 말해도, 사람이 직접 파일을 열어
   버튼을 눌러보기 전까지는 완성된 게 아닙니다.

바로 다음 STEP 4의 체크리스트가 이 원칙을 실제로 지키는 절차입니다.
"말을 믿지 말고 눈으로 확인하라"가 오늘 실습에서 가장 중요한 습관입니다.
```
### STEP 4 — 동적 기능 테스트 (6회차와 동일한 체크리스트)
```plain text
□ 모든 버튼이 클릭하면 반응하나요?
□ 폼 제출 시 성공 메시지 + 목록 반영이 되나요?
□ 요약 카드 숫자가 자동으로 갱신되나요?
□ 검색·필터가 실시간으로 작동하나요?
□ 모든 텍스트가 한글로 나오나요?
```
### STEP 5 — 문제 발견 시, 증상으로 설명 (6회차 원칙 재사용)
```plain text
❌ "필터 로직에 조건문 추가해줘" (해결책 지시)
✅ "검색창에 글자를 입력해도 목록이 안 줄어들어요" (증상 설명)

Claude Code도 Lovable과 똑같이, 증상을 설명하면 스스로
원인을 찾아 고치는 경우가 정확도가 더 높습니다.
```
**디자인 문제는 스크린샷으로 — 텍스트보다 훨씬 정확합니다**
```plain text
원리: Claude는 이미지를 직접 볼 수 있습니다(비전 기능).
      "3번째 카드가 이상해요"라는 텍스트보다,
      화면을 캡처해서 붙여넣는 것이 훨씬 정확하게 전달됩니다.

실전 방법:
1. 브라우저에서 문제 있는 화면을 캡처합니다
   (Mac: Cmd+Shift+4, Windows: Win+Shift+S)
2. Claude Code 입력창에 이미지를 붙여넣거나 드래그합니다
3. "이 부분(캡처에 표시된 곳)의 여백이 너무 좁아요.
    더 넓게 만들어주세요"처럼 캡처와 함께 설명합니다

→ 레이아웃·색상·정렬처럼 말로 설명하기 애매한 문제일수록
   스크린샷 하나가 긴 설명보다 낫습니다.
```
### STEP 6 — 방향이 틀렸으면 Rewind

```plain text
수정이 계속 꼬인다 싶으면, 끝까지 밀어붙이지 말고
Rewind로 안정적이었던 지점까지 되돌린 뒤 계획을 다시 세웁니다.
```

## 한 걸음 더 — 실무자들이 쓰는 고급 기법
> 오늘 실습에는 필수가 아니지만, 알아두면 다음에 더 복잡한 작업을 할 때 바로 꺼내 쓸 수 있는 개념 세 가지입니다.
**① ultrathink — 더 깊이 생각하게 만드는 한 단어**
```plain text
원리: Claude는 평소 "즉답 모드"와 "깊이 사고하는 모드"를 자동으로
      오가며 작동합니다. 복잡한 화면 구조 설계나 어려운 버그
      원인 분석처럼 신중한 판단이 필요할 때는, 프롬프트 안에
      "ultrathink"라는 단어를 넣으면 그 요청에 한해 깊이 사고하는
      모드가 켜집니다.

실전 사용법:
"ultrathink로 생각해줘. 지금 이 앱에 검색·필터·정렬을 동시에
 넣으려는데, 세 기능이 서로 꼬이지 않게 하려면 어떤 순서로
 만드는 게 좋을지 계획을 먼저 세워줘."

⚠️ 참고: "심사숙고해줘", "잘 생각해봐" 같은 일반 문장은
   그냥 보통 지시로 처리될 뿐 실제로 깊이 사고하는 모드를
   켜지 않습니다. 정확히 "ultrathink"라는 단어를 써야 작동합니다.

언제 쓰면 좋은가: 단순한 텍스트 수정에는 필요 없습니다.
여러 기능이 서로 얽혀서 설계 자체를 고민해야 할 때 씁니다.
```
**② Hooks — "말해도 안 지켜질 규칙"은 아예 자동화하기**
```plain text
원리: CLAUDE.md는 Claude가 "읽고 기억해서" 지키는 방식입니다.
      대화가 길어지면 이 기억이 흐려질 수 있습니다(6회차에서
      배운 컨텍스트 붕괴와 같은 원리).

      Hooks는 다릅니다. "파일을 수정할 때마다 반드시 이 작업을
      자동으로 실행한다"처럼, Claude의 기억력에 의존하지 않고
      도구 차원에서 강제로 실행되는 규칙입니다.

실무자들의 원칙:
"반드시 항상 지켜져야 하는 것은 프롬프트가 아니라 Hooks로
 만들어라." (CLAUDE.md에 아무리 강조해서 써도, 대화가 길어지면
 놓칠 수 있지만 Hooks는 매번 무조건 실행됩니다.)

이사님이 상상해볼 수 있는 예:
"파일이 수정될 때마다 자동으로 '모든 텍스트가 한글인지'
 검사하는 규칙을 걸어둔다"처럼, 절대 놓치면 안 되는 조건을
 도구 자체에 심어두는 것입니다.

오늘은 설정까지 하지 않지만, 1권에서 배운 "서브에이전트
자가복제를 막는 disallowedTools 설정"이 사실 이 원리와
같은 계열입니다 — 프롬프트로 부탁하는 대신 도구 차원에서
아예 못 하게 막아버리는 방식입니다.
```
**③ 모델 사고력 조절 — /effort**
```plain text
Claude Code는 작업 난이도에 따라 얼마나 신중하게 사고할지
직접 조절할 수 있습니다. /effort 명령을 입력하면 사고 강도를
선택할 수 있는 메뉴가 뜹니다.

간단한 텍스트 수정: 낮은 강도로도 충분 (빠르고 저렴)
복잡한 구조 설계, 어려운 버그: 높은 강도로 전환

ultrathink가 "이번 한 번만" 깊이 사고하게 만드는 것이라면,
/effort는 "이 세션 전체"의 기본 사고 강도를 바꾸는 것입니다.
```

## 완성 후 — 다른 사람과 공유하려면
```plain text
Lovable은 [Publish] 버튼 하나로 URL이 나왔지만,
Claude Code로 만든 파일은 기본적으로 내 컴퓨터 안에만 있습니다.
다른 사람과 공유하려면 아래 중 하나가 필요합니다.

가장 쉬운 방법 — 파일 그대로 전달:
  index.html 파일 자체를 카카오톡·이메일로 전달
  받는 사람이 그 파일을 다운로드해서 더블클릭하면 실행됨
  (단, URL 형태는 아니고 파일을 내려받아야 함)

URL이 꼭 필요하다면 — 무료 정적 호스팅:
  Netlify Drop(app.netlify.com/drop) 같은 서비스에
  폴더를 그대로 드래그&드롭하면 몇 초 안에 URL이 생성됩니다.
  가입 없이도 임시로 가능하고, 계정 연결 시 계속 유지됩니다.

→ 오늘은 파일 공유까지만 다루고, 정식 호스팅 연결은
  다음 단계로 남겨둡니다.
```
