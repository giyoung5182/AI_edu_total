### 2-1. 바이브코딩의 정확한 기원과 정의
```plain text
2025년 2월, Andrej Karpathy(전 Tesla AI 총괄, OpenAI 공동창업자)가
소셜미디어에서 "바이브코딩(Vibe Coding)"이라는 용어를 처음 만들었습니다.

핵심 정의:
"코드가 존재한다는 사실조차 거의 잊어버릴 정도로,
 AI에게 완전히 위임해서 소프트웨어를 만드는 것"
= 원하는 것을 설명하고, 결과를 받아들이고, 보이는 것을 보고 반복하는 것

★ 5회차에서 배운 계보와 시기가 정확히 겹칩니다.
  프롬프트 엔지니어링(2022) → 컨텍스트 엔지니어링(2025.6) →
  하네스 엔지니어링(2026.2) → 루프 엔지니어링(2026.6)
  바이브코딩(2025.2)은 이 계보에서 "가장 먼저 대중에게 실전 형태로
  체감된" 사례입니다. 개념이 이름 붙기 전부터 이미 현장에서
  이 방식으로 일하는 사람들이 있었다는 뜻입니다.
```

### 2-2. 바이브코딩이 가능해진 이유 — 기술적 배경
```plain text
2022년 이전: AI는 간단한 코드 조각만 제안 가능
2023년 이후 (GPT-4, Claude 3): 코드 이해·생성 능력이 인간 상위 10% 수준
2024~2025년 (Lovable, v0, Bolt): "프롬프트 → 완성된 앱" 파이프라인 상용화

핵심 변화:
  "코드를 짜는 능력"보다
  "무엇을 만들지 정확히 설명하는 능력"이 더 중요해짐
```
**왜 이 변화가 일어났는가 — 원리 수준의 이해**
```plain text
AI가 코드를 잘 짜게 된 것은 단순히 "똑똑해져서"가 아닙니다.
0회차·2회차에서 배운 트랜스포머·Attention 구조를 기억해보면,
코드는 자연어보다 오히려 구조가 엄격합니다(문법 규칙이 명확함).
AI 입장에서는 "다음에 올 가장 그럴듯한 토큰"을 예측하는 게
자연어보다 코드에서 더 정확하게 맞아떨어지는 경우가 많습니다.

즉, 코드는 원래 AI가 잘할 수 있는 영역이었고,
2023년 이후 모델 규모와 학습 데이터가 임계점을 넘으면서
그 잠재력이 실전에서 드러난 것입니다.
```

### 2-5. 바이브코딩의 핵심 기술 개념 — 왜 알아야 하는가
> 아래 개념들을 몰라도 Lovable은 작동합니다. 하지만 이 개념을 정확히 아는 사람과 모르는 사람의 프롬프트는 완전히 다릅니다. "왜 이 지시어가 필요한가"를 알면, 처음 보는 문제 상황에서도 스스로 올바른 프롬프트를 만들어낼 수 있습니다.
**React — 오늘 만드는 앱의 기반 기술**
```plain text
Lovable이 만들어주는 앱은 대부분 React로 만들어집니다.
React는 화면을 "컴포넌트"(부품) 단위로 조립하는 방식입니다.

컴포넌트 = 화면의 부품 (버튼 하나 / 테이블 하나 / 입력 폼 하나)

원리: 화면 전체를 하나의 덩어리로 다루지 않고, 작은 부품 단위로
쪼개서 관리하면 — 부품 하나를 수정해도 나머지가 영향받지 않습니다.
이것이 "이 버튼 컴포넌트만 수정해줘"라고 말했을 때
AI가 다른 부분을 건드리지 않고 정확히 그 부분만 고칠 수 있는 이유입니다.
```
**State(상태) — 동적 기능의 핵심**
```plain text
State = 앱이 "지금 이 순간" 기억하고 있는 데이터

동적 기능 = State가 바뀌면 화면도 즉시 바뀌는 것
정적 기능 = State 없이 그냥 고정된 화면

원리: 브라우저에 표시되는 화면은 "지금 State가 어떤 값인가"를
그대로 반영한 결과물입니다. 버튼을 클릭했다는 사실 자체가
State를 바꾸고, State가 바뀌면 화면이 자동으로 다시 그려집니다.

"React useState 사용"이라고 프롬프트에 명시하는 이유:
  이 원리대로 작동하는 코드를 만들어달라는 명시적 요청입니다.
  이 지시어가 없으면 AI가 "보기에만 그럴듯한" 정적 화면을
  만들 수도 있습니다 — 겉모습은 똑같아 보이지만
  버튼을 눌러도 아무 일도 일어나지 않는 상태입니다.
```
**프론트엔드 vs 백엔드**
```plain text
프론트엔드: 사용자 눈에 보이는 화면 → Lovable이 오늘 만들어주는 것
백엔드: 데이터 저장, 서버, 데이터베이스 → 오늘은 샘플 데이터로 대체

오늘의 현실적 한계:
  오늘 만드는 앱은 프론트엔드만 있습니다.
  브라우저를 닫으면 입력한 데이터가 사라집니다.
  → 오늘의 목표는 "화면과 기능 구조 완성"이며,
     실제 데이터 저장(백엔드 연결)은 다음 단계에서 다룹니다.
```

### 2-6. 동적 기능이란 — 실제로 작동해야 한다
```plain text
❌ 정적(Static) 화면 — 작동 안 하는 것:
  버튼이 있지만 눌러도 반응 없음
  폼이 있지만 제출해도 아무 일도 없음
  요약 숫자가 항상 같은 값으로 고정됨

✅ 동적(Dynamic) 화면 — 실제로 작동하는 것:
  버튼을 누르면 즉시 반응이 생김
  폼을 제출하면 성공 메시지가 뜨고 목록에 추가됨
  요약 숫자가 새 데이터 입력 시 자동으로 갱신됨
```
오늘 만드는 것은 반드시 동적으로 작동해야 합니다.
> ⚠️ 버튼이 눌리지 않거나 기능이 작동하지 않으면 → "이 기능들이 실제로 작동하게 고쳐줘. React useState를 사용해서 버튼, 폼, 필터 모두 클릭하면 즉시 반응이 있어야 해."라고 요청하세요.

```plain text
한계 1: 데이터가 저장되지 않음 (오늘)
```

## PART 3. "벽에 부딪히기" — 실패의 해부학 (25분)
> 이 파트는 오늘 교안에서 가장 중요합니다. 바이브코딩 실사용자들이 가장 공통적으로 겪는 실패 패턴이며, 이를 미리 알면 오늘 실습에서 같은 함정에 빠지지 않습니다.
---
### 3-1. "벽(The Wall)"이란 무엇인가
```plain text
바이브코딩은 작동합니다 — 벽에 부딪히기 전까지는.

실패는 항상 같은 모양입니다:
  프롬프트를 10개쯤 넣었을 때, 앱이 복잡해지기 시작하고,
  AI가 스스로 모순되기 시작합니다.
  이전에 작동하던 기능이 새 기능을 추가하면서 깨집니다.
  AI의 혼란을 고치는 데 쓰는 시간이,
  차라리 직접 만드는 것보다 더 걸리게 됩니다.

★ 중요한 사실: 벽은 프롬프트 2~3번째에서 오지 않습니다.
  보통 10번째에서 20번째 프롬프트 사이에서 옵니다.
  이게 우연이 아니라 구조적인 이유가 있습니다 — 다음 절에서 다룹니다.
```
---
### 3-2. 컨텍스트 로트, 바이브코딩 버전 — "컨텍스트 붕괴"
5회차에서 배운 컨텍스트 로트(Context Rot)를 기억하실 겁니다. "많이 넣을수록 AI가 오히려 헷갈린다"는 원리였죠. 바이브코딩에서는 이게 \*\*"컨텍스트 붕괴(Context Collapse)"\*\*로 나타납니다.
```plain text
원리: 대화형 AI는 언어모델(LLM)이 고정된 양의 컨텍스트만 처리할 수 있습니다.
      대화가 길어지고 앱이 커질수록, 앱 초반에 내린 결정들이
      AI의 유효 컨텍스트 윈도우 밖으로 밀려나기 시작합니다.

왜 하필 10~20번째인가:
  초반 몇 개 프롬프트는 화면 하나, 기능 하나 정도라 컨텍스트가
  가볍습니다. 하지만 기능이 쌓일수록 "지금까지 이 앱이 어떻게
  구성되어 있는지"를 설명하는 정보량 자체가 기하급수적으로
  늘어납니다. 10번째쯤 되면 이 누적 정보가 AI의 유효 기억
  용량을 넘기 시작하고, 여기서부터 초반 결정들이 조금씩
  "잊히기" 시작합니다.

증상:
  AI가 이전 결정과 모순되는 제안을 함
  이미 확립된 것과 일치하지 않는 패턴을 도입함
  같은 질문을 다시 물어보는 것처럼 행동함

해결책 — "요약 후 재시작":
  새 세션을 시작하기 전에, 지금까지 무엇을 만들었는지
  한 문단으로 요약해서 새 대화의 첫 프롬프트로 사용합니다.
  → 이것이 Lovable에서 컨텍스트 한계에 걸렸을 때
    "새 프로젝트 + PRD 재활용"을 권장하는 이유입니다.
    PRD 자체가 "지금까지의 결정을 압축한 요약본" 역할을 합니다.
```

### 3-3. 벽을 피하는 3가지 방어선
**방어선 1 — 모듈식 프롬프팅 (한 프롬프트 = 한 관심사)**
```plain text
원리: 컨텍스트 붕괴는 "한 번에 담아야 하는 정보량"에서 비롯됩니다.
      요청을 작게 쪼개면, 각 요청이 처리해야 할 정보량 자체가
      줄어들어서 AI가 정확하게 처리할 확률이 올라갑니다.

❌ "프로젝트 관리 앱 만들어줘" (한 번에 거대한 요청)

✅ 단계별로 쪼개기:
  "클라이언트, 상태, 마감일 필드가 있는 프로젝트 데이터베이스를 설정해줘"
  → 확인 →
  "이제 상태별로 필터링되는 대시보드 화면을 만들어줘"
  → 확인 → (다음 단계로)

각 단계가 컨텍스트 한계 안에 머물고,
계속 진행하기 전에 결과를 확인할 기회를 줍니다.
```
**방어선 2 — 프롬프트를 서로 연결하기**
```plain text
원리: 이전 단계를 명시적으로 참조하면, AI가 매번 새로운 패턴을
      추측해서 만드는 대신 이미 확립된 구조 위에 정확히 쌓아
      올릴 수 있습니다.

❌ (맥락 없이) "필터링과 보관 기능을 추가해줘"

✅ (맥락 연결) "로그인과 할 일 목록은 이미 작동해.
    이제 완료된 작업에 대한 필터링과 보관 기능을 구현해줘."
```
**방어선 3 — 계획을 먼저 승인받기 (가장 중요한 습관)**
```plain text
원리: AI가 계획을 세우지 않고 바로 코드부터 생성하면,
      방향이 틀렸을 때 이미 상당한 코드가 만들어진 후에야
      그 사실을 알게 됩니다. 되돌리는 비용이 처음부터
      다시 만드는 것보다 더 클 수 있습니다.

실전 프롬프트:
"이 기능을 구현하기 전에, 어떻게 만들 계획인지
 먼저 3~4줄로 요약해서 알려줘. 내가 확인한 다음에 진행해줘."

→ 계획 단계에서 방향이 틀렸다는 걸 알면 그 자리에서 바로잡을 수 있고,
   전체를 다 만든 후에 뒤엎는 것보다 훨씬 빠릅니다.
   이 원칙은 오늘 작성할 PRD의 마지막 문장에도 반영됩니다.
```

### 3-4. "고쳐줘"가 아니라 "증상을 설명해줘"
```plain text
가장 흔한 실수: 원하는 해결책을 지시하는 것

❌ "정렬 로직에 WHERE 절 추가해줘" (해결책을 지시)
✅ "항목이 추가되는 중에 목록을 넘기면 중복된 항목이 나와"
    (증상·현상을 설명)

원리: 사람이 추측한 해결책이 실제 원인과 다를 때가 많습니다.
      틀린 해결책을 지시하면 AI는 그 틀린 방향으로 계속
      시도하게 되고, 근본 원인은 계속 남아있게 됩니다.
      반대로 증상만 정확히 설명하면, AI가 코드 전체를
      스스로 진단해서 사람이 미처 생각 못 한 진짜 원인을
      찾아내는 경우가 많습니다.

→ PART 9 공식 디버깅 프로토콜과, PART 8 프롬프트 아키타입
   "디버거"가 이 원칙을 구조화한 것입니다.
```

### 3-5. 프롬프트 로그 — 왜 기록해야 하는가
```plain text
많은 시행착오 끝에 실사용자들이 도달한 결론:
  "무엇을 물었고 AI가 어떻게 반응했는지"를 기록해두면
  나중에 같은 실수를 반복하지 않습니다.

간단한 기록 습관:
  - 무엇을 요청했는지 한 줄
  - 왜 그 결정을 내렸는지 (데이터 구조를 왜 바꿨는지 등)
  - 결과가 좋았는지 나빴는지

오늘은 정식 문서화까지는 안 해도 되지만,
"이 프롬프트가 잘 먹혔다"는 것을 기록해두면
다음 회차(Claude Code)에서 CLAUDE.md 개념으로 바로 이어집니다.
CLAUDE.md는 오늘의 프롬프트 로그가 발전된 형태 —
"매번 설명하지 않아도 AI가 프로젝트 규칙을 기억하게 만드는 파일"입니다.
```

## PART 6. PRD 작성 — 3층 구조의 원리 (20분)
> 실사용자들이 도달한 결론: 효과적인 프롬프트는 3개의 층으로 정보를 구성합니다. 이 구조를 따르면 AI가 "이 코드가 어떻게 보이고 작동해야 하는지"를 훨씬 정확히 이해합니다.
### 왜 3층 구조가 필요한가 — 원리
```plain text
AI에게 앱을 설명할 때 사람이 흔히 하는 실수는
"무엇을 원하는지"만 말하고 "어떤 조건에서"와 "어떻게 보여야 하는지"를
빠뜨리는 것입니다. 3층 구조는 이 빠뜨림을 구조적으로 방지합니다.

Layer 1 — 기술적 맥락과 제약 (How it should behave under the hood)
  스택, 스타일링 방식, 아키텍처 패턴을 명시
  → AI에게 "코드가 프로젝트 안에서 어떻게 보이고 작동해야 하는지" 알려줌
  → 이 층이 빠지면: 겉보기엔 그럴듯하지만 동작 원리가 부실한 결과물

Layer 2 — 기능 요구사항과 사용자 스토리 (What it does for the user)
  기능이 사용자 관점에서 무엇을 하는지, 구체적 동작과 상호작용을 설명
  → 이 층이 빠지면: 화면은 있지만 실제 업무 흐름과 안 맞는 결과물

Layer 3 — 디자인·톤 요구사항 (How it should feel)
  분위기, 색상, 여백 등 시각적 디테일
  → 이 층이 빠지면: 기능은 작동하지만 "AI가 만든 티"가 나는 결과물

세 층 모두 채워야, PART 3에서 배운 "계획 선승인" 원칙과 결합했을 때
첫 결과물의 완성도가 눈에 띄게 올라갑니다.
```

### 7-2. 안전장치 — Pin, Revert, Try to Fix
```plain text
Pin(고정) — 안정적인 버전을 표시해두기
  "여기까지는 확실히 잘 작동한다"는 지점을 고정해두면,
  이후 실험적인 수정이 잘못됐을 때 빠르게 되돌릴 기준점이 됩니다.
  모든 수정은 하나의 커밋(commit)으로 기록되므로,
  Pin으로 표시해둔 버전은 언제든 안전하게 복귀할 수 있습니다.

Revert(되돌리기) — 이전 상태로 복귀
  ⚠️ 중요한 함정: Supabase(데이터베이스)는 깔끔하게 되돌려지지 않습니다.
  버전을 되돌리면 화면 코드는 이전으로 돌아가지만,
  데이터베이스 스키마(구조)는 그대로 남아있어서 불일치가 생길 수 있습니다.
  → 되돌린 후에는 반드시 "데이터베이스 스키마를 검증해줘.
     깨진 부분이 있는지 확인해줘"라고 요청할 것.

"Try to Fix" 버튼 — 자동 오류 감지·해결
  Lovable이 자체적으로 오류를 감지하고 해결을 시도하는 버튼입니다.
  복잡한 오류 설명 없이도 1차 시도로 유용합니다.
```

## PART 8. 프롬프트 아키타입 5가지 (15분)
> 실전에서 반복되는 프롬프트 패턴을 5가지 유형(아키타입)으로 정리한 것입니다. 상황마다 어떤 아키타입을 쓸지 알면 매번 처음부터 프롬프트를 고민하지 않아도 됩니다.
```plain text
① 스캐폴드(Scaffold) — 뼈대를 세우는 프롬프트
   "이런 화면 구조를 처음부터 만들어줘" — 오늘 PRD가 이 역할

② 리파이너(Refiner) — 다듬는 프롬프트
   "이 부분은 작동은 하는데 더 다듬고 싶어" — 세부 조정용
   예: "카드 디자인은 좋은데 여백만 조금 더 넓게 해줘"

③ 디버거(Debugger) — 문제를 진단하는 프롬프트
   증상을 설명하고 원인을 찾아달라고 요청 (PART 3-4 원칙)
   예: "제출 버튼을 눌러도 아무 반응이 없어"

④ 트랜슬레이터(Translator) — 요구를 기술 언어로 바꾸는 프롬프트
   비유·일상어로 표현한 것을 기술적으로 명확하게 재요청
   예: "따뜻한 느낌으로" → "베이지·코랄 톤, 둥근 모서리, 부드러운 그림자"

⑤ 가드레일(Guardrail) — 제약을 미리 거는 프롬프트
   "이건 절대 건드리지 마"라고 미리 선을 그어두는 것
   예: "로그인 화면은 그대로 두고 대시보드만 수정해줘"
```
**오늘 실습에서 아키타입 활용 순서**
```plain text
① 스캐폴드로 시작 (PRD 붙여넣기)
→ ③ 디버거로 문제 발견 (동적 기능 테스트)
→ ⑤ 가드레일로 안전하게 수정 범위 지정
→ ② 리파이너로 세부 다듬기
→ ④ 트랜슬레이터로 애매한 디자인 요청을 명확히
```

### STEP 3 — 4가지 관점 검수
#### **체크 1 — 예외/엣지 케이스가 빠지지 않았는가**
- 점검 질문: "이 업무에서 흔히 발생하는 특이 케이스가 빠졌나?"<br>→ 예시 (휴무 변경 앱): 일반 변경 말고 "휴무 취소"라는 케이스도 있는데 PRD에는 "변경"만 가정되어 있었음
- 피드백 방법: "변경 후 날짜를 비워두면 '취소'로 인식되게 해주세요. 목록에서도 일반 변경과 다른 색 배지로 구분해주세요."
#### `<br>`체크 2 — 한눈에 보고 싶은 정보가 다 들어있는가
- 점검 질문: "이 화면을 열었을 때 가장 먼저 보고 싶은 게 다 보이나?"<br>→ 예시: "오늘 휴무자 수"만 있었는데 업무상 "내일 휴무자 수"도 미리 알아야 하는 상황이 있었음
- 피드백 방법: "상단 요약 카드에 '내일 휴무자 수'도 같이 추가해주세요."
#### <br>체크 3 — 위험하거나 중요한 것을 빠르게 찾을 수 있는가
- 점검 질문: "데이터가 많아졌을 때도 중요한 것을 빨리 찾을 수 있나?"<br>→ 예시: 직원 이름으로만 검색 가능했는데 "과다 휴무자"처럼 조건 기반으로 찾을 방법이 없었음
- 피드백 방법:<br>→ "검색·필터에 '이번 달 누적 5일 이상'처럼 숫자 기준으로도 필터링되게 해주세요."
#### <br>체크 4 — 실수를 막는 안전장치가 있는가
- 점검 질문: "바쁠 때 실수로 잘못 입력·제출할 가능성은 없나?"<br>→ 예시: 버튼 한 번 누르면 바로 등록·발송되는 구조라 오등록 시 되돌리기 어려운 구조였음
- 피드백 방법:<br>→ "등록 버튼을 누르면 입력 내용을 한 번 더 보여주는 확인 팝업을 추가해주세요. 확인을 눌러야 최종 등록되게 해주세요."
💡 정리하면:<br>첫 PRD는 "기본 설계도"입니다. 위 4가지 관점(예외 케이스 / 한눈에 보기 / 빠른 검색 / 실수 방지)으로 한 번 더 점검하면, 실제로 매일 쓸 수 있는 수준의 완성도로 올라갑니다. <br>이 점검은 PRD 단계에서 해도 되고, Lovble로 화면이 다 만들어진 뒤 수정 요청으로 해도 됩니다.

## Lovable 활용 꿀팁 모음
실제로 사용하면서 알게 되는 꿀팁들을 미리 공유합니다.
**꿀팁 1: PRD를 한 번에 붙여넣으면 완성도가 높아진다**
```plain text
PRD 없이 한 줄씩 요청: "비즈머니 현황 앱 만들어줘"
→ Lovable이 임의로 판단해서 만듦, 원하는 것과 다를 수 있음

PRD 통째로 붙여넣기:
→ 유형·기능·디자인·동적 요구사항까지 한 번에 전달
→ 첫 결과물 완성도가 훨씬 높음
→ 수정 횟수(=크레딧 소모)가 줄어듦
```
**꿀팁 2: 생성 중에는 기다린다**
```plain text
PRD 붙여넣기 후 → 오른쪽 화면이 만들어지는 동안:
  절대 중간에 채팅창에 새 요청 입력하지 않기
  → 완성 전에 새 요청이 들어오면 충돌 가능성

완성 신호:
  왼쪽 채팅창에 AI 응답이 완료됨
  오른쪽 미리보기가 안정된 상태로 표시됨
  → 그때부터 테스트하고 수정 요청
```
**꿀팁 3: ****`작동 안 하는 기능은 구체적인 기술 지시어를 추가한다`**
```plain text
기능이 작동 안 할 때 (버튼 눌러도 반응 없음):
  → "React useState를 사용해서
     이 기능이 실제로 작동하게 해줘.
     페이지 새로고침 없이 즉시 화면이 업데이트돼야 해."

요약 카드 숫자가 안 바뀔 때:
  → "요약 카드의 숫자가 테이블 데이터에서
     자동으로 계산되도록 해줘.
     새 데이터가 추가될 때마다 즉시 갱신돼야 해."
```
**꿀팁 4: "이 부분만" 선택해서 수정하면 정확하다**
```plain text
전체를 다시 만들지 말고:
  Edit 모드 → 수정할 섹션 클릭(파란 테두리)
  → 채팅창에 "이 섹션의 [구체적 수정]"
  → 다른 부분 건드리지 않고 원하는 곳만 수정
```
**꿀팁 5: 컨텍스트 한계에 걸리면 새 프로젝트 + PRD 재활용**
```plain text
증상:
  대화가 많이 쌓인 후 수정 요청을 했는데
  이전에 만든 기능이 갑자기 사라지거나 이상해짐
  → 컨텍스트 토큰 한계에 걸린 것

해결:
  Lovable에서 새 프로젝트 시작
  → 원래 PRD + 지금까지 추가한 기능을 합친 새 PRD 작성
  → 붙여넣기
  → 깨끗하게 다시 시작
```
**꿀팁 6: 디자인 참고 이미지를 활용한다**

## 실전 상황별 대처법
Lovable 사용 중 가장 자주 마주치는 상황과 해결법입니다.
**상황 1: 화면이 하얗게 빈 채로 아무것도 안 나올 때**
```plain text
원인: 코드에 오류가 있거나 로딩 중
해결:
  ① 오른쪽 상단 새로고침 아이콘 클릭
  ② 그래도 안 되면:
     채팅창에 "화면이 아무것도 안 보여. 오류를 고쳐줘."
  ③ F12 → 콘솔 탭 → 빨간 오류 메시지 복사 → 채팅창에 붙여넣기
     "이 오류가 났어. 원인과 해결 방법 알려줘."
```
**상황 2: 버튼이 눌리지 않거나 기능이 전혀 작동 안 할 때**
```plain text
원인: 정적 UI로 만들어진 것 (State 없음)
해결:
  "버튼과 폼이 실제로 작동하게 고쳐줘.
   React useState를 사용해서
   클릭하면 즉시 반응이 생기고
   새로고침 없이 화면이 업데이트돼야 해."
```
**상황 3: 원하는 것과 완전히 다른 결과가 나왔을 때**
```plain text
두 가지 선택:
  선택 A: 수정 요청으로 고치기
    구체적으로 무엇이 다른지 설명
    예: "입력 폼이 아니라 테이블만 나왔어.
        상단에 입력 폼이 있고 아래에 테이블이 있어야 해."

  선택 B: 새로 만들기 (PRD 개선 후 재시도)
    Gems에 돌아가서 PRD를 더 구체적으로 수정
    → 새 프로젝트에 붙여넣기
    → 더 좋은 결과가 나올 확률이 높음
```
**상황 4: 텍스트가 영어로 나올 때**
```plain text
해결:
  "모든 UI 텍스트를 한글로 바꿔줘.
   버튼, 라벨, 플레이스홀더, 성공/오류 메시지, 헤더 전부.
   영어 텍스트가 하나도 없어야 해."
```
**상황 5: 레이아웃이 모바일에서 깨질 때**
```plain text
해결:
  "스마트폰(375px 너비)에서 레이아웃이 깨져.
   모바일 반응형으로 수정해줘:
   - 테이블은 가로 스크롤 가능하게 하거나 카드 형식으로
   - 버튼은 모바일 터치에 충분한 크기(최소 44px 높이)로
   - 입력 필드는 풀 너비(100%)로"
```
**상황 6: 작업 중간에 멈추거나 절반만 완성됐을 때**
```plain text
원인: AI 컨텍스트 토큰 한계로 처리 중단
해결:
  "방금 작업이 완료됐나요?
   [확인한 결과, 빠진 부분] 기능이 아직 없어.
   이 부분만 이어서 만들어줘."
```
**상황 7: 오류 화면이 나왔는데 내용이 복잡할 때**
```plain text
해결:
  화면 캡처 (Windows: Win+Shift+S / Mac: Cmd+Shift+4)
  → Lovable 채팅창에 이미지 첨부
  → "이런 오류가 났어. 원인이 뭐고 어떻게 고쳐?"

또는:
  브라우저 F12 → Console 탭 → 빨간 오류 텍스트 복사
  → 채팅창에 붙여넣기 + 설명
```

## Publish 방법
결과물이 완성되면 실제 URL로 공개할 수 있습니다.
```plain text
STEP 1. 오른쪽 상단 [Publish] 버튼 클릭

STEP 2. 설정값 입력
  · 앱 이름 (브라우저 탭에 표시됨)
  · 설명 (공유 시 미리보기에 표시)
  · 아이콘 (없으면 기본 아이콘 사용)

STEP 3. [Publish] 클릭
  → 수십 초 후 URL 생성
  → 예: [개별 링크 제외]

STEP 4. URL 복사해서 공유
  → 카카오톡, 이메일 등으로 공유
  → 스마트폰에서도 설치 없이 바로 접속 가능
```
> 💡 코드가 수정되면 자동으로 재배포됩니다. Publish를 다시 누르지 않아도 URL로 접속하면 최신 버전이 열립니다.
> ⚠️ Pro 플랜은 lovable.app 무료 도메인으로 공개 가능합니다. 개인 도메인 연결은 7회차에서 다룹니다.

## 핵심 요약
```plain text
바이브코딩 = "코딩 시간 제로"가 아니라 "코딩 시간을 디버깅 시간으로 이동"
             (개발자 63%가 AI 코드 디버깅에 더 많은 시간)

벽에 부딪히기 = 프롬프트 10~20개 사이, 컨텍스트 붕괴로 발생
              → 모듈식 프롬프팅 + 연결된 프롬프트 + 계획 선승인으로 예방

증상을 말하되 해결책은 지시하지 말 것
  ("정렬 로직 고쳐줘" X → "목록에 중복이 나와요" O)

워크시트(엑셀) → PRD 3층 구조(기술·기능·디자인) → Lovable

크레딧 무료 구간: 프리뷰 툴바 인라인 수정
크레딧 소비 구간: Select/Draw 모드, 채팅 요청

안전장치: Pin(고정) → Revert(복귀, 단 DB는 별도 검증 필요) → Try to Fix(자동)

프롬프트 5아키타입: 스캐폴드·리파이너·디버거·트랜슬레이터·가드레일

공식 디버깅 8단계: 식별→검토→보고→검증→경계확인→로깅→감사→도구활용
```
