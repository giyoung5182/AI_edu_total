## 이번 세션에서 할 일
지금 우리에게는 두 개의 자산이 따로 놓여 있습니다.<br>하나는 협업하는 에이전트 팀과 그들의 채팅방입니다.<br>다른 하나는 재난·안전 문서가 적재된 벡터DB와 하이브리드 검색기입니다.<br>집필팀은 문서를 검색하지 않고 자기 기억으로 썼고,<br>검색기는 챗봇 하나만 쓰고 있습니다.
이번 세션에서 이 둘을 합칩니다.<br>그리고 새 데이터 하나를 더합니다. 전국 대피소의 위치 좌표입니다.<br>질문 하나가 들어오면 문서 담당, 위치 담당, 웹 담당이<br>각자 다른 도구로 일하고, 결과가 하나의 브리핑으로 합쳐지며,<br>채점 담당이 그 브리핑을 검수하는 재난 대응 팀을 완성합니다.
이번 세션에서 우리가 하는 일은 세 가지입니다.
1. 벡터DB를 조회하는 검색 담당과, 브리핑을 검수하는 채점 담당을<br>팀에 합류시킵니다.
2. 대피소 좌표 데이터를 다루는 위치 담당을 합류시킵니다.<br>채팅방에 지도가 말풍선으로 올라옵니다.
3. 웹 검색 담당까지 합류한 5인 팀으로 종합 시연을 하고,<br>문서에 없는 질문이 들어왔을 때의 우회 동작을 실험합니다.
> 💡 이번 세션의 핵심은 "데이터 성격에 따라 도구가 갈린다"입니다.<br>문서는 검색으로, 좌표는 계산으로, 최신 정보는 웹으로.<br>어떤 데이터에 어떤 도구를 붙일지 판단하는 눈이<br>이 팀 구성 전체에 들어 있습니다.

### 기억으로 쓴 글의 문제
집필팀이 만든 재난 생존 가이드에는 약점이 하나 남아 있습니다.<br>문장들이 에이전트의 학습된 기억에서 나왔다는 점입니다.<br>기억은 대체로 그럴듯하고, 가끔 틀립니다.<br>그리고 틀릴 때조차 그럴듯합니다.

\[집필팀이 기억으로 쓴 문장\]<br>심폐소생술은 가슴을 3cm 깊이로, 분당 80회 속도로 압박합니다.
\[적재된 응급대처 매뉴얼의 실제 서술\]<br>가슴압박은 약 5cm 깊이로, 분당 100\~120회 속도로 실시합니다.

숫자가 다릅니다. 문장만 봐서는 어느 쪽이 맞는지 알 수 없습니다.<br>일반 상식이라면 웃고 넘기겠지만, 응급처치 수치는 생명이 걸린 정보입니다.
해결의 방향은 이미 우리 손에 있습니다.<br>공식 매뉴얼이 적재된 벡터DB, 그리고 하이브리드 검색기입니다.<br>글 쓰는 에이전트에게 기억 대신 검색된 근거를 재료로 주고,<br>완성된 글이 근거와 일치하는지 검수까지 붙이면 됩니다.<br>검색과 검수를 각각 전담하는 팀원을 두는 것,<br>그것이 이번 세션의 팀 개편입니다.
---
### 데이터 성격에 따라 도구가 갈린다
이번 팀은 세 종류의 데이터를 다룹니다.<br>종류마다 알맞은 도구가 다릅니다.
**① 비정형 데이터 — 서술형 문서**<br>행동요령과 매뉴얼은 문장으로 쓰인 비정형 데이터입니다.<br>"지진 나면 어떻게 하나"의 답은 의미가 비슷한 문단을<br>찾아야 나옵니다. 하이브리드 검색이 맞는 도구입니다.
**② 정형 데이터 — 대피소 좌표 표**<br>배부받은 대피소 데이터는 행과 열이 정해진 정형 데이터입니다.
```php
[data/shelters.csv 의 실제 행]
시설명,구분,위도,경도,주소
판교원마을1단지 지하주차장,민방위대피시설,37.4021,127.1088,경기 성남시...
낙생대공원,지진 옥외대피장소,37.4102,127.1015,경기 성남시...
```
"여기서 가장 가까운 대피소는?"의 답은<br>의미 검색이 아니라 계산으로 나옵니다.<br>모든 행에 대해 현재 위치와의 거리를 구해 정렬하면 끝입니다.<br>두 좌표 사이의 거리를 구하는 표준 계산식이 있으며,<br>**하버사인 공식(Haversine Formula)**이라고 부릅니다.
좌표를 벡터DB에 넣지 않는 이유도 여기 있습니다.<br>임베딩은 문장의 의미를 숫자로 바꾸는 도구입니다.<br>"37.4021"이라는 좌표값에는 찾아낼 의미가 없습니다.<br>정형 데이터에는 조회와 연산이 맞는 도구입니다.
**③ 실시간 데이터 — 웹**<br>문서에도 좌표에도 없는 것이 있습니다. 지금의 정보입니다.<br>현재 발효 중인 기상특보 같은 것은 웹 검색으로만 얻습니다.<br>우리는 키 발급 없이 무료로 쓸 수 있는 **DuckDuckGo 검색 라이브러리(ddgs)**를 사용합니다.

### 재난 대응 5인 팀의 구성
세 도구에 담당을 하나씩 붙이고, 종합과 검수를 더하면<br>팀이 완성됩니다.
[원본 이미지 제외]
읽는 법 두 가지를 짚어 둡니다.
첫째, 역할 이름이 직함이 아니라 **기능**입니다.<br>기획자, 대리, 팀장 같은 이름은 하는 일을 알려주지 않습니다.<br>검색 담당, 위치 담당은 이름 자체가 명세입니다.
둘째, 검색·위치·웹 담당은 **도구가 일의 본체**입니다.<br>검색 실행, 거리 계산이 실제 작업이고,<br>모델은 그 결과를 보고 문장으로 다듬는 정도만 맡습니다.<br>그래서 이 세 담당은 모델 호출 없이 정해진 틀의 문장으로<br>보고하는 절약 모드로 바꾸기가 쉽습니다.<br>무료 사용량이 바닥나는 상황의 대비책이 됩니다.
채점 담당의 검수 기준은 근거 정합성입니다.<br>브리핑의 문장이 검색 담당이 가져온 청크와<br>위치 담당이 가져온 데이터에 실제로 있는 내용인지 대조합니다.<br>기준 미달이면 반려하고, 라이터가 고쳐서 다시 냅니다.<br>반려에는 최대 수정 횟수 제한이 그대로 적용됩니다.

### 팀은 실패에도 대비한다 — 우회 경로
질문이 항상 문서 안에 있으리라는 보장은 없습니다.<br>"올해 태풍 전망은 어떤가요?" 같은 질문에는 적재된 매뉴얼 어디에도 답이 없습니다.
준비 없는 팀이라면 검색 담당이 엉뚱한 청크라도 가져오고, 라이터는 그걸로 억지 브리핑을 씁니다.<br>준비된 팀은 다르게 움직입니다.
[원본 이미지 제외]
실패를 숨기지 않고 보고하게 하고,<br>보고를 받은 관리자가 경로를 바꾸는 것.<br>이런 대비 동작을 **우회(Fallback)**라고 부릅니다.<br>이번 실습에서 이 장면을 직접 확인합니다.

## 실습 안내
### 실습 1. 검색 담당과 채점 담당의 합류
채팅방에 재난 대응 모드를 만들고, 4인 팀부터 가동합니다.<br>(오케스트레이터, 검색 담당, 브리핑 라이터, 채점 담당)
작업 시작 전에 창②(Claude Code)에서 `/clear`를 실행합니다.
**Claude Code 프롬프트**
```plain text
팀 채팅방에 재난 대응 모드를 추가해 주세요. 요구사항입니다.

1. /team 페이지에 모드 전환을 두어, 집필 모드와
   재난 대응 모드를 오갈 수 있게 해 주세요.
   재난 대응 모드에는 질문 입력칸이 있습니다.

2. 질문이 들어오면 다음 팀이 협업합니다. 멤버 목록,
   상태 배지, 말풍선, 메시지 기록 방식은 집필 모드와 같습니다.
   - 오케스트레이터(gemini-2.5-flash): 질문을 받아 작업을
     분배하고 결과를 취합합니다.
   - 검색 담당(gemini-2.5-flash-lite): 기존 하이브리드 검색으로
     벡터DB에서 상위 3개 청크를 찾아 보고합니다. 보고 말풍선에는
     청크 번호, 출처 문서명, 점수가 들어갑니다.
     최고 점수가 기준(0.4) 미만이면 "관련 근거를 찾지
     못했습니다"라고 보고합니다.
   - 브리핑 라이터(gemini-2.5-flash): 검색 담당의 청크만
     근거로 브리핑을 작성합니다. 문장마다 근거 청크 번호를
     표기합니다.
   - 채점 담당(gemini-2.5-flash-lite): 브리핑을 근거 청크와
     대조해 근거 정합성을 1~5점으로 채점합니다. 3점 이하면
     문제 지점을 명시해 반려하고, 라이터가 수정해 다시 냅니다.
     반려에는 기존의 최대 수정 횟수 제한(2회)을 적용합니다.

3. 최종 브리핑은 구분되는 말풍선으로 올리고,
   근거 청크 번호를 누르면 원문이 펼쳐지게 해 주세요.

4. 무료 한도 보호를 위한 호출 간 대기를 유지해 주세요.
```
진행 순서

1. 창②에 프롬프트를 입력하고 진행한 뒤 서버를 재시작합니다.
2. 재난 대응 모드에서 질문합니다:<br>"지진이 나면 가장 먼저 뭘 해야 하나요?"
3. 관전합니다. 검색 담당의 보고 말풍선에서 청크 번호와<br>점수를 확인합니다.
4. 최종 브리핑의 근거 번호를 눌러 원문과 한 줄씩 대조합니다.
5. \[반려 목격\] 채점 담당의 채점 말풍선을 확인합니다.<br>반려가 나오면 어느 문장이 문제였는지, 수정본에서 어떻게<br>바뀌었는지 추적합니다. 승인만 나온다면 두세 가지 질문을<br>더 던져 봅니다. 반려는 언제든 나올 수 있는 정상 동작입니다.
6. 응급처치 질문을 하나 던집니다:<br>"심폐소생술은 어떻게 하나요?"<br>브리핑의 수치(깊이, 속도)가 근거 청크의 수치와<br>정확히 일치하는지 확인합니다.

**잘 안 될 때**
**Q. 브리핑에 근거 번호가 없음**
- **원인**: 라이터 지시 누락
- **해결**: 창②에 "라이터가 문장마다 근거 번호를 표기하는지 점검해 주세요"라고 요청합니다
**Q. 채점 담당이 모든 것을 반려함**
- **원인**: 채점 기준 과격
- **해결**: 창②에 "채점 기준을 완화하고 3점 이하만 반려로 바꿔 주세요"라고 요청합니다
**Q. 반려 루프가 길어짐**
- **원인**: 제한 미적용
- **해결**: 최대 수정 횟수 제한이 이 모드에도 적용되는지 창②에 확인을 요청합니다
**Q. 429 에러**
- **원인**: 호출 수 증가
- **해결**: 1\~2분 뒤 재시도합니다. 반복되면 대기를 늘려 달라고 요청합니다

### 실습 2. 위치 담당의 합류 — 채팅방에 지도가 뜬다
대피소 데이터와 지도를 다루는 위치 담당을 투입합니다.<br>아래 파일을 현재 프로젝트 폴더에 추가합니다. 대피소 좌표 파일입니다.

[첨부 원본 제외: 파일 권리·개인정보 확인 전입니다.]

**Claude Code 프롬프트**
```plain text
재난 대응 팀에 위치 담당을 추가해 주세요. 요구사항입니다.

1. 위치 담당(gemini-2.5-flash-lite)의 도구 동작입니다.
   - shelters.csv를 읽습니다. 시설명, 구분, 위도, 경도,
     주소 열이 있습니다.
   - 현재 위치는 코드의 상수로 둡니다.
     위도 37.4046195450827, 경도 127.105814002504 입니다.
   - 하버사인 공식으로 전체 대피소와의 거리를 계산해
     가까운 순으로 3곳을 고릅니다.
   - 질문에 재난 유형이 있으면 구분 열로 걸러 주세요.
     지진 관련 질문이면 지진 옥외대피장소를 우선합니다.

2. 위치 담당의 보고는 지도 카드 말풍선입니다.
   - Leaflet과 OpenStreetMap 타일을 CDN으로 사용해 주세요.
     별도 API 키는 필요 없습니다.
   - 지도에는 현재 위치 표식과 대피소 3곳의 마커가 찍히고,
     마커를 누르면 시설명, 구분, 거리(m)가 팝업으로 뜹니다.
   - 지도 아래에 세 곳의 이름과 거리를 글로도 적어 주세요.

3. 오케스트레이터는 대피 관련 질문일 때 검색 담당과
   위치 담당에게 함께 일을 맡기고, 라이터는 두 보고를 종합해
   브리핑을 작성합니다. 행동요령에는 청크 근거 번호를,
   대피소 안내에는 위치 담당 보고를 근거로 표기합니다.

4. 절약 모드를 만들어 주세요. Gemini 호출에서 429 오류가
   나면 위치 담당은 모델 호출 없이 계산 결과를 정해진 틀의
   문장으로 보고하는 방식으로 자동 전환하고,
   전환 사실을 채팅방과 로그에 남깁니다.
```
진행 순서

1. 창②에 프롬프트를 입력하고 진행한 뒤 서버를 재시작합니다.
2. 질문합니다: "지금 여기서 지진이 나면 어디로 대피해야 하나요?"
3. 관전합니다. 검색 담당과 위치 담당의 배지가 함께<br>움직이는 것을 확인합니다.
4. 지도 카드 말풍선이 올라오면 마커 세 개를 눌러<br>시설명과 거리를 확인합니다.
5. \[실지 대조\] 가장 가까운 대피소의 이름을 지도 앱이나<br>기억 속 동네 지리와 맞춰 봅니다. 실제로 걸어갈 수 있는<br>곳인지 가늠해 보는 것이 이 데이터의 실감입니다.
6. 최종 브리핑을 읽습니다. 행동요령(청크 근거)과<br>대피소 안내(위치 보고 근거)가 한 문서로 합쳐져 있고,<br>근거 표기가 각각 달려 있으면 성공입니다.

> 💡 4번의 지도 말풍선이 이 팀의 성격을 보여줍니다.<br>문장만 오가던 채팅방에 지도가 올라온 것은,<br>팀에 다른 종류의 도구를 쥔 담당이 들어왔다는 뜻입니다.<br>에이전트를 늘린다는 것은 머릿수가 아니라<br>도구의 종류를 늘리는 일입니다.
**잘 안 될 때**
**Q. 지도가 회색으로만 뜸**
- **원인**: 타일 로딩 실패
- **해결**: 인터넷 연결을 확인하고 새로고침합니다. 계속되면 창②에 로그와 함께 문의합니다
**Q. 마커가 바다나 엉뚱한 곳에 찍힘**
- **원인**: 위도·경도 열이 뒤바뀜
- **해결**: 창②에 "위도와 경도 열 매핑을 확인해 주세요"라고 요청합니다
**Q. 거리 값이 비현실적으로 큼**
- **원인**: 단위 혼동
- **해결**: 창②에 "거리 계산 결과의 단위(m)를 확인해 주세요"라고 요청합니다
**Q. CSV를 못 읽음**
- **원인**: 경로·인코딩 문제
- **해결**: 창②에 "data/shelters.csv 경로와 인코딩(UTF-8)을 확인해 주세요"라고 요청합니다
**Q. 절약 모드 전환이 안 보임**
- **원인**: 429 미발생
- **해결**: 정상입니다. 전환은 한도 초과 때만 일어납니다

### 실습 3. 웹 담당 합류와 종합 시연
마지막 멤버를 합류시키고, 팀 전체를 가동합니다.
**Claude Code 프롬프트**
```plain text
재난 대응 팀에 웹 담당을 추가해 주세요. 요구사항입니다.

1. 웹 담당(gemini-2.5-flash-lite)은 Tavily로 웹을 검색하고,
   상위 결과 2~3건을 제목, 요약, 출처 주소와 함께 보고합니다.

2. 오케스트레이터의 분배 규칙을 확장해 주세요.
   - 기본: 검색 담당(문서)을 우선 사용합니다.
   - 검색 담당이 "관련 근거를 찾지 못했습니다"라고 보고하면,
     웹 담당 단독 경로로 전환합니다. 전환 결정을
     채팅방에 말풍선으로 남깁니다.
   - 웹 경로의 브리핑에는 "문서 근거 없음, 웹 출처 기반"
     표기와 출처 주소가 들어갑니다.

3. 채점 담당은 웹 경로 브리핑도 검수합니다.
   이때 대조 기준은 웹 담당의 보고 내용입니다.

4. 필요한 패키지 설치 명령을 알려 주세요.
```
진행 순서

1. 창②에 프롬프트를 입력하고 진행한 뒤,<br>패키지를 설치하고 서버를 재시작합니다.
2. \[종합 시연\] 질문합니다:<br>"지금 여기서 지진이 나면 어떻게 해야 하죠?"<br>손을 떼고 처음부터 끝까지 관전합니다.<br>분배 → 검색·위치 보고 → 브리핑 → 채점까지<br>개입 없이 완주되는지 봅니다.
3. \[우회 실험 예측\] 다음 질문을 준비합니다:<br>"올해 태풍 전망은 어떤가요?"<br>적재된 문서에 답이 없는 질문입니다. 검색 담당이 뭐라고<br>보고할지, 팀이 어떻게 움직일지 예측해 적습니다.
4. 질문을 던지고 \[확인\]합니다.
- 검색 담당의 "관련 근거를 찾지 못했습니다" 보고
- 오케스트레이터의 경로 전환 말풍선
- 웹 담당의 검색 결과 보고 (출처 주소 포함)
- "문서 근거 없음, 웹 출처 기반" 표기가 붙은 브리핑
5. 자유 질문으로 팀을 시험합니다. 문서에 있을 질문과<br>없을 질문을 섞어 던지고, 경로가 알맞게 갈리는지 봅니다.

> 💡 4번에서 확인한 것은 실패의 처리입니다.<br>"모른다"를 숨기지 않고 보고하게 만들고,<br>보고받은 관리자가 다른 경로를 여는 것.<br>좋은 자동화는 성공 경로가 아니라<br>실패 경로의 설계에서 갈립니다.
**잘 안 될 때**
**Q. 웹 검색 결과가 비어 있음**
- **원인**: 라이브러리 또는 네트워크 문제
- **해결**: 창②에 오류 로그를 붙여넣어 해결을 요청합니다

- **해결**: 창②에 "근거 없음 판정 기준을 낮춰 주세요"라고 요청합니다

- **해결**: 반대로 기준을 높여 달라고 요청합니다. 기준값 조정도 파라미터 튜닝입니다

## 실습 확장 (선택)
