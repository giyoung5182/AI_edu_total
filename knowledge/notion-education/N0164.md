## 2-2. ⚠️ 길수록 나빠집니다
Claude Code를 만든 사람이 인터뷰에서 한 말입니다.
> **"가장 자주 나오는 실패는 과잉 지정입니다.<br>모델이 할 수 있는 것이 있는데 우리가 방해하고 있습니다."**
그는 이걸 **'발목 잡기'** 라고 불렀습니다. 못 해서 안 하는 게 아니라 우리가 못 하게 막아둔 상태라는 뜻입니다.
**그리고 CLAUDE.md는 매 턴 다시 읽힙니다.** 여기 넣은 것은 계속 비용을 치릅니다.
```plain text
✅ 3~5개로 시작
✅ 같은 실수가 반복될 때 한 줄씩 추가
❌ 처음부터 20개
```
> 📌 **150\~200줄 안에서 관리**하는 것이 일반적인 권고입니다. 실제로는 훨씬 짧아도 됩니다.
## 2-3. 한 줄씩 지워보는 방법
감으로 지우지 않고 확인하면서 지웁니다.
```plain text
1. 파일을 복사해서 백업합니다
2. 한 줄만 지웁니다
3. 평소 하던 작업을 그대로 시켜봅니다
4. 결과가 똑같으면 → 원래 없어도 됐던 줄. 지운 채로 둡니다
5. 결과가 나빠지면 → 되돌립니다. 단, 더 짧게 고쳐서
6. 다음 줄로
```
> ⚠️ **한 번에 한 줄만.** 여러 줄을 같이 지우면 어느 줄이 일하고 있었는지 알 수 없습니다.
## 2-4. 판단 기준 한 줄
> **"이건 AI가 알아낼 수 있나?"**
알아낼 수 있으면 지웁니다. 절대 알 수 없으면 남깁니다.
## 2-5. 실제 예시 — 초등 SW 강사용
```markdown
# 우리 반 작업 규칙

## 대상
- 초등 3~4학년이 보는 화면입니다.
- 학생들은 휴대폰으로 봅니다.

## 화면
- 글자 크기는 18px 이상. 기본값으로 두면 학생이 못 읽습니다.
- 표를 쓰지 않습니다. 휴대폰에서 잘립니다. 카드를 세로로 쌓습니다.

## 표현
- 어려운 낱말은 풀어씁니다. '실행' → '해 보기'

## 금지
- 학생 화면에 외부 링크를 넣지 않습니다.
- 학생 이름·사진·연락처를 넣지 않습니다.

## 작업 방식
- 산출물은 항상 현재 프로젝트 폴더 안에만 만듭니다.
- 만든 뒤에는 저장 경로를 알려줍니다.
- 제가 직접 열어서 확인할 테니, 대신 확인하고 넘어가지 마세요.
```
> 💡 **열 줄 남짓입니다.** 이 정도가 실제로 잘 작동하는 분량입니다.<br>마지막 세 줄은 실수를 막는 장치라 특히 값어치가 큽니다.

# 3. MEMORY.md — 오래 기억할 사실
## 무엇이 다른가







CLAUDE.md

MEMORY.md




담는 것

**규칙** (이렇게 해라)

**사실** (이건 이렇다)




예

글자는 18px 이상

우리 학교는 4학년이 3개 반




바뀌는 빈도

거의 안 바뀜

학기마다 갱신


## 이런 걸 적습니다
```markdown
# 기억해둘 것

## 수업 환경
- 인천 ○○초, 4학년 3개 반, 반당 24명 내외
- 컴퓨터실 태블릿 20대. 모자라서 2인 1대로 씁니다
- 학교 와이파이가 느립니다. 무거운 건 피합니다

## 진행 상황
- 2026년 1학기: 1~4차시까지 진행함
- 3반은 진도가 한 차시 늦습니다

## 지난 결정
- 패턴 카드는 8세트로 확정 (모둠 수 기준)
- 활동지는 항상 A4 한 장으로
```
## 언제 필요해지나
```plain text
□ 같은 프로젝트를 여러 달에 걸쳐 한다
□ "저번에 정한 게 뭐였지"가 반복된다
□ 학기가 바뀌어도 이어서 쓴다
```
> 💡 **오늘 하루짜리 작업에는 필요 없습니다.**<br>한 학기 이상 이어질 때 만드시면 됩니다.
> ⚠️ 이것도 **길면 안 됩니다.** 사실만 적고, 안 쓰는 건 지웁니다.

# 4. AGENT.md — 전문 담당자 정의
## 무엇인가
**"이 역할은 이런 기준으로 본다"를 적어두는 파일**입니다.
6교시 마무리에서 본 서브에이전트를, 매번 설명하는 대신 **파일로 정해두는 것**입니다.
## 예시
```markdown
# 개인정보 점검 담당

## 역할
파일이나 화면에 학생 개인정보가 들어갔는지 확인한다.

## 확인할 것
- 학생 실명, 사진, 연락처, 생년월일
- 학번·주소 등 개인을 특정할 수 있는 것
- 파일명에 들어간 이름

## 판단 기준
- 번호(3-2-14)나 모둠명은 괜찮다
- 애매하면 위험한 쪽으로 판단하고 이유를 적는다

## 하지 말 것
- 발견한 것을 자동으로 지우거나 옮기지 않는다
- 목록만 만들고 사람이 판단하게 한다
```
## 언제 필요해지나
```plain text
□ 같은 관점의 검토를 매번 반복한다
□ 그 관점에서 봐야 할 기준이 여러 개다
□ 다른 선생님께도 같은 기준을 쓰게 하고 싶다
```
> 💡 오늘 부록 「서브에이전트」의 **위험 담당**을 파일로 굳혀둔 것이 이 예시입니다.<br>매번 프롬프트에 길게 쓰는 대신, 파일 하나 만들고 불러 쓰면 됩니다.

# 5. BRD · PRD — 왜 / 어떻게
## 두 문서의 차이







BRD

PRD




질문

**왜** 만들었나

**어떻게** 만들었나




담는 것

목적, 대상, 제약, 기대 효과

구조, 기능, 화면, 범위, 다음 계획




독자

사람 + 다음 AI

**주로 다음 AI**


## 두 가지 시점
이 문서들은 **두 번 씁니다.**
```plain text
만들기 전   PRD   무엇을 만들 것인가          ← 3교시에 하신 것
만든 뒤     BRD   왜 만들었고 무엇을 했는가    ← 6교시에 하신 것
            PRD   실제로 어떻게 만들었는가     ← 6교시에 갱신
```
> 💡 **오전에 쓴 prd.md를 저녁에 갱신하는 구조**입니다.<br>계획이 실제와 달라진 부분을 반영하는 것이 진짜 인수인계 문서입니다.
## 다음에 이어받게 하는 법
```plain text
brd.md와 prd.md를 읽고 이 프로젝트를 파악해줘.
그리고 이어서 [원하는 것]을 추가해줘.
```
**처음부터 설명할 필요가 없습니다.**

## ⚠️ 다 만들지 마세요
Claude Code를 오래 쓴 사람들이 공통으로 하는 말입니다.
> **"처음부터 다 세팅하지 마세요."**
좋다는 걸 전부 만들면 오히려 느려지고 헷갈립니다.<br>기본 상태로 쓰다가, **같은 불편이 반복될 때 그것만** 추가하세요.
```plain text
① 그냥 프롬프트로 해본다
        ↓ 같은 말을 세 번 반복하게 되면
② CLAUDE.md에 적는다
        ↓ 같은 작업을 세 번 하게 되면
③ SKILL.md로 만든다
        ↓ 그래도 부족하면
④ 나머지를 하나씩
```
**세 번이 기준입니다.** 두 번까지는 그냥 하시고, 세 번째에 적으세요.
