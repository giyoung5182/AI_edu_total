## 이번 세션에서 할 일
지금 우리에게는 오케스트레이터가 이끄는 집필팀이 있습니다.<br>지시서가 만들어지고, 다섯 장이 집필되고, 검토와 수정이 돌아갑니다.<br>그런데 그 협업의 과정은 터미널 로그 속에만 있습니다.<br>화면에는 결과물 카드만 나타납니다.
이번 세션에서는 과정을 화면으로 꺼냅니다.<br>집필팀 전원이 참여하는 단체 채팅방을 만들어,<br>지시가 내려가고 보고가 올라오는 모든 순간을<br>말풍선으로 실시간 관전합니다.<br>그리고 조율이 폭주하면 어떻게 되는지, 고장도 직접 내 봅니다.
이번 세션에서 우리가 하는 일은 세 가지입니다.
1. 집필팀의 협업이 실시간 중계되는 팀 채팅방 페이지를 만듭니다.
2. 수정 지시가 끝없이 반복되는 폭주를 일부러 일으키고,<br>제한 장치를 걸어 직접 멈춥니다.
3. 손을 떼고 한 사이클 전체를 관전하며, 화면의 말풍선 하나와<br>서버의 메시지 기록 한 줄을 짝지어 봅니다.
> 💡 이번 세션의 핵심은 "보이면 달라진다"입니다.<br>같은 협업이라도 로그로 훑는 것과 채팅방으로 보는 것은<br>이해의 깊이가 다릅니다. 그리고 문제가 생겼을 때<br>어디서 막혔는지 찾는 속도도 완전히 달라집니다.

### 결과만 보이고 과정이 안 보이면 생기는 일
집필 한 사이클 동안 서버 로그에는 이런 기록이 흘러갑니다.
```php
[14:22:31] orchestrator: 지시서 5건 생성 완료
[14:22:33] chapter_1: 집필 시작
[14:22:33] chapter_2: 집필 시작
[14:22:48] chapter_1: 집필 완료 (742자)
[14:23:02] orchestrator: 교차 검토 시작
[14:23:07] orchestrator → chapter_3: 수정 요망 (용어 불일치)
[14:23:21] chapter_3: 수정본 제출
```
정보는 전부 있습니다. 하지만 읽기가 어렵습니다.<br>누가 누구에게 말했는지 줄마다 해독해야 하고,<br>지금 전체가 어느 단계인지 한눈에 들어오지 않습니다.<br>협업이 커질수록 이 로그는 더 길고 빽빽해집니다.
우리에게 필요한 것은 정보의 추가가 아니라 표현의 전환입니다.<br>사람이 여럿의 대화를 읽는 데 가장 익숙한 형식이 있습니다.<br>단체 채팅방입니다.<br>같은 기록을 채팅방으로 옮기면, 누가 말했고(이름표),<br>누구에게 말했고(말풍선 내용), 지금 무엇을 하는지(상태 표시)가<br>해독 없이 즉시 읽힙니다.

### 채팅방의 구성 요소
우리가 만들 채팅방 화면의 뼈대입니다.
[원본 이미지 제외]
구성 요소는 세 가지입니다.
- **멤버 목록과 상태 배지**: 에이전트마다 색이 다른 표식과<br>이름표가 붙고, 현재 상태가 배지로 표시됩니다.<br>상태는 다섯 가지입니다: 대기 / 집필 중 / 검토 중 / 수정 중 / 완료.
- **말풍선 스트림**: 에이전트 사이에 오간 메시지가<br>시간 순서로 쌓입니다. 발신자 이름과 시각이 함께 붙습니다.
- **조작 단추**: 집필을 시작하는 단추와,<br>진행 중인 협업을 즉시 멈추는 중지 단추입니다.

### 메시지 프로토콜 — 말풍선 한 개의 실체
채팅방에 뜨는 말풍선은 장식이 아닙니다.<br>에이전트 사이에 실제로 전달된 데이터 한 건과 1:1로 대응합니다.<br>에이전트들은 정해진 형식의 메시지로 소통하는데,<br>이 형식 약속을 메시지 프로토콜(Protocol)이라고 부릅니다.
우리 팀의 메시지 한 건은 이런 형식입니다.
```json
{
  "time": "14:23:07",
  "from": "orchestrator",
  "to": "chapter_3",
  "type": "revision_request",
  "content": "용어 통일: '제세동기'를 '자동심장충격기'로 수정"
}
```
이 한 건이 채팅방에서는 이 말풍선 한 개가 됩니다.
```php
오케스트레이터  14:23:07
│ 수정 요망: "제세동기"를 "자동심장충격기"로 통일해 주세요.
```
발신자(from)는 이름표로, 시각(time)은 타임스탬프로,<br>내용(content)은 말풍선 본문으로 옮겨졌을 뿐입니다.<br>type 항목은 메시지의 종류입니다.<br>지시서 전달, 집필 보고, 수정 요망, 완료 선언이 각각 다른 type을 갖고,<br>화면에서는 말풍선의 색이나 표식으로 구분됩니다.
이 대응 관계를 알면 화면과 서버를 오가며 확인할 수 있습니다.<br>채팅방에서 이상한 말풍선을 발견하면,<br>같은 시각의 메시지 기록을 서버에서 찾아 원본을 보면 됩니다.
---
### 폭주 — 조율에도 멈춤 장치가 필요하다
오케스트레이터의 수정 지시는 품질을 지키는 장치입니다.<br>그런데 이 장치에는 위험한 가정이 숨어 있습니다.<br>"수정하면 언젠가 통과한다"는 가정입니다.<br>**통과 기준이 지나치게 엄격하거나 지시가 모호하면, 이런 일이 벌어집니다.**
[원본 이미지 제외]
끝나지 않습니다.<br>그동안 호출은 계속 쌓입니다. 유료 환경이라면 비용이, 무료 환경이라면 사용량 한도가 소진됩니다.<br>사람이 지켜보지 않는 자동화라면 밤새 돌 수도 있습니다.
그래서 다중 에이전트 시스템에는 멈춤 장치를 반드시 답니다.<br>대표적인 두 가지입니다.
- **최대 수정 횟수 제한**: 같은 장에 대한 수정 지시를<br>정해진 횟수(예: 2회)까지만 허용합니다. 초과하면<br>"제한 도달, 현재 본으로 확정"을 선언하고 다음으로 넘어갑니다.
- **타임아웃(Timeout)**: 한 단계가 정해진 시간을 넘기면<br>중단하고 실패로 보고합니다. 응답이 없는 에이전트를<br>무한정 기다리는 사고를 막습니다.
⚠️ 멈춤 장치는 품질 장치와 반대 방향으로 당깁니다.<br>제한이 없으면 폭주하고, 제한이 너무 빡빡하면 고칠 수 있던 문제를 안고 끝납니다.<br>정답 값은 없으며, 상황에 맞게 정하고 기록해 두는 것이 실무입니다.

### 실습 2. 고장 실험 — 무한 수정 루프
폭주를 일부러 일으키고, 제한 장치로 멈춥니다.<br>이 실험은 우연에 맡기지 않고, 실험용 스위치로 확실하게 재현합니다.
**Claude Code 프롬프트**
```plain text
채팅방에 폭주 실험 기능을 추가해 주세요. 요구사항입니다.

1. 페이지에 실험용 설정 두 개를 추가해 주세요.
   - [항상 반려 모드] 켜면 오케스트레이터가 교차 검토에서
     3장을 무조건 수정 요망 처리합니다. 실험 전용입니다.
   - [최대 수정 횟수 제한] 끄고 켤 수 있고, 켜면 기본값 2회입니다.

2. 제한이 켜진 상태에서 같은 장의 수정 요망이 제한 횟수를
   넘으면, 오케스트레이터가 "수정 제한 도달. 현재 본으로
   확정합니다."라는 메시지를 남기고 다음 단계로 넘어갑니다.

3. 각 수정 요망 말풍선에 회차 표시를 붙여 주세요.
   예: "수정 요망 (3회차)"

4. [중지] 단추가 폭주 중에도 즉시 동작하는지 확인해 주세요.
```
진행 순서

1. 창②에 프롬프트를 입력하고 진행한 뒤 서버를 재시작합니다.
2. \[항상 반려 모드\] 켬 + \[최대 수정 횟수 제한\] 끔으로 설정합니다.
3. \[예측\] 이 설정으로 집필을 시작하면 채팅방에 무슨 일이<br>벌어질지, 그리고 저절로 끝날 수 있을지 예측해 적습니다.
4. \[집필 시작\]을 누르고 관전합니다.
5. \[확인\] 3장을 둘러싼 "수정 요망 (N회차) ↔ 수정본 제출"<br>말풍선이 끝없이 쌓이는 것을 확인합니다.<br>회차 숫자가 5를 넘으면 충분히 봤습니다.
6. \[중지\]를 눌러 폭주를 직접 멈춥니다.
7. 이번에는 \[최대 수정 횟수 제한\]을 켜고(2회) 다시 시작합니다.
8. 3장이 2회차까지 반려된 뒤, "수정 제한 도달. 현재 본으로<br>확정합니다." 말풍선과 함께 협업이 정상 종료되는 것을<br>확인합니다.
9. 실험이 끝나면 \[항상 반려 모드\]를 반드시 끕니다.

> 💡 6번과 8번의 차이를 기억해 둡니다.<br>6번은 사람이 달려들어 멈춘 것이고,<br>8번은 시스템이 스스로 멈춘 것입니다.<br>사람이 지켜보지 않아도 되는 자동화란<br>8번이 설계되어 있는 자동화를 말합니다.
**잘 안 될 때**
**Q. 항상 반려 모드인데 통과됨**
- **원인**: 스위치 미반영
- **해결**: 창②에 "항상 반려 모드가 교차 검토에 적용되는지 확인해 주세요"라고 요청합니다
**Q. 중지가 안 먹힘**
- **원인**: 중단 처리 누락
- **해결**: 창①에서 Ctrl+C로 서버를 끄면 즉시 멈춥니다. 이후 창②에 중지 단추 수리를 요청합니다
**Q. 제한을 켰는데 3회차가 나옴**
- **원인**: 횟수 집계 오류
- **해결**: 창②에 "수정 횟수 집계가 장별로 되는지 점검해 주세요"라고 요청합니다
**Q. 실험 후 결과물 품질이 이상함**
- **원인**: 항상 반려 모드가 켜진 채 확정됨
- **해결**: 정상입니다. 실험 모드를 끄고 다시 집필하면 됩니다
