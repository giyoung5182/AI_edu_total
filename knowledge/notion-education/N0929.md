## 이번 시간에 만들 것
2권에서는 Claude Code를 실행하고 폴더 안 파일을 읽게 해봤습니다. 거기까지는 "내 파일을 읽는다"는 점만 빼면 챗봇과 크게 다르지 않았습니다. **이번 시간에 진짜 차이가 드러납니다.**
이번에 만들 것은 **서브에이전트(Subagent)** 입니다. 메인 에이전트가 모든 일을 직접 하지 않고, 특정 업무를 전담하는 **부하 직원**에게 일을 맡기는 구조입니다.
```plain text
data 폴더에 매장 클레임 접수서 10건이 쌓여 있습니다.

"이 클레임들 검토해줘" 하면
  → 서브에이전트가 10개 파일을 모두 읽고
  → 클레임 대응 매뉴얼의 판정 기준과 대조해서
  → 건별로 [즉시조치 / 본사확인 / 매장자체해결 / 추가확인] 판정과
    사유를 표로 만들어 줍니다.
```
2권에서는 "클레임 1건 요약해줘"에 답을 받았습니다. 이번 서브에이전트는 **10건을 한꺼번에 조사하고, 정해진 기준으로 판단해서, 검토 결과 문서를 만들어 냅니다.**
---
## 왜 굳이 에이전트를 만드나 — 먼저 이해할 것
메인 Claude에게 그때그때 시켜도 결과는 나옵니다. 그런데도 에이전트를 만드는 이유가 셋 있습니다.
```plain text
① 기준이 고정됩니다
   판정 기준·출력 형식·태도가 파일에 박혀 있어
   매번 다시 설명하지 않아도 같은 잣대가 적용됩니다.

② 대화가 깨끗해집니다
   에이전트는 자기만의 공간에서 10건을 처리하고
   결과 표만 돌려줍니다. 파일 더미가 메인 대화를 어지럽히지 않습니다.

③ 팀에 넘길 수 있습니다
   잘 다듬어진 에이전트는 파일 하나입니다.
   그 파일을 주면 동료도 같은 기준으로 일합니다.
```
**③이 실무에서 가장 큽니다.** 담당자가 바뀌어도 판단 기준이 흔들리지 않습니다.

## 1-2. 왜 하필 이 네 가지인가
```plain text
역할이 없으면      → 무슨 일을 할지 몰라 매번 다르게 답합니다
정보 범위가 없으면  → 엉뚱한 파일을 읽거나, 없는 내용을 지어냅니다
출력 형식이 없으면  → 어떤 날은 표, 어떤 날은 줄글로 나옵니다
페르소나가 없으면   → 판단이 들쭉날쭉해집니다
                    (같은 건인데 어제는 즉시조치, 오늘은 매장자체해결)
```
**네 칸을 혼자 다 채우려 하지 마세요.** 부담되면 역할 정도만 정하고 나머지는 Claude에게 제안해 달라고 해도 됩니다. 잠시 후 생성 단계에서 Claude가 함께 만들어 줍니다.

## 2-4. 중요한 규칙만 짧게 보정합니다
초안이 나오면, **놓치면 안 되는 판단 규칙만 한두 줄로 덧붙여** 고칩니다. 처음부터 다 적는 대신, 초안을 보고 필요한 것만 조여주는 방식입니다.
마무리가 된 시점에 아래를 붙여넣습니다.
```plain text
좋아. 세 가지만 반영해줘.
자료에 없는 내용은 추측하지 말고 '확인 필요'로 표시해.
애매하면 즉시조치로 단정하지 말고 추가확인으로 둬.
보상 금액이나 책임 소재는 확정하지 말고 1차 검토 의견만 내.
```
**이 세 줄은 매뉴얼 5항("접수 단계에서 하지 않는 것")과 같은 내용입니다.** 회사의 실제 규칙을 에이전트에 심는 작업이라고 보면 됩니다.
이 "초안을 보고 규칙을 더한다"는 흐름은 뒤의 Step 4(검증과 튜닝)와 같은 방식입니다. 실무에서도 보통 처음엔 느슨하게 만들고 결과를 보며 기준을 더하니, 오히려 더 현실적입니다.

## 2-5. 만들어진 것을 확인합니다
실습 폴더 안에 `.claude` 폴더가 새로 생겼습니다.
```plain text
교육기관_클레임실습\
   ├─ .claude\
   │    └─ agents\
   │         └─ claim-review-assessor.md    ← 방금 만든 에이전트
   ├─ data\
   └─ 클레임_대응매뉴얼.txt
```
**`.claude`**** 폴더가 안 보이는 경우** 이름이 점(.)으로 시작하는 폴더는 Windows에서 숨겨져 있을 수 있습니다.
```plain text
파일 탐색기 상단 [보기] → [표시] → [숨긴 항목] 체크
```
**파일을 메모장으로 열어보세요.** 맨 위 설정 영역과 그 아래 지시문으로 되어 있습니다. **이 파일 하나가 그 에이전트의 전부입니다.** 나중에 동료에게 이 파일만 주면 똑같은 에이전트를 쓸 수 있습니다.

## 2-6. Claude Code를 재시작합니다
새로 만든 에이전트는 Claude Code를 재시작해야 잡힙니다
**이 단계를 건너뛰면 다음 실행에서 반드시 막힙니다.**
우리는 방금 처음으로 에이전트를 만들었기 때문에, 지금 대화 중인 Claude Code는 `.claude` 폴더를 아직 인식하지 못할 가능성이 높습니다. 이 상태로 실행하면 아래 메시지가 뜹니다.
```plain text
Agent type 'claim-review-assessor' not found
```
**우리는 처음 Agent를 만들었기 때문에 현재 대화에선 ****`.claude`**** 폴더가 인식 안 될 가능성이 높습니다.**
이 상태에서 바로 실행하면 "Agent type ... not found"처럼 에이전트를 못 찾는다는 메시지가 뜰 수 있습니다.
한 번만 재시작하면 됩니다.** 입력창에서 ****`/exit`****로 Claude Code를 끄고(또는 Ctrl+C를 두 번), 같은 폴더에서 다시 ****`claude`****를 실행**하세요. 재시작하면 새 에이전트가 목록에 등록됩니다.
**재시작 방법**
```plain text
① 입력창에 /exit 입력 (또는 Ctrl + C 를 두 번)
② 같은 폴더에서 다시 claude 입력
```
재시작하면 새 에이전트가 목록에 등록됩니다. **에이전트를 만들거나 고칠 때마다 재시작한다**고 외워두면 편합니다.

## (참고 2) 파일을 직접 만드는 방법 (고급)
익숙해지면 `.claude/agents/[이름].md` 파일을 직접 만들어도 됩니다. **맨 위에 설정(YAML)을 적고, 그 아래에 지시문을 적는 구조**입니다.
```markdown
---                                      ← 이 사이가 설정(YAML) 영역
name: claim-review-assessor
description: >-
  매장 클레임 접수 건을 클레임 대응 매뉴얼 기준과 대조해
  처리 구분을 판정하는 접수 검토 에이전트.
  사용자가 "클레임 검토", "접수 건 검토", "매장 클레임 판정",
  "요청사항 검토"를 요청하면 반드시 이 에이전트를 사용할 것.
  data 폴더의 클레임 접수서를 매뉴얼의 판정 기준·유형별 처리 기준과
  대조하여 건별로 [즉시조치 / 본사확인 / 매장자체해결 / 추가확인] 중
  하나로 판정하고 사유와 함께 표로 정리한다.
model: sonnet
disallowedTools: [Agent]
---

너는 매장 클레임 접수 건을 검토하는 접수 담당 보조 에이전트다.
data 폴더의 클레임 건들을 모두 읽고, 클레임_대응매뉴얼.txt의 기준과 대조해
건별로 [즉시조치 / 본사확인 / 매장자체해결 / 추가확인] 중 하나로 판정하고
사유를 적는다.
출력은 표로 하며 열은 접수번호 / 매장명 / 유형 / 판정 / 사유로 한다.
자료에 없는 내용은 추측하지 말고 '확인 필요'로 표시하고,
애매하면 추가확인으로 두며, 보상 금액과 책임 소재는 확정하지 않는다.
```
**Claude가 만든 파일을 열어보면 이와 비슷하게 작성되어 있습니다.** 수업에서는 앞의 "말로 만들기"만 해도 충분합니다. 이 파일 방식은 **나중에 세부를 손볼 때** 알아두면 좋습니다.

# Step 3. 메인에 연결하고 실행하기 (라우팅)

## 3-1. 라우팅이란
우리가 어떤 요청을 하면, 메인 Claude가 그 일을 **어느 담당자에게 넘길지** 정합니다. 요청을 맞는 에이전트에게 이어 주는 이 과정을 **라우팅**이라고 합니다.
**조직에 비유하면**, 팀장이 들어온 일을 보고 담당자를 정해 배정하는 것과 같습니다.
[원본 이미지 제외]
```plain text
라우팅 두 가지 방식

이름을 불러 배정
  "클레임검토 에이전트한테 맡겨줘"
  → 그 담당자로 확실히 넘어갑니다

자동 배정
  "클레임 검토해줘"
  → 메인이 요청과 각 에이전트의 description을 보고 스스로 판단
  → 편하지만 항상 걸린다고 보장하기 어렵습니다
```
---
## 3-2. 실행 — 담당자를 이름으로 불러 맡깁니다
입력창에 아래를 입력하고 Enter를 누릅니다.
```plain text
클레임검토 에이전트한테 data 폴더의 클레임 건들을 검토 맡겨줘.
클레임_대응매뉴얼.txt의 기준으로, 건별로 판정과 사유를 표로 정리해줘.
```
**화면에서 일어나는 일**
```plain text
① 에이전트 이름이 표시되며 호출됩니다
② 그 에이전트가 data 폴더의 파일을 하나씩 읽습니다
③ 매뉴얼을 읽어 기준을 확인합니다
④ 건별 판정 결과가 표로 나옵니다
```
시간이 조금 걸립니다. **멈춘 것 같으면 ****`Ctrl + O`** 를 눌러 지금 무엇을 하는 중인지 확인하세요.
Step 2에서 description에 적어 둔 호출 조건이, 이 에이전트가 클레임 검토 담당이라는 것을 Claude가 알게 해 줍니다.
---
## 3-3. 주의 — 이름을 빼면 메인이 직접 해버릴 수 있습니다
**이 부분이 실습에서 가장 많이 헷갈리는 지점입니다.**
이름을 빼고 "data 폴더의 클레임 검토해줘"라고만 하면, 메인 Claude가 "이 정도는 내가 하면 되겠다"고 판단해 **에이전트를 부르지 않고 직접 처리해 버리는 경우**가 있습니다. 이때 화면에는 에이전트 이름 없이, 메인이 폴더를 읽고 10건을 확인하는 흐름만 보입니다.
**이건 고장이 아니라 자동 라우팅의 원래 성질입니다.** 결과 표 자체는 나오지만, 우리가 만든 에이전트가 도는 모습은 보이지 않습니다. 그래서 처음 확인할 때는 반드시 이름을 불러 배정하세요.
**이름을 불렀는데도 메인이 직접 해버린다면 두 가지를 확인합니다**
```plain text
① 요청에 에이전트를 가리키는 말("클레임검토")을 넣었는지
② .claude/agents/ 안 파일의 description에
   "클레임 검토, 접수 건 검토, 매장 클레임 판정" 같은 호출 문구가 있는지
   → 이 문구가 약하면 이름을 불러도 잘 안 걸립니다
```
**반드시 고정하고 싶다면 ****`@`****를 쓰세요.** 입력창에서 `@`를 누르면 목록이 뜨고, 에이전트를 태그하면 그 작업은 **해당 에이전트 실행이 보장됩니다.** 슬랙에서 담당자를 태그하는 것과 같습니다.
**반대로, description을 강하게 써 두면** 이름을 부르지 않고 "클레임 검토해줘"라고만 해도 넘어가는 경우가 많습니다. 다만 자동은 판단이라 보장은 아니니, **확실히 보여줘야 할 때는 이름을 부르거나 ****`@`****로 태그하세요.**
## ※참고 서브에이전트 자가 복제 오류 사전 대응 방법
[원본 이미지 제외]

**요약 가이드**
최근 클로드 코드(Claude Code)의 시스템 업데이트로 인해, 서브에이전트가 복잡한 분석을 하다가 막히면 스스로를 똑같이 카피(자가 복제)해서 무한으로 호출하는 현상(재귀 호출)이 발생할 수 있습니다. 이 경우 시간과 비용(토큰)이 낭비되므로, 아래 설정을 통해 에이전트의 다른 에이전트 호출 권한을 확실하게 잠가주어야 합니다.

### 1️⃣ 현상 및 원인
- **어떤 현상이 일어나나요?**
- 대시보드 생성이나 대량 파일 분석 명령을 내렸을 때, 화면에 `Waiting for background agents` 메시지가 뜨며 특정 에이전트(예: 면책 사유 점검, 리스크 점검 등)가 일을 끝내지 않고 뱅글뱅글 도는 현상이 발생합니다.
- **왜 이런 일이 생기나요?**
- 기존에는 에이전트가 다른 에이전트를 부르는 기능이 제한되어 있었으나, 최신 업데이트로 제한이 해제되었습니다. 이로 인해 서브에이전트가 판단하기 모호한 상황을 마주하면, 자기 자신을 또 하나의 서브에이전트로 중첩 호출(재귀 호출)하여 일을 떠넘기는 구조적 버그가 발생하게 된 것입니다.
### 2️⃣ 해결 방법: `disallowedTools` 옵션으로 락(Lock) 걸기
에이전트를 생성할 때 설정 창(YAML 영역)에 "너는 다른 에이전트를 소환하는 도구를 절대 쓸 수 없다"는 강력한 제한 규칙을 한 줄 추가해 주면 해결됩니다.
#### 📌 \[방법 A\] 처음 에이전트를 만들 때 (프롬프트 추가)
에이전트 생성 프롬프트 맨 마지막에 아래 문구를 함께 적어줍니다.
Plaintext
```plain text
"추가로, 이 에이전트가 스스로를 무한 호출하거나 다른 에이전트에게 업무를 토스하지 못하도록 설정(disallowedTools)에 'Agent'를 반드시 추가해줘."
```
#### 📌 \[방법 B\] 이미 만든 에이전트 파일을 수정할 때 (YAML 직접 수정)
1. 실습 폴더 내의 `.claude/agents/` 폴더로 이동합니다.
2. 문제가 발생하는 에이전트 파일(예: `claim-review.md`)을 메모장이나 에디터로 엽니다.
3. 파일 맨 위 `--` 와 `--` 사이(YAML 설정 영역)에 **`disallowedTools: [Agent]`** 문구를 삽입하고 저장합니다.
- **수정 전 예시:**
YAML
```plain text
---
name: insurance-risk-screener
description: 청약 건들 중 위험 신호가 있는 건을 가려내는 에이전트
model: sonnet
---
```
- **🟢 수정 후 예시 (참고)**
YAML
```plain text
---
name: insurance-risk-screener
description: 청약 건들 중 위험 신호가 있는 건을 가려내는 에이전트
model: sonnet
disallowedTools: [Agent]
---
```
> **⚠️ 주의:** `disallowedTools: [Agent]`에서 **Agent의 'A'는 반드시 대문자**로 적어주어야 시스템이 정확하게 인식합니다.
### 3️⃣ 반드시 기억할 마무리: 세션 새로고침
에이전트 설정을 말로 수정했거나 파일을 직접 고쳤다면, 클로드 코드가 바뀐 규칙(자물쇠)을 새로고침하여 인식할 수 있도록 **반드시 프로그램을 재시작**해야 합니다.
1. 대화창에 `/exit`를 입력하거나 `Ctrl + C`를 두 번 눌러 클로드 코드를 완전히 종료합니다.
2. 터미널 창에 다시 `claude`를 입력하여 실행하면, 이제 비서가 딴짓을 하지 않고 한 방에서 자기 혼자 깔끔하게 업무를 완수합니다.

# Step 4. 결과 확인과 검증
---
## 4-1. 결과 읽기
검토가 끝나면 클레임 10건의 판정 결과가 표로 나옵니다. 아래 항목을 눈으로 확인하세요. (실제 표현은 다를 수 있습니다.)
```plain text
□ 10건이 모두 표에 들어왔는가
□ 판정이 4종 안에서만 쓰였는가
□ 사유에 매뉴얼의 기준이 근거로 언급되는가
□ 증빙이 없는 건이 즉시조치로 단정되지 않았는가
```
**특히 이 두 건을 보세요**
```plain text
광주상무점 (대파 품질)     증빙 사진 없음 + 이미 사용함
일산라페스타점 (발주 시스템)  증상·시점 불명, 담당부서 미지정

→ 이 두 건이 즉시조치로 갔다면 판정 기준이 느슨한 것입니다.
   추가확인 쪽으로 갔다면 잘 만들어진 것입니다.
```
**정보가 부족한 건을 어떻게 처리했는지가 품질의 핵심입니다.** 자료에 없는 것을 지어내지 않고 "확인 필요"로 남겼다면 제대로 동작한 것입니다.
---

**튜닝할 때도 메뉴가 아니라 말로 합니다**
```plain text
"클레임검토 에이전트가 사유를 더 구체적으로 쓰도록 에이전트를 수정해줘."

"클레임검토 에이전트를 수정해줘.
 증빙 사진이 없는 건은 즉시조치로 판정하지 말고
 반드시 추가확인으로 두게 해줘."

→ Claude가 .claude/agents/ 안의 파일을 직접 고쳐 줍니다.

```
**튜닝은 새 대화에서 하면 더 깔끔합니다.** `/clear`를 입력하면 앞의 결과에 끌려가지 않고 새로 시작할 수 있습니다.

## 4-3. 검증 체크포인트 3가지
세 가지가 모두 충족되어야 신뢰할 수 있는 서브에이전트가 됩니다.

```plain text
시트 1. 팀 정보        □ 팀 이름 / 팀원 / 구성 방식
시트 2. 타 부서 인터뷰  □ Q1 반복 수기 업무 / Q2 가장 오래 걸리는 일 / Q3 데이터가 쌓이는 곳

```
**지금까지 제출된 것을 보면 시트 2(인터뷰)는 잘 채워진 반면, 시트 1과 시트 3이 비어 있는 경우가 있습니다.** 인터뷰는 했는데 "그래서 우리 팀이 뭘 할지"까지 정리가 안 된 상태입니다. 11회차는 시트 3을 놓고 시작하므로, 이 칸이 비어 있으면 출발이 늦어집니다.
### 잘 채워진 인터뷰 예시 (실제 제출본)
한 팀이 사무국을 인터뷰해 아래와 같은 내용을 가져왔습니다.
```plain text
Q1. 반복되는 수기 업무
    · 신입 입사 시 근로계약서·입사서류 요청 → 매장에서 인사담당자에게
      입사 사실이 전달되지 않아 서류 요청 자체가 누락됨
    · 급여명세서 수령확인서, 연차사용대장 확인서를 이메일로 보내고
      매장이 출력·서명 → 배송 직원 편으로 회수

Q2. 가장 오래 걸리는 일
    · 확인서 취합. 안 보낸 매장을 찾아 매장마다 전화를 돌려야 함
    · 담당자는 한 명인데 매장은 여럿 → 길게는 4개월까지 걸림

Q3. 데이터가 쌓이는 곳
    · 전부 종이 보관 (퇴사 후 3년 보관 의무)

Q4. 그 밖에 바꾸고 싶어 하는 점
    · 누락 여부를 시트로 체크하고 주 1회 누락 매장에 자동 안내가 갔으면 함
```
**이 인터뷰가 좋은 이유는 세 가지입니다.**
```plain text
① 업무 순서가 단계별로 드러남      → 어디가 막히는지 짚을 수 있음
② 시간이 숫자로 나옴 (최대 4개월)   → 개선 효과를 측정할 수 있음
③ 데이터가 어디 있는지 명확함(종이) → 어떤 도구가 필요한지 판단 가능
```
시트 3을 채울 때는 이 세 가지가 답에 들어가는지 확인하세요.
**아직 못 한 팀은 11회차 전까지 반드시 마무리해 주세요.**
