## 오프닝 — 지난 시간과 무엇이 다른가
```plain text
6회차(Lovable): 화면이 있는 웹/앱을 AI가 만들어줬다
7회차(Claude Code, 오늘): AI가 내 파일을 직접 읽고,
                          여러 명의 담당자에게 일을 나눠서,
                          결과를 하나의 보고서로 만들어준다
```
지난 시간까지 Claude Code를 실행해서 폴더 안 파일을 읽게 해봤습니다. 거기까지는 "내 파일을 읽는다"는 점만 빼면 챗봇과 크게 다르지 않았습니다. 오늘 진짜 차이가 드러납니다.
오늘 만들 것은 \*\*Subagent(서브에이전트)\*\*입니다. 메인 에이전트가 모든 일을 직접 하지 않고, 특정 업무를 전담하는 부하 직원에게 일을 맡기는 구조입니다. 오늘은 **강의 교안을 검수하는 서브에이전트**를 만들어, 회차별 교안 여러 개를 한 번에 검토하게 만들어 보겠습니다.
> ⚠️ 오늘 실습은 진행 편의를 위해 "강의 교안 검수"라는 특정 주제로 진행합니다. 이후 "나만의 실습해보기" 세션에서 이사님 실제 업무에 맞는 주제로 다시 만듭니다.

## 왜 서브에이전트가 필요한가 — 원리부터
> 이 원리를 모르고 서브에이전트를 쓰면 "그냥 메인한테 시켜도 되는 거 아닌가?"라는 의문이 계속 남습니다. 아래 원리를 알면 그 의문이 완전히 풀립니다.
```plain text
핵심 원리: 서브에이전트는 각자 자기만의 독립된 컨텍스트 윈도우를 가집니다.

메인 에이전트가 직접 10개 파일을 읽고 분석하면:
  → 그 10개 파일의 내용 전체가 메인 대화의 컨텍스트에 쌓입니다
  → 5회차에서 배운 컨텍스트 로트(많이 넣을수록 성능 저하)가
    메인 대화 자체를 오염시킵니다
  → 다음 작업을 이어갈 때 메인이 "무엇에 집중해야 할지"를
    잃어버리기 시작합니다

서브에이전트에게 맡기면:
  → 10개 파일은 서브에이전트의 별도 컨텍스트 윈도우 안에서만 읽힙니다
  → 메인 대화로는 "결과 요약"만 돌아옵니다
  → 메인의 컨텍스트는 깨끗하게 유지됩니다

Anthropic 공식 문서의 표현을 빌리면:
"컨텍스트는 당신의 근본적인 제약 자원입니다.
 서브에이전트는 그 제약을 다루는 가장 강력한 도구 중 하나입니다."
```
**Boris Cherny(Anthropic, Claude Code 총괄)의 원칙** — 5회차에서 루프 엔지니어링을 다룰 때 등장했던 바로 그 인물입니다.
```plain text
"기능별로 구체적인 서브에이전트가, 범용적인 '품질검증' '백엔드
 엔지니어' 같은 서브에이전트보다 낫다. 구체성이 더 나은 도구
 선택과 더 촘촘한 컨텍스트를 만든다."

→ 오늘 "강의 교안 검수 에이전트"를 만들 때, "뭐든 도와주는 AI"가
   아니라 "정확히 무엇을 검수하는지"를 좁게 정의할수록 좋습니다.
```
**알아둘 실무 비용**
```plain text
서브에이전트를 많이 쓸수록 좋은 것만은 아닙니다.
서브에이전트마다 별도의 컨텍스트 윈도우를 유지하기 때문에,
서브에이전트를 많이 쓰는 작업은 단일 세션 대비
토큰을 약 7배까지 더 쓸 수 있습니다.

→ "이 작업이 메인 컨텍스트를 어지럽힐 만큼 큰가?"를 먼저
   판단하고, 그럴 때만 서브에이전트를 쓰는 것이 합리적입니다.
   간단한 질문 하나에 서브에이전트를 부르는 건 낭비입니다.
```
**"넓게 vs 깊게" — 언제 서브에이전트를 쓰고 언제 메인에서 직접 할까**
```plain text
서브에이전트에 맡기기 좋은 것 (Fork for breadth):
  여러 파일을 뒤져서 훑어보고, 찾고, 요약하는 작업
  예: "폴더 안 10개 교안을 훑어서 문제 있는 부분만 골라줘"

메인에서 직접 하는 게 나은 것 (Stay inline for depth):
  추론이 깊게 필요한 작업, 사람이 매 단계를 보면서 방향을 잡아야 하는 작업
  예: "이 교안의 이 문단을 어떻게 다시 쓸지 나랑 같이 고민해줘"

→ 오늘 만들 검수 에이전트는 "여러 파일을 훑어서 찾아내는" 작업이라
   서브에이전트에 맡기기 정확히 좋은 사례입니다.
```

## 오늘 만들 서브에이전트
```plain text
work 폴더에 이사님 교안 파일 여러 개가 쌓여 있다고 가정합니다.
"이 교안들을 검수해줘" 하면
→ 서브에이전트가 모든 파일을 읽고
→ 지금까지 배운 원칙(0회차 정직성 기준, 5회차 콘텐츠 원칙 등)과 대조해서
→ 파일별로 [문제없음 / 표현 수정 필요 / 근거 확인 필요 / 검토 보류]
  판정과 사유를 표로 만들어 줍니다.
```
지난 시간 챗봇은 "이 교안 하나 요약해줘"에 답했습니다. 이번 서브에이전트는 여러 개를 한꺼번에 조사하고, 정해진 기준으로 판단해서, 검수 결과 문서를 만들어 냅니다.

## Step 2. 서브에이전트 생성 — 자연어로 만들기
### 실습 순서
**1. 실습 폴더에서 Claude Code를 실행합니다.**
```plain text
work 폴더 빈 공간을 오른쪽 클릭해 터미널을 열고 claude를 입력합니다.
```
**2. Claude에게 짧게 브리핑합니다.**
```plain text
work 폴더의 강의 콘텐츠 파일(C001~C010)들을 검수하는 서브에이전트를
.claude/agents/ 폴더에 만들어줘.

검수 기준은 work 폴더 안의 AI강의_콘텐츠_검수기준.md 문서를 따르고,
사실 관계 확인이 필요할 때는 교육기관 20_공식정보_요약.md를 참고해서
아래 4개 중 하나로 판정하고 사유와 함께 표로 정리하는 역할이야.

- 문제없음: 표현 원칙을 지키고 근거도 명확함
- 표현수정필요: 단정·과장·수익 암시 표현이 있음
- 근거확인필요: 통계·인용은 있는데 출처가 불명확함
- 검토보류: 아직 확정 안 됐거나 판단이 애매해서 사람이 다시 봐야 함

'교안 검수', '자료 검토', '교안 점검' 요청이 오면
반드시 이 에이전트가 쓰이도록 description을 써줘.
에이전트 이름(name)은 영어 소문자와 하이픈으로 지어줘.
도구는 읽기 전용(Read-only)으로만 허용해줘. 모델은 Sonnet으로 해줘.
```
> 💡 판정 4종의 세부 기준은 AI강의_콘텐츠_검수기준.md 문서 안에 이미 정리되어 있습니다. 프롬프트에서 이 문서를 참고하라고만 지시하면, 매번 기준을 길게 다시 설명하지 않아도 됩니다. 표의 열 구성까지는 미리 다 적을 필요 없습니다 — Claude가 초안을 만들어줍니다.
> ⚠️ **이름은 반드시 영어로**: Claude Code는 에이전트의 실제 이름(name)을 영어 소문자와 하이픈으로만 인식합니다(예: `lecture-content-reviewer`). 한글 이름으로 만들면 "Agent type ... not found" 오류가 납니다.
**3. Claude가 초안을 만듭니다.**
```plain text
Claude가 브리핑을 정리해서 서브에이전트 정의 파일을
.claude/agents/ 폴더에 만들어 줍니다.
파일 생성 여부를 물으면 허용(1번 또는 엔터)을 선택합니다.
```
**4. 중요한 규칙만 짧게 보정합니다.**
```plain text
초안이 나오면, 놓치면 안 되는 심사 규칙만 한두 줄로 덧붙여 고칩니다.

좋아. 세 가지만 반영해줘.
자료에 없는 내용은 추측하지 말고 '확인 필요'로 표시해.
애매하면 문제없음으로 단정하지 말고 검토보류로 둬.
표현 수정이 필요하면, 어떻게 고치면 좋을지 예시도 함께 제안해줘.
```
> "초안을 보고 규칙을 더한다"는 흐름은 실무에서도 똑같습니다. 처음엔 느슨하게 만들고 결과를 보며 기준을 더하는 게 오히려 현실적입니다.
**5. 만들어진 것을 확인합니다.**
```plain text
.claude/agents 폴더 안에 에이전트 파일(예: lecture-content-reviewer.md)이
만들어진 것을 볼 수 있습니다.
```
**6. Claude Code를 재시작합니다.**
```plain text
처음 만든 에이전트는 현재 세션에서 인식이 안 될 수 있습니다.
/exit로 끄고(또는 Ctrl+C 두 번), 같은 폴더에서 다시 claude를 실행하세요.
재시작하면 새 에이전트가 목록에 등록됩니다.
```

### 참고 — 도구와 모델은 이렇게 정합니다
```plain text
Read-only tools: 파일 읽기, 검색 등 아무것도 바꾸지 않는 도구
Edit tools: 파일 수정, 생성하는 도구
Execution tools: 터미널 명령을 실행하는 도구
MCP tools: 연결된 외부 서비스의 도구

교안 검수는 파일을 읽고 대조만 하면 되므로 Read-only로 두면 안전합니다.
```

## Step 3. 메인에 연결하고 실행하기 (라우팅)
### 라우팅이란
```plain text
우리가 어떤 요청을 하면, 메인 Claude가 그 일을 어느 담당자에게
넘길지 정합니다. 이 과정을 라우팅이라고 합니다.
조직에 비유하면, 팀장이 들어온 일을 보고 담당자를 정해 배정하는 것과 같습니다.

라우팅 두 가지 방식:
① 이름을 불러 배정: "교안검수 에이전트한테 맡겨줘"처럼 부르면 확실히 넘어감
② 자동 배정: 이름을 안 부르면, 메인이 요청과 description을 보고
   스스로 넘길지 판단. 편하지만 항상 걸린다고 보장하기 어려움
```
### 실행 — 이름으로 불러 맡기기
```plain text
교안검수 에이전트한테 work 폴더의 C001~C010 콘텐츠 파일들을 검수 맡겨줘.

```
### ⚠️ 주의 — 이름을 빼면 메인이 직접 해버릴 수 있습니다
```plain text
이름을 빼고 "work 폴더의 교안들을 검토해줘"라고만 하면,
메인 Claude가 "이 정도는 내가 하면 되겠다"고 판단해
에이전트를 부르지 않고 직접 처리해 버리는 경우가 있습니다.

이건 고장이 아니라 자동 라우팅의 원래 성질입니다.
결과 표는 나오지만, 우리가 만든 에이전트가 도는 모습은 보이지 않고,
서브에이전트를 쓴 이점(메인 컨텍스트 보호)도 사라집니다.
데모나 확실히 보여줘야 하는 상황에서는 반드시 이름을 부르세요.

이름을 불렀는데도 메인이 직접 해버린다면:
① 요청에 에이전트를 가리키는 말("교안검수")을 넣었는지 확인
② description에 "교안 검수, 자료 검토, 교안 점검" 같은
   호출 문구가 들어 있는지 확인 (문구가 약하면 이름을 불러도 잘 안 걸림)
```

## 서브에이전트 공유하기
```plain text
.claude/agents 폴더의 에이전트 파일이 곧 그 에이전트의 전부입니다.
그래서 공유는 간단합니다 — 그 파일을 전달하면 됩니다.
받는 사람이 자신의 프로젝트 폴더 안 같은 위치에 넣으면
동일한 에이전트를 바로 쓸 수 있습니다.

참고 — 저장 범위 우선순위:
프로젝트 범위(.claude/agents/, 코드와 함께 git으로 관리)는
그 프로젝트에 결합된 에이전트에, 사용자 범위(~/.claude/agents/)는
어디서든 따라다니는 개인용 도우미에 적합합니다.
같은 이름의 에이전트가 둘 다 있으면 프로젝트 범위가 우선합니다.
```
