## C-1. 세 가지 도구 층위를 구분하는 이유

프로그래밍 언어, 라이브러리, 프레임워크라는 세 가지 층위를 구분해야 하는 이유를 확인합니다.

프로젝트를 진행하다 보면 다양한 도구 이름이 나옵니다.
- Python
- JavaScript
- pandas
- openpyxl
- React
- FastAPI
- Vite
처음 접하면 이 이름들이 전부 같은 종류의 도구처럼 보입니다. 실제로는 그렇지 않습니다. 이 도구들은 **프로그래밍 언어**, **라이브러리**, **프레임워크**라는 세 가지 층위에 나뉘어 있습니다.
층위를 구분할 수 있으면 두 가지가 바뀝니다.
첫째, 새로운 도구 이름이 나와도 "이건 어느 층위인가?"라는 질문 하나로 역할을 빠르게 파악할 수 있습니다. 둘째, AI에게 작업을 시킬 때 "어떤 언어로, 어떤 라이브러리를 쓰고, 어떤 프레임워크 위에서 작업하는지"를 명확하게 전달할 수 있습니다.
세 층위는 한꺼번에 등장한 것이 아닙니다. 시간 순서대로 필요에 의해 하나씩 생겨났습니다. 그 순서를 따라가면 각 층위가 왜 존재하는지 자연스럽게 이해됩니다.

## C-2. 프로그래밍 언어: 컴퓨터에게 일을 시키는 말

프로그래밍 언어가 무엇인지, 이번 프로젝트에서 쓰는 두 가지 언어를 확인합니다.

가장 먼저 있었던 것은 프로그래밍 언어입니다.
컴퓨터는 스스로 판단하지 않습니다. 사람이 지시를 내려야 움직입니다. 그 지시를 적는 데 쓰는 것이 프로그래밍 언어입니다. 사람과 사람 사이에 한국어, 영어가 있듯이 사람과 컴퓨터 사이에는 프로그래밍 언어가 있습니다.
초기에는 이 언어만으로 모든 것을 직접 작성했습니다. 파일을 읽는 코드, 날짜를 계산하는 코드, 화면에 결과를 보여주는 코드 — 전부 처음부터 한 줄씩 적었습니다.
이번 교육에서 다루는 언어는 두 가지입니다.



**Python**<br>데이터 처리, 계산, 파일 읽기 등 서버 쪽 작업에 널리 쓰입니다. 이번 프로젝트에서는 **백엔드**를 Python으로 작성합니다.




**JavaScript**<br>웹 브라우저에서 화면을 움직이게 만듭니다. 이번 프로젝트에서는 **프론트엔드**를 JavaScript로 작성합니다.



정리하면, 프로그래밍 언어는 컴퓨터에게 일을 시키기 위한 가장 기본적인 도구입니다. 다른 모든 도구는 이 언어 위에서 동작합니다.

## C-3. 코드가 길어지면서 생긴 두 가지 문제

언어만으로는 해결할 수 없는 두 가지 문제를 확인하고, 라이브러리와 프레임워크가 왜 필요해졌는지 이해합니다.

프로그래밍 언어만으로 프로그램을 만들 수 있었지만, 프로젝트가 커지면서 두 가지 문제가 반복적으로 나타났습니다.

**문제 1: 반복 작업** — 같은 기능을 매번 처음부터 작성해야 했습니다. 이전 코드를 재사용하기 어려워 매번 낭비가 생겼습니다.

### 문제 1: 같은 기능을 매번 처음부터 작성해야 했습니다
CSV 파일을 읽는 기능, 날짜를 계산하는 기능, 표 데이터를 정렬하는 기능 — 이런 작업은 프로젝트가 달라져도 거의 같은 방식으로 필요합니다.
그런데 언어만 있던 시절에는 프로젝트를 새로 시작할 때마다 이런 기능을 처음부터 다시 작성해야 했습니다. 이전 프로젝트에서 이미 만들었더라도 그 코드를 그대로 가져다 쓰기가 어려웠습니다. 코드가 프로젝트 전체에 뒤섞여 있어서, 필요한 부분만 분리하는 데 시간이 많이 들었습니다.
결국 매 프로젝트마다 비슷한 코드를 반복해서 작성하는 낭비가 생겼습니다.

**문제 2: 제각각인 코드 구조**
같은 언어를 쓰더라도 코드를 정리하는 방식이 사람마다 달라서, 다른 사람의 코드를 이어받으면 구조 파악에만 오랜 시간이 곸렸습니다.

### 문제 2: 코드 구조가 사람마다 달랐습니다
같은 언어를 쓰더라도 코드를 정리하는 방식은 프로그래머마다 제각각이었습니다.
- 어떤 사람은 파일 하나에 모든 기능을 넣었습니다.
- 어떤 사람은 기능별로 파일을 나누되 이름 규칙이 독자적이었습니다.
- 어떤 사람은 데이터 처리와 화면 표시를 섞어 놓았습니다.
이렇게 되면 A가 작성한 코드를 B가 이어받아 수정할 때 문제가 생깁니다. B는 A의 구조를 파악하는 데만 오랜 시간을 쓰게 됩니다. 코드의 내용이 아니라 코드가 어디에 무엇이 놓여 있는지를 먼저 이해해야 하기 때문입니다.
업무 현장에서도 마찬가지입니다. 담당자가 바뀌면 인수인계에 시간이 걸리는 것처럼, 코드도 구조가 통일되어 있지 않으면 넘겨받는 사람이 파악하는 데 오래 걸립니다.
이 두 가지 문제를 해결하기 위해 라이브러리와 프레임워크가 차례로 등장했습니다.

## C-4. 라이브러리: 자주 쓰는 기능을 묶어둔 것

라이브러리가 무엇인지, 이번 프로젝트에서 쓰는 라이브러리를 확인합니다.

라이브러리는 문제 1의 해결책입니다.
누군가가 자주 쓰이는 기능을 미리 만들어서 묶어 두었습니다. 다른 사람들은 그 묶음을 가져와서 필요한 기능만 꺼내 쓰면 됩니다. 처음부터 작성할 필요가 없어졌습니다.
예를 들어 CSV 파일을 읽는 코드를 직접 작성하려면 파일을 열고, 한 줄씩 읽고, 쉼표로 나누고, 빈 값을 처리하고, 숫자를 변환하는 과정을 전부 직접 만들어야 합니다. 하지만 이 기능을 미리 만들어 둔 라이브러리가 있다면 한 줄로 끝납니다.
이번 프로젝트에서 사용하는 라이브러리 두 가지를 봅니다.
**pandas** 표 형태의 데이터를 다루는 Python 라이브러리입니다. CSV 파일 읽기, 특정 컬럼 추출, 조건에 맞는 행 필터링, 합계나 평균 같은 수치 계산 등을 간결한 코드로 처리할 수 있습니다.
이런 기능을 Python만으로 직접 구현하려면 수십 줄에서 수백 줄의 코드가 필요합니다. pandas를 쓰면 같은 작업을 몇 줄로 끝낼 수 있습니다. 데이터를 다루는 업무에서 가장 널리 쓰이는 라이브러리 중 하나입니다.
**openpyxl** 엑셀 파일(.xlsx)을 읽고 쓰는 Python 라이브러리입니다. 특정 셀의 값을 읽거나, 새 시트를 만들거나, 서식을 지정해서 결과 파일을 생성할 수 있습니다. 업무에서 엑셀 파일을 자동으로 처리해야 할 때 사용합니다.
라이브러리의 핵심적인 특징이 하나 있습니다.
**라이브러리는 내가 필요할 때 꺼내 쓰는 것입니다.**
내가 코드를 작성하다가 특정 기능이 필요한 시점에 라이브러리를 불러옵니다. 어떤 라이브러리를 쓸지, 언제 쓸지, 어떻게 조합할지는 전부 내가 결정합니다. 라이브러리는 도구 상자에서 꺼내 쓰는 연장과 같습니다. 어떤 연장을 꺼낼지는 작업자가 정합니다.

## C-5. 프레임워크: 코드를 정리하는 표준 구조

프레임워크가 무엇인지, 라이브러리와 어떻게 다른지 확인합니다.

프레임워크는 문제 2의 해결책입니다.
라이브러리가 등장하면서 같은 기능을 반복 작성하는 문제는 해결되었습니다. 하지만 코드 구조가 사람마다 다른 문제는 여전히 남아 있었습니다. 프로젝트 규모가 커질수록 이 문제는 더 심해졌습니다.
그래서 경험 많은 개발자들이 표준적인 코드 구조를 만들어 공유하기 시작했습니다. "코드를 이런 방식으로 정리하면 누가 봐도 어디에 무엇이 있는지 알 수 있다"는 약속입니다. 이것이 프레임워크입니다.
프레임워크를 사용하면 코드를 어디에 어떻게 배치할지 고민할 필요가 줄어듭니다. 구조가 이미 정해져 있기 때문입니다. 개발자는 그 구조 안에서 실제 업무 로직만 채우면 됩니다.
이번 프로젝트에서 사용하는 프레임워크 두 가지를 봅니다.
**React** 프론트엔드(화면) 코드를 정리하는 JavaScript 프레임워크입니다. 화면을 **컴포넌트**라는 단위로 나누는 구조를 제공합니다.
컴포넌트란 화면의 독립적인 조각입니다. 예를 들어 파일 업로드 영역, 결과 표시 카드, 경고 배지 등이 각각 하나의 컴포넌트가 됩니다. React는 이 컴포넌트들을 어떻게 만들고, 어떻게 데이터를 전달하고, 화면이 어떻게 바뀌는지에 대한 규칙을 정해 둡니다.
이 규칙이 있기 때문에 React를 아는 사람이라면 다른 사람이 만든 React 프로젝트를 열어도 구조를 빠르게 파악할 수 있습니다.
**FastAPI** 백엔드(서버) API 코드를 정리하는 Python 프레임워크입니다. 서버가 외부 요청을 받고 응답하는 구조를 표준화합니다.
API란 외부에서 서버에 요청을 보내고 결과를 받는 통로입니다. FastAPI는 이 통로를 어떤 방식으로 정의하고, 요청 데이터를 어떻게 받고, 결과를 어떤 형태로 돌려주는지에 대한 구조를 제공합니다.
예를 들어 "CSV 파일을 업로드하면 분석 결과를 JSON으로 돌려주는 API"를 만든다고 하면, FastAPI는 파일을 받는 경로, 파일을 처리하는 함수, 결과를 반환하는 형식을 어디에 어떻게 작성해야 하는지 정해 놓았습니다.

**라이브러리 vs 프레임워크의 핵심 차이**<br>**라이브러리** = 내가 필요할 때 꺼내 쓰는 것 (내가 주도)<br>**프레임워크** = 틀이 정해져 있고 내가 그 안을 채우는 것 (틀이 주도)

## C-7. 예시 프로젝트에서의 도구 배치
[원본 이미지 제외]

예시 프로젝트에 각 도구가 어떻게 배치되는지 구체적으로 확인합니다.

이번 교육에서 진행하는 "주간 운영 현황 / 이슈 리포트 생성 서비스"에 각 도구가 어떻게 배치되는지 구체적으로 봅니다.
### 백엔드 (서버 쪽)
**Python** (프로그래밍 언어) 서버 전체를 작성하는 데 쓰이는 언어입니다. 파일 읽기, 조건 분기, 반복 처리 등 기본적인 로직을 Python 문법으로 작성합니다.
**pandas** (라이브러리) 업로드된 CSV 파일을 읽고, 컬럼을 정리하고, 수치를 계산하고, 조건에 맞는 데이터를 추출하는 작업을 담당합니다. Python 코드 안에서 필요한 시점에 불러와서 사용합니다.
**FastAPI** (프레임워크) 서버 코드의 전체 구조를 잡아 줍니다. "이 주소로 파일을 보내면 이 함수가 실행된다", "분석 결과는 이 형태로 돌려준다"와 같은 요청-응답 구조가 FastAPI의 규칙을 따릅니다. 개발자는 FastAPI가 정해 놓은 구조 안에서 pandas를 활용한 분석 로직을 채워 넣습니다.
정리하면: **Python**(언어)으로 코드를 작성하고, **pandas**(라이브러리)로 데이터를 처리하고, **FastAPI**(프레임워크)가 정해 준 구조 안에 이 코드를 배치합니다.
### 프론트엔드 (화면 쪽)
**JavaScript** (프로그래밍 언어) 브라우저에서 화면의 동작을 제어하는 언어입니다. 버튼 클릭 반응, 입력값 검증, 서버로 데이터 전송, 결과 화면 표시 등의 동작을 JavaScript 문법으로 작성합니다.
**React** (프레임워크) 화면 코드의 전체 구조를 잡아 줍니다. 파일 업로드 영역, 메모 입력 폼, 결과 카드, 경고 배지 등을 각각 독립된 컴포넌트로 나누고, 이 컴포넌트들이 어떻게 데이터를 주고받는지에 대한 구조가 React의 규칙을 따릅니다. 개발자는 React가 정해 놓은 구조 안에서 각 컴포넌트의 내용을 채워 넣습니다.
정리하면: **JavaScript**(언어)로 코드를 작성하고, **React**(프레임워크)가 정해 준 구조 안에 화면 코드를 배치합니다.

## C-8. 자주 혼동되는 개념

헷갈리기 쉬운 개념 쌍을 정리하고 층위 구분을 다시 확인합니다.

### Python과 pandas

**Python** = 언어 → **pandas** = Python으로 만든 라이브러리<br>Python이 없으면 pandas를 쓸 수 없습니다. Python만 있어도 데이터 처리는 가능하지만, 코드 양이 크게 늘어납니다.

### React와 JavaScript

**JavaScript** = 언어 → **React** = JavaScript로 만든 프레임워크<br>JavaScript가 없으면 React를 쓸 수 없습니다. JavaScript만으로도 화면을 만들 수 있지만, 프로젝트가 커지면 코드 구조가 복잡해집니다.

### Vite
Vite는 React 프로젝트를 빠르게 실행하고 빌드해주는 도구입니다. 개발 중에 코드를 수정하면 화면에 즉시 반영해 주고, 완성된 코드를 배포용으로 변환해 주는 역할을 합니다. 프레임워크나 라이브러리가 아니라 **빌드 도구**로 분류됩니다. 이번 프로젝트에서 React(Vite)라고 표기하는 이유는 React 프레임워크를 Vite 빌드 도구 위에서 실행하기 때문입니다.
