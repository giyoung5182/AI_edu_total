## 나눠 맡긴다 — 왜 나누고, 나누면 무엇을 잃는가
먼저 나누지 않는 선택지부터 봅니다.<br>AI 하나에게 세 장을 한 번에 다 쓰게 하면 어떻게 될까요.<br>생성이 길어질수록 뒷부분의 밀도가 떨어지는 것이<br>AI의 일반적인 경향입니다.

한 명이 3장 집필:   1장 ████████  2장 █████  3장 ██<br>세 명이 1장씩:         1장 ████████  2장 ████████  3장 ████████

그래서 나눕니다. 장 하나에 에이전트 하나.<br>각자 자기 장에만 온전히 집중하니 분량과 밀도가 고르게 나옵니다.
대신 잃는 것이 있습니다.<br>Ch4의 회의에서는 서버가 발언록을 배달해 서로의 말을 보게 했습니다.<br>병렬 집필에서는 배달할 것이 없습니다. 셋이 동시에 쓰기 때문입니다.<br>**1장 담당은 3장 담당이 무엇을 쓰는지 모릅니다.**<br>서로의 존재조차 모릅니다.<br>이 독립성이 속도의 원천이자, 이번 세션 전반부의 사고 원인입니다.

## 지시서 — 일을 시키기 전에 조율한다
구조의 문제는 구조로 풉니다.<br>전체를 보는 오케스트레이터를 다시 투입합니다.<br>다만 이번 문제는 Ch4와 성격이 다릅니다.<br>회의는 진행 중에 끼어들어 조율할 수 있지만,<br>병렬 집필은 셋이 동시에 쓰므로 끼어들 틈이 없습니다.<br>그래서 조율의 시점을 앞으로 당깁니다.<br>**일이 시작되기 전에, 지시서를 씁니다.**
오케스트레이터가 이끄는 집필은 다섯 단계로 진행됩니다.
```plain text
① 지시서 생성    장마다 상세 작성 지시서를 만듭니다
② 배포·집필      집필 에이전트 셋이 지시서를 받아 병렬로 씁니다
③ 취합·교차 검토  세 장을 나란히 놓고 어긋남을 점검합니다
④ 편집장 질문    사람의 결정이 필요한 사안을 물어 옵니다
⑤ 수정·완성      결정과 점검 결과를 반영해 최종본을 확정합니다
```
핵심은 ①의 지시서입니다.<br>무질서 집필에서 에이전트가 받은 것은 장 제목 한 줄이었습니다.<br>이번에는 이런 지시서를 받습니다.

\[오케스트레이터 → 3장 담당 집필 에이전트\]<br>\{<br>"task": "3장 '안전과 비상 대처' 집필",<br>"용어집": \{ "숙소": "호텔·머무는 곳 대신 이 표기로 통일" \},<br>"문체": "권유형 합니다체 산문. 소제목과 번호 목록 병용.",<br>"범위": "짐 준비와 예방 요령의 총론은 1장 담당입니다.<br>이 장은 사고가 이미 벌어진 뒤의 대처만 다룹니다.",<br>"분량": "600\~800자"<br>\}


실습 1의 세 어긋남이 지시서의 세 항목과 정확히 짝을 이룹니다.<br>범위 중복은 "범위"가, 용어 불일치는 "용어집"이,<br>문체 불일치는 "문체"가 막습니다.<br>③의 교차 검토는 그래도 새어 나간 문제를 잡는 안전망이고,<br>④는 Ch4에서 본 휴먼 인 더 루프가 여기서도 그대로 쓰이는 자리입니다.<br>용어를 무엇으로 통일할지는 기술 문제가 아니라<br>독자를 아는 사람이 정할 문제이기 때문입니다.
> ⚠️ ⑤의 수정 지시에는 "고치면 언젠가 통과한다"는 가정이<br>숨어 있습니다. 통과 기준이 지나치게 엄격하면 수정과 반려가<br>끝없이 반복될 수 있습니다. 그래서 실무의 다중 에이전트<br>시스템에는 최대 수정 횟수 제한 같은 멈춤 장치를 함께 답니다.<br>이 폭주는 실습 확장에서 직접 일으켜 볼 수 있습니다.
💡 **역할마다 모델을 다르게 배정합니다.**<br>판단이 무거운 오케스트레이터는 gemini-2.5-flash,<br>호출 횟수가 많은 집필 에이전트는 빠르고 저렴한<br>gemini-2.5-flash-lite입니다. 품질과 비용을 함께 잡는<br>실무 배정 기법이고, 유료 키를 쓰는 지금은 그대로 돈 이야기입니다.

### 실습 2. 지시서 집필 — 같은 가이드북, 다시
같은 주제로 다시 만듭니다. 이번에는 지시서가 먼저 나갑니다.<br>프롬프트에 빈칸이 하나 있습니다.<br>**지시서의 문체 규칙에 들어갈 나만의 규칙 한 줄**입니다.<br>내 규칙 하나가 세 장 전체를 통제하는 것을 확인하는 장치입니다.
**Claude Code 프롬프트**
```plain text
집필 모드를 별도 페이지로 옮겨주세요.
집필 모드에 오케스트레이터 집필을 추가해 주세요. 요구사항입니다.

1. [지시서 집필 시작] 버튼을 추가해 주세요.
   누르면 다음 단계가 순서대로 실행됩니다.

2. [지시서 생성] 오케스트레이터가
   세 장 각각의 상세 작성 지시서를 마크다운으로 만듭니다. 해당 파일을 폴더에 생성하고 대화창에는 파일 링크를 띄워주세요. 집필자는 이 파일을 열어서 내용을 확인하고 집핑을 시작합니다.
   지시서에는 반드시 포함해 주세요.
   - 용어집 (표기를 통일할 용어)
   - 문체 규칙 (합니다체 산문, 소제목과 번호 목록 병용)
     (예: 각 장의 첫 문장은 독자에게 말을 거는 질문으로
     시작할 것 / 비워 두면 추가 규칙 없음)
   - 범위 경계 (다른 장이 다룰 내용은 언급만 하고 넘어갈 것)
   - 분량 (600~800자)
   생성된 지시서 세 개를 말풍선으로 먼저 보여 주세요.

3. [집필] 집필 에이전트 셋(gemini-2.5-flash-lite)이
   각자 지시서를 받아 병렬로 장을 작성합니다. 작성한 결과를 마크다운 파일로 해당 폴더에 저장하고, 대화방에 파일 링크를 올립니다.

4. [교차 검토] 오케스트레이터가 세 장을 한 번에 읽고
   범위 중복, 용어 불일치, 문체 불일치를 점검합니다.
   점검 결과를 항목별 말풍선으로 보여 주세요.

5. [편집장 질문] 검토 중 사람의 결정이 필요한 사안이 있으면
   오케스트레이터가 질문 1개를 선택 버튼과 함께 화면에
   띄우고 내 입력을 기다립니다. 용어 표기 선택이 좋은
   예입니다. 결정이 불필요하면 이 단계는 건너뜁니다.

6. [수정·완성] 내 답과 점검 결과를 반영한 수정 지시를
   해당 장 담당에게 보내 재집필시키고, 최종본 세 장을
   무질서 버전 카드와 나란히 비교되는 화면으로 보여 주세요.

7. 모든 단계가 채팅방 말풍선과 상태 표시로 중계되고,
   서버 로그에도 한 줄씩 남게 해 주세요.
```
진행 순서

1. 빈칸에 내 규칙을 채워 프롬프트를 입력하고, 진행합니다.
2. 서버를 재시작하고 \[지시서 집필 시작\]을 누릅니다.
3. \[지시서 읽기\] 말풍선으로 올라온 지시서 하나를 골라<br>읽습니다. 용어집, 문체(내 규칙 포함), 범위, 분량<br>네 항목이 들어 있는지 확인합니다.
4. \[예측\] 실습 1에서 수집한 어긋남 중, 이 지시서가<br>막아 줄 것과 못 막을 것을 나눠 예측해 적습니다.
5. 집필과 교차 검토가 진행되는 동안 말풍선을 관전합니다.
6. \[선택\] 편집장 질문이 뜨면 버튼으로 답합니다.<br>고른 이유를 한 줄 메모해 둡니다.
7. 최종본 세 장을 처음부터 끝까지 이어 읽습니다.
8. \[확인\] 실습 1의 메모를 꺼내 항목마다 대조합니다.<br>특히 두 가지를 확인합니다.
- 6번에서 내가 정한 용어가 세 장 전체에 반영되었는가
- 프롬프트 빈칸에 넣은 내 규칙이 세 장 전체에 살아 있는가


> 💡 8번의 대조가 이번 세션의 결승선입니다.<br>"지시서가 있으니 좋아졌다"가 아니라, "내 목록의 몇 번은<br>지시서의 어느 항목이 막았고, 그중 둘은 내 결정과 내 규칙이다"<br>라고 말할 수 있으면 이 세션을 완전히 가져간 것입니다.
**FAQ**
- **Q. 편집장 질문이 안 뜹니다**
- 결정이 필요한 사안이 없다고 판단한 정상 동작일 수 있습니다. Claude Code에 "교차 검토에서 용어 표기 선택은 항상 사람에게 묻게 해 주세요"라고 요청하고 다시 실행합니다.
- **Q. 수정 후에도 일부 어긋남이 남았습니다**
- 교차 검토의 한계이며 실무에서도 생기는 일입니다. 남은 문제를 메모하고, Claude Code에 "교차 검토 항목에 ○○ 점검을 추가해 주세요"라고 요청해 봅니다.
- **Q. 내 규칙이 일부 장에만 반영되었습니다**
- Claude Code에 "지시서의 문체 규칙이 세 장 모두에 같은 내용으로 들어가는지 점검해 주세요"라고 요청합니다.
- **Q. 단계 중간에 멈췄습니다**
- 터미널 B의 마지막 로그를 Claude Code에 붙여넣어 해결을 요청합니다.
- **Q. 전체 소요가 깁니다**
- 지시서 → 집필 → 검토 → 수정의 다단계라 정상입니다. 상태 표시로 어느 단계인지 확인하며 기다립니다.

## 실습 확장 (선택)
기본 실습을 마친 분은 아래를 자유롭게 시도합니다.
- **폭주 실험 — 끝나지 않는 수정 루프**: Claude Code에<br>요청합니다. "실험용 설정 두 개를 추가해 주세요.<br>\[항상 반려 모드\]를 켜면 교차 검토가 2장을 무조건 수정 요망<br>처리합니다. \[최대 수정 횟수 제한\]을 켜면 같은 장의 수정이<br>2회를 넘을 때 '제한 도달, 현재 본으로 확정'을 선언하고<br>넘어갑니다. 수정 요망 말풍선에는 회차를 표시해 주세요."<br>제한을 끈 채 반려 모드로 실행해 회차가 쌓이는 폭주를<br>구경하고 \[중지\]로 멈춘 뒤, 제한을 켜고 다시 실행해<br>시스템이 스스로 멈추는 것을 확인합니다.<br>실험이 끝나면 반려 모드를 반드시 끕니다.
- **범위 항목 빼기**: "1장과 3장의 지시서에서 범위 항목만<br>빼고 실행하는 옵션을 추가해 주세요"라고 요청합니다.<br>범위 중복이 되살아나는지 관찰합니다.
- **4장 추가**: "4장 ○○을 목차에 추가해 주세요"라고<br>요청합니다. 오케스트레이터가 지시서 생성부터 알아서<br>확장하는지 확인합니다.
- **코드 열어 보기**: "지시서를 생성하는 오케스트레이터<br>프롬프트를 보여 주고, 어떻게 세 장의 범위를 나누는지<br>설명해 주세요"라고 요청합니다.

- 조율 없는 병렬 집필의 어긋남을 직접 수집한 목록
- 지시서·교차 검토·수정 지시로 그 어긋남을 해소한<br>오케스트레이터의 두 번째 얼굴

- 무질서 버전과 지시서 버전을 나란히 비교한 경험
