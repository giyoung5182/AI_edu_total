앞에서는 PPT 템플릿에 내용을 채워보고,<br>그 작업 방식을 SKILL로 정리해봤습니다.<br><br>이제는 동작하는 프로그램을 만들어보려고 합니다.<br><br>먼저 프로그램을 만들 때 자주 나오는<br>프론트엔드, 백엔드, 프레임워크라는 말을<br>가볍게 이해하고 넘어가겠습니다.

## 자, 그러면 이제 프로그램을 만들어볼 건데요
우리가 앞에서는 PPT를 만들었습니다.
PPT는 결과물이 파일로 딱 나오죠.
그런데 프로그램은 조금 다릅니다.
사용자가 버튼을 누르거나,<br>파일을 올리거나,<br>값을 입력했을 때<br>화면이 반응하고 결과를 보여줘야 합니다.
예를 들어<br>엑셀 파일을 올리면<br>그 내용을 웹 화면에서 표와 차트로 보여주는 도구를 만들 수 있습니다.
[원본 이미지 제외]
이번 과정 뒤쪽에서 우리가 만들 공통 실습도<br>이런 방식의 작은 웹앱입니다.
---
## 자동차로 한번 생각해보겠습니다
프로그램을 자동차라고 생각해볼게요.
[원본 이미지 제외]
자동차에는 눈에 보이는 부분이 있습니다.
차 문, 창문, 핸들, 계기판, 좌석처럼<br>우리가 직접 보고 만지는 부분이 있죠.
그리고 눈에 잘 보이지는 않지만<br>자동차를 실제로 움직이게 하는 부분도 있습니다.
엔진, 배터리, 배선, 제어장치 같은 것들입니다.
프로그램도 비슷하게 나눠볼 수 있습니다.
### 자동차 비유
```plain text
자동차 외관과 계기판
→ 사용자가 직접 보는 부분
→ 프론트엔드

엔진과 내부 장치
→ 뒤에서 실제로 동작하는 부분
→ 백엔드
```
---
## 프론트엔드
프론트엔드는<br>사용자가 직접 보는 화면입니다.
버튼, 입력창, 표, 차트, 파일 업로드 영역처럼<br>눈에 보이고 클릭할 수 있는 부분이라고 생각하시면 됩니다.
우리가 엑셀 대시보드를 만든다면<br>이런 것들이 프론트엔드에 해당합니다.
### 프론트엔드 예시
```plain text
- 엑셀 업로드 버튼
- 데이터 표
- 매출 차트
- 필터 선택창
- 다운로드 버튼
```
쉽게 말하면<br>사용자가 보는 화면 쪽입니다.
---
## 백엔드
백엔드는<br>사용자 눈에는 잘 보이지 않지만<br>뒤에서 실제 처리를 담당하는 부분입니다.
예를 들어<br>데이터를 저장하거나,<br>로그인을 확인하거나,<br>여러 사람이 같은 데이터를 볼 수 있게 관리하거나,<br>외부 API를 호출하는 작업이 여기에 들어갑니다.
### 백엔드 예시
```plain text
- 로그인 처리
- 데이터베이스 저장
- 사용자 권한 확인
- 외부 API 호출
- 여러 사람의 데이터 관리
```
그러니까 프론트엔드가 화면이라면,<br>백엔드는 그 화면 뒤에서 움직이는 기능이라고 보면 됩니다.
[원본 이미지 제외]
---
## 참고 사항
여기서 한 가지를 짚고 가겠습니다.
이번 공통 실습에서는 백엔드를 빼도 됩니다
우리가 뒤에서 만들 엑셀 대시보드는<br>엑셀 파일을 서버에 저장하지 않습니다.
로그인도 만들지 않습니다.<br>데이터베이스도 쓰지 않습니다.<br>AI API도 연결하지 않습니다.
그냥 사용자가 올린 엑셀 파일을<br>브라우저 안에서 읽고,<br>바로 표와 차트로 보여줄 겁니다.
그래서 이 공통 실습은<br>프론트엔드만으로도 충분합니다.

이번 실습에서는 백엔드를 억지로 만들지 않습니다.<br><br>필요 없는 구조를 넣으면<br>수업이 더 복잡해지고,<br>오히려 핵심이 흐려질 수 있습니다.

### 백엔드가 필요해지는 경우
```plain text
- 데이터를 서버에 저장해야 할 때
- 여러 사용자가 같은 데이터를 함께 봐야 할 때
- 로그인과 권한 관리가 필요할 때
- AI API나 외부 API를 안전하게 호출해야 할 때
- 데이터베이스를 사용해야 할 때
```
이런 상황이 되면 그때 백엔드를 붙이면 됩니다.

## 프레임워크는 코드를 정리하는 규칙입니다
이번에는 프레임워크라는 말을 보겠습니다.
[원본 이미지 제외]
자동차를 만든다고 할 때<br>바퀴는 아래에 달고,<br>핸들은 운전석 앞에 있고,<br>엔진은 정해진 위치에 들어가야겠죠.
이런 기본 구조가 없으면<br>일단 굴러가긴 해도<br>나중에 기능을 추가하기가 어려워집니다.
[원본 이미지 제외]
프로그램도 마찬가지입니다.
파일을 어디에 두고,<br>화면은 어디에서 만들고,<br>데이터 처리는 어디에서 할지<br>정해진 구조가 있으면 작업이 훨씬 편해집니다.
[원본 이미지 제외]
이런 구조를 잡아주는 도구나 방식이<br>프레임워크라고 보면 됩니다.
[원본 이미지 제외]
### 프레임워크를 쓰는 이유
```plain text
- 파일 구조를 정리하기 쉽다
- AI가 프로젝트를 이해하기 쉽다
- 기능을 추가하기 쉽다
- 오류를 찾기 쉽다
- 나중에 배포하기 좋다
```

## 웹앱 구조
뒤쪽 공통 실습에서는<br>React + Vite라는 구조로 웹앱을 만들 예정입니다.
지금 이 이름을 외울 필요는 없습니다.
일단은 이렇게 생각하시면 됩니다.
```plain text
React
→ 화면을 만들기 위한 도구

Vite
→ 개발 서버를 빠르게 실행하고 프로젝트를 관리하기 위한 도구
```
Claude Code에게 요청할 때는<br>이렇게 말하면 됩니다.
### 요청 예시
```plain text
프론트엔드는 React + Vite로 만들어주세요.
백엔드는 FastAPI로 만들어주세요.
프론트엔드, 백엔드 서버 실행은 run.bat으로 실행할 수 있도록 해주세요.

엑셀 파일은 브라우저에서 직접 읽고,
표와 차트로 보여주는 웹앱으로 만들어주세요.
```
[원본 이미지 제외]
```plain text
프론트엔드는 React + Vite로 만들어주세요.
이번 실습은 백엔드 없이 진행합니다.
프론트엔드 서버 실행은 run.bat으로 실행할 수 있도록 해주세요.

엑셀 파일은 브라우저에서 직접 읽고,
표와 차트로 보여주는 웹앱으로 만들어주세요.
```

