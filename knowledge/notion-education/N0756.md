# 4️⃣ 부록 D. AI와 일하는 순서: 구상 / 계획 / 실행 / 검토

정리일: 2026-10-08 · 교육 에셋 N0756

본문 수집·공개 편집. 도구 실행·최신 기능 재검증은 미실시. 고객·참여자 정보와 개별 접근 링크, 원본 첨부는 제외했습니다.

---

AI에게 일을 시킬 때도 업무를 할 때와 같은 순서가 필요합니다. 구상 → 계획 → 실행 → 검토, 이미 하고 있는 순서를 AI에게도 똑같이 적용하면 결과가 달라집니다.

---
## D-1. 업무 지시를 받았을 때 우리가 하는 순서
[원본 이미지 제외]

팀장이 "이번 주 운영 현황 보고서 좀 만들어봐"라고 했다고 합시다.
이 말을 듣고 바로 엑셀을 여는 사람은 거의 없습니다. 머릿속에서 자연스럽게 몇 가지를 먼저 따져봅니다.

먼저 무슨 내용이 들어가야 하는지 확인합니다 — **구상**


데이터를 어디서 가져오고 어떤 순서로 정리할지 정합니다 — **계획**


실제로 데이터를 뽑고 보고서를 씁니다 — **실행**


다 쓰고 나서 빠진 것 없는지, 수치가 맞는지 확인합니다 — **검토**

**1) 먼저 무슨 내용이 들어가야 하는지 확인합니다.** 누가 볼 건지, 어떤 수치가 필요한지, 범위가 어디까지인지 파악합니다. 임원 보고용이면 핵심 수치 위주로, 팀 내부 공유용이면 상세 데이터가 더 들어가야 합니다. 이것이 **구상**입니다.
**2) 데이터를 어디서 가져오고, 어떤 순서로 정리할지 정합니다.** ERP에서 뽑을 것, 공유 폴더에서 가져올 것, 담당자한테 물어볼 것을 나누고, 보고서 목차를 대략 잡습니다. 이것이 **계획**입니다.
**3) 실제로 데이터를 뽑고 보고서를 씁니다.** 수치를 정리하고, 표를 만들고, 이슈를 적고, 요약을 붙입니다. 이것이 **실행**입니다.
**4) 다 쓰고 나서 빠진 것 없는지, 수치가 맞는지 확인합니다.** 지난주 보고서와 비교해서 빠진 항목은 없는지, 합계가 맞는지, 이상한 문장은 없는지 훑어봅니다. 이것이 **검토**입니다.
이 순서는 특별한 방법론이 아닙니다. 업무를 할 때 이미 하고 있는 것입니다. 보고서뿐 아니라 기획안, 제안서, 회의 자료를 만들 때도 비슷한 흐름을 따릅니다. 별도로 배운 적이 없어도 경험이 쌓이면서 자연스럽게 몸에 붙은 순서입니다.

## D-2. AI에게 일을 시킬 때 흔히 빠지는 실수
[원본 이미지 제외]

AI에게 일을 시킬 때 업무 순서를 생략하면 어떤 일이 벌어지는지 확인합니다.

그런데 같은 사람이 AI에게 같은 업무를 시킬 때는 이 순서를 생략합니다.
"운영 현황 보고서 만들어줘."
이 한 문장으로 끝내는 경우가 많습니다. 누가 볼 건지 안 알려주고, 어떤 수치가 핵심인지 안 정하고, 어디까지 만들지 범위도 안 정합니다. 계획도 없이, 단계도 나누지 않고, 한 번에 전부 맡깁니다.
이것은 신입사원에게 "보고서 만들어놔"라고 말해놓고 아무런 맥락 없이 완벽한 결과를 기대하는 것과 비슷합니다. 경험 많은 직원이라면 이런 상황에서 되물어볼 것입니다. "어떤 형태로 드릴까요?" "지난주 양식 그대로 할까요?" 하지만 AI는 되묻지 않고 바로 만들기 시작합니다. 그리고 자기가 판단한 대로 채워 넣습니다.
## D-3. 순서 없이 시켰을 때 생기는 문제

**순서 없이 시키면 AI가 빈자리를 자기 판단으로 채웁니다.** 그 결정이 내가 원하는 방향과 다를 수 있고, 수정을 반복할수록 기준점 없이 결과가 흔들립니다.

AI는 지시에 빠진 부분을 스스로 결정합니다. 문제는 그 결정이 내가 원하는 방향과 다를 수 있다는 것입니다.
**AI가 알아서 정해버리는 것들:**

보고서 대상을 모르니까 일반적인 구성으로 만듭니다.


핵심 수치를 모르니까 전부 나열합니다. 정작 중요한 지표가 묻혔니다.


범위를 모르니까 필요 이상으로 확장합니다.


이슈 기준을 모르니까 자기가 만들어 넣습니다. 그 기준이 우리 팀에 안 맞습니다.

결과물을 받아보면 그럴듯해 보입니다. 형식도 갖추어져 있고 문장도 매끄럽습니다. 하지만 막상 팀장에게 가져갈 수 있는 상태는 아닙니다.
**수정을 시작하면 더 꼬입니다.**
"이 부분은 빼고, 이 수치를 위로 올리고, 경고는 따로 분리해줘."
이렇게 수정을 요청하면 AI가 전체를 다시 고칩니다. 그런데 처음에 방향이 안 잡혀 있었기 때문에, 고칠 때마다 다른 부분이 같이 바뀝니다. 한번은 수치 순서가 바뀌고, 한번은 요약 톤이 바뀌고, 한번은 항목 개수가 줄어들어 있습니다. 기준점이 없으니 수정할수록 흔들리는 것입니다.
결국 여러 번 고치다가 "그냥 내가 처음부터 다시 쓰는 게 낫겠다"는 결론에 이릅니다.
## D-4. 같은 순서를 AI에게도 적용하기

업무에서 이미 하고 있는 순서를 AI에게도 똑같이 적용하는 방법을 확인합니다.

해결 방법은 의외로 단순합니다. 업무할 때 이미 하고 있는 순서를 AI에게도 똑같이 적용하면 됩니다.
사람에게 일을 시킬 때 하던 것을 AI에게도 하면 됩니다.
- 보고서를 만들기 전에, 뭘 넣을지 먼저 정리해서 알려줍니다 → **구상**
- 어떤 순서로 진행할지, 어디까지 할지 범위를 잡아서 알려줍니다 → **계획**
- 한 번에 다 시키지 않고, 단계별로 나누어 요청합니다 → **실행**
- 받은 결과를 확인하고, 부족한 부분을 기록합니다 → **검토**
D-2에서 한 줄로 시켰던 것을 이 네 단계로 나누어 시키면, 수정 횟수가 줄어들고 결과 품질이 올라갑니다. 새로 배워야 할 것이 아니라, 이미 하고 있는 것을 AI에게도 적용하는 것뿐입니다.
아래에서 각 단계를 예시 프로젝트에 대입해서 하나씩 살펴봅시다.
## D-5. 구상: 무엇을 만들지 정리하기
[원본 이미지 제외]

구상 단계에서 정리해야 할 여섯 가지 항목을 예시 프로젝트에 대입해 봅니다.

구상 단계에서는 여섯 가지를 정리합니다. 무엇을 만들지, 누가 쓰는지, 무엇이 들어오고 나가는지, 어디까지 만들지, 아직 정해지지 않은 것은 무엇인지 적습니다.
예시 프로젝트(주간 운영 현황 / 이슈 리포트 생성 서비스)를 기준으로 채워보면 아래와 같습니다.
**1) 문제** 매주 운영 수치를 수작업으로 정리하는 데 시간이 오래 걸린다.
**2) 사용자** 운영팀 담당자
**3) 입력** 주간 운영 CSV 파일 + 담당자가 적은 메모
**4) 출력** 핵심 수치 / 주요 이슈 / 경고 / 권장 조치 / 짧은 요약
**5) 범위** CSV 한 파일 기준으로, 결과가 화면에 나오는 것까지
**6) 애매한 부분** 경고 기준을 누가 정하는가? 관리자가 직접 기준값을 입력하는 것인지, 데이터에서 자동으로 잡는 것인지 아직 정해지지 않았다.
이 여섯 가지가 빠짐없이 적혀 있으면 AI에게 전달할 때 방향이 확실해집니다. 반대로 이 중 하나라도 비어 있으면, AI가 빈자리를 자기 판단으로 채웁니다. D-3에서 본 문제가 여기서 시작됩니다.
이것만 적혀 있어도 AI가 엉뚱한 방향으로 가는 것이 크게 줄어듭니다.

## D-6. 계획: 만드는 순서와 구조 잡기

구상을 어떻게 쪤개서 만들지 — 순서, 파일 구조, 역할 분담, 테스트 준비를 정합니다.

구상에서 적은 것을 어떻게 쪼개서 만들지 정하는 단계입니다.
계획 단계에서 잡아야 할 것은 네 가지입니다.
**1) 만드는 순서** 어디부터 시작할지 정합니다. 예시 프로젝트에서는 아래 순서로 진행합니다.
1. 백엔드 응답 구조 정의 — JSON에 어떤 항목이 들어갈지 먼저 잡습니다
2. 백엔드 CSV 읽기와 수치 계산 — 파일을 읽고 핵심 수치를 뽑습니다
3. 백엔드 이슈 추출과 요약 생성 — 이슈, 경고, 조치, 요약을 만듭니다
4. 프론트 업로드 화면 — 파일과 메모를 입력받는 화면을 만듭니다
5. 프론트 결과 화면과 API 연결 — 백엔드 응답을 화면에 표시합니다
6. 전체 연결 테스트 — 업로드부터 결과 표시까지 한 번에 돌려봅니다
백엔드부터 시작하는 이유가 있습니다. 화면을 먼저 만들면 데이터 구조가 정해지기 전에 화면을 짜게 되고, 나중에 백엔드 응답 형태가 바뀌면 화면도 같이 고쳐야 합니다. 데이터 구조를 먼저 잡아 두면 프론트에서 그 구조에 맞추어 화면을 만들면 되니까 수정이 줄어듭니다.
**2) 파일 구조**
```plain text
project/
  frontend/        ← React(Vite)
    src/
    package.json
  backend/         ← FastAPI
    app/
    main.py
    requirements.txt
  data/
    sample/        ← 테스트용 CSV
  start.bat
```
**3) 프론트/백 역할 분담**
- 프론트: 파일 업로드, 메모 입력, 결과 표시
- 백엔드: CSV 읽기, 수치 계산, 이슈 추출, 요약 생성, JSON 응답
**4) 테스트 준비**
- 샘플 CSV 파일을 data/sample/ 폴더에 미리 준비합니다
- 메모 예시 문장을 두세 줄 적어둡니다
- 각 단계마다 확인 기준을 정해둡니다 (예: "응답 JSON에 다섯 가지 항목이 모두 있는가")
이렇게 순서와 구조가 적혀 있으면, AI에게 요청할 때 "1번부터 해주세요"라고 말할 수 있습니다. 전체를 한꺼번에 던지는 것과 단계를 지정해서 주는 것은 결과 차이가 큽니다.
## D-7. 실행: AI에게 단계별로 요청하기
[원본 이미지 제외]

AI에게 한 번에 전부 시키지 않고, 단계별로 요청하고 확인하는 방법을 엵니다.

실행 단계에서 가장 중요한 원칙은 한 번에 전부 시키지 않는 것입니다.
D-6에서 정한 순서대로, 한 단계씩 요청하고, 결과를 확인한 뒤에 다음 단계로 넘어갑니다. 이 확인 과정이 빠지면 D-3에서 본 문제가 다시 생깁니다.
**요청 흐름 예시:**
1. 응답 구조를 먼저 요청합니다 → AI가 보여주면 항목이 맞는지 확인합니다
2. CSV 읽기와 계산을 요청합니다 → 샘플 데이터로 수치가 맞는지 확인합니다
3. 이슈 추출과 요약을 요청합니다 → 내용이 데이터와 맞는지 확인합니다
4. 프론트 화면을 요청합니다 → 화면이 뜨는지 확인합니다
5. 연결을 요청합니다 → 업로드부터 결과까지 한 번에 돌아가는지 확인합니다
각 단계에서 AI가 내 의도와 다르게 만들었으면, 그 자리에서 바로 잡습니다. 다음 단계로 넘어간 뒤에 돌아오면 고치기가 더 어렵습니다.
아래는 첫 번째 단계를 요청하는 예시입니다.
```plain text
지금부터 백엔드 API를 만들어 주세요.
프레임워크는 FastAPI입니다.

먼저 분석 응답 JSON 구조부터 정리해 주세요.
응답에는 아래가 들어가야 합니다.
- 핵심 수치 (총 건수, 평균, 전주 대비 변화)
- 주요 이슈 (목록)
- 경고 항목 (목록)
- 권장 조치 (목록)
- 짧은 요약 (1~2문장)

전체 코드를 한 번에 쓰지 말고, 응답 구조만 먼저 보여 주세요.
```
이 요청에는 세 가지가 들어 있습니다.
- **무엇을 할지** — 백엔드 API, FastAPI
- **지금 단계에서 할 것** — 응답 JSON 구조 정리
- **하지 말아야 할 것** — 전체 코드를 한 번에 쓰지 말 것
"하지 말아야 할 것"을 적어주는 것이 중요합니다. 이것이 없으면 AI는 응답 구조와 함께 전체 코드까지 한 번에 만들어버리는 경우가 많습니다. 그러면 확인 없이 넘어가게 되고, 나중에 돌아와서 고치기 어려워집니다.
AI가 응답 구조를 보여주면, 항목이 맞는지 확인하고 괜찮으면 "좋습니다. 다음으로 CSV 파일 읽기를 만들어 주세요."라고 다음 단계를 요청합니다.
## D-8. 검토: 결과를 확인하고 기록하기

결과를 직접 돌려보고, 흔들리는 부분을 네 영역으로 나누어 기록합니다.

실행이 끝나면 직접 돌려봅니다.
**확인하는 순서:**
1. 프론트와 백엔드가 실행되는지 확인합니다
2. 샘플 CSV를 올려서 결과가 나오는지 확인합니다
3. 결과 수치가 맞는지 CSV를 열어서 한두 개를 직접 대조합니다
4. 다섯 가지 항목(핵심 수치, 주요 이슈, 경고, 권장 조치, 요약)이 모두 나오는지 확인합니다
**흔들리는 부분을 적어둡니다.**
결과가 완벽하게 나오는 경우는 거의 없습니다. 검토할 때 발견한 문제를 네 영역으로 나누어 기록합니다.

**화면**

항목 순서가 자연스러운가?




"빈 값이 절반 넘으면 평균이 이상하게 나온다", "경고가 세 개 넘으면 화면이 밀린다" 같은 구체적인 메모를 남겨둡니다. 이 메모가 있으면 다음에 AI에게 수정을 요청할 때도 방향이 뚜렷해집니다. "경고가 세 개 넘을 때 화면이 밀리지 않게 고쳐주세요"라고 말할 수 있기 때문입니다.
이 메모가 다음 개선의 출발점입니다.

## D-9. 네 단계 요약

구상/계획/실행/검토 네 단계를 한눈에 정리합니다.


네 단계를 한눈에 정리하면 아래와 같습니다.






단계

핵심 질문

산출물




**구상**

무엇을 만들 것인가

문제, 사용자, 입력, 출력, 범위 정리




**계획**

어떤 순서로 만들 것인가

구현 순서, 파일 구조, 역할 분담




**실행**

AI에게 어떻게 요청할 것인가

동작하는 코드




**검토**

결과가 맞는가

검증 결과, 흔들리는 부분 메모


네 단계가 특별해 보이지 않는 것이 맞습니다. 업무를 할 때 이미 하고 있는 순서이기 때문입니다.
차이는 이 순서를 AI에게도 적용하느냐, 건너뛰느냐에 있습니다. 구상 없이 시키면 AI가 방향을 알아서 정합니다. 계획 없이 시키면 AI가 순서를 알아서 정합니다. 검토 없이 넘어가면 문제가 쌓입니다. 반대로 이 네 단계를 챙기면, AI가 내가 원하는 방향으로 움직이는 것을 직접 확인할 수 있습니다.
## D-10. 다른 업무에의 적용

예시 프로젝트 외에도 같은 순서를 적용할 수 있는 업무 예시를 확인합니다.

이 네 단계는 예시 프로젝트에만 해당하는 것이 아닙니다. 업무에서 자주 만나는 다른 상황에도 같은 순서를 적용할 수 있습니다.
<details color="gray_bg">
<summary>📊 월간 운영 요약 생성</summary>
구상에서 월간 데이터 범위와 요약 수준을 정합니다. 계획에서 주차별 비교 항목을 잡고, 실행에서 주차별 데이터 읽기 → 추세 계산 → 요약 생성 순서로 나누어 요청합니다. 검토에서 추세 방향이 실제 수치와 맞는지 대조합니다.
</details>
<details color="gray_bg">
<summary>📋 VOC 이슈 정리</summary>
구상에서 VOC 데이터 형식과 분류 기준을 정합니다. 계획에서 분류 → 빈도 집계 → 상위 이슈 추출 순서를 정합니다. 실행에서 한 단계씩 요청하고, 검토에서 VOC 원문과 분류 결과를 대조합니다.
</details>
<details color="gray_bg">
<summary>👥 팀별 상태 리포트</summary>
구상에서 어떤 팀의 어떤 지표를 볼지 정합니다. 실행에서 팀 하나를 기준으로 먼저 만들고, 확인되면 나머지 팀으로 확장합니다. 검토에서 팀 간 수치가 비교 가능한 형태인지 확인합니다.
</details>
업무가 달라져도 구상 → 계획 → 실행 → 검토 순서는 비슷하게 남습니다. 달라지는 것은 각 단계에서 채우는 내용뿐입니다.

**체크포인트**<br>- 구상, 계획, 실행, 검토 네 단계를 구분할 수 있습니다.<br>- AI에게 한 번에 시키면 왜 문제가 생기는지 설명할 수 있습니다.<br>- 각 단계에서 무엇을 정리해야 하는지 알고 있습니다.<br>- 이 순서를 다른 업무에도 적용할 수 있습니다.
