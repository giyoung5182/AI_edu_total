## 📋 목차

## 이번 세션에서 할 일
지금 우리 서비스의 AI는 언제나 혼자 일합니다.<br>질문 하나가 들어오면 검색하고, 답 하나를 만들어 돌려줍니다.<br>한 번에 한 명, 한 가지 일. 지금까지는 이걸로 충분했습니다.
이번 세션에서는 AI를 한 방에 둘 이상 넣습니다.<br>그런데 이 둘은 서로 원하는 것이 다릅니다.<br>한쪽은 빨리 출시하고 싶고, 한쪽은 더 다듬고 싶습니다.<br>사람의 회사에서 매주 벌어지는 그 장면을,<br>AI들의 단체 채팅방에서 그대로 관전합니다.<br>싸움을 붙이고, 안 끝나는 것을 확인하고,<br>회의를 끝내는 존재를 투입합니다.<br>그리고 마지막 결정은 우리가 내립니다.
이번 세션에서 우리가 하는 일은 세 가지입니다.

1. 입장이 다른 팀장 둘을 회의방에 넣고 싸움을 붙입니다.<br>사회자 없는 회의가 어떻게 흘러가는지 관전합니다.
2. 회의를 진행하는 관리자 AI, 오케스트레이터를 본부장으로<br>투입합니다. 본부장의 속마음까지 화면에서 지켜봅니다.
3. 본부장이 결정을 물어 오면 결정권자로서 답하고,<br>내 결정이 박힌 결정문을 받습니다. 결정문이 마음에 안 들면<br>직접 뜯어고칩니다.


> 💡 이번 세션의 핵심은 "지켜보는 재미"입니다.<br>개발이 끝날 때마다 실행하고, 말풍선이 올라오는 것을 관전하고,<br>갈림길에서 선택하면 이야기가 그쪽으로 흘러갑니다.<br>그 재미 속에 멀티 에이전트의 핵심 기술이 전부 들어 있습니다.

## 에이전트 — 역할과 입장을 부여받은 AI 호출
여러 AI가 함께 일할 때, 그 하나하나를 에이전트(Agent)라고 부릅니다.<br>실체는 단순합니다. 역할 지시가 붙은 AI 호출 한 단위입니다.<br>같은 Gemini라도 앞에 붙는 지시문이 다르면 전혀 다른 인물이 됩니다.<br>이 지시문을 브리프(brief)라고 부르겠습니다.
이번 회의에 참석할 영업팀장의 브리프 실물입니다.

\[영업팀장 브리프\]<br>역할: 신제품 담당 영업팀장<br>지키려는 것: 다음 달 출시. 이미 잡힌 고객 미팅과 분기 매출 목표<br>양보하기 어려운 것: 출시 연기<br>말투: 짧은 구어체. 상대 발언을 직접 인용해 받아친다.<br>수주 건수, 예상 매출 같은 구체적인 숫자를 근거로 든다.


개발팀장의 브리프는 "지키려는 것"이 품질과 안정성으로,<br>"양보하기 어려운 것"이 미완성 출시로 바뀝니다.<br>브리프 세 줄이 다를 뿐인데, 두 호출은 회의에서 정반대로 움직입니다.
한 가지 기술적 사실을 짚어 둡니다.<br>**각 에이전트의 호출은 서로 독립된 대화입니다.**<br>영업팀장 호출은 개발팀장이 방금 뭐라고 했는지 저절로 알지 못합니다.<br>우리 서버가 지금까지의 발언록을 매 호출에 함께 넣어 주기 때문에<br>상대의 말을 받아치는 회의가 성립합니다.<br>말풍선 뒤에서 서버가 발언록 배달부로 일하는 셈입니다.

### 실습 1. 회의방을 만들고, 싸움을 붙인다
회의방 페이지를 만들고, 사회자 없이 두 팀장만 넣어 회의를 시킵니다.<br>안건은 하나로 고정합니다.<br>**"신제품, 다음 달 출시 강행이냐, 3개월 연기냐."**
작업 시작 전에 터미널 A의 Claude Code에서 `/clear`를 실행합니다.
프롬프트를 조립합니다. 빈칸은 두 팀장의 이름입니다.<br>성 뒤에 직책을 붙여 부르면 회의 맛이 삽니다.
**Claude Code 프롬프트**
```plain text
AI들이 회의하는 단체 채팅방 페이지를 만들어 주세요. 요구사항입니다.

1. /meeting 경로에 새 페이지를 만들고,
   상단 메뉴바에 "회의방" 메뉴를 추가해 주세요.

2. 회의 참석자는 AI 에이전트 두 명입니다. 모델은 둘 다
   gemini-2.5-flash를 사용합니다.
   - 영업팀장 (이름: ______ / 비워 두면 "강 팀장")
     지키려는 것: 다음 달 출시, 고객 미팅과 분기 매출 목표.
     양보하기 어려운 것: 출시 연기.
   - 개발팀장 (이름: ______ / 비워 두면 "서 팀장")
     지키려는 것: 제품 품질과 안정성. 미해결 버그 처리.
     양보하기 어려운 것: 미완성 상태의 출시.
   두 사람의 말투 공통 지시입니다: 짧은 구어체 문장.
   상대의 직전 발언을 직접 인용해 받아친다. 수주 건수,
   버그 개수, 예상 매출 같은 구체적인 숫자를 지어내서라도
   근거로 제시한다. 절대 먼저 물러서지 않는다.

3. 안건은 "신제품을 다음 달에 출시 강행할 것인가,
   3개월 연기할 것인가"로 고정합니다.

4. [회의 시작] 버튼을 누르면 두 팀장이 번갈아 발언합니다.
   서버는 매 호출에 지금까지의 발언록 전체를 전달해,
   서로의 발언을 받아칠 수 있게 해 주세요.
   발언 4라운드(총 8회)가 지나면 "정해진 라운드가 끝났습니다"
   라는 시스템 메시지와 함께 회의를 그냥 종료해 주세요.
   합의 여부는 판정하지 않습니다.

5. 화면 구성입니다.
   - 상단: 참석자 이름표와 상태 표시(대기/발언 중/종료)
   - 중앙: 말풍선 스트림. 발언자 이름과 시각이 붙고,
     두 사람의 말풍선 색을 다르게 해 주세요.
     새 발언이 1초 간격 폴링으로 실시간 반영되게 해 주세요.
   - 하단: [회의 시작] 버튼과 [중지] 버튼.
     중지는 진행 중인 회의를 즉시 멈춥니다.

6. 서버 로그에 발언 한 건당 한 줄(발언자, 요지)이 남게 해 주세요.
```

## 우리가 본 것 정리 — 회의는 저절로 끝나지 않는다
발언록에는 정보가 쌓였습니다. 그런데 결론이 없습니다.<br>원인을 발언록에서 직접 확인했습니다.
두 사람 모두 자기 입장의 대변인일 뿐,<br>**회의 전체를 책임지는 사람이 없습니다.**<br>쟁점을 정리하는 사람도, 근거를 검증하는 사람도,<br>"이제 결정합시다"라고 말하는 사람도 없습니다.<br>라운드가 소진되어 멈췄을 뿐, 회의가 끝난 것이 아닙니다.
전제 불일치도 같은 원인입니다.<br>버그가 30건인지 몇 건인지 아무도 확인을 시키지 않으니,<br>각자 자기에게 유리한 숫자 위에서 말합니다.<br>반박은 오가지만 논의는 앞으로 가지 않습니다.
빠진 것은 발언자가 아니라 진행자입니다.

## 오케스트레이터 — 회의를 진행하고 끝내는 관리자
[원본 이미지 제외]
전체를 보며 조율하는 관리자 에이전트를 **오케스트레이터(Orchestrator)**라고 부릅니다.<br>이번 회의에서는 본부장 역할입니다. 본부장은 자기 입장을 주장하지 않습니다.<br>**쟁점을 정리하고, 발언을 배정하고, 근거를 확인시키고, 결정이 필요한 순간에 결정권자를 부릅니다.**
본부장이 진행하는 회의는 여섯 단계로 흘러갑니다.

① 쟁점 정리     안건을 선택지가 분명한 형태로 정식화합니다<br>② 입장 발표     각 팀장에게 근거를 갖춘 입장문을 요구합니다<br>③ 반박 라운드   정해진 횟수만큼 반박과 재반박을 진행시킵니다<br>근거가 부족하면 확인 숙제를 배정합니다<br>④ 쟁점 분리     합의된 것과 끝내 갈린 것을 나눠 정리합니다<br>⑤ 결정권자 호출  갈린 쟁점의 최종 결정을 사람에게 묻습니다<br>⑥ 결정문 작성   결정을 반영한 최종 결정문을 냅니다

⑤가 이 구조의 중요한 설계입니다.<br>스스로 정해도 되는 것은 AI가 정하고,<br>판단이 필요한 것만 사람에게 올라옵니다.<br>AI에게 전부 맡기는 것도, 사람이 전부 하는 것도 아닌<br>이 협업 형태를 \*\*휴먼 인 더 루프(Human-in-the-loop)\*\*라고 부릅니다.<br>이번 회의의 결정권자는 우리 자신입니다.
그리고 이번 구현에는 장치를 하나 더 답니다.<br>본부장이 다음 진행을 정하기 전에 떠올리는 생각을<br>**속마음 말풍선**으로 화면에 공개합니다.
```php
일반 발언      본부장  14:22:31
│ 서 팀장, 버그 30건의 심각도 분포를 보고해 주세요.

속마음         본부장  14:22:30   (회색, 혼잣말 표시)
│ (양쪽 다 숫자가 붙었지만 검증된 건 없군.
│  매출 손실보다 출시 후 사고가 더 뼈아플 텐데...)
```
오케스트레이터의 실체는 "판단하는 프롬프트"입니다.<br>평소에는 그 판단이 로그 속에 숨어 있습니다.<br>속마음을 꺼내 보이면, 관리자 AI가 매 순간<br>무엇을 저울질하는지 처음으로 눈에 보입니다.

### 실습 2. 본부장 투입 — 회의를 끝까지 진행시킨다
같은 안건으로 회의를 다시 엽니다. 이번에는 본부장이 있습니다.<br>프롬프트를 조립합니다. 이번 선택은 본부장의 성향입니다.<br>아래 두 블록 중 하나를 골라 \[성향 블록\] 자리에 붙입니다.
**Claude Code 프롬프트**
```php
회의방에 본부장 진행 모드를 추가해 주세요. 요구사항입니다.

1. [본부장 회의 시작] 버튼을 추가해 주세요. 누르면 본부장
   에이전트(gemini-2.5-flash)가 회의를 진행합니다.
   본부장의 성향입니다.
   [성향 블록]

2. 회의는 다음 단계로 진행됩니다.
   ① 본부장이 안건을 "강행 vs 연기" 선택지로 정식화해
      발표합니다.
   ② 두 팀장이 근거를 갖춘 입장문을 발표합니다.
   ③ 반박 라운드 2회를 진행합니다. 라운드 사이에 본부장이
      근거가 약한 쪽을 짚어, 결정권자(사용자)에게 화면으로
      묻습니다: "누구에게 확인 숙제를 줄까요?"
      선택지 두 개를 버튼으로 제시합니다.
      (예: 개발팀장에게 버그 심각도 보고 /
      영업팀장에게 고객 이탈 예측 보고)
      선택된 팀장이 다음 발언에서 그 숙제를 보고합니다.
   ④ 본부장이 합의된 지점과 끝내 갈린 쟁점을 나눠 정리합니다.
   ⑤ 본부장이 갈린 쟁점의 최종 결정을 결정권자에게 묻습니다.
      [강행] [연기] 버튼을 화면에 제시하고 입력을 기다립니다.
   ⑥ 결정을 반영한 최종 결정문을 말풍선으로 발표합니다.

3. 본부장이 발언하기 직전마다, 진행 판단의 속마음을
   한두 문장으로 생성해 별도 말풍선으로 표시해 주세요.
   속마음 말풍선은 회색 바탕에 혼잣말 표시를 붙여
   일반 발언과 뚜렷이 구분되게 해 주세요.

4. 결정권자 질문 말풍선은 버튼 입력칸이 함께 뜨고,
   내 선택이 답장 말풍선으로 올라가게 해 주세요.

5. 상태 표시에 본부장을 추가하고, 서버 로그에는 속마음을
   포함한 모든 발언이 한 줄씩 남게 해 주세요.
```
**성향 블록 — 하나를 골라 \[성향 블록\] 자리에 붙입니다**
**\[A\]**
```plain text
── 신중형 본부장 ──────────────────────
데이터 없이는 움직이지 않는 성향입니다. 근거가 약한 발언에는
반드시 확인을 요구하고, 속마음에도 숫자 걱정이 자주 나옵니다.
```
**\[B\]**
```plain text
── 결단형 본부장 ──────────────────────
회의가 길어지는 것을 싫어하는 성향입니다. 논점을 빠르게
좁히고 결정을 재촉하며, 속마음에 "이쯤이면 됐다"는
판단이 자주 나옵니다.
```
진행 순서

1. 성향 블록을 골라 조립한 프롬프트를 입력하고, 진행합니다.
2. 서버를 재시작하고 \[본부장 회의 시작\]을 누릅니다.
3. 관전합니다. 실습 1과 같은 안건, 같은 팀장들이지만<br>진행이 어떻게 다른지 지켜봅니다. 특히 속마음 말풍선과<br>그 직후의 실제 발언을 짝지어 읽습니다.
4. \[선택\] 확인 숙제 질문이 뜨면 둘 중 하나를 고릅니다.<br>다음 발언에서 그 보고가 실제로 나오는지 확인합니다.
5. \[선택\] 최종 결정 질문이 뜨면 \[강행\] 또는 \[연기\]를<br>누릅니다. 누르기 전에, 어느 쪽이든 고른 이유를<br>한 줄로 메모해 둡니다.
6. 결정문을 읽습니다. 내 결정이 어떻게 반영되었는지,<br>결정에서 진 쪽의 우려는 어떻게 다뤄졌는지 살핍니다.
7. 실습 1의 체크리스트를 꺼내, 평행선·전제 불일치·결론 부재가<br>각각 어느 단계에서 해소되었는지 대조합니다.

> 💡 7번의 대조가 이번 실습의 결승선입니다.<br>"본부장이 있으니 좋아졌다"가 아니라, "실습 1의 전제 불일치는<br>③의 확인 숙제가, 결론 부재는 ⑤와 ⑥이 해결했다"라고<br>말할 수 있으면 오케스트레이터를 완전히 가져간 것입니다.
**FAQ**
- **Q. 결정권자 질문이 안 뜹니다**
- 단계 진행이 멈춘 상태입니다. 터미널 B의 마지막 로그를 Claude Code에 붙여넣어 해결을 요청합니다.
- **Q. 버튼을 눌렀는데 진행이 안 됩니다**
- 응답 대기 처리 오류입니다. 같은 방법으로 로그를 붙여넣어 요청합니다.
- **Q. 속마음이 안 보입니다**
- Claude Code에 "본부장 발언 직전의 속마음 말풍선이 표시되는지 점검해 주세요"라고 요청합니다.
- **Q. 숙제를 배정했는데 보고가 안 나옵니다**
- Claude Code에 "확인 숙제가 해당 팀장의 다음 발언 지시에 포함되는지 점검해 주세요"라고 요청합니다.

### 실습 3. 결정문이 마음에 안 든다 — 직접 뜯어고친다
방금 받은 결정문을 결정권자의 눈으로 다시 읽습니다.<br>첫 결정문은 대개 어딘가 부족합니다.<br>이긴 쪽 논리만 반복하거나, 진 쪽 우려를 흘려보내거나,<br>그래서 무엇을 언제 하자는 것인지 흐릿하거나.<br>**첫 결정문이 아쉬운 것은 고장이 아니라 출발점입니다.**<br>무엇이 아쉬운지 짚어내는 눈이 결정권자의 실력이고,<br>그 아쉬움을 지시로 바꾸면 시스템이 그대로 좋아집니다.
진행 순서

1. 결정문에서 아쉬운 점을 한 가지 고릅니다.<br>혹시 결정문이 흠잡을 데 없이 훌륭하면,<br>더 좋아질 수 있는 한 곳을 고릅니다.
2. 아쉬운 점을 Claude Code에게 개선 지시로 요청합니다.<br>지시는 내 언어로 씁니다. 막히면 아래 예시를 참고합니다.
3. \[본부장 회의 시작\]으로 회의를 다시 실행합니다.<br>같은 선택을 해도 되고, 다른 선택을 해 봐도 됩니다.
4. 새 결정문과 이전 결정문을 나란히 놓고, 내가 지시한<br>부분이 실제로 달라졌는지 대조합니다.
5. 옆자리와 결정문을 바꿔 읽습니다. 같은 안건인데<br>각자의 지시에 따라 결정문의 결이 달라져 있습니다.

개선 요청 예시입니다. 그대로 쓰지 말고, 내 아쉬움에 맞게 고칩니다.
**\[A\]**
```plain text
결정문에 반대 측의 핵심 우려와 그에 대한 보완 조치를
반드시 포함하게 해 주세요.
```
**\[B\]**
```plain text
결정문 첫 문장에 결정 사항을 못 박고, 실행 일정과
담당을 명시하게 해 주세요.
```
**\[C\]**
```plain text
결정문에 이 결정을 되돌릴 조건(예: 출시 후 중대 결함
발생 시)을 한 줄 넣게 해 주세요.
```
**FAQ**
- **Q. 개선을 지시했는데 결정문이 그대로입니다**
- 지시가 본부장의 결정문 생성 프롬프트에 반영되지 않은 상태입니다. Claude Code에 "결정문 생성 지시에 방금 요청이 반영되었는지 보여 주세요"라고 요청합니다.
- **Q. 무엇이 아쉬운지 모르겠습니다**
- 결정에서 진 쪽 팀장의 눈으로 결정문을 다시 읽어 봅니다. 그 사람이 억울해할 지점이 대개 아쉬운 지점입니다.
