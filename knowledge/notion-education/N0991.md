## 한 번에 이해하기
```javascript
프롬프트
  AI에게 무엇을 할지 말한다

컨텍스트
  AI에게 무엇을 보고 판단할지 준다

하네스
  AI가 어떤 환경·규칙·도구 안에서 일할지 만든다

루프
  그 안에서 결과가 기준을 만족할 때까지 반복시키는 구조를 만든다

그래프
  이런 작업자나 루프가 여러 개라면 누가 누구에게 일을 넘길지 연결한다
```

**흔한 오해 — "프롬프트 엔지니어링은 이제 끝났다"**
정확하지 않습니다. 각 단계는 앞 단계를 밀어내는 것이 아니라 **그 위에 쌓입니다.**
```javascript
프롬프트 ⊂ 컨텍스트 ⊂ 하네스 ⊂ 루프 ⊂ 그래프
```
루프를 설계해도 그 안에서 프롬프트는 여전히 핵심입니다. **조악한 지시로 짠 루프는 조악하게 돌아갑니다.**

**좋은 프롬프트와 필요한 컨텍스트를 가진 AI가 하네스 안에서 일하고, 필요하면 루프를 돌며, 여러 작업자가 그래프로 연결됩니다.**

# ③ 하네스 — 어떤 환경에서 일하게 할까
## 어원 — 왜 마구라고 부르는가
```javascript
하네스(harness)는 원래 말의 몸통에 채우는 마구를 뜻합니다.

AI는 힘센 야생마와 같습니다. 능력은 있지만 환각도 있고 통제도 어렵습니다.
이 야생마를 적절히 통제해서 목표 지점까지
빠르면서도 정확하게 달리게 만드는 것이 하네스 엔지니어링입니다.

핵심 질문: AI가 실제로 일할 수 있는 환경을 어떻게 만들 것인가
```
## 신입사원 비유

**아주 뛰어난 신입사원이 첫 출근을 했는데**
- 업무 매뉴얼이 없다
- 어디서 무슨 파일을 찾는지 모른다
- 팀 규칙이 문서로 없다
- 누가 검토해주는지 모른다
- 실수를 확인할 체크리스트가 없다
이 신입은 결국 **내 마음대로 해보겠다**가 됩니다.
**AI가 일을 못하는 이유는 머리가 나빠서가 아니라 회사가 정리되어 있지 않아서입니다.**

## 2단계와 3단계는 무엇이 다른가
```javascript
컨텍스트 엔지니어링
  AI에게 무엇을 보여줄 것인가 (정적인 재료 준비)

하네스 엔지니어링
  그 재료를 가지고 AI가 실제로 무엇을 할 수 있게 할 것인가 (동적인 실행 장비)
```
**요리에 비유하면 이렇습니다.**







비유




컨텍스트

요리사에게 좋은 재료를 챙겨주는 것




하네스

요리사가 실제로 요리할 수 있는 주방을 만드는 것 (도구·불·작업대·레시피 확인 절차)


**우리 교육에 대입하면**
```javascript
폴더 + 지침서 파일 + 원본 + 기준 + 결과 저장 위치 = 하네스

그 하네스 안에서
만들기 → 기준 검사 → 수정 → 재검사 → 통과하면 종료 = 루프
```
## 실제 사례 — 코드 한 줄 없이 만든 서비스
2026년 2월, OpenAI의 코드용 AI 에이전트 팀이 이 개념을 널리 알린 실험을 공개했습니다.
```javascript
실험 내용
  3명의 엔지니어가 5개월간
  단 한 줄의 기능 코드도 직접 짜지 않고
  AI만 활용해서 100만 줄 규모의 서비스를 완성

결과
  사람이 작성한 것보다 버그 발생률이 40% 낮음
  문서화 수준도 비교할 수 없을 만큼 높음
```
소프트웨어 공학의 거장 마틴 파울러는 이를 두고 **제3세대 프로그래밍의 시작**이라고 표현했습니다.
OpenAI 시니어 엔지니어 라이언 로포폴로는 이렇게 말했습니다.
> 엔지니어의 핵심 역할은 모델을 훈련시키는 것이 아니라,
> 모델이 최상의 성과를 낼 수 있는 완벽한 작업장을 만드는 것입니다.

**중요한 구분** — 이것은 프롬프트 몇 개로 대충 만드는 방식과 다릅니다.
AI가 참고할 지식의 지도(컨텍스트)를 설계하고, 결과물을 실시간으로 검증할 시스템을 구축하는 데 모든 에너지를 쏟은 결과입니다.
**즉 잘 만든 하네스가 성과를 만들었습니다.**

## 루프 데모에 대입하면
2권 4부에서 실행한 `교육기관_루프데모` 폴더를 이 다섯 가지로 나누면 이렇습니다.





요소

데모의 어느 부분




트리거

사람이 실행 명령을 입력 (아직 수동)




실행

`act/` 초안 생성




검증

`evaluate/` 6개 기준 검사




기록

`logs/` 회차별 검사 결과




종료 조건

6개 통과 또는 3회 반복


**트리거만 자동으로 바꾸면 사람 손이 완전히 떨어집니다.** 매주 월요일 아침에 알아서 도는 구조가 되는 것입니다.

**가장 중요한 것은 종료 조건입니다.**
AI 시스템이 실패하는 이유는 성능 부족보다 **루프에 출구가 없어서**인 경우가 많습니다.
잘 설계된 루프는 "더 이상 의미 있는 변화가 없다", "이 지점부터는 사람의 판단이 필요하다"를 스스로 알고 멈춥니다.

# ⑤ 그래프 — 여러 AI를 어떻게 연결할까
## 어디서 시작됐나
2026년 7월 18일, 개발자 Peter Steinberger가 짧은 글을 올렸습니다.
> 우리 아직도 루프 얘기 하나요, 아니면 이미 그래프로 넘어갔나요?
몇 시간 만에 57만 회가 조회됐고, 그때부터 그래프 엔지니어링이 다음 화두가 됐습니다.
## 무엇이 다른가





단계

통제 단위




프롬프트

한 번의 응답




루프

한 AI의 반복 주기




**그래프**

**여러 AI의 조직**


```javascript
루프    AI 하나가 혼자 반복하며 일한다
그래프  여러 AI가 서로 일을 넘기며 일한다
```
## 우리 업무로 옮기면
```javascript
[에이전트 A]  들어온 클레임을 읽고 유형을 판단
                 ↓
[에이전트 B]  긴급이면 공문 초안, 아니면 단순 회신
                 ↓
[에이전트 C]  쓴 것을 규정 관점에서 검토
                 ↓
[자동화]      통과한 것만 시트에 기록하고 발송
```
**10회차에 만든 에이전트를 여러 개 엮으면 자연스럽게 이 모양이 됩니다.**
## 지금 필요한가

**아직은 아닙니다.**
그래프는 여러 AI가 동시에 돌아가며 서로 일을 넘길 때 필요합니다. 하나를 제대로 돌리지 못하는 상태에서 여러 개를 엮으면 어디서 틀렸는지 알 수 없게 됩니다.
**우리는 지금 하네스까지 왔습니다.** 다음은 루프입니다.

# 자동화가 향하는 방향





단계

사람이 하는 일




프롬프트

매번 요청하고 확인




컨텍스트

자료를 챙겨줌




하네스

규칙을 정해둠




루프

기준만 정하고 검사는 맡김




그래프

흐름만 설계하고 처리는 맡김


**단계가 올라갈수록 사람이 하는 일이 줄어듭니다.** 없어지는 것이 아니라 앞쪽으로 옮겨갑니다. 실행에서 손을 떼고, 기준을 정하는 일로 이동하는 것입니다.

**전부 떼는 것이 목표가 아닙니다.**
판단과 책임은 사람이 집니다. 자동화가 가져가는 것은 실행과 검사이지 결정이 아닙니다.
좋은 자동화는 사람을 없애지 않고, **사람이 판단할 자리를 앞으로 당겨줍니다.**
