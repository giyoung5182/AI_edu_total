# 06. 메타 프롬프팅과 CoT 고도화

정리일: 2026-10-08 · 교육 에셋 N0231

본문 수집·공개 편집. 도구 실행·최신 기능 재검증은 미실시. 고객·참여자 정보와 개별 접근 링크, 원본 첨부는 제외했습니다.

**이 모듈의 목표**
AI에게 **설정문을 대신 설계하게 하고(메타 프롬프팅)**, **스스로 약점을 찾게 해(CoT 자가진단)** 혼자 고민하는 것보다 빠르게 정교화합니다.

# 혼자 짜지 않습니다
지금까지는 **사람이 재료를 생각해 AI에게 주는** 구조였습니다. 기본이지만 한계가 명확합니다.
> "어떤 규칙을 넣어야 할지 모르겠어요."
사실 **AI에게 설정문을 만들어달라고 시키면 됩니다.** 이것이 **메타 프롬프팅**입니다.





기존 방식

메타 프롬프팅 방식




사람이 다섯 칸을 채움

사람은 상황만 설명함




완성본을 넣고 작동 확인

AI가 질문하며 재료를 대신 뽑아냄




빠뜨린 항목을 나중에 발견

대화하면서 점점 정교해짐




내가 아는 만큼만 나옴

내가 못 떠올린 규칙까지 나옴



**역설계와 어떻게 다른가요?**
역설계는 **결과물이 있을 때** 그걸 분석해 만듭니다.
메타 프롬프팅은 **결과물이 없을 때** 상황을 설명해 만듭니다. 둘을 이어 붙이면 가장 강합니다.

---
# 메타 프롬프팅 5단계
```plain text
STEP 1  상황 투입      내 반복 업무를 설명합니다
           ↓
STEP 2  AI가 질문     한 번에 하나씩 물으며 재료를 뽑습니다
           ↓
STEP 3  초안 생성     모은 재료로 설정문을 만듭니다
           ↓
STEP 4  자가 진단     AI가 스스로 약점을 찾아 개선합니다
           ↓
STEP 5  테스트 확정    한 줄 입력으로 작동을 확인합니다
```
## STEP 1 · 시작 프롬프트
```plain text
저는 여신전문금융사에서 일하고 있습니다.
아래 업무를 도와줄 AI 담당자를 만들려고 합니다.

업무            : [예: 거래처 안내문 작성]
자주 반복되는 이유 : [예: 주 2~3회 같은 형식으로 발송]
지금 번거로운 점   : [예: 매번 톤을 잡는 데 시간이 걸림]

이 업무를 위한 최적의 설정문을 만들어 주세요.
단, 바로 만들지 말고 먼저 저에게 필요한 정보를 물어봐 주세요.
한 번에 하나씩 질문해 주세요.
```

**마지막 두 줄이 전부입니다.**
`바로 만들지 말고 먼저 물어봐 줘` + `한 번에 하나씩`
이 두 줄이 없으면 AI가 **불완전한 정보로 성급하게 만들어냅니다**(`원리 1`). 질문을 하나씩 받아야 답하기도 쉽습니다.

## STEP 2 · AI가 이렇게 물어옵니다
```plain text
AI  "첫 번째, 이 안내문을 받는 사람은 주로 누구인가요?"
나   "딜러사 담당자입니다. 오래 거래한 곳도 있고 신규도 있어요."

AI  "두 번째, 결과물로 원하는 것은 바로 발송 가능한 완성본인가요,
     아니면 참고할 초안인가요?"
나   "초안이면 됩니다. 제가 검토해서 보내요."

AI  "세 번째, 반드시 피해야 할 표현이나 주의할 점이 있나요?"
나   "조건을 확정해서 말하면 안 돼요. 금액이나 기한을 제가 안 준 건
     절대 넣으면 안 됩니다."
```

**여기서 일어나는 일** — 세 번째 질문에 대한 답이 바로 **금지 조항**이 됩니다.
혼자 빈칸을 보면 안 떠오르는데, 누가 물어보면 바로 나옵니다. 그게 이 기법의 핵심입니다.

## STEP 3 · 초안 생성 요청
```plain text
좋습니다. 지금까지 제가 답한 내용을 바탕으로
아래 다섯 항목의 설정문을 만들어 주세요.

[역할] [목적] [진행 방식] [예시] [지식·원칙]

각 항목이 무엇을 담당하는지 한 줄씩 라벨을 달아 보여주세요.
```
---
# CoT 자가진단 — 이 모듈의 진짜 핵심
초안을 받았다고 끝이 아닙니다. **바로 확정하지 말고 AI에게 약점을 물어보세요.**

**왜 이게 통하는가**
AI에게 "잘했니?"라고 막연히 물으면 "잘 됐습니다"라고 답합니다. 그게 가장 흔한 반응이니까요(`원리 1`).
그런데 **평가 기준을 단계로 주면** 그 순서를 밟으면서 실제로 구멍을 찾아냅니다. 이게 **CoT(단계적 사고)**입니다.

## 그대로 복사해 쓰는 자가진단 프롬프트
```plain text
방금 만든 설정문의 약점을 스스로 찾아 주세요.
아래 기준으로 단계별로 평가해 주세요.

1단계  다섯 항목이 충분히 구체적인가?
        모호한 표현이 있으면 집어주세요.
2단계  이 설정문만 보고 매번 일관된 결과를 낼 수 있는가?
3단계  없는 정보를 지어낼 위험이 있는 부분은 어디인가?
        특히 금액·날짜·조항 번호 관련으로.
4단계  빠진 제약 조건이 있을 것 같은 부분은?
5단계  금융사 문서로서 분쟁 소지가 있는 표현을 허용하고 있지 않은가?

평가가 끝나면 개선된 버전을 보여주세요.
```

**5단계가 우리 버전입니다.** 일반 기업용 자가진단에는 없는 항목인데, 금융권에서는 이게 가장 중요합니다.
단정적 약속, 확정되지 않은 조건 명시 같은 것을 AI가 잡아줍니다.

## 특정 부분만 깊게 파기
개선판을 받고도 부족하면 칸을 콕어서 요청합니다.
```plain text
규칙 부분이 아직 부족한 것 같습니다.
제가 이 업무에서 절대 하면 안 되는 것들을 다시 물어봐 주세요.
그 답변을 반영해서 규칙을 더 구체적으로 다시 만들어 주세요.
```
## 가상 입력으로 미리 돌려보기
```plain text
완성된 설정문을 기준으로,
아래 상황이 들어왔다고 가정하고 실제로 작동해봐 주세요.

[상황: A딜러사 서류 미접수, 기한 안내 필요]
```

**저장하기 전에 돌려보는 이유** — Gem으로 저장한 뒤 고치려면 편집 화면을 오가야 합니다.
대화창에서 미리 검증하고 넣는 편이 훨씬 빠릅니다.

# 전후 비교
### 역설계로만 만든 버전
```plain text
[역할] 당신은 캐피탈사 영업지원 담당자입니다.
[목적] 거래처 안내문을 작성합니다.
[진행 방식] 요청받으면 초안을 씁니다.
[예시] 제목 + 본문 + 문의처
[지식·원칙] 정중하게 씁니다.
```
작동은 합니다. 다만 **정보가 부족해도 그냥 써버리고**, 금액을 지어내는 일이 생깁니다.
### 메타 프롬프팅 + CoT 자가진단을 거친 버전
```plain text
[역할]
당신은 여신전문금융사 영업지원 담당자입니다. 다음을 잘합니다.
① 필요한 정보만 남기고 군더더기를 걷어냅니다.
② 상대가 무엇을 언제까지 해야 하는지 명확히 드러냅니다.
③ 재촉으로 느껴지지 않는 사무적 문체를 씁니다.

[목적]
사용자가 거래처·딜러사에 보낼 안내문을 빠르고 일관되게
작성하도록 돕습니다. 최종 발송 전 검토는 사용자가 합니다.

[진행 방식]
1단계  받는 사람, 안내할 내용, 기한을 확인합니다.
        하나라도 알 수 없으면 추측하지 말고 먼저 질문합니다.
2단계  제목을 3개 제안하고 각각의 인상을 한 줄로 설명합니다.
3단계  본문 초안을 작성합니다.
4단계  "수정할 부분이 있으신가요?"라고 묻습니다.

[예시]
  제목 후보 3개
  본문 (10줄 이내)
  필요 사항 항목 정리
  문의처 한 줄

[지식·원칙]
- 알려주지 않은 날짜·금액·금리·조항 번호는 만들지 않으며
  사용자가 채울 자리는 [ ]로 비웁니다.
- 상품 조건을 단정적으로 약속하는 표현을 쓰지 않으며,
  확정되지 않은 것은 "확인 후 안내" 형태로 씁니다.
- 과장된 표현과 불필요한 인사말은 넣지 않습니다.
```





추가된 것

어느 단계에서 나왔나




역할에 능력 3가지

자가진단 1단계 (모호함 지적)




1단계 되묻기 규칙

자가진단 3단계 (지어낼 위험)




단정 금지 · 확인 후 안내

자가진단 5단계 (분쟁 소지)




최종 검토는 사용자 명시

자가진단 2단계 (책임 경계)



**대화 두 번이 혼자 한 시간 고민보다 낫습니다.**
위에 추가된 네 가지는 대부분 혼자였으면 떠올리지 못했을 것들입니다.

```plain text
1단계  새 대화창을 열고 내 설정문을 붙여넣는다
```

AI가 규칙을 과하게 늘려놓는 경우가 있습니다. 규칙이 열 줄이 넘으면 중요한 게 묻힙니다(`원리 2`).
