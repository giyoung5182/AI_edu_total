정리일: 2026-10-08 · 교육 에셋 N0180

본문 수집·공개 편집. 도구 실행·최신 기능 재검증은 미실시. 고객·참여자 정보와 개별 접근 링크, 원본 첨부는 제외했습니다.

---

> 도구는 배웠지만, AI 자체가 지금 어디로 가고 있는지 모르면 3개월 뒤엔 낡은 강사가 됩니다. 이 파트가 회차 전체, 나아가 이 바이브코딩 과정 전체에서 가장 중요한 섹션입니다. <br>도구(Gamma·NotebookLM·Canva)는 이름이 바뀌어도, 이 4단계 진화의 사고 구조는 훨씬 오래갑니다.

### 7-1. 왜 "진화"인가 — 대체가 아니라 누적


```plain text
많은 사람이 이 4단계를 "프롬프트 엔지니어링은 이제 죽었다"처럼
이전 단계를 버리는 것으로 오해합니다. 정확하지 않습니다.

각 단계는 이전 단계를 밀어내는 것이 아니라
그 위에 새로운 "관심의 층"을 하나씩 쌓는 구조입니다.

프롬프트(문장) ⊂ 컨텍스트(문장+자료+기록) ⊂ 하네스(컨텍스트+환경+검증장치) ⊂ 루프(하네스+반복+종료조건)

→ 루프 엔지니어링을 한다고 프롬프트를 잘 쓸 필요가 없어지는 게 아니라,
   프롬프트 위에 컨텍스트가, 그 위에 하네스가, 그 위에 루프가
   차곡차곡 얹히는 구조입니다. 4단계 전부가 동시에 작동합니다.
```

### 7-2. 1단계 — 프롬프트 엔지니어링
**핵심 질문: "무엇을 어떻게 물어볼 것인가?"**
```plain text
정의: "잘 부탁해"가 아니라 "무엇을, 어떤 형식으로, 어떤 조건으로
      해달라"를 명확하게 말하는 기술
```

### 7-3. 2단계 — 컨텍스트 엔지니어링 (2025년 6월\~)
**정확한 탄생 배경 — 날짜까지 기록된 실제 사건**
[원본 이미지 제외]
```plain text
2025년 6월 18일, Shopify CEO 토비 뤼트케(Tobi Lütke)가
소셜미디어에 이런 글을 올렸습니다:

"나는 '프롬프트 엔지니어링'보다 '컨텍스트 엔지니어링'이라는
 용어를 훨씬 선호한다. 이 말이 핵심 기술을 더 잘 설명한다:
 LLM이 그 작업을 그럴듯하게 풀 수 있도록 모든 맥락을
 제공하는 기술이다."

6일 뒤인 2025년 6월 25일, AI 연구자 안드레이 카파시
(Andrej Karpathy, 전 Tesla AI 총괄·OpenAI 공동창업자)가
이 트윗에 동의하며 정의를 한 단계 더 정교화했습니다:

"모든 진짜 실전급 LLM 애플리케이션에서, 컨텍스트 엔지니어링은
 다음 단계를 위해 딱 맞는 정보로 컨텍스트 윈도우를 채우는
 섬세한 과학이자 기술이다."

→ 이 두 게시물이 컨텍스트 엔지니어링이라는 용어의 공식 시작점입니다.
```

**비유로 이해하기 — "어제 뽑은 신입 vs 6개월 함께한 인턴"**
```plain text
어제 뽑은 아무리 뛰어난 신입보다,
6개월을 함께 한 인턴이 더 일을 잘하는 이유는 무엇일까요?
능력이 아니라 "맥락"을 알기 때문입니다.

AI에게 회사 문서, 작업 히스토리, 필요한 배경지식을
잘 전달하는 방식 — 이것이 컨텍스트 엔지니어링입니다.
대표 구현 기술: RAG(검색 증강 생성), LangChain 같은 프레임워크
```
**핵심 개념 — 카파시의 "CPU와 RAM" 비유**
```plain text
소프트웨어 1.0: 사람이 코드로 "어떻게(How)"를 직접 지시
소프트웨어 2.0: 데이터로 "무엇을(What)"을 예시로 보여줌 (머신러닝)
소프트웨어 3.0: 자연어로 "원하는 것"을 말함 (LLM) — 지금 여기

이 3.0 시대에서 LLM은 CPU(연산 장치)이고,
컨텍스트 윈도우는 RAM(작업 기억)입니다.
컨텍스트 엔지니어의 일 = 운영체제(OS)의 일:
지금 어떤 데이터를 작업 기억에 올릴지, 언제 비울지,
어떻게 정리해야 프로세서가 효율적으로 실행할지 결정하는 것
```

### 7-4. 3단계 — 하네스 엔지니어링 (심화)
> 이 단계가 2026년 업계에서 가장 뜨거운 화두입니다. 야생마를 다루는 마구(harness)에서 이름을 따온 이유부터, 실제로 100만 줄 코드를 사람 없이 완성한 사례, 그리고 이 문제에 대한 두 회사(OpenAI·Anthropic)의 서로 다른 접근까지 구체적으로 다룹니다.
**어원 — 왜 "하네스(마구)"라고 부르는가**
```plain text
하네스(Harness)란 원래 말의 몸통에 채우는 '마구'를 뜻합니다.
AI는 힘센 야생마와 같습니다 — 환각도 있고 통제도 어렵습니다.
이 야생마를 적절히 통제해서 목표 지점까지
빠르면서도 정확하게 달리게 만드는 것이 하네스 엔지니어링입니다.

핵심 질문: "AI가 실제로 일할 수 있는 환경을 어떻게 만들 것인가?"
```

**실제 증거 — OpenAI의 '프로젝트 1M'**
```plain text
2026년 2월, OpenAI의 코드용 AI 에이전트 '코덱스팀'이
이 개념을 유행시켰습니다.

실험 내용: 단 3명의 엔지니어가 5개월간

AI만 활용해서 100만 줄 규모의 프로덕션급 서비스를 완성

결과:

- 문서화 수준도 비교할 수 없을 만큼 완벽

소프트웨어 공학의 거장 마틴 파울러는 이를 두고
"제3세대 프로그래밍의 시작"이라 선언했습니다.

OpenAI 시니어 엔지니어 라이언 로포폴로의 말:
"엔지니어의 핵심 역할은 모델을 훈련시키는 것이 아니라,
 모델이 최상의 성과를 낼 수 있는 완벽한 작업장을
 만드는 것입니다."

★ 중요한 구분: 이건 프롬프트 몇 개로 대충 만드는
  '바이브 코딩'과는 다릅니다. AI가 참고할 지식의 지도
  (컨텍스트)를 설계하고, 결과물을 실시간으로 검증할
  정교한 시스템을 구축하는 데 모든 에너지를 쏟은 결과입니다.
```

**OpenAI의 접근 — "특출난 신입 vs 정리된 회사"**


```plain text
비유: 매우 능력이 특출난 신입사원이 첫 출근을 했는데—
- 업무 매뉴얼이 없다
- 어디서 무슨 파일을 찾아야 하는지 모른다
- 팀 규칙이 문서로 정리되어 있지 않다
- 누가 검토·확인해주는지 모른다
- 실수를 확인할 체크리스트가 없다
- 이전에 비슷한 문제가 있었는지 기록이 없다

→ 이 신입은 결국 "내 마음대로 일해보겠다"는 결론에 이릅니다.

OpenAI의 결론: AI라는 신입사원이 일을 못하는 이유는
"머리가 나빠서"가 아니라 "회사가 정리가 안 되어 있기 때문"

이를 해결하기 위한 7가지 구체적 장치("레일을 깔아주는 것"):

① 리포지터리 문서화 — 코드·문서·규칙·작업 기록이 담긴 작업장
② AGENTS.md — 입사 첫날 주는 매뉴얼 (뭘 먼저 읽어야 하는지,
   어떤 규칙을 지켜야 하는지, 실수 방지를 위해 뭘 확인해야 하는지)
③ 린터(Linter) — 형식이 틀리면 옆에서 자동으로 "이건 틀렸습니다"
   귀띔해주는 친절한 선배 같은 장치
④ 구조 테스트 — "이 규칙대로 만들어졌는지" 확인하는 사내 시험
⑤ 리뷰 자동화 — 결과물을 처음부터 끝까지 실시간으로 확인하는
   엄격한 선배 같은 시스템
⑥ 관측 가능성(Observability) — AI가 지금 뭘 하고 있는지
   엿볼 수 있는 투명한 창문
⑦ 워크트리(Worktree) — 중요한 프로젝트를 바로 맡기지 않고
   먼저 연습해볼 수 있는 연습용 공책

→ 아무리 특출난 인재라도 명확한 지침·체크리스트·업무 매뉴얼·
   피드백 없이는 업무를 제대로 수행하기 어렵다는 것이
   OpenAI 접근의 핵심 메시지입니다.
```

**Anthropic의 접근 — "반려동물 vs 가축"**
```plain text
Anthropic은 다른 질문에서 출발합니다:
"AI 신입이 갑자기 아프거나 자리를 비우면 어떻게 될까?
 지금까지의 기록도 찾기 힘들고, 어디까지 했는지도 알기 어렵고,
 다시 이어서 하기도 힘들어진다."

Anthropic의 해법 — 한 명에게 모든 역할을 몰아주지 말고 나누기:

① 생각·판단하는 역할 = 하네스
   "지금 무엇을 해야 하지", "다음엔 무엇을 해야 하지"를 정리
   → 일을 어떤 순서로 진행할지 조율하는 관리자

② 기록하는 역할 = 세션(Session)
   지금까지 어떤 일이 있었고 어디까지 진행했는지 남기는 업무 일지

③ 실제로 일하는 역할 = 샌드박스(Sandbox)
   실제 작업을 수행하는 별도의 작업 공간

이렇게 나누는 이유는 단 하나: 하나가 망가져도
전체를 고치지 않고 그 부분만 바로 교체할 수 있기 때문입니다.

비유 — 반려동물(Pet) vs 가축(Cattle):
반려동물: 이름이 있고, 아끼는 존재. 아프면 병원에 데려가고
  끝까지 돌봐야 함. (컴퓨터 용어로는 "고장 나면 버리지 못하고
  꼭 살려야 하는 서버")
가축 무리: 개체 하나하나에 이름 붙여 감정적으로 돌보지 않고
  전체가 시스템처럼 운영됨. 문제 생긴 개체는 밤새 간호하지 않고
  빼고 새 개체로 교체. (컴퓨터 용어로는 "고장 나도 그냥
  새로 만들면 되는 서버·컨테이너")

→ Anthropic의 철학: AI 작업 시스템을 "가축 무리"처럼 설계하면,
   부분적으로 문제가 생겨도 전체를 다시 세우지 않고
   그 부분만 교체해서 훨씬 안정적으로 운영할 수 있습니다.
```

**OpenAI vs Anthropic — 철학의 차이**
```plain text
OpenAI: "유능한 신입사원이 일을 잘하도록
        회사 매뉴얼과 규칙과 선배 시스템을 잘 갖추자"
        → 한 명(하나의 에이전트)을 잘 보조하는 환경 설계

Anthropic: "애초에 한 신입사원에게 너무 많은 역할을 몰아주지 말고,
           생각하는 역할·기록하는 역할·실행하는 역할을 분리하자"
           → 여러 개체로 나눠서 회복탄력성을 확보하는 구조 설계

★ 강사가 알아야 할 이유: 두 회사가 완전히 다른 것을 만드는 게
  아니라, "AI를 신뢰할 수 있게 만드는 방법"에 대한
  서로 다른 강조점입니다. 어느 한쪽이 정답이 아니라,
  풀려는 문제의 성격(한 명이 오래 일할 프로젝트인가 여러 부분이 독립적으로 돌아가야 하는 시스템인가)에 따라
  다른 접근이 어울립니다.
```
**하네스의 5개 레이어 (실무 표준 구조 — 위 7가지 장치를 일반화한 것)**
```plain text
① 도구 오케스트레이션 — 어떤 도구를 언제 어떻게 호출할지
② 검증 루프 — 결과가 맞는지 확인하는 절차
③ 컨텍스트·메모리 — 2단계의 실행 담당 부분
④ 가드레일 — 하면 안 되는 행동을 막는 안전장치
⑤ 관측성(Observability) — 무슨 일이 일어났는지 기록·추적
```
**규모의 증거 — 모델은 그대로, 하네스만 바꿔 순위 25계단 상승**
```plain text
2026년 3월, LangChain 엔지니어링 팀은 자신들의 코딩 에이전트를
Terminal Bench 2.0 벤치마크에서 30위에서 5위로 끌어올렸습니다.
이때 한 일은 "더 좋은 모델로 교체"가 아니라 "하네스만 최적화"였습니다.

기업용 AI 도입 사례 분석에 따르면, 기업 AI 프로젝트 실패의
65%가 "하네스 결함"(컨텍스트 드리프트, 스키마 불일치, 상태 저하)에서

생각보다 적습니다.
```

### 7-7. 앤드류 응의 프레임워크 — 서로 다른 속도로 도는 3개의 루프
[원본 이미지 제외]
```plain text
① 에이전틱 코딩 루프 (가장 빠름, 분 단위)
   에이전트가 작업 → 실행해 테스트 → 문제 발견 시 수정 → 다시 테스트
   → 명세와 평가 기준을 충족할 때까지 스스로 반복

② 개발자 피드백 루프 (중간 속도, 수십 분~몇 시간)
   개발자가 결과물을 직접 써보고 방향을 제시
   → 그 판단이 새로운 명세·평가 기준에 반영됨
   → 다시 ①번 루프를 돎

③ 외부 피드백 루프 (가장 느림, 며칠~몇 주)
   실제 사용자에게 보여주고 반응 확인 → 제품 비전 자체를 조정
   → 조정된 비전이 다시 ①번 루프를 이끎

핵심 통찰 — "맥락 우위(context advantage)":
인간이 AI보다 사용자와 제품이 놓인 상황을 더 깊이 이해하기 때문에,
"무엇을 만들지·무엇이 좋은 결과인지"를 판단할 수 있습니다.
```
**강사 관점 적용 — 나의 3개 루프**
```plain text
① 강사의 "에이전틱 루프" (분 단위): AI에게 초안을 맡기고
   즉시 확인하고 지적하고 수정 (2회차 멀티턴·체이닝)

② 강사의 "피드백 루프" (한 회차 준비 기간): 초안을 보고
   강의 방향 자체를 조정 ("이 부분은 너무 어렵다" → 기준 수정)

③ 강사의 "외부 피드백 루프" (매주 토요일): 실제 수강생 반응을
   보고 강의에 대한 비전 자체를 조정

→ 지금까지 이 코칭 과정 전체가 이 3중 루프 구조로 설계되어
   있었습니다. "토요일 피드백을 다음 회차에 반영한다"는 과제
   안내가 바로 ③번 외부 피드백 루프입니다.
```

### 7-8. 실무자 관점 — "드리프트"와 작업 자산
> 구글 시니어 AI PM 슈밤 사부(Shubham Saboo)가 정리한, 코드를 다루지 않는 사람들을 위한 루프 엔지니어링 관점입니다.
**작업 자산(Work Asset)이란**
```plain text
루프는 작업 자산을 반복적으로 수정하고 검증하는 과정입니다.
에이전트를 실행해 결과를 평가하고, 좋아지면 유지, 나빠지면 되돌리고,
검증된 변경만 다음 실행에 반영합니다.

소프트웨어 개발에서는 코드·테스트가 대상이지만,
다른 직군에서는: PRD 리뷰 스킬, 고객 통화 요약기, 평가 루브릭,
출시 체크리스트, 리서치 워크플로 같은 것들이 작업 자산이 됩니다.

강사에게 작업 자산이란:
- 프롬프트 라이브러리 (2회차)
- 시스템 프롬프트(R.O.P.E.+K로 만든 Gem 설정)
- 강의 교안 템플릿
- Before/After 시연 세트
- NotebookLM의 소스 아키텍처

★ 이것들은 "한 번 쓰고 버리는 프롬프트"가 아니라 판단 기준을
  담고 반복 사용되며, 여러 강의 회차에 걸쳐 계속 영향을 주는 자산입니다.
```
**드리프트(Drift) — 작업 자산이 서서히 변질되는 현상**
[원본 이미지 제외]
```plain text
정의: 작업 자산이 반복 사용되며 품질이 서서히 저하되어
결국 결과물 품질까지 함께 떨어지는 현상

강사 맥락에서의 드리프트:
- 프롬프트 라이브러리에 초기 회차 때 쓴 낡은 지시가 남아
  최신 강의 방향과 안 맞는 결과가 나옴
- 시스템 프롬프트가 여러 번 수정되며 앞뒤가 안 맞는 지시가 섞임
  ("60대 대상"이라고 써놓고 나중에 "젊은 층 대상" 지시를 덧붙이며
   원래 지시를 안 지움)
- 체크리스트형 검토 기준이 계속 늘어나 정작 중요한 항목이 묻힘

★ 이럴 때 문제는 AI 모델이 아니라 "관리되지 않은 작업 자산"입니다.
  결과가 이상해졌을 때 "AI가 이상해졌나?"보다
  "내 작업 자산이 드리프트되지 않았나?"를 먼저 점검하는 것이 순서입니다.

강사 실천 — 정기적 자산 점검 루틴:
매달 한 번, 프롬프트 라이브러리와 시스템 프롬프트를 처음부터
다시 읽어보면서: □ 지금도 유효한가? □ 모순되는 지시는 없는가?
□ 너무 길어져서 핵심이 묻히지 않았는가?
```
**루프의 5요소 해부**
```plain text
① 트리거(Trigger) — 언제 시작하는가
   예: 매주 토요일 강의 후, 또는 새 교안 작성을 시작할 때
② 실행(Execution) — 무엇을 수행하는가
   예: AI가 교안 초안을 작성하는 행위
③ 검증(Verification) — 무엇을 성공의 증거로 인정하는가
   예: "60대 수강생이 이해할 수 있는 표현인가"를 확인하는 기준
④ 메모리/상태(Memory/State) — 무엇을 다음 실행에 남기는가
   예: 이번에 수정한 톤·기준이 다음 회차 작업에도 이어지는가
⑤ 종료 조건(Termination) — 언제 성공·실패·에스컬레이션으로 끝내는가
   예: 몇 번까지 수정을 반복할지, 안 되면 언제 사람이 개입할지

★ 가장 중요한 요소 — 종료 조건:
AI 시스템이 실패하는 이유는 모델의 성능 부족보다
"루프에 명확한 출구가 없기 때문"인 경우가 많습니다.
잘 설계된 루프는 "의미 있는 변화가 더 이상 없다",
"이 지점부터는 사람의 판단이 필요하다"를 스스로 판단하고
멈출 수 있어야 합니다.
```
**강사 실전 프롬프트 — 5요소를 명시적으로 담아서 설계하기**
```plain text
"[검증] 이 강의 자료에서 60대 수강생이 이해하기 어려운
 전문용어가 있는지 확인하고, 있으면 고쳐줘.

 [실행] 고친 뒤에는 처음부터 다시 검토해서
 남은 게 없는지 재확인해줘.

 [종료 조건] 단, 이 과정을 최대 3번까지만 반복하고,
 3번을 반복해도 여전히 애매한 부분이 있다면
 '사람이 직접 확인이 필요합니다'라고 표시하고 멈춰줘."
```
**자기 검증의 함정 — 만든 것과 검증하는 것을 분리하라**
```plain text
"모델이 자기 숙제를 스스로 채점하면 항상 스스로에게 A를 줍니다."

해결책: 검증자를 분리하는 것 — 다른 지시사항을 받은 별도 모델이
검증(교차 검증)하거나, 사람이 최종 검토 단계에 반드시 개입

강사 관점 적용 — 검증자 분리 3단계:
1단계(생성): "이 강의 자료 초안을 60대 수강생 눈높이로 써줘"
2단계(검증 — 새 대화창, 다른 역할로): "너는 이 자료를 처음 보는
  깐깐한 편집자야. 이해하기 어려운 부분, 논리가 안 맞는 부분만
  비판적으로 찾아줘. 좋은 점은 말하지 말고 문제점만 말해줘."
3단계(수정): 검증에서 나온 문제점을 1단계 자료에 반영
```

### 7-9. AI 업계가 실제로 이 방향으로 가고 있다는 증거
```plain text
하네스·루프 엔지니어링이 이론에 그치지 않고 실제 산업을
바꾸고 있다는 최신 사례들입니다.

원클릭 개발 플랫폼의 등장:
자연어 몇 마디만 입력하면 기획부터 배포까지 전 과정을
AI가 대신 처리하는 엔드투엔드 서비스들이 2026년 상반기에
다수 등장했습니다. 백엔드 지식이 없어도 결제·장바구니가
포함된 사이트가 완성되고, "관리자 화면도 필요해"라고
덧붙이면 전사 자원 관리 시스템까지 자동으로 붙는 수준입니다.
```

### 7-10. AI 업계를 계속 따라가는 법 — 정보 판별 프레임워크
**2026년 AI 업계의 특징 — 소음이 신호보다 많다**
```plain text
기술 자체는 그 어느 때보다 강력해졌지만,
이를 둘러싼 담론은 그 어느 때보다 혼란스럽습니다.
AGI 논쟁처럼 정의조차 불분명한 채 계속 화제가 되는 주제가 있는 반면,
실제로 의미 있는 진보는 조용히 기업 현장에서 측정 가능한
형태로 쌓이고 있습니다.
```
**가트너 하이프 사이클 — 새 기술의 감정 곡선**
```plain text
혁신 촉발 → 기대 거품의 정점 → 환멸 단계 → 계몽 단계 → 생산성 안정기

2026년 기준: AI 에이전트는 "기대 거품의 정점"에 위치
→ 자율적으로 일하는 AI 에이전트에 대한 기대가 과도하게 부풀어 있음

강사 활용: 새 개념(하네스·루프 엔지니어링 포함)을 접했을 때

습관이 과장 없이 정직하게 설명하는 강사의 기초 체력입니다.
```
**정보 판별 체크리스트**
```plain text
□ 실제 제품/기능인가, 개념/논의 단계인가?
□ 누가 말하는가? (마케팅인가, 실무자 경험담인가)

```

```plain text

2단계: "누가, 언제, 왜" 확인
3단계: 내 강의에 필요한 만큼만 소화
```

### 7-11. 정리 — AI를 가장 잘 활용하는 사람의 조건
[원본 이미지 제외]
```plain text
"앞으로 AI를 가장 잘 활용하는 강사는
 어떤 작업을 반복 가능한 루프로 만들지,
 어떤 작업 자산으로 그 루프를 이끌지,
 그리고 어떤 결정을 끝까지 강사 자신의 몫으로 남겨둘지를
 아는 사람입니다. 루프는 설계하되, 판단하는 자리는 지키면서."

이것이 오늘 배운 4단계 진화(프롬프트→컨텍스트→하네스→루프)의
최종 목적지입니다. AI에게 더 많은 것을 맡기면서도,
"무엇이 좋은 것인가"를 정하는 자리는 강사가 계속 지키는 것.

★ 사람에게도 같은 원리가 적용됩니다:
  "저 사람은 원래 뛰어나서 그래"라는 말 뒤에는
  좋은 환경(매뉴얼·규칙·다시 시도할 수 있는 문화)이 숨어있는
  경우가 많습니다. AI에게 하네스가 필요하듯,
  사람에게도 실수를 바로잡을 수 있는 교육, 방향을 잃지 않게 하는
  규칙, 다시 시도할 수 있게 하는 문화가 필요합니다.
  이 원리는 강사가 수강생을 가르치는 방식에도 그대로 적용됩니다.
```
