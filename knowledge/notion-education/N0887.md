## ④ 부딪힌 문제와 기술적 원인 분석
```plain text
문제 1: 새로고침 시 저장한 휴무 데이터가 원복됨
문제 2: 한 기기에서 수정 시 다른 기기에 반영 안 됨

기술적 원인 (거의 확실):
  두 증상이 동시에 나타나는 것은 데이터가 실제 데이터베이스가 아니라
  브라우저 메모리(React state)에만 저장되고 있었다는 전형적 신호.
  React state는 "그 브라우저 탭이 열려있는 동안만" 유지되는
  임시 저장소이므로:
  · 새로고침 → state 초기화 → 데이터 소실 (문제 1)
  · 기기 간 공유 자체가 불가능 (문제 2)

  최초 Supabase 연동이 "코드에 연결 시도는 있었으나
  실제 쓰기(INSERT)가 작동하지 않는 상태"였을 가능성이 높음.

해결 시도: GAS + 구글시트를 실제 저장소로 전환
  → 방향은 타당함. 검증 항목은 ⑤ 참고.
```

```plain text
  장점: 구글시트를 직접 열어 데이터를 눈으로 확인·수정 가능,
        별도 DB 비용 없음, 이미 익숙한 도구
  약점: ① GAS 웹앱 URL을 아는 사람은 누구나 데이터 접근 가능
          (RLS 같은 행 단위 보안이 없음 — 사내 도구로는 수용 가능한 수준)
        ② 시트 열 이름·순서가 코드와 정확히 일치해야 함
        ③ 동시 다중 쓰기에 상대적으로 취약 (7인 부서 규모에서는 문제 없음)

  □ 휴무 등록 → 새로고침 → 데이터 유지되는가
  □ PC에서 등록 → 스마트폰에서 확인되는가
  □ GAS 웹앱 배포 설정이 "모든 사용자" 접근으로 되어 있는가
    (앱이 로그인 없이 GAS를 호출하려면 필요)
```

## ④ 부딪힌 문제와 기술적 원인 분석
```plain text
문제 (본인 원문):
"구글 시트를 db로 연동해서 사용하려고 하다보니
 gas수정, 시트양식 수정, 그외 조건에 맞지 않는 출력이 있다보니
 러버블에서 내용이 표시되지 않거나 db에 기록을 해주지 않는등의
 오류가 많아서 수정하는데 시간이 오래걸렸음"

기술적 원인:
  구글시트를 DB로 쓰는 구조는 "암묵적 스키마 계약"에 의존함.
  즉, 코드가 "3번째 열은 상태값이고 '대기' 또는 '입고완료'만 온다"고
  가정하는데, 사람이 시트를 직접 수정하는 순간 이 가정이 깨짐:
  · 열 순서 변경 → 코드가 엉뚱한 열을 읽음
  · '대기 ' (뒤 공백) → 필터 조건 불일치 → 화면에 안 나옴
  · 셀 형식 변경(텍스트→날짜) → 파싱 오류

  전용 DB(Supabase 등)는 이런 계약을 시스템이 강제하지만
  구글시트는 사람의 규율에 의존함 — 이것이 시간이 오래 걸린 근본 원인.
```

## ⑤ 데이터·보안 아키텍처 진단
```plain text

  [React 앱 22화면] → [Supabase (PostgreSQL)]
  + 별도: [구글시트 근태] → [GAS] → [Make] → [Telegram]

Supabase 사용자라서 반드시 점검해야 할 것 — RLS:
  Supabase는 앱(브라우저)이 DB와 직접 통신하는 구조이므로
  RLS(Row Level Security) 정책이 곧 보안의 전부임.

  이 시스템은 특히 중요한 이유:
  · 일반 직원(S1~S14) vs 관리자(A1~A8) 권한이 명확히 나뉨
  · 직원 연락처·매장 점검 기록 등 민감 데이터 포함
  · RLS가 disabled 상태라면 anon key를 아는 누구나
    관리자 데이터까지 접근 가능한 상태일 수 있음

  참고 통계: 2025년 보안 분석에서 AI 생성 앱의 10.3%가
  RLS 미설정으로 데이터 노출 (심화가이드 1부 참고)

7회차 점검 순서:
  □ Table Editor에서 테이블·데이터 실존 확인 (연동 검증)
  □ 각 테이블 RLS 상태 확인 (enabled + 정책 존재 여부)
  □ Cursor로 코드 레벨 연결 상태 확인
```

```plain text
  파생자료를 만들어 요청자(임원/비서실)에게 사진으로 발송
  · 특정 PC에서만 작업 가능
  · 매일 사진 촬영·발송 (형식 비일관)
  · 과거 자료 재확인 곤란 (사진·카톡 뒤지기)
  · 파생자료 오류 검토 부담
```
## ② PRD 제작 프로세스
```plain text
1단계: 6회차 워크시트 (업무 흐름 상세 서술)
2단계: 기능설계시트 5개 기능 설계
       (기능5 마감별 누적 매출은 세부 미기입 → "제안 단계" 표시)
3단계: "매출현황_PRD.md" 정식 PRD 문서 작성
       배경·문제정의 → 사용자정의 → IA(5탭) → 기능별 상세 →
       데이터 모델 → 비기능 요구사항 → 기대효과 →
       Lovable용 요약 프롬프트까지 — 정식 기획 문서 형식
4단계: Lovable용 영문 PRD(txt) 재작성
       → 3탭 축소판 (매출 입력 Upload/주차별 요일/매장별 객단가)
       → "가상 매출 데이터 업로드 시뮬레이션" 방식 채택

프로세스 특징: 6명 중 가장 "문서 완성도"가 높은 PRD.
배경→문제→IA→데이터모델로 이어지는 구조는
실무 기획서 표준 양식과 동일. 다만 문서 완성도 대비
실제 구현 진행 여부가 미확인 상태 — "기획은 강하고
실행 검증이 남은" 프로필.
```
