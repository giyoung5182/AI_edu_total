# 2️⃣ 부록 B. 프론트엔드와 백엔드

정리일: 2026-10-08 · 교육 에셋 N0715

본문 수집·공개 편집. 도구 실행·최신 기능 재검증은 미실시. 고객·참여자 정보와 개별 접근 링크, 원본 첨부는 제외했습니다.

프론트엔드와 백엔드라는 구분이 처음부터 있었던 것은 아닙니다. 프로그램이 커지면서 생긴 문제를 해결하다 보니 자연스럽게 이 구조가 자리 잡았습니다. 그 과정을 순서대로 따라갑니다.

## B-1. 초기 웹 프로그램의 구조

처음에는 모든 코드가 한 파일에 있었고, 그것만으로 충분했다는 것을 확인합니다.

프로그램을 처음 만들 때는 코드가 많지 않습니다. 화면에 보여주는 코드, 데이터를 계산하는 코드, 파일을 읽는 코드가 모두 한 파일 안에 들어 있었습니다.
예를 들어 "파일을 업로드하면 수치를 계산해서 화면에 표로 보여주는" 프로그램이 있다고 하면, 하나의 파일 안에 아래 내용이 전부 섞여 있었습니다.
- 업로드 버튼을 그리는 코드
- 파일을 열어서 읽는 코드
- 숫자를 더하고 평균을 구하는 코드
- 계산 결과를 표 형태로 화면에 그리는 코드
프로그램이 작을 때는 이 방식이 충분히 잘 돌아갑니다. 한 파일만 열면 전체 동작이 한눈에 보이고, 수정할 곳도 금방 찾을 수 있습니다. 실제로 초기 웹 프로그램 대부분이 이 구조로 만들어졌습니다.
## B-2. 코드가 복잡해지면서 생긴 문제

코드가 커지면 한 파일 구조에서 어떤 문제가 반복적으로 생기는지 확인합니다.

프로그램은 한 번 만들고 끝나지 않습니다. 업무 요구사항이 바뀌고, 기능이 추가되고, 버그가 발견되고, 화면 디자인도 바뀝니다.
그때마다 같은 파일을 열어서 고치게 됩니다. 처음에는 수십 줄이던 코드가 수백 줄, 수천 줄로 늘어납니다.
이 과정에서 아래와 같은 문제가 반복적으로 생깁니다.

**화면을 고치다가 계산이 깨집니다** — 결과 표 디자인을 바꾸려고 코드를 수정했는데, 옆에 붙어 있던 평균 계산 코드가 영향을 받아 숫자가 틀어집니다.


**계산을 고치다가 화면이 깨집니다** — 계산 방식을 수정했더니, 결과를 표시하는 부분에서 예상 못한 데이터가 들어와 화면이 깨집니다.


**어디를 고쳐야 할지 찾기 어렵습니다** — 화면 코드 사이에 계산 코드가 끼어 있어 흐름을 따라가기 어렵습니다.


**여러 사람이 함께 작업하기 어렵습니다** — 같은 파일을 동시에 고치면 서로의 수정이 충돌합니다.

정리하면, 프로그램이 커질수록 모든 코드가 한 곳에 뒤섞여 있는 구조는 유지하기 어려워집니다. 고치면 고칠수록 다른 곳이 망가지고, 망가진 곳을 고치면 또 다른 곳이 망가지는 악순환이 반복됩니다.
## B-3. 역할 분리의 시작

"역할이 다른 코드는 분리하자"라는 원칙이 어떻게 생겼는지 확인합니다.

이 문제를 계속 겪다 보니 개발자들 사이에서 하나의 원칙이 자리를 잡았습니다.
**"역할이 다른 코드는 분리하자."**
화면에 무언가를 보여주는 코드와, 데이터를 계산하는 코드는 하는 일이 다릅니다. 하는 일이 다른 코드를 같은 자리에 두면 서로 영향을 주기 쉽습니다. 그래서 화면을 담당하는 코드는 한쪽에, 처리를 담당하는 코드는 다른 쪽에 나누어 두기 시작했습니다.
이렇게 나누면 어떤 일이 달라지는지 보겠습니다.

**역할 분리의 효과**
- 화면 디자인을 바꿀 때 계산 코드를 건드리지 않아도 됩니다.
- 계산 방식을 바꿀 때 화면 코드를 건드리지 않아도 됩니다.
- 화면 쪽 / 처리 쪽 코드가 분리되어 각각 독립적으로 읽힙니다.
- 여러 사람이 동시에 작업해도 충돌이 줄어듭니다.

역할에 따라 코드를 나누는 것만으로도 문제가 상당히 줄어든다는 것을 경험적으로 알게 된 것입니다.

## B-4. 프론트엔드와 백엔드라는 표준

웹서비스에서 가장 널리 쓰이는 분리 방식인 프론트엔드/백엔드 구조를 이해합니다.

코드를 나누는 방식은 여러 가지가 있을 수 있습니다. 그중에서 웹서비스 분야에서 가장 널리 자리 잡은 방식이 **프론트엔드**와 **백엔드**의 분리입니다.



**프론트엔드 (frontend)**<br>사용자가 직접 보고 조작하는 부분. 브라우저에서 실행되며, 화면에 버튼을 그리고, 입력을 받고, 결과를 표시합니다. 사용자 눈에 보이는 모든 것이 프론트엔드의 영역입니다.




**백엔드 (backend)**<br>서버에서 실행되는 부분. 사용자 눈에는 보이지 않지만, 파일을 읽고, 데이터를 정리하고, 계산을 수행하고, 결과를 저장합니다.



이 구분이 표준으로 자리 잡은 이유가 있습니다. 웹서비스는 기본적으로 사용자의 컴퓨터(브라우저)와 서비스 제공자의 컴퓨터(서버)가 나뉘어 있습니다. 브라우저에서 실행되는 코드와 서버에서 실행되는 코드는 물리적으로도 다른 곳에서 돌아가기 때문에, 이 경계를 기준으로 나누는 것이 가장 자연스러웠습니다.
현재 대부분의 웹서비스는 이 구조로 만들어져 있습니다.

## B-5. 프론트와 백을 연결하는 API

[원본 이미지 제외]

API가 무엇인지, 프론트와 백이 어떻게 대화하는지 이해합니다.

프론트엔드와 백엔드가 나뉘어 있으면, 둘 사이에 대화하는 방법이 필요합니다. 같은 파일 안에 있을 때는 코드가 바로 옆에서 서로 호출하면 되었지만, 이제는 브라우저와 서버라는 서로 다른 곳에서 실행되고 있기 때문입니다.
이 대화 방식이 **API(Application Programming Interface)**입니다.
구체적으로 어떻게 작동하는지 보겠습니다.

사용자가 브라우저에서 "분석 실행" 버튼을 누릅니다.


프론트엔드가 백엔드에 **요청(request)**을 보냅니다. "이 파일을 분석해 주세요."


백엔드가 요청을 받아서 파일을 읽고, 계산하고, 결과를 정리합니다.


백엔드가 프론트엔드에 **응답(response)**을 보냅니다. "분석 결과는 이렇습니다."


프론트엔드가 응답을 받아서 화면에 결과를 표시합니다.

이 요청과 응답의 규칙, 즉 "어떤 형식으로 보내고 어떤 형식으로 받는지"를 미리 정해 둔 약속이 API입니다.

**API 흐름**
프론트 → "이 파일 분석해줘" (요청) → 백엔드 → 처리 → "결과입니다" (응답) → 프론트

이때 요청과 응답에 담기는 데이터는 **JSON**이라는 형식을 주로 사용합니다. JSON은 데이터를 주고받기 위한 텍스트 형식으로, 아래와 같이 생겼습니다.
```json
{
  "total_count": 1284,
  "issue_count": 3,
  "summary": "전체 수량은 안정적이나 3건의 지연 이슈가 있습니다."
}
```
사람이 읽어도 어떤 내용인지 대략 파악할 수 있고, 컴퓨터도 쉽게 처리할 수 있는 형식입니다. 프론트엔드와 백엔드는 이 JSON을 주고받으면서 대화합니다.
## B-6. 예시 프로젝트의 역할 분담
[원본 이미지 제외]

예시 프로젝트에서 프론트엔드와 백엔드가 각각 무엇을 맡는지 구분합니다.

이번 교육의 예시 프로젝트인 "주간 운영 현황 / 이슈 리포트 생성 서비스"를 기준으로 프론트엔드와 백엔드의 역할을 나누어 보겠습니다.

**프론트엔드 (React/Vite)**
파일 업로드 화면, 메모 입력, 분석 실행 버튼, 결과 카드/목록/경고 표시

**프론트엔드 (React/Vite) 가 맡는 일**
- 파일 업로드 화면을 보여줍니다.
- 운영 메모를 입력받는 폼을 보여줍니다.
- "분석 실행" 버튼을 만들고, 버튼이 눌리면 백엔드에 요청을 보냅니다.
- 백엔드에서 돌아온 결과를 카드, 목록, 경고 배지 등으로 화면에 표시합니다.

**백엔드 (FastAPI)**<br>파일 읽기, 컬럼 정리, 수치 계산, 이슈 추출, 요약 생성, JSON 응답 반환

**백엔드 (FastAPI) 가 맡는 일**
- 업로드된 파일을 받아서 읽습니다.
- 컬럼을 정리하고 필요한 수치를 계산합니다.
- 이슈를 추출하고 경고 조건을 판단합니다.
- 요약 문장을 생성합니다.
- 모든 결과를 JSON 형태로 만들어서 프론트엔드에 돌려줍니다.
**전체 흐름을 이어서 보면 이렇습니다.**
```plain text
사용자가 파일과 메모를 입력
        ↓
프론트엔드가 파일 + 메모를 백엔드에 전송 (API 요청)
        ↓
백엔드가 파일을 읽고 분석 수행
        ↓
백엔드가 결과 JSON을 프론트엔드에 반환 (API 응답)
        ↓
프론트엔드가 결과를 화면에 표시
```
프론트엔드는 화면을 담당하고, 백엔드는 처리를 담당하고, 둘 사이는 API로 연결되어 있습니다. 이 구조를 알고 있으면 이후 실습에서 "지금 고치려는 부분이 프론트인지 백인지"를 구분하기가 수월해집니다.

## B-7. 분리 구조의 장점

프론트/백 분리 구조가 실무에서 어떤 장점을 주는지 정리합니다.

<details color="gray_bg">
<summary>✅ 화면만 따로 고칠 수 있습니다</summary>
결과 표 디자인을 바꾸거나 버튼 위치를 옮길 때, 계산 코드를 전혀 건드리지 않고 프론트엔드만 수정하면 됩니다.
</details>
<details color="gray_bg">
<summary>✅ 계산만 따로 고칠 수 있습니다</summary>
평균 계산 방식을 바꾸거나 새로운 이슈 추출 조건을 추가할 때, 화면 코드를 건드리지 않고 백엔드만 수정하면 됩니다.
</details>
<details color="gray_bg">
<summary>✅ 각자 따로 테스트할 수 있습니다</summary>
프론트는 "화면이 제대로 나오는지"를, 백엔드는 "계산 결과가 맞는지"를 독립적으로 확인할 수 있습니다.
</details>
<details color="gray_bg">
<summary>✅ 나중에 다른 화면을 붙일 수 있습니다</summary>
백엔드는 API로 결과를 돌려주므로, 새로운 프론트엔드(모바일 등)만 추가하면 백엔드를 새로 만들 필요 없이 그대로 쓸 수 있습니다.
</details>
B-2에서 보았던 문제들 — 화면을 고치면 계산이 깨지고, 계산을 고치면 화면이 깨지던 상황 — 이 분리 구조 덕분에 크게 줄어듭니다.

체크포인트<br>- 웹서비스가 왜 프론트엔드와 백엔드로 나뉘게 되었는지 설명할 수 있습니다.<br>- 프론트엔드와 백엔드가 각각 무엇을 맡는지 구분할 수 있습니다.<br>- API가 무엇인지, 둘이 어떻게 대화하는지 설명할 수 있습니다.<br>- 예시 프로젝트에서 프론트와 백의 역할을 구분할 수 있습니다.
