## 1-1. 나만의 에이전트 설계
---
### 지금까지는 공통 예시였습니다
클레임 검토와 반복매장 점검은 **방법을 익히기 위한 공통 소재**였습니다. 여기서부터는 각자의 업무입니다. 만드는 방법은 같고, **달라지는 것은 주제뿐입니다.**
---
### 사내 사례로 옮겨 보면
앞의 사무국 인터뷰에 나온 "확인서 취합" 업무를 4축으로 바꾸면 이렇게 됩니다.
```plain text
내가 만들 에이전트: 확인서 회수 점검 에이전트

  역할      매장별 확인서 회수 현황을 확인해 누락 매장을 가려낸다
  정보 범위  회수된 확인서 파일이 쌓인 폴더, 전체 매장 목록
  출력 형식  매장명 / 대상 월 / 회수 여부 / 미회수 기간 을 표로,
            미회수 기간이 긴 순서로 정렬
  페르소나  독촉하지 않고 사실만 정리하는 담당자.
            확인이 안 되는 건은 단정하지 말고 '확인 필요'로 표시
```
**지난 회차에 만든 클레임 검토 에이전트와 구조가 완전히 같습니다.** <br>폴더의 자료를 읽고, 기준과 대조하고, 표로 정리합니다.

```plain text
  퇴근 전에 상사나 관계 부서에 제출해야 하는 파일

  그 원본을 읽어 최종 파일로 만들 때, 머릿속에서 거치는
  2~3가지 다른 기준(예: 금액 검산, 누락 확인, 요약)은 무엇인가요?
```

## 1-2. 에이전트 제작 프롬프트 (범용 템플릿)
컨셉이 정해지면 아래 틀에 넣어 그대로 쓰면 됩니다.
```plain text
[내가 만들 에이전트]를 .claude/agents/ 폴더에 만들어줘.

[역할]
이 에이전트는 [역할]을 담당한다.

[정보 범위]
작업 폴더 안의 [파일 이름 또는 폴더명] 자료를 읽고 참고한다.

[출력 형식]
결과는 [출력 형식]으로 작성한다.
표로 만들 경우 열은 [열 구성]으로 한다.

[페르소나 및 판단 기준]
- [페르소나]
- 자료에 없는 내용은 추측하지 말고 '확인 필요'로 표시한다.
- 최종 의사결정이나 승인 결과를 확정하지 않고, 검토 의견 또는 초안으로 제시한다.
- 근거가 되는 파일명 또는 자료명을 함께 밝힌다.

'[호출 문구 1]', '[호출 문구 2]', '[호출 문구 3]'과 같거나 비슷한 요청이 오면
반드시 이 에이전트가 쓰이도록 description을 작성해줘.
에이전트 이름(name)은 영어 소문자와 하이픈으로 만들어줘.
도구와 모델은 현재 실습 환경에 맞게 적절히 설정해줘.
disallowedTools에 'Agent'를 추가해줘.
```
**만들고 실행하는 순서는 지난 회차와 같습니다**
```plain text
① 폴더에서 claude 실행 (cwd 확인)
② 위 템플릿을 채워 붙여넣어 생성
③ 규칙 보정 (추측 금지, 단정 금지 등)
④ /exit 후 재시작
⑤ 이름을 불러 실제 업무 요청
⑥ 결과를 보고 다듬기
```
**자료가 필요한 에이전트라면 폴더 안에 관련 파일을 넣어 두고 시키면 됩니다.** 지난 회차에 data 폴더의 클레임을 읽었던 것과 같습니다.

## 1-3. 동료 에이전트 붙이기
이미 하나를 만들었다면, **보는 각도가 다른 동료**를 추가합니다.
```plain text
한 명일 때   메인이 하나에게 위임 → 하나의 결과
팀일 때      메인이 여럿에게 나눠 위임 → 여러 결과를 모은 종합 산출물
```
**한 에이전트가 모든 자료를 다 읽고 모든 일을 하면 헷갈리고 느려집니다.** 각자 자기 영역만 깊게 보고 메인이 결과만 모으면 더 정확합니다.
### 동료를 고르는 법 — 같은 자료를 다른 각도로
```plain text
첫 번째가 "건별로 판정"한다면
  동료 후보 ①  반복·이상 신호만 골라내기   (패턴을 봄)
  동료 후보 ②  유형별로 집계하기            (분포를 봄)
  동료 후보 ③  결과를 안내문 초안으로       (형태를 바꿈)
```
### 제작 프롬프트
```plain text
[동료 에이전트 이름]을 .claude/agents/ 폴더에 만들어줘.
[대상 자료]를 읽고, [보는 각도]에 해당하는 건만 골라
[정렬 기준] 순으로 표로 정리하는 역할이야.
표 열은 [열 구성]으로 하고, 해당 없는 건은 넣지 마.

'[호출 문구 1]', '[호출 문구 2]'와 같거나 비슷한 요청이 오면
반드시 이 에이전트가 쓰이도록 description을 써줘.
에이전트 이름(name)은 영어 소문자와 하이픈으로 만들어줘.
도구는 모두 허용해줘. 모델은 Sonnet으로 해줘.
disallowedTools에 'Agent'를 추가해줘.
```
**만든 뒤 반드시 ****`/exit`**** 후 재시작합니다.**

## 1-4. \[선택\] 종합 대시보드 만들기
> 시간이 남는 분만 진행하세요. 에이전트 두 개를 먼저 완성하는 것이 우선입니다.
---
### 대시보드가 무엇인가 — 먼저 그림부터
**지금까지는 에이전트를 하나씩 따로 불렀습니다.** 대시보드는 **여러 에이전트를 한 번에 불러 결과를 하나의 화면으로 합치는 것**입니다.
```plain text
지금까지 (에이전트를 따로 부름)

  "클레임검토 에이전트한테 맡겨줘"     → 판정 표가 터미널에 출력
  "반복매장 점검 에이전트한테 맡겨줘"   → 주의 목록이 터미널에 출력

  → 결과가 따로 나오고, 터미널 안에만 있습니다
  → 남에게 보여주려면 복사해서 옮겨야 합니다


대시보드 (한 번에 불러 합침)

  "이번 주 현황을 대시보드로 만들어줘"
     ↓
  메인이 클레임검토 에이전트 호출 → 건별 판정 결과 받음
  메인이 반복매장 에이전트 호출   → 주의 매장 목록 받음
     ↓
  메인이 두 결과를 합쳐 HTML 파일 생성
     ↓
  dashboard.html 파일이 폴더에 생김 → 더블클릭하면 브라우저에서 열림

  → 결과가 파일로 남고, 그대로 보고에 쓸 수 있습니다
```
**핵심 차이는 세 가지입니다.**

```plain text
매주 월요일 아침에 이 파일 하나만 열면

  · 어떻게 분류됐는지
  · 주의할 것이 무엇인지

그대로 캡처해서 보고에 붙이거나, 파일을 메일로 보낼 수 있습니다.
```

### 시작 전 확인
```plain text
□ .claude/agents 폴더에 에이전트 파일이 2개 이상 있는가

   → 안 했으면 "에이전트를 찾을 수 없다"는 오류가 납니다
□ 두 에이전트의 이름을 정확히 아는가
   → 파일 이름(영어)이 아니라 부를 때 쓰는 이름
```

## 2-2. 왜 이 단계에서 대부분 멈추는가
2025년 MIT NANDA 연구진이 기업의 AI 도입 실태를 조사했습니다.\[\^1\] 경영진 인터뷰 150건, 직원 설문 350건, 도입 사례 300건을 분석한 자료입니다.
```plain text
조사 결과의 핵심

  · 기업이 만든 맞춤형 AI 도구 중 실제 운영 단계까지 간 것은 약 5%
  · 나머지는 시범 단계에서 멈췄고, 손익에 측정 가능한 영향이 없었음
  · 실패 원인은 기술이나 모델 성능이 아니라 조직에 통합하는 방식이었음
```
연구진은 이 격차를 \*\*"파일럿에서 운영으로 가는 절벽"\*\*이라고 표현했습니다. 만드는 것과 운영되는 것 사이에 큰 단절이 있다는 뜻입니다.
**성공한 5%의 공통점**은 세 가지로 정리됐습니다.
```plain text
① 하나의 문제 지점을 골랐다 (여러 개를 동시에 하지 않음)
② 그것을 끝까지 실행했다
③ 실제로 그 도구를 쓸 사람들과 협업했다
```
> **③이 오늘 오후에 하려는 것입니다.** 혼자 만들어서 내놓는 것이 아니라, 쓸 사람에게 실제로 써보게 하고 그 반응으로 다듬는 것.
\[\^1\]: MIT NANDA Initiative, *The GenAI Divide: State of AI in Business 2025* (2025). Fortune, VentureBeat 등이 보도한 내용을 참고했습니다.

## 2-4. 사용자 관점으로 보는 네 가지 렌즈
지금까지는 "내가 쓰기 편한가"로 봤습니다. 이제 \*\*"남이 쓸 수 있는가"\*\*로 봅니다.
### 렌즈 ① 진입 — 처음 쓰는 사람이 들어올 수 있는가
```plain text
확인할 것
  · 계정을 어떻게 받나
  · 주소를 어떻게 아나
  · 처음 열었을 때 뭘 해야 할지 아는가

흔한 걸림돌
  계정이 하나뿐이라 나눠 쓸 수 없음
  주소를 아는 사람이 나뿐
```
### 렌즈 ② 이해 — 설명 없이 쓸 수 있는가
```plain text
확인할 것
  · 버튼 이름만 보고 무엇을 하는지 아는가
  · 어디에 뭘 입력해야 하는지 보이는가
  · 실수했을 때 되돌릴 수 있는가

흔한 걸림돌
  내가 만들어서 나만 아는 흐름
  "이거 어디서 해요?"를 반복해서 묻게 됨
```
### 렌즈 ③ 연결 — 기존 업무와 이어지는가
```plain text
확인할 것
  · 앱에 입력한 것이 다음 단계로 넘어가나
  · 아니면 그다음은 여전히 사람이 손으로 잇나
  · 앞으로도 병행할 수밖에 없는 과정이 있나 (규정·결재 등)

흔한 걸림돌
  앱에 등록해도 따로 카톡·전화로 알려야 함
  결재는 그룹웨어라 결국 양쪽에 입력
```
> **③이 이번 회차에서 가장 많이 나올 항목입니다.** 특히 \*\*"앞으로도 병행할 수밖에 없는 것"\*\*을 파악하는 것이 중요합니다. 없앨 수 없다면 **잇는 방법**을 설계해야 합니다.
### 렌즈 ④ 지속 — 내가 없어도 굴러가는가
```plain text
확인할 것
  · 사용법이 문서로 있나
  · 오류가 나면 누가 어떻게 대응하나
  · 계정·권한이 개인 것에 묶여 있지 않나

흔한 걸림돌
  전부 내 머릿속에만 있음
  개인 계정으로 만들어져 있음
```

```plain text
빈도    얼마나 자주 걸리나       1 가끔 / 2 주간 / 3 매일
장벽    이게 없으면 남이 못 쓰나  1 불편 / 2 걸림 / 3 못 씀
난이도  2주에 되나              1 쉬움 / 2 보통 / 3 어려움
```
**'장벽' 점수가 3인 항목을 특히 보세요.** 그것이 남이 못 쓰는 이유입니다.
### 난이도 판정 기준
```plain text
난이도 1   앱 안에서 끝나는 수정 (화면·계산·표시)
난이도 2   데이터 연동 마무리 / 알림 붙이기 / 앱 밖 도구와 잇기
난이도 3   로그인·권한 체계 전면 변경 / 데이터 이전 / 사내 시스템 직접 연동
```
> **난이도 3은 2주에 위험합니다.** 특히 로그인 체계 전면 변경은 앱이 멈출 수 있습니다. 꼭 필요하면 컨설팅에서 함께 판단합니다.

## 2-7. 설계 원칙 세 가지
### 원칙 1 — 판단은 사람에게, 준비는 도구에게
```plain text
나쁜 설계   앱이 알아서 승인 처리한다
            → 책임 소재가 사라집니다

좋은 설계   승인이 필요한 건을 한 화면에 모아 보여준다
            사람은 보고 누르기만 한다
```
AI 도입 실무에서 이를 **통제된 위임**이라고 부릅니다. 도구가 일을 하되 사람이 책임과 확인을 유지하는 구조입니다.\[\^2\]
\[\^2\]: MIT NANDA 보고서 및 관련 실무 논의에서 제시된 개념입니다.
### 원칙 2 — 예외를 먼저 설계하라
```plain text
전체의 90%는 규칙대로 흘러갑니다. 나머지 10%가 운명을 결정합니다.

예외 경로가 없으면
  → 예외가 나올 때마다 손으로 처리합니다
  → "그냥 손으로 하는 게 빠르다"고 판단합니다
  → 다시 안 씁니다
```
**"90% 자동 + 10% 사람 경로"가 100%보다 낫습니다.**
### 원칙 3 — 종료 조건을 먼저 정하라
```plain text
나쁜 종료 조건
  "앱이 더 편해진다"           → 측정 불가
  "알림 기능을 추가한다"        → 기능 이름. 안 쓰일 수 있음

좋은 종료 조건
  "총무팀 김 대리가 결제 요청을 앱에 등록하고,
   나는 더 이상 카톡으로 요청을 받지 않는다."
  → 됐는지 눈으로 확인됩니다
```
**"누가 + 무엇을 하게 되고 + 무엇이 없어지는가"** 세 가지가 들어가야 합니다.

## 2-8. 만든 뒤에 오는 문제 — 조용한 실패
1983년 인지심리학자 리산 베인브리지가 쓴 짧은 논문이 있습니다.\[\^3\] 자동화가 만들어내는 새로운 문제를 처음으로 정리한 글로, 40년이 지난 지금도 계속 인용됩니다. 기술이 아니라 **사람과 자동화 시스템의 관계**를 다루기 때문입니다.
논문의 지적 중 우리에게 직접 해당하는 것은 이것입니다.
```plain text
자동 시스템은 문제가 생겨도 조용히 넘어가다가,
완전히 무너질 때가 되어서야 실패를 드러낸다.
```
```plain text
우리 상황으로 옮기면

  틀리게 돌면   결과가 이상해서 누군가 알아챕니다
  멈추면        아무 일도 안 일어나서 아무도 모릅니다
                → 한 달 뒤 "그거 요즘 안 오네요?"로 발견됩니다
```
**자동 알림이 "처음만 되고 끊겼던" 경험이 있다면 정확히 이 사례입니다.**
### 그래서 설계에 반드시 넣을 세 가지
```plain text
① 0건이어도 결과를 보낸다
   "이상 없으면 아무것도 안 보낸다"는 설계는 금지입니다.
   이상 없는 것과 멈춘 것을 구분할 수 없습니다.

② 생성 시각을 함께 표시한다
   언제 기준인지, 갱신이 멈췄는지 바로 보입니다

③ 근거를 함께 보여준다
   "미수금 12,345,000원 (45건 / 3월 31일 기준)"
   → 받는 사람이 검산하지 않아도 됩니다
```
같은 논문은 **사람이 따라갈 수 있는 방식으로 결과가 나와야 한다**는 점도 지적합니다. 결과만 나오고 근거가 없으면, 사람이 그 결과에 동의하지 않을 때 어디서 어긋났는지 찾을 수 없기 때문입니다. ③번이 그 대응입니다.
\[\^3\]: Lisanne Bainbridge, "Ironies of Automation", *Automatica* 19(6), 1983. 자동화 설계의 인간 요인을 다룬 고전으로 1,800회 이상 인용되었습니다.

## 2-9. 먼저 간 회사들은 어떻게 했나
우리만 이 단계에서 고민하는 것이 아닙니다. 규모가 훨씬 큰 회사들도 같은 지점을 지나갔습니다. <br>**두 사례가 서로 반대 방향의 교훈을 줍니다.**
### 사례 1 — JPMorgan: 소수의 전문가가 아니라 전원이 쓰게 했다
미국 최대 은행 JPMorgan Chase는 2024년 여름 사내 전용 AI 플랫폼(LLM Suite)을 열었습니다.\[\^3\]
```plain text
· 8개월 만에 20만 명이 사용 시작 — 전 직원의 약 3분의 2
· 현재 전 직원의 절반 가까이가 매일 사용
· 운영 중인 AI 업무가 450건 이상
```
**주목할 점은 확산 방식입니다.** 위에서 "쓰라"고 지시한 것이 아니라, **직원들이 자발적으로 쓰기 시작해 퍼졌습니다.** 맥킨지는 이 확산을 "놀랍도록 빠르게 번졌다"고 표현했습니다.
또 하나 중요한 것은 **자사 데이터를 결합했다는 점**입니다. 범용 AI 도구를 그냥 쓴 것이 아니라, 은행이 가진 거래 데이터와 붙여서 그 회사에서만 가능한 결과를 만들었습니다.
> **우리에게 옮기면 이렇습니다.**<br>교육기관이 가진 자사 데이터는 **매장 클레임 이력, 발주·단가 이력, 점검 기록, 정산 자료**입니다. 범용 AI가 갖지 못한 자산입니다. \*\*"우리 데이터에 AI를 붙이면 어떤 판단이 빨라지는가"\*\*가 우리가 던져야 할 질문입니다.
### 사례 2 — Klarna: 사람을 전부 빼려다 되돌렸다
스웨덴 핀테크 기업 Klarna는 2024년 AI 고객 상담 도입으로 크게 주목받았습니다.\[\^4\]
```plain text
· 첫 달에 230만 건의 상담을 처리
· 상담원 약 700명분의 업무량을 소화
· 평균 처리 시간 11분 → 2분 미만
```
**그런데 2025년 5월, 회사는 사람을 다시 뽑기 시작했습니다.** CEO는 비용을 지나치게 앞세운 결과 품질이 떨어졌다고 인정했습니다.
**여기서 정확히 이해할 것이 있습니다.** 이것은 "AI를 걷어냈다"가 아니라 \*\*"역할을 다시 나눴다"\*\*입니다.
```plain text
단순·반복 문의       AI가 계속 담당  (여전히 대부분을 처리)
복잡·감정적인 문의   사람이 담당      (다시 사람을 배치)
```
> **교훈은 "완전 대체를 노리면 실패한다"입니다.** 우리 교재의 원칙과 같습니다. **판단은 사람에게, 준비는 도구에게.**
\[\^3\]: JPMorganChase, "LLM Suite named 2025 Innovation of the Year by American Banker" (2025) 및 관련 보도(American Banker, McKinsey 인터뷰). 20만 명 온보딩·450건 이상 운영은 공개 보도된 수치입니다.
\[\^4\]: Klarna 보도자료(2024) 및 Bloomberg·CNBC 보도(2025년 5월). 2024년 효율 수치는 Klarna 자체 발표이며, 2025년 재조정은 독립 언론이 보도한 내용입니다.

## 2-10. 사내 AI 핵심 인재로서 알아두면 좋은 것
여섯 분은 회사에서 **이 도구들을 실제로 만들어본 몇 안 되는 사람**입니다. 앞으로 주변에서 물어보는 일이 생깁니다. 그때 도움이 될 것들입니다.
### ① 물어보면 답해줄 수 있는 위치가 됐습니다
```plain text
"그거 어떻게 만들었어요?"
"우리 부서도 그런 거 되나요?"

→ 이 질문이 오면 이미 확산이 시작된 것입니다.
→ 만드는 법을 알려주는 것보다,
  "그 업무가 어떻게 돌아가는지" 함께 뜯어보는 것이 더 도움이 됩니다.
```
**오늘 배운 진단 관점(병행·연결·지속)이 그때 쓰입니다.**
### ② 쓰는 모습을 보여주는 것이 설명보다 강합니다
```plain text
"AI 써보세요"라고 말하는 것    → 잘 안 움직입니다
"이거 AI로 만든 초안인데요"     → 자연스럽게 퍼집니다
```
JPMorgan의 확산이 지시가 아니라 자발적으로 일어났다는 점이 이것을 보여줍니다. **결과물을 보여주고, 어떻게 만들었는지 짧게 말하는 것**이 가장 효과적입니다.
### ③ 검증 없이 쓰지 않는다는 기준을 함께 전하세요
```plain text
AI 결과를 그대로 쓰는 것이 가장 흔한 사고입니다.

전할 것
  · 숫자는 반드시 검산한다
  · 근거가 없는 결과는 쓰지 않는다
  · 자료에 없는 내용은 '확인 필요'로 둔다
```
**만드는 법보다 이 기준을 먼저 전하는 것이 안전합니다.**
### ④ 회사 자산으로 남기는 것까지가 일입니다
```plain text
개인 계정으로 만든 것         담당자가 바뀌면 사라집니다
사용법이 머릿속에만 있는 것    본인이 없으면 멈춥니다
```
**12회차에 사내 지식베이스를 만드는 이유가 이것입니다.** 만든 것을 넘길 수 있는 상태로 두는 것까지가 이 과정의 마무리입니다.
### ⑤ 다음에 만들 때 쓸 순서
```plain text
① 업무를 단계로 쪼갠다
② 어느 단계가 판단·규칙·전달·기록인지 나눈다
③ 병행이 생기는 지점을 찾는다
④ 데이터가 어디에 어떤 상태로 있는지 본다
⑤ 그 상태에서 만들 수 있는 것을 고른다
⑥ 종료 조건을 "누가 + 무엇을 + 무엇이 없어지나"로 쓴다
⑦ 만들고, 남에게 쓰게 하고, 관찰한다
```
**도구는 바뀌어도 이 순서는 바뀌지 않습니다.**

## 2-11. 오후에 쓸 판단 기준 정리
```plain text
무엇을 고를 것인가

  · 남이 못 쓰게 만드는 것부터        (장벽 3점)
  · 없앨 수 있는 병행을 없애는 것
  · 없앨 수 없는 병행을 잇는 것
  · 내가 없어도 굴러가게 만드는 것

  화면을 예쁘게 만드는 것은 이것들이 끝난 뒤에.
```
```plain text
어디까지 할 것인가

  종료 조건에 세 가지를 넣습니다
    누가 + 무엇을 하게 되고 + 무엇이 없어지는가
```
---
> **강사용 노트 — 1권**
**① 오전 두 트랙은 진도가 크게 갈립니다.** 시작 전에 손을 들게 해서 트랙 A가 몇 명인지 파악하세요. 절반 이상이면 B는 각자 진행시키고 A에 붙는 것이 효율적입니다.
**② 재시작(/exit)을 놓치면 전원이 같은 오류를 만납니다.** 에이전트 생성 직후 다 같이 하게 하세요.
**③ 2-1의 5단계 표가 오늘의 문을 엽니다.** "우리는 4단계에 있고, 오늘은 5단계로 가는 날"이라는 위치 확인이 되면 이후 진행이 매끄럽습니다.
**④ 2-5(병행 두 종류)가 이번 회차의 핵심입니다.** 없앨 수 없는 병행을 없애려다 시간을 쓰는 것을 막는 장치입니다. 반드시 짚으세요.
**⑤ 2-3의 판별 질문("내가 자리를 비워도 돌아가는가")을 오후 내내 반복하세요.** 컨설팅에서 이 질문 하나로 대화가 짧아집니다.
**⑥ 2-8은 알림이 끊겼던 경험이 있는 분의 사례로 설명하면 즉시 이해됩니다.**
**⑦ 2-1의 PoC 개념을 먼저 짚으면 오늘의 위치가 명확해집니다.** "우리가 만든 건 실패작이 아니라 PoC이고, 오늘은 그것을 운영으로 옮기는 날"이라는 프레임이 부담을 덜어줍니다.
**⑧ 2-9의 두 사례는 방향이 반대라는 점을 짚으세요.** JPMorgan은 "전원이 쓰게 하라", Klarna는 "사람을 다 빼지 마라"입니다. 둘 다 오늘 설계에 필요한 교훈입니다.
**⑨ 2-10은 시간이 부족하면 읽기 자료로 넘기세요.** 다만 ③(검증 기준을 함께 전한다)만은 짚어주는 것이 좋습니다. 주변에 확산될 때 가장 위험한 지점입니다.
