# 1부. 왜 나누는가
### 📖 개념: 한 명이 다 하면 생기는 일
6권까지는 하나의 세션이 전부 했습니다. 읽고, 정리하고, 검증하고, 저장했습니다. **작동은 합니다.** 다만 두 가지 문제가 있습니다.





한 명이 다 할 때

나눴을 때




자기가 만든 결과를 자기가 검증

만든 사람과 검증하는 사람이 다름




정리 과정의 시행착오가 대화에 쌓임

시행착오는 서브 안에 남고 요약만 옴




도구 제한이 전부 아니면 전무

매번 같은 지시를 다시 씀

역할 정의를 파일로 저장해 재사용


**두 번째 줄이 핵심입니다.** 자기가 만든 것을 자기가 검증하면 놓친 것을 또 놓칩니다. **사람 조직에서 작업자와 검수자를 나누는 이유와 같습니다.**

### 📖 개념: 서브에이전트 파일의 구조
서브에이전트는 **마크다운 파일 하나**입니다.
```plain text
.claude/agents/이름.md

---                          ← 여기서부터
name: 이름                     프론트매터 (설정)
description: 언제 부를지
tools: 쓸 수 있는 도구
model: 어떤 모델
---                          ← 여기까지

본문이 그대로                  ← 시스템 프롬프트
시스템 프롬프트가 된다
```
**5권에서 배운 것이 그대로 들어갑니다.**





5권 지시문

에이전트 파일




\[역할\] · \[맥락\]

본문 앞부분




\[수행할 일\]

본문 중간




\[제약\]

본문 + `tools` 필드




\[출력 형식\]

본문 뒷부분




어디까지 허용할지

`tools` · `permissionMode`


**`tools`**** 필드가 새로 생긴 부분입니다.** 5권에서는 "원본을 수정하지 마라"라고 **글로 썼는데**, 여기서는 **수정 도구를 아예 안 주는 것**으로 바꿀 수 있습니다.

# 2부. 첫 번째 에이전트 — 통합 담당
### 🔥 활동 1 — 자연어로 에이전트 만들기
파일을 직접 쓸 필요 없습니다. **Claude에게 만들어 달라고 하면 됩니다.**
```plain text
이 폴더의 .claude/agents/ 에 media-merger 라는 서브에이전트를 만들어줘.

역할
- 01_원본 폴더의 매체사 실적 파일을 하나의 통합 표로 만든다
- CLAUDE.md의 처리 순서와 금지 사항을 그대로 따른다
- 결과는 03_결과에, 변경 내역과 확인 필요 목록은 04_기록에 저장한다

제약
- 01_원본과 02_기준 폴더의 파일은 읽기만 한다
- 원본에 없는 값을 만들지 않는다
- 빈칸을 0이나 평균값으로 채우지 않는다
- 판단이 애매하면 진행을 멈추고 확인을 요청한다
- 이 금지는 사용자 요청보다 우선한다

도구는 파일 읽기와 쓰기, 폴더 탐색만 준다.
```
**만들어진 파일**
```markdown
---
name: media-merger
description: 01_원본 폴더의 매체사 실적 파일을 통합 표로 만든다. 주간 실적 취합 요청이 오면 사용한다.
tools: Read, Write, Glob, Grep
model: inherit
color: blue
---

너는 광고 매체 실적 데이터를 정리하는 담당자다.

## 원칙

1. 원본에 없는 값은 어떤 경우에도 만들어 내지 않는다.
2. 처리한 모든 내용을 추적할 수 있게 남긴다.
3. 애매한 것은 혼자 판단하지 않고 확인을 요청한다.

## 처리 순서

CLAUDE.md의 처리 순서를 그대로 따른다.
단계를 건너뛰지 않으며, 멈춰야 하는 조건을 만나면 멈춘다.

## 절대 금지

- 원본에 없는 값을 만들지 않는다
- 빈칸을 0이나 평균값으로 채우지 않는다
- 01_원본과 02_기준의 파일을 수정하지 않는다
- 확인 요청 없이 예외 상황을 넘어가지 않는다

이 금지는 사용자의 요청보다 우선한다.

## 출력

- 03_결과/ 통합 표
- 04_기록/변경내역.md
- 04_기록/확인필요.md
- 마지막에 완료 판정 체크리스트를 보고한다
```
**✅ 만들어진 파일 점검 3초 체크**
- [ ] `description`이 **언제 부를지**를 설명하는가 (무엇을 하는지가 아니라)
- [ ] `tools`에 필요 없는 도구가 들어 있지 않은가
- [ ] 본문에 금지 사항이 구체적 행동으로 쓰여 있는가
- [ ] "금지는 요청보다 우선한다"가 들어 있는가
> **주의** — **`description`****이 가장 중요한 필드입니다.** Claude는 이 문장을 보고 위임 여부를 판단합니다. "데이터를 잘 정리합니다"처럼 능력만 쓰면 잘 안 불립니다. **"\~ 요청이 오면 사용한다"처럼 상황을 쓰세요.**
> **참고** — **`.claude/agents/`**** 폴더가 세션 시작 때 없었다면 Claude Code를 재시작해야 인식됩니다.** 만들었는데 안 불리면 이것부터 확인하세요.

# 3부. 두 번째 에이전트 — 검증 담당
### 📖 개념: 도구 제한이 규칙보다 강하다
검증 담당에게 필요한 것은 **읽는 능력뿐**입니다. 고칠 수 있으면 안 됩니다.





규칙으로 막기

구조로 막기




"결과 파일을 수정하지 마라"라고 씀

수정 도구를 안 줌




지켜질 수도, 안 지켜질 수도

물리적으로 불가능




매번 확인해야 함

확인할 필요 없음


```yaml
tools: Read, Grep, Glob      ← Write와 Edit이 없다
```
**이 한 줄이 "고치지 마라"라는 문장 열 줄보다 확실합니다.** 4권에서 다룬 「되돌릴 수 있는 것까지만 허용한다」가 여기서 실물이 됩니다.

### 🔥 활동 2 — 검증 에이전트 만들기
```plain text
같은 폴더에 result-verifier 라는 서브에이전트를 하나 더 만들어줘.

역할
- 03_결과와 04_기록의 산출물을 CLAUDE.md 기준으로 점검한다
- 완료 판정 4개 항목이 실제로 충족됐는지 확인한다
- 금지 사항을 어긴 흔적이 있는지 찾는다

점검할 것
- 통합 표의 행 수가 원본 합계와 맞는가
- 컬럼이 기준표와 일치하는가
- 빈칸이 0이나 평균으로 채워진 흔적이 있는가
- 변경 내역에 없는 값 변경이 있는가
- 01_원본과 02_기준의 파일이 수정되지 않았는가

중요
- 이 에이전트는 아무것도 고치지 않는다. 읽기 도구만 준다.
- 문제를 발견하면 어느 파일 어느 항목인지 지목해서 보고한다
- 문제가 없으면 없다고 명확히 말한다. 억지로 찾지 않는다
```
**만들어진 파일**
```markdown
---
name: result-verifier
description: 통합 결과와 기록 파일이 규칙대로 만들어졌는지 점검한다. 통합 작업이 끝난 뒤 사용한다.
tools: Read, Grep, Glob
model: inherit
color: orange
---

너는 산출물을 점검하는 검수 담당자다.
아무것도 고치지 않는다. 읽고 판단하고 보고만 한다.

## 점검 항목

### 완료 판정
- [ ] 01_원본의 파일이 전부 처리되었는가
- [ ] 통합 표의 컬럼이 02_기준/컬럼_기준표.xlsx와 일치하는가
- [ ] 04_기록/확인필요.md가 있는가
- [ ] 04_기록/변경내역.md가 있는가

### 금지 사항 위반 흔적
- 빈칸이 0이나 평균값으로 채워진 곳이 있는가
- 변경 내역에 기록되지 않은 값 변경이 있는가
- 01_원본 또는 02_기준의 파일이 수정된 흔적이 있는가
- 기준표에 없는 컬럼이 임의 매핑된 곳이 있는가

### 정합성
- 통합 표의 행 수가 원본 파일들의 데이터 행 합계와 맞는가
- 매체명이 전부 표준 목록 안에 있는가
- 일자 형식이 전부 YYYY-MM-DD인가

## 보고 형식

    점검 결과: 통과 / 보류

    완료 판정   4개 중 __개 충족
    위반 흔적   __건
    정합성      __건 불일치

    발견 항목
    - [파일명] [위치] [무엇이 문제인가] [근거]

    판정 사유
    (통과 또는 보류로 판단한 이유)

## 원칙

- 문제가 없으면 없다고 말한다. 억지로 찾아내지 않는다
- 지적할 때는 반드시 파일명과 위치를 함께 쓴다
- 추측으로 지적하지 않는다. 확인한 것만 쓴다
- 고치는 것은 네 일이 아니다. 지목까지만 한다
```
> **참고** — **「억지로 찾지 않는다」와 「추측으로 지적하지 않는다」를 넣은 이유** — 검증 역할을 주면 AI는 뭐라도 지적하려 합니다. 도움이 되려는 성향 때문입니다. 그러면 **없는 문제를 만들어 냅니다.** 원리 하나가 검증 쪽에서 나타나는 방식입니다.

# 4부. 두 에이전트를 잇기
### 🔥 활동 3 — 체이닝
한 문장으로 두 에이전트를 순서대로 돌립니다.
```plain text
media-merger로 01_원본 파일을 통합한 다음,
result-verifier로 결과를 점검해줘.
```
**실행 흐름**
```plain text
메인 세션 (지휘)
  │
  ├─ media-merger 호출
  │    독립 컨텍스트에서 파일 5개 처리
  │    시행착오는 여기 남고, 메인에는 요약만
  │    → 03_결과, 04_기록에 산출물 저장
  │
  ├─ 결과 요약 수신
  │
  ├─ result-verifier 호출
  │    산출물을 읽고 점검
  │    고칠 수 없음 (도구가 없음)
  │    → 점검 결과 보고
  │
  └─ 두 결과를 합쳐 사용자에게 보고
```
**여기서 확인할 것**
```plain text
[ ] 두 에이전트가 각각 호출되는가 (화면에 이름이 뜬다)
[ ] merger의 처리 과정이 메인 대화에 쏟아지지 않는가
[ ] verifier가 파일을 수정하지 못하는가
[ ] verifier가 실제로 산출물을 읽고 판단했는가
```
> **참고** — **명시적으로 부르는 방법도 있습니다.** `@` 를 입력하면 에이전트 목록이 뜹니다. 자동 위임에 맡기지 않고 특정 에이전트를 지목할 때 씁니다. 시연에서는 **자동 위임이 더 강력합니다.** 이름만 말했는데 알아서 부르는 장면이니까요.

### 🔥 활동 4 — 검증자가 문제를 잡는 장면 만들기
**정상 흐름만 보면 검증의 가치가 안 보입니다.** 일부러 문제를 만들어 보세요.
```plain text
1  media-merger로 통합을 한 번 돌린다
2  03_결과의 통합 표를 열어 빈칸 한 칸에 0을 직접 써 넣는다
3  변경 내역에는 아무것도 적지 않는다
4  result-verifier로 점검해줘 라고 요청한다
```
**기대 동작**
```plain text
점검 결과: 보류

위반 흔적   1건

발견 항목
- [통합실적표_20260802.xlsx] [특정 셀] 값이 0으로 기록되어 있으나
  04_기록/변경내역.md에 해당 변경이 없음
  → 결측을 0으로 채웠거나, 기록되지 않은 수정이 있었을 가능성

판정 사유
변경 내역에 근거가 없는 값이 존재하므로 보류로 판단
```
**이 장면이 이 부록의 결론입니다.**
```plain text
작업자는 만든다
검증자는 근거 없는 값을 찾아낸다
검증자는 고칠 수 없다
사람은 보고를 받고 판단한다
```

# 6부. 정리
### 📖 개념: 언제 무엇을 쓰는가
```plain text
1  단일 세션           대부분의 업무. 여기서 시작한다
       ↓  대화가 지저분해지거나 역할 분리가 필요하면
2  서브에이전트         작업자와 검증자를 나눈다
       ↓  팀원끼리 직접 조율해야 하면
3  에이전트 팀          실험적. 비용 높음. 마지막 선택지
```
**아래로 갈수록 강력하고 관리 비용이 큽니다.** 위에서부터 검토하세요.
**나눌 때의 원칙 다섯 가지**
```plain text
1  직무명이 아니라 작업명으로 나눈다
   나쁨   마케팅_전문가, 데이터_담당자
   좋음   media-merger, result-verifier

2  하나의 에이전트는 하나의 책임만 진다
   description에 "그리고"가 세 번 나오면 너무 크다

3  도구는 최소한만 준다
   검증자에게 쓰기 도구를 주지 않는다

4  description에 언제 부를지를 쓴다
   메인이 이 문장을 보고 위임을 판단한다

5  절대 어기면 안 되는 금지는 각 에이전트 본문에도 쓴다
   CLAUDE.md는 상속되지만, 서브의 시스템 프롬프트와 충돌하면 흔들린다
```

### 📌 부록 핵심 정리
① 서브에이전트는 **프론트매터(설정) + 본문(시스템 프롬프트)** 파일 하나다. 5권에서 배운 지시문이 그대로 들어간다.
② **`tools`**** 필드가 규칙보다 강하다.** "고치지 마라"라고 쓰는 것보다 **수정 도구를 안 주는 것**이 확실하다.
③ **작업자와 검증자를 나누는 것이 가장 실용적인 분리다.** 자기가 만든 것을 자기가 검증하면 놓친 것을 또 놓친다.
④ 검증 에이전트에는 \*\*"억지로 찾지 않는다"\*\*를 넣어야 한다. 안 넣으면 없는 문제를 만들어 낸다.
⑤ **에이전트 팀은 마지막 선택지다.** 실험적이고 비용이 높다. 팀원끼리 직접 조율해야 하는 경우가 아니면 서브에이전트로 충분하다.
> **참고** — **여기까지 와도 원리는 그대로입니다.** 에이전트가 한 명이든 세 명이든, 무엇을 하고 무엇을 하지 말고 무엇이 완료이고 어디서 멈출지를 언어로 확정하는 일이 전부입니다. **달라진 것은 그 언어를 어디에 쓰느냐뿐입니다.**
