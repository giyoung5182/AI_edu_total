# PART 2. 바이브코딩 — 이론 심화 (참고)
> 📖 **이 파트는 강의에서 전체를 다루지 않습니다.**<br>다만 아래 개념들을 정확히 아는 사람과 모르는 사람의 프롬프트는 완전히 다릅니다.<br>**"왜 이 지시어가 필요한가"를 알면, 처음 보는 문제 상황에서도 스스로 올바른 프롬프트를 만들어낼 수 있습니다.**
---
## 2-1. 바이브코딩의 정확한 기원과 정의
```plain text
2025년 2월, Andrej Karpathy(전 Tesla AI 총괄, OpenAI 공동창업자)가
소셜미디어에서 "바이브코딩(Vibe Coding)"이라는 용어를 처음 만들었습니다.

핵심 정의:
"코드가 존재한다는 사실조차 거의 잊어버릴 정도로,
 AI에게 완전히 위임해서 소프트웨어를 만드는 것"
= 원하는 것을 설명하고, 결과를 받아들이고, 보이는 것을 보고 반복하는 것
```
> ⚠️ **학생에게 설명하실 때 정확히 하실 것**
"AI가 코딩을 대신해준다"는 표현은 부정확합니다.<br>**코드가 사라진 게 아니라, 사람이 안 쓸 뿐 코드는 그대로 생성됩니다.**<br>이따 실습에서 오른쪽 패널에 수백 줄이 쌓이는 걸 직접 보실 겁니다.
정확한 표현: **"AI가 코드를 대신 써주는데, 뭘 만들지는 사람이 정해야 한다"**
---
## 2-2. 왜 지금 가능해졌는가 — 기술적 배경
```plain text
2022년 이전:
  AI는 간단한 코드 조각만 제안 가능. 앱 전체 생성은 불가능

2023년 이후 (GPT-4, Claude 3):
  코드 이해·생성 능력이 급격히 향상
  수천 줄의 코드를 한 번에 작성·이해·수정 가능

2024~2026년 (Lovable, v0, Bolt, Artifacts):
  "프롬프트 → 완성된 앱" 파이프라인이 상용화
  비개발자도 수십 분 안에 작동하는 앱 완성 가능

핵심 변화:
  "코드를 짜는 능력"보다
  "무엇을 만들지 정확히 설명하는 능력"이 더 중요해짐
```
**왜 이 변화가 일어났는가 — 원리 수준의 이해**
```plain text
AI가 코드를 잘 짜게 된 것은 단순히 "똑똑해져서"가 아닙니다.

언어모델의 동작 원리를 한 문장으로 줄이면:
  "지금까지의 텍스트를 보고, 다음에 올 조각(토큰)을 확률로 고른다.
   고른 조각을 포함해서 다시 다음 조각을 고른다. 반복한다."
  → 이걸 자기회귀(autoregressive) 생성이라고 합니다.

여기서 결정적인 사실:
  코드는 자연어보다 규칙이 훨씬 엄격합니다.
    · 괄호는 반드시 닫혀야 하고
    · 문법이 정해져 있고
    · 같은 기능의 구현 패턴이 어느 정도 정형화되어 있습니다

  → "다음에 올 가장 그럴듯한 조각"을 예측하는 모델 입장에서는
    자연어보다 코드에서 훨씬 정확하게 맞아떨어집니다.

즉, 코드는 원래 AI가 잘할 수 있는 영역이었고,
2023년 이후 모델 규모와 학습 데이터가 임계점을 넘으면서
그 잠재력이 실전에서 드러난 것입니다.
```
[원본 이미지 제외]

> 💡 **정보이론 용어로는 "엔트로피"입니다**
```plain text
엔트로피 = 불확실성의 정도. 선택지가 많을수록 높습니다.

  시·에세이:  다음 단어의 선택지가 매우 넓다  → 고엔트로피
  코드:      선택지가 좁고 정형화되어 있다   → 저엔트로피
```
**AI가 코딩을 잘하는 건 코드가 어려워서가 아니라 규칙이 명확해서입니다.**
그렇다면 우리가 할 일도 명확해집니다.<br>**입력의 엔트로피를 낮추는 것.** 요구사항이 명확할수록 "정답에 가까운 것"이 나옵니다.<br>프롬프트 공학이라는 게 결국 이겁니다.
> 📌 **학생에게 이 원리를 응용하는 법**<br>"AI에게 시를 쓰게 하면 매번 다른데, 계산기를 만들게 하면 비슷하게 나오는 이유"<br>— 이걸 설명할 수 있으면 학생들이 AI의 성격을 훨씬 잘 이해합니다.<br>그리고 "AI에게 뭘 시키면 잘하고 뭘 시키면 못하는지"를 스스로 판단하게 됩니다.

## 2-3. 냉정한 통계 — 바이브코딩의 그림자
```plain text
Stack Overflow 2025 개발자 설문(약 4만9천 명 응답) 기준,
개발자의 45%가 "AI가 만든 코드를 디버깅하는 데
직접 코드를 짜는 것보다 더 많은 시간을 쓴다"고 답했습니다.
가장 흔한 불만(66%)은 "거의 맞는데 완전히 맞지는 않다"는 것이었습니다.

그리고 METR의 통제 실험(2025)에서는,
숙련된 개발자들이 AI 도구를 썼을 때 오히려 19% 더 오래 걸렸습니다.
정작 본인들은 빨라졌다고 느꼈다는 점이 더 흥미롭습니다.

원인으로 지목된 것:
  · 출력을 한 글자씩 다 읽으려는 습관
  · 처음부터 직접 만들려는 습관
  · "빨리 타이핑하면 빨리 끝난다"는 전제
```
> ⚠️ **이 통계가 중요한 이유**
바이브코딩은 "코딩 시간을 없애는 것"이 아니라<br>"코딩 시간을 검수·디버깅 시간으로 옮기는 것"입니다.<br>이걸 모르고 시작하면 "왜 이렇게 오래 걸리지?"라는 좌절에 빠집니다.
→ **오늘 배우는 대부분의 원칙은 이 45%를 줄이기 위한 것입니다.**<br>생성 속도를 높이는 게 아니라, 검수·디버깅을 체계화해서 낭비를 줄이는 방향입니다.
> 💡 **학생 지도에 그대로 적용됩니다**<br>"AI를 쓰면 무조건 빨라진다"고 가르치면 안 됩니다.<br>"검증하는 눈을 기르면 빨라진다"가 정확합니다.

## 2-4. 인지 노력의 방향 전환
```plain text
기존 개발: 인지 에너지의 70%가 "생각을 문법으로 옮기는 데" 들어감
AI 개발:   70%가 "무엇을 만들지 명확히 하고, 나온 걸 검증하는 데" 들어감

→ 역할이 줄어드는 게 아니라 바뀌는 겁니다
→ 타자수에서 설계자로
```
**70%의 문제**
```plain text
AI는 어떤 결과물의 70%를 아주 빠르게 만들어냅니다.
그런데 나머지 30% — 예외 처리, 세부 검증, 실제 현장 조건 —
이 부분이 전체 시간의 대부분을 잡아먹습니다.

오늘 실습에서도 겪으실 겁니다.
첫 결과물은 1분 만에 나오는데, 쓸 만하게 만드는 데 30분이 걸립니다.
```

## 2-5. 추상화 계층의 역사 — 이 논쟁은 처음이 아닙니다


```plain text
프로그래밍의 역사는 "추상화 계층이 올라가는 역사"입니다.

1940s  기계어      0과 1을 직접 입력

2010s  노코드      화면에서 조립
2020s  자연어      "이런 걸 만들어줘" ← 지금 여기
```


[원본 이미지 제외]


> 💡 **매 단계마다 같은 논쟁이 있었습니다**
"어셈블리를 쓰면 진짜 프로그래머가 아니다"<br>"고급 언어는 느려서 못 쓴다"<br>"프레임워크만 쓰면 원리를 모른다"
그리고 매번, 추상화 계층이 올라가면서 **더 많은 사람이 소프트웨어를 만들게 됐습니다.**<br>낮은 계층을 아는 사람이 사라진 것도 아닙니다. 역할이 나뉜 것입니다.
> 📌 **학생에게 이 관점을 주는 게 중요합니다**
"AI가 코딩을 대신하니 코딩을 안 배워도 된다"는 결론은 위험합니다.<br>정확한 결론은 "만드는 층이 하나 더 올라갔다"입니다.
그리고 위 계층에서 일하려면 아래 계층을 **읽을 줄은 알아야** 합니다.<br>고급 언어를 쓰는 개발자도 메모리와 자료구조를 압니다.<br>자연어로 만드는 사람도 **코드가 무엇을 하는지 판단할 수 있어야** 합니다.

## 2-6. 알아두면 프롬프트가 달라지는 개념들

### 토큰 — 한글은 비싸다
```plain text
토큰 = 모델이 처리하는 텍스트의 최소 단위

영어:  단어 하나가 대략 0.8~1.5 토큰
한글:  글자 하나가 대략 1~2 토큰

→ 같은 내용이라도 한글이 영어보다 토큰을 2~3배 씁니다
→ 긴 한글 문서를 붙여넣으면 컨텍스트가 훨씬 빨리 찹니다
```

### State(상태) — 동적 기능의 핵심
```plain text
State = 앱이 "지금 이 순간" 기억하고 있는 데이터

  지금 몇 번째 문제인지        → State
  몇 개 맞혔는지               → State
  어떤 보기를 골랐는지          → State

동적 기능 = State가 바뀌면 화면도 즉시 바뀌는 것
정적 기능 = State 없이 그냥 고정된 화면

원리: 화면에 표시되는 것은 "지금 State가 어떤 값인가"를 그대로 반영한 결과입니다.
      버튼 클릭이 State를 바꾸고, State가 바뀌면 화면이 자동으로 다시 그려집니다.
```
> ⚠️ **이 개념이 왜 실무에 필요한가**
버튼이 안 눌리거나 점수가 안 바뀔 때, 이렇게 요청하면 정확히 통합니다:
```plain text
이 기능들이 실제로 작동하게 고쳐줘.
버튼을 누르면 즉시 반응이 있어야 하고,
페이지 새로고침 없이 화면이 바뀌어야 해.
```
"고쳐줘"만 하면 AI가 뭘 고칠지 모릅니다. **State 개념을 알면 지시가 명확해집니다.**
### 프론트엔드 vs 백엔드
```plain text
프론트엔드: 사용자 눈에 보이는 화면 → 오늘 만드는 것
백엔드:     데이터 저장, 서버, 회원 관리 → 오늘 못 만드는 것

오늘의 경계:
  버튼·화면·계산·판정  → 전부 됩니다
  로그인·이메일 발송   → 안 됩니다

  단, 데이터 저장은 예외적으로 됩니다 (3권에서 다룸)
```

## 3-3. 두 번째 벽 — 회귀(Regression)
> 🎓 **오늘 실습에서 반드시 겪습니다. 미리 시연으로 보여줄 예정입니다.**
### 왜 생기는가 — 원리
```plain text
수정을 요청하면 Claude는 기존 코드를 다시 씁니다.
전체를 새로 쓰거나, 바꿔야 할 부분을 찾아 고칩니다.

요청을 다섯 개 몰아서 넣으면:
  → 다섯 개를 동시에 만족시키려고 코드를 크게 건드립니다
  → 건드리는 범위가 커질수록, 손대지 말아야 할 곳까지 닿습니다
  → 그 과정에서 원래 잘 돌던 게 깨집니다

개발에서는 이걸 회귀(regression)라고 부릅니다.
"뒤로 돌아간다"는 뜻입니다.
```
**비유로 이해하기**
```plain text
회귀는 이런 상황과 같습니다:

  방 정리를 부탁했는데
  "책상도 치우고, 옷장도 정리하고, 침대보도 갈고,
   창문도 닦고, 화분도 옮겨줘"라고 한꺼번에 시켰습니다.

  결과: 책상은 치웠는데 그 위에 있던 서류가 어디 갔는지 모르고,
       옷장 정리하다 옷걸이 순서가 뒤바뀌었습니다.

  하나씩 시켰다면 각각 확인하면서 갔을 텐데,
  한꺼번에 시키니 뭘 건드렸는지 추적이 안 됩니다.
```
### 방어 — "나머지는 그대로"
```plain text
수정 요청 끝에 이 한마디를 붙입니다:

  "정답을 맞혔을 때 축하 효과를 추가해줘. 다른 기능은 그대로 두고."
                                          ↑ 이것

원리: 모델에게 "건드리지 말아야 할 범위"를 명시하는 것입니다.
      경계가 생기면 그 밖으로 손이 덜 나갑니다.
```
> 📌 **오늘 실습에서 습관으로 만드세요**<br>저는 수정할 때 거의 항상 붙입니다. 붙이는 것과 안 붙이는 것의 차이가 눈에 띄게 납니다.

## 3-4. 세 번째 벽 — 조용한 실패 (Artifacts 특유) ★★
> ⚠️ **이건 Artifacts에만 있는 함정입니다. 다른 도구를 쓰시던 분들이 반드시 걸립니다.**
### 조용한 실패란
```plain text
보통의 실패:
  뭔가 안 되면 → 오류 메시지가 뜬다 → 원인을 안다 → 고친다

조용한 실패(silent failure):
  뭔가 안 되는데 → 오류 메시지가 없다 → 원인을 모른다 → 헤맨다

  · 앱은 정상적으로 화면에 뜹니다
  · 버튼도 눌립니다
  · 성공 메시지도 뜹니다
  · 그런데 실제로는 아무 일도 일어나지 않습니다
```
### Artifacts에서 조용한 실패가 나는 두 지점
**① localStorage — 브라우저 저장소가 막혀 있습니다**
```plain text
웹 개발을 조금 아시는 분은 localStorage를 떠올리실 겁니다.
브라우저에 데이터를 저장하는 가장 표준적인 방법입니다.

Artifacts에서는 작동하지 않습니다.

원리:
  Artifacts는 격리된 실행 환경(샌드박스)에서 돌아갑니다.
  보안 정책상 브라우저 저장소 접근이 차단되어 있습니다.

문제는 실패 방식입니다:
  오류 없음 → 앱 정상 렌더링 → 저장 버튼 눌림 → 데이터만 안 감
```
**② 게시 전 저장 — 저장소는 게시 후에만 작동합니다**
```plain text
Artifacts는 세션을 넘어 데이터를 저장할 수 있습니다.
단, 조건이 있습니다:

  ★ 게시(Publish)된 아티팩트에서만 작동합니다
  ★ 게시 전에는 저장 요청이 "조용히 실패"합니다

즉, 개발·테스트 중에는:
  앱이 잘 돌아갑니다 → 저장 버튼도 눌립니다 → 데이터가 안 남습니다 → 오류도 없습니다
```
> 📌 **그래서 오늘 3차시는 "게시 → 저장" 순서입니다**<br>반대로 하면 "저장이 안 돼요"가 동시다발로 터집니다.<br>이건 예측이 아니라 구조입니다.
### 조용한 실패에 대한 방어
```plain text
방어 1 — 프롬프트에 미리 금지
  "브라우저 localStorage는 절대 쓰지 마"
  "Artifacts의 공유 저장소(window.storage, shared 옵션)를 사용해줘"

방어 2 — 순서를 지킨다
  게시 먼저 → 저장 기능 → 테스트

방어 3 — "저장되는 것처럼 보이는 것"과 "진짜 저장"을 구분한다
  · 화면에 남아 있다 ≠ 저장됐다
  · 새로고침 후에도 있다 → 1차 통과
  · 다른 기기·다른 사람에게도 보인다 → 진짜 저장
```

## 3-5. 벽을 피하는 4가지 방어선
### 방어선 1 — 모듈식 프롬프팅 (한 프롬프트 = 한 관심사)
```plain text
원리: 컨텍스트 붕괴와 회귀는 모두 "한 번에 처리해야 하는 정보량"에서 비롯됩니다.
      요청을 작게 쪼개면 각 요청의 정보량이 줄어 정확도가 올라갑니다.

❌ "퀴즈 앱 만들고 타이머도 넣고 순위표도 만들어줘"

✅ 단계별로:
  "퀴즈 앱을 만들어줘" → 확인 →
  "타이머를 추가해줘. 나머지는 그대로" → 확인 →
  "순위표를 추가해줘. 나머지는 그대로"

각 단계가 컨텍스트 한계 안에 머물고,
계속 진행하기 전에 결과를 확인할 기회를 줍니다.
```
### 방어선 2 — 프롬프트를 서로 연결하기
```plain text
원리: 이전 단계를 명시적으로 참조하면, AI가 매번 새로운 패턴을 추측하는 대신
      이미 확립된 구조 위에 정확히 쌓아 올립니다.

❌ (맥락 없이) "타이머를 추가해줘"

✅ (맥락 연결) "지금 5문제가 한 문제씩 넘어가고 채점도 잘 되고 있어.
    여기에 문제당 30초 타이머를 추가해줘. 기존 흐름은 그대로."
```
### 방어선 3 — 계획을 먼저 승인받기
```plain text
원리: AI가 계획 없이 바로 코드부터 생성하면,
      방향이 틀렸을 때 이미 상당한 코드가 만들어진 후에야 알게 됩니다.
      되돌리는 비용이 처음부터 다시 만드는 것보다 클 수 있습니다.

실전 프롬프트:
"이 기능을 구현하기 전에, 어떻게 만들 계획인지
 먼저 3~4줄로 요약해서 알려줘. 내가 확인한 다음에 진행해줘."

→ 계획 단계에서 방향이 틀렸다는 걸 알면 그 자리에서 바로잡을 수 있습니다.
```
### 방어선 4 — 체크포인트를 스스로 만든다
> ⚠️ **실측 정정 — 버전 되돌리기 버튼은 없습니다**<br>리허설로 직접 확인했습니다. Artifacts 결과물 패널에는 버전 번호도, 이전 버전으로 가는 화살표도 뜨지 않습니다.<br>다른 AI 코딩 도구에는 버전 히스토리가 있는 경우가 많아 혼동하기 쉬운데, Artifacts는 다릅니다.
```plain text
원리: 고치는 것보다 되돌리는 게 빠른 경우가 훨씬 많습니다.
      특히 회귀가 일어난 뒤에는 거의 항상 그렇습니다.
      다만 Artifacts에서 "되돌리기"는 버튼이 아니라 두 가지 방법입니다.

방법 ① 다운로드로 체크포인트 만들기
      잘 되는 상태가 나오면 그 시점에 HTML로 내려받아 둡니다.
      꼬였을 때 그 파일을 새 대화에 올려 "여기서부터 다시 시작해줘"

방법 ② 말로 되돌려달라고 요청하기
      "방금 요청은 취소하고 그 전 상태로 돌아가줘"
      Claude가 직전 대화를 참조해서 되돌립니다.
      버튼 클릭만큼 즉시·완벽하진 않지만 대부분 작동합니다.
```
> 📌 **오늘 가장 중요한 습관 — 고치지 말고 되돌리기**
꼬인 상태에서 계속 고치면 코드가 누더기가 됩니다.<br>위 두 방법 중 하나로 **먼저 되돌린 다음, 요청을 다르게 써서 다시 시도**하는 게 훨씬 빠릅니다.
> 💡 **평소에 다운로드해두는 습관이 유일한 안전장치입니다**<br>버전 목록을 뒤져서 예전 상태를 찾는 방법 자체가 없습니다.<br>마음에 드는 상태가 나올 때마다 습관적으로 내려받아 두세요.

## 3-6. "고쳐줘"가 아니라 "증상을 설명해줘"
```plain text
가장 흔한 실수: 원하는 해결책을 지시하는 것

❌ "State 관리를 다시 해줘"        (해결책을 지시)
✅ "답을 골라도 아무 반응이 없어"   (증상을 설명)

원리: 사람이 추측한 해결책이 실제 원인과 다를 때가 많습니다.
      틀린 해결책을 지시하면 AI는 그 틀린 방향으로 계속 시도하게 되고,
      근본 원인은 계속 남아있게 됩니다.

      반대로 증상만 정확히 설명하면, AI가 코드 전체를 스스로 진단해서
      사람이 미처 생각 못 한 진짜 원인을 찾아내는 경우가 많습니다.
```
**증상을 잘 설명하는 형식**
```plain text
"[어느 화면]에서 [무엇]을 하면 [무슨 일]이 일어납니다.
 (원래는 [무엇]이 되어야 합니다.)"

예시:
"마지막 결과 화면에서 점수가 항상 0점으로 나옵니다.
 (정답을 맞힌 개수만큼 점수가 올라가야 합니다.)"
```

## 3-7. 프롬프트 로그 — 왜 기록해야 하는가
```plain text
많은 시행착오 끝에 실사용자들이 도달한 결론:
  "무엇을 물었고 AI가 어떻게 반응했는지"를 기록해두면
  나중에 같은 실수를 반복하지 않습니다.

간단한 기록 습관:
  - 무엇을 요청했는지 한 줄
  - 결과가 좋았는지 나빴는지
  - 나빴다면 어떻게 바꿔서 성공했는지
```

## ① 스캐폴드 (Scaffold) — 뼈대를 세우는 프롬프트
```plain text
언제: 처음부터 만들 때
특징: 길고, 구조화되어 있고, 제약이 명시되어 있음

핵심 구성 4층:
  [대상]     누가 어떤 환경에서 쓰는가
  [내용]     무엇을 다루는가
  [형태]     어떤 흐름으로 움직이는가
  [제약]     무엇을 하면 안 되는가

→ 오늘 실습의 첫 프롬프트가 정확히 이 형태입니다 (2권 참고)
```
> 💡 **왜 항목별로 묶는가**<br>대괄호로 \[내용\] \[디자인\] \[기술 조건\]을 나누면 모델이 각 영역을 별개 요구사항 묶음으로 처리합니다.<br>나열식보다 누락이 눈에 띄게 줄어듭니다.
Anthropic이 공식 문서에서 **XML 태그로 프롬프트를 구조화**하라고 권하는 것도 같은 원리입니다.<br>대괄호든 XML 태그든, **경계를 명확히 하는 것**이 핵심입니다.
---
## ② 리파이너 (Refiner) — 다듬는 프롬프트
```plain text
언제: 작동은 하는데 더 다듬고 싶을 때
특징: 짧고, 범위가 좁고, "나머지는 그대로"가 붙음

예시:
  "축하 효과를 추가해줘. 다른 기능은 그대로 두고."
  "글자 크기를 1.5배로 키워줘. 기능은 그대로."
  "스타일 부분만 바꿔줘. 좀 더 차분한 색으로."

★ "스타일 부분만", "문제 목록만" 처럼 범위를 짚으면 정확도가 크게 올라갑니다.
```

## ③ 디버거 (Debugger) — 문제를 진단하는 프롬프트
```plain text
언제: 뭔가 안 될 때
특징: 해결책이 아니라 증상을 설명 (PART 3-6 원칙)

형식:
  "[어느 화면]에서 [무엇]을 하면 [무슨 일]이 일어납니다.
   (원래는 [무엇]이 되어야 합니다.)"

예시:
  "답을 골라도 아무 반응이 없어. 고르면 즉시 정답 여부가 표시되어야 해."
  "마지막 점수가 항상 0점이야. 맞힌 개수만큼 올라가야 해."
```
> 💡 **오류 메시지는 통째로 복사해서 붙여넣으세요**<br>요약하지 마세요. 원문에 몇 번째 줄에서 무슨 문제인지가 들어 있습니다.<br>브라우저 F12 → Console 탭 → 빨간 글씨 전체 복사가 가장 빠른 길입니다.

## ④ 트랜슬레이터 (Translator) — 요구를 기술 언어로 바꾸는 프롬프트
```plain text
언제: 원하는 게 있는데 어떻게 말해야 할지 모를 때
특징: 비유·일상어를 구체적 사양으로 바꿔 다시 요청

예시:
  "친근한 느낌으로"
   → "밝은 파스텔 톤, 둥근 모서리, 큰 글씨, 여백 넉넉하게"

  "폰에서 이상해"
   → "휴대폰 세로 화면(375px)에서 보기 버튼이 화면 밖으로 잘려.
      버튼을 세로로 쌓고 글자 크기를 화면 폭에 맞게 조정해줘."
```
> 💡 **막히면 Claude에게 번역을 시켜도 됩니다**
```plain text
초등학생이 쓸 화면인데 지금 너무 딱딱해 보여.
어떻게 요청하면 친근하게 바뀔지 프롬프트를 만들어줘.
```

## ⑤ 가드레일 (Guardrail) — 제약을 미리 거는 프롬프트
```plain text
언제: 건드리면 안 되는 게 있을 때
특징: "이건 절대 하지 마"를 미리 선언

예시:
  "브라우저 localStorage는 절대 쓰지 마"
  "AI 호출 기능은 넣지 마"
  "외부 이미지 링크는 쓰지 말고 이모지나 도형으로"
  "지금 잘 작동하는 채점 로직은 건드리지 마"
```
> ⚠️ **부정 지시는 약합니다 — 대체안을 함께 주세요**
"코끼리를 생각하지 마세요"라고 하면 코끼리가 떠오릅니다. 모델도 비슷합니다.
```plain text
❌ "이모지를 쓰지 마"          → 가끔 여전히 씁니다
✅ "텍스트만 사용해"            → 훨씬 잘 지켜집니다

❌ "AI 호출 기능은 넣지 마"
✅ "순수 HTML과 자바스크립트로만 만들어줘. AI 호출 기능은 넣지 마"
    ↑ 대체안 먼저, 금지는 확인 사살
```

## 5-1. 바이브코딩의 근본 난제
[원본 이미지 제외]
```plain text
전통 개발: 내가 짰으니 내가 안다
바이브코딩: 내가 안 짰다. 그럼 맞는지 어떻게 아나?

이게 이 방식의 핵심 난제입니다.
그리고 PART 2에서 본 "개발자 45%가 디버깅에 더 많은 시간을 쓴다"는
통계의 진짜 의미이기도 합니다.
```
**검증 가능성의 스펙트럼**
```plain text
쉬움 ←──────────────────────────────────────→ 어려움

화면에 뜨나?          점수 계산이 맞나?        보안 구멍이 없나?
버튼이 눌리나?         예외 상황 처리되나?      성능이 괜찮나?
(눈으로 확인)          (검산 필요)             (전문 지식 필요)
     ↑                      ↑                       ↑
  오늘 실습            오늘 검증 단계            오늘 안 다룸
```
> 📌 **오늘 실습 설계에 이 원리가 반영되어 있습니다**
오늘 만드는 퀴즈 앱은 **검증 가능성이 높은 쪽**에 있습니다.<br>동작하는지 눈으로 보이고, 점수는 검산할 수 있습니다.
반면 로그인·결제·개인정보처럼 **검증이 어려운 영역**은 오늘 다루지 않습니다.<br>"Artifacts가 못 해서"이기도 하지만, 더 근본적으로는<br>**초보자가 검증할 수 없는 걸 만들면 안 되기 때문**입니다.

## 5-2. 할루시네이션 — 메커니즘부터
```plain text
할루시네이션 = 사실과 다른 내용을 그럴듯하게 생성하는 현상

가장 흔한 오해: "AI가 거짓말을 한다"
  → 틀렸습니다. 거짓말은 사실을 알면서 다르게 말하는 것입니다.

정확한 설명:
  모델의 목표는 "다음에 올 그럴듯한 조각"을 고르는 것입니다.
  "사실인 조각"을 고르는 게 아닙니다.

  그래서 모르는 것을 물어봐도
  → 그럴듯한 형태의 답이 만들어집니다
  → 존재하지 않는 개념, 틀린 연도, 없는 함수 이름이
    문법적으로 완벽한 문장 안에 들어갑니다
```
[원본 이미지 제외]
**왜 "모르겠다"고 안 하는가**
```plain text
학습 과정에서 "도움이 되는 답"이 보상을 받습니다.
"모르겠습니다"는 도움이 안 되는 답으로 취급되기 쉽습니다.
→ 모르는 영역에서도 답을 만들어내는 경향이 생깁니다.

최근 모델들은 이 문제를 줄이는 방향으로 훈련되고 있지만,
구조적으로 완전히 사라지지는 않습니다.
```

## 5-3. 검증 프로토콜 — 순서를 지키면 시행착오가 줄어듭니다
> "일단 아무거나 해보자"가 아니라 순서대로 하면 원인을 훨씬 빨리 찾습니다.
```plain text
① 동작 확인 — 화면이 뜨는가, 버튼이 눌리는가
   → 안 되면 여기서 멈추고 해결. 이 위로 못 갑니다

② 흐름 확인 — 처음부터 끝까지 한 번 통과되는가
   → 중간에 막히면 그 지점을 증상으로 설명

③ 계산 검산 — 숫자가 맞는가
   → 극단값으로 확인 (다 틀리기 / 다 맞히기)

④ 내용 검수 — 사실관계가 맞는가
   → ★ 여기는 AI가 못 합니다. 사람만 가능합니다

⑤ 환경 확인 — 다른 기기·다른 화면에서도 되는가
   → 폰, 시크릿 창, 다른 사람

⑥ 경계 확인 — 예외 상황에서 안 깨지는가
   → 아무것도 안 고르고 넘기기, 빠르게 연타하기 등
```

## 5-4. 화면 메시지 판별법
> 실습 중 여러 메시지가 뜹니다. **무시해도 되는 것과 진짜 문제를 구분**해야 합니다.
```plain text
✅ 무시해도 되는 것

  "이 앱은 브라우저에서만 실행됩니다"
    → 정상 안내입니다

  공유 저장소 사용 시 뜨는 확인 창
    → "데이터가 다른 사용자에게 보입니다" 같은 안내. 정상입니다

  옆자리와 결과물이 다름
    → 정상. 확률적 생성이라 매번 다릅니다

  코드에 익숙하지 않은 함수 이름이 잔뜩 보임
    → 정상. 읽을 필요 없습니다


❌ 진짜 문제인 것

  오른쪽 결과물 패널이 아예 안 열림
    → 설정 문제 (2권 참고)

  화면이 하얗게 비어 있음
    → 코드 오류 또는 외부 리소스 차단

  게시 링크에서 로그인 화면이 뜸
    → AI 호출 기능이 들어간 것 (3권 참고)

  저장했는데 새로고침하면 사라짐
    → 게시 전이거나 localStorage가 쓰인 것
```

## 6-2. 연령 제한 — 이 교육의 구조적 전제
```plain text
Claude를 포함한 대부분의 소비자용 AI 서비스는 연령 제한이 있습니다.

Claude:
  · 만 18세 이상만 계정 생성 가능
  · 계정 생성 시 연령 확인 절차
  · 미성년자 이용 정황 감지 시 계정 비활성화

→ 초·중·고 학생이 직접 계정을 만드는 수업은 불가능합니다
→ 교사가 학생 계정을 만들어주는 것도 안 됩니다
```
> 📌 **그럼 어떻게 수업에 쓰는가 — 오늘 교육의 핵심 구조**
**"학생이 AI를 쓴다"가 아니라 "교사가 AI로 만들어 학생에게 준다"**
```plain text
교사 → Claude로 학습 도구 제작 → 게시 → 링크
                                         ↓
                                   학생이 링크로 접속
                                   (계정 불필요, 가입 불필요)
```
이 구조가 3권에서 실습할 내용이고, 이 교육 전체의 결론입니다.
> ⚠️ **현장에서 절대 하면 안 되는 것**
- 학생 이름으로 계정 만들어주기
- 교사 계정을 학생에게 빌려주기
- 학생 개인정보를 AI에 입력하기
세 번째는 특히 주의하세요. 게시된 결과물은 공개 주소이고, 검색에 노출될 수 있습니다.

## 6-3. 저작권과 출처
```plain text

  AI가 만든 결과물의 권리 귀속은 나라마다 판단이 다르고 정리 중입니다.
  현재 한국에서는 "인간의 창작적 기여"가 있어야 저작권이 인정되는 방향입니다.

  · 기존 저작물을 그대로 재생성시키지 않기
```

# 핵심 요약
```plain text
바이브코딩 = "코딩 시간 제로"가 아니라 "코딩 시간을 검수·디버깅으로 이동"
             (Stack Overflow 2025 설문, 개발자 45%가 AI 코드 디버깅에 더 많은 시간)

AI가 코드를 잘하는 이유 = 코드가 저엔트로피 영역이기 때문
  → 우리 일은 입력의 엔트로피를 낮추는 것 = 프롬프트를 좁히는 것

세 개의 벽:
  ① 컨텍스트 붕괴  — 10~20턴에서 초반 지시가 묻힘 → 30턴 규칙, 새 대화
  ② 회귀          — 수정 범위가 크면 있던 게 깨짐 → "나머지는 그대로"
  ③ 조용한 실패    — 오류 없이 안 됨 → localStorage 금지, 게시 먼저

네 개의 방어선:
  모듈식 프롬프팅 / 프롬프트 연결 / 계획 선승인 / 되돌리기 우선

증상을 말하되 해결책은 지시하지 말 것
  ("State 관리 고쳐줘" X → "답을 골라도 반응이 없어" O)

프롬프트 5아키타입:
  스캐폴드 · 리파이너 · 디버거 · 트랜슬레이터 · 가드레일

검증 프로토콜 6단계:
  동작 → 흐름 → 계산 → 내용 → 환경 → 경계
  ★ "내용 검수"는 AI가 못 합니다. 사람만 가능합니다

교육 현장의 구조:
  학생이 AI를 쓰는 게 아니라, 교사가 만들어 링크로 준다
```
