# 개발 문서가 무엇인지부터
<details>
<summary>세 문서가 각각 무엇인지 — 비개발자용 설명</summary>
### 요구사항 정의서
**「이 소프트웨어가 무엇을 할 수 있어야 하는가」를 목록으로 적은 문서**입니다.
```plain text
REQ-001 | 기능 | 사용자는 발전량 예측값을 시간 단위로 조회할 수 있어야 한다
REQ-002 | 성능 | 조회 응답은 3초 이내여야 한다
REQ-003 | 제약 | 시스템 재기동 없이 설정을 변경할 수 있어야 한다
```
개발 전에 만들고, 개발 후에 **「이거 다 됐나」 확인하는 기준**이 됩니다.
### 릴리스 노트
**버전을 배포할 때 「이번에 뭔가 바뀌었다」를 적는 문서**입니다.
앱 업데이트하면 나오는 「버그 수정 및 성능 개선」이 바로 이겁니다. 실무에서는 훨씬 구체적입니다.
```plain text
v2.3.1 (2026-09-14)

[신규] 발전량 예측 API 연동 추가
[개선] 조회 속도 개선 (30초 → 3초)
[수정] 스케줄 저장 시 간헐적 실패 현상
[주의] 설정 파일 마이그레이션 필요
```
### 테스트 케이스
**「이렇게 넣으면 이렇게 나와야 한다」를 미리 적어두는 것**입니다.
```plain text
TC-001 | 정상 | 온도 25도 입력 → 정상 범위 판정
TC-002 | 경계 | 온도 75도 입력 → 상한 경고 (매뉴얼 상한값)
TC-003 | 예외 | 온도 999도 입력 → 입력 오류 반환
```

# 01. 요구사항 정리서

**쓰는 상황** — 고객 요청이나 회의 내용을 요구사항 문서로 옮길 때
**설문 근거** — 개발 문서 작성 8명 · 「요구사항관리 문서 최신화」 언급

```plain text
[역할]
ESS 제어 소프트웨어를 [N]년간 개발하며
요구사항 정의서를 직접 작성해 온 선임 개발자입니다.

[맥락]
수신처는 [사내 개발팀 / 발주처 / 협력사]입니다.
목적은 [이번 개발 범위를 확정하기 위함]입니다.
분량은 표 중심, A4 [N]장입니다.

[지시]
아래 자료에서 요구사항을 추출해 정리하세요.

1. 요구사항을 기능 / 성능 / 인터페이스 / 제약 으로 분류하세요.
2. 각 요구사항을 아래 컴럼으로 표에 정리하세요.
   ID / 분류 / 요구사항 내용 / 출처 / 검증 방법
3. 요구사항 내용은 「∼할 수 있어야 한다」 형태로 통일하세요.
4. 검증 방법 칸에는 이 요구사항이 충족됐는지
   어떻게 확인할지 적으세요. 자료에 없으면 [확인 필요]로 두세요.
5. 서로 충돌하는 요구사항이 있으면 마지막에 따로 모으세요.
6. 자료에서 판단하기 어려운 항목을 질문 목록으로 정리하세요.

[자료]
(여기에 회의 메모나 요청 내용을 붙여넣습니다)

[제약]
- 제가 제공한 자료에 없는 요구사항을 추가하지 마세요.
- 자료에 없는 항목은 [확인 필요]로 표시하세요.
- 일반적인 개발 관행으로 빈칸을 채우지 마세요.
- 「∼하면 좋겠다」 수준의 언급을 요구사항으로 승격하지 마세요.
  그런 항목은 「검토 필요」로 따로 분리하세요.
- 원문의 수치와 단위를 그대로 옮기세요.
```
<details>
<summary>응용 — 요구사항과 구현 대조</summary>
```plain text
아래 두 자료를 대조해 주세요.

[A] 요구사항 정의서
[B] 실제 구현 내용 또는 코드 설명

1. 요구사항별로 구현 여부를 표시하세요.
   컴럼 — 요구사항 ID / 요구사항 / 구현 여부 / 근거
2. 구현 여부는 아래 셋 중 하나로만 적으세요.
   구현됨 / 미구현 / [코드 확인 필요]
3. B에는 있는데 A에 없는 기능을 따로 모으세요.

판단이 어려운 것은 전부 [코드 확인 필요]로 두세요.
추측으로 「구현됨」이라고 적지 마세요.
```
설문에서 「요구사항관리 문서 최신화, 실제 구현로직과 일치 여부 판별」을 적어주신 분이 계셨습니다.
**최종 판단은 사람이 하셔야 하지만, 차이를 뽑아내는 것까지는** AI가 합니다.
</details>

# 02. 릴리스 노트

**쓰는 상황** — 버전 배포 시 변경 내역을 정리할 때

```plain text
[역할]
[제품명] 개발을 [N]년간 담당하며
릴리스 노트를 매 버전 작성해 온 개발자입니다.

[맥락]
수신처는 [사내 운영팀 / 고객사 담당자]입니다.
읽는 사람은 [개발자 / 비개발 운영자]입니다.

[지시]
아래 변경 내역을 릴리스 노트로 정리하세요.

1. 변경 내역을 아래 순서로 분류하세요.
   신규 기능 → 개선 사항 → 버그 수정 → 알려진 이슈
2. 각 항목을 한 줄로 쓰되, 사용자 관점에서 쓰세요.
   「A 함수를 리팩터링함」이 아니라
   「조회 속도가 개선됨」처럼 적습니다.
3. 조치가 필요한 항목에는 「조치 필요」를 표시하세요.
   (재기동 · 설정 변경 · 데이터 마이그레이션 등)
4. 하위 호환이 깨지는 변경은 맨 위에 따로 표시하세요.
5. 마지막에 적용 전 확인 사항을 3개 이내로 적으세요.

[자료]
(커밋 로그나 변경 목록을 붙여넣습니다)

[제약]
- 자료에 없는 변경 사항을 추가하지 마세요.
- 영향 범위를 추측하지 마세요. 불확실하면 [확인 필요]로 두세요.
- 성능 개선 수치를 만들어내지 마세요.
  측정값이 자료에 있을 때만 적으세요.
- 버전 번호와 날짜는 제가 준 것만 쓰세요.
```

# 03. 테스트 케이스

**설문 근거** — 「테스트 코드 작성 및 수행」 5\~10시간 · 「개발 후 테스트」 3\~5시간 · 「완성한 기능에 대한 검증」 10시간 이상

```plain text
[역할]
[분야] 소프트웨어를 [N]년간 개발하며
테스트 케이스를 직접 설계해 온 개발자입니다.

[맥락]
대상은 [기능명 또는 모듈명]입니다.
환경은 [운영체제 · 런타임 · 하드웨어 조건]입니다.

[지시]
아래 요구사항 또는 기능 설명을 보고 테스트 케이스를 만드세요.

1. 케이스를 아래 컴럼으로 표에 정리하세요.
   ID / 구분 / 사전 조건 / 입력 / 기대 결과 / 판정 기준
2. 구분은 아래 셋으로 나누세요.
   정상 흐름 / 경계값 / 예외 상황
3. 경계값은 자료에 범위가 명시된 항목만 만드세요.
   (최소값 · 최대값 · 경계 바로 밖)
4. 예외 상황은 자료에 언급된 오류 조건만 다루세요.
5. 판정 기준은 「정상 동작」 같은 표현 대신
   무엇을 보고 합격으로 볼지 구체적으로 적으세요.
6. 자료만으로 기대 결과를 알 수 없는 케이스는
   따로 모아 「확인 필요」 목록으로 주세요.

[자료]
(요구사항이나 기능 명세를 붙여넣습니다)

[제약]
- 자료에 없는 조건을 만들어내지 마세요.
- 임계값을 추측하지 마세요. 자료에 없으면 [확인 필요]입니다.
- 일반적인 테스트 관행으로 케이스를 추가하지 마세요.
- 단위를 변환하지 마세요. 원문 그대로 씁니다.
```
<details>
<summary>응용 — 누락 케이스 점검</summary>

```plain text
아래 테스트 케이스 목록을 점검해 주세요.

1. 요구사항 중 테스트 케이스가 없는 항목을 찾아 주세요.
2. 경계값 테스트가 빠진 항목을 찾아 주세요.
   (자료에 범위가 명시된 항목만)
```

# 04. 연동 규격 검토

**설문 근거** — 「해외 벤더 기술문서 확인」 10시간 이상 · 제품 매뉴얼 10명이 자주 조회

```plain text
[역할]
ESS 제어 소프트웨어를 [N]년간 개발하며
국내외 [장비 유형] 제조사 연동 규격서를 직접 검토해 온 선임 개발자입니다.

[맥락]
수신처는 사내 기술 검토회입니다.
목적은 [제조사명] 장비와의 연동 가능 여부를 판단하기 위함입니다.
현장 조건은 [기존 연동 장비 · 통신 방식 · 제약 사항]입니다.
분량은 표 중심, A4 1장입니다.

[지시]
아래 규격서에서 연동 검토에 필요한 항목을 정리하세요.

1. 통신 방식을 찾아 적으세요.
   (프로토콜 · 속도 · 포트 · 동시 접속 수)
2. 제어 관련 항목을 표로 정리하세요.
   컴럼 — 항목 / 값 / 단위 / 문서 위치
3. 2번 표에서 값이 범위로 적힌 항목만 따로 모으세요.
   현장 조건에 따라 달라지는 값이므로 확인이 필요합니다.
4. 기존 환경과 충돌할 가능성이 있는 항목을 적으세요.
   판단이 아니라 「충돌 가능성 있음」 표시만 하세요.
5. 문서에 없어 제조사에 문의해야 할 항목을 5개 이내로 정리하세요.

[자료]
(규격서 해당 부분을 붙여넣습니다)

[제약]
- 문서에 없는 값은 절대 만들지 마세요.
- 문서에 없는 항목은 [확인 필요]로 표시하세요.
- 원문 단위를 그대로 쓰고 변환하지 마세요.
- 적합 여부를 판정하지 마세요. 사실만 정리하세요.
- 일반적인 기술 지식으로 빈칸을 채우지 마세요.
- 정보가 부족하면 추측하지 말고 먼저 물어보세요.
```

# 05. 기술 검토 회신
```plain text
[역할]
[분야] 기술검토 회신을 [N]년간 작성해 온 [직책]입니다.

[맥락]
수신처는 [발주처 기술검토팀 / 제조사 기술담당자]입니다.
목적은 [질의 내용]에 대한 공식 회신입니다.
배경은 [상대방이 보낸 질의 요지]입니다.
분량은 A4 1장 이내, 공문 형식입니다.

[지시]
1. 상대방 질의를 항목별로 분리하세요.
2. 항목마다 아래 세 가지로 답하세요.
   - 회신 내용 : 확인된 사실만
   - 근거 : 규격서 · 시험기록 등 출처. 없으면 [확인 필요]
   - 추가 확인 필요 여부
3. 즉답 가능한 것과 내부 확인이 필요한 것을 나누세요.
4. 마지막에 회신 예정일을 적는 문장을 넣으세요.

[자료]
(질의 원문과 참고 자료를 붙여넣습니다)

[제약]
- 측정하지 않은 값을 적지 마세요.
- 확인되지 않은 것을 단정하여 답하지 마세요.
- 「문제없을 것으로 사료됨」 같은 근거 없는 단정을 쓰지 마세요.
- 공식 문서 격식을 유지하세요.
- 감정적인 표현이나 변명을 넣지 마세요.
```

# 06. 장애 분석 보고
```plain text
[역할]
[분야] 현장 장애 대응을 [N]년간 수행하며
장애 보고서를 작성해 온 [직책]입니다.

[맥락]
수신처는 [사내 / 발주처]입니다.
분량은 A4 1장, 개조식입니다.

[지시]
```
